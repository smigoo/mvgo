# mvgo Figma 结构整理插件｜部门使用说明

版本：2026-11-16

## 1. 下载哪个包

在随附的分发目录中按使用环境选择：

| 包             | 适用场景                           | 文件                                             |
| ------------- | ------------------------------ | ---------------------------------------------- |
| macOS 桌面端     | Mac 上使用 Figma 桌面客户端            | `mvgo-figma-structure-client-mac-20261116.zip` |
| Windows 桌面端   | Windows 上使用 Figma 桌面客户端        | `mvgo-figma-structure-client-win-20261116.zip` |
| Figma 网页端团队发布 | 管理员发布到公司 Figma 团队后，成员从团队插件列表安装 | `mvgo-figma-structure-web-20261116.zip`        |

三个包的插件本体相同。桌面端 zip 可本地导入开发插件；网页端**不能**通过本地 manifest 导入，需管理员发布到团队。

## 2. 桌面端安装

1. 解压对应系统的 zip 到本机目录。
2. 打开 **Figma 桌面端**。
3. 菜单选择 **插件 → 开发 → 导入插件 / Import plugin from manifest…**。
4. 选择解压目录中的 `src/cursor_mcp_plugin/manifest.json`。
5. 从 **插件 → 开发** 菜单运行 `mvgo-figma-structure`。
6. 如果本机已导入过旧版，先 Remove 旧开发插件，再导入新包，避免 Figma 缓存旧文件。

## 3. 推荐使用流程

> 🔴 **核心原则：AI 整理结果只能当辅助，不能当终稿。** 模型可能认错图表类型、拆错模块边界、把图例挪离图表、删掉看起来冗余实际有用的图层。**每一次整理后都必须人工检查**，确认无误才用于正式稿；整理错了宁可撤回重来，不要手工去迁就错误结果。

### 先检查，不确定时不要直接整理

1. 在画布中只选中**一个组件根节点**，不要选整张画板或包含多个组件的 Frame。
2. 确认插件「当前选区」显示正确节点；根节点不明确时先停止。
3. 点击「📐 生成结构方案（只读预览）」检查将要识别的结构。
4. 需要零 token 操作时，用「仅结构化整理」；它不调用模型，但会改图层命名/分组和导出设置。
5. 需要 AI 判定语义、层级和顺序时再使用「AI 全自动整理」。使用 AI 前先在 Figma 文件副本或复制的页面验证。【我们主要用这个】
6. 整理后查看结果、图层树和画布视觉；确认符合预期后再导出结构契约或保存 JSON。

### 重要边界

- 插件用于本地 Figma 图层结构整理；结果缓存于 Figma `clientStorage`，可手动下载 JSON/结构契约。
- 纯本地整理也会改图层，AI 全自动整理还可能执行视觉分析返回的删除、重排、归父和成组操作。先复制文件/页面再试，确认无误后再用于正式稿。
- 不要一次整理多组件 Frame；插件遇到多组件根警告时停止，逐个组件处理。
- 不要把 Auto Layout 自检报告当成自动修复：该报告是只读建议；AL 设置由使用者在 Figma 中确认并手动修改。
- 图例（`legend-*`）永远与对应图表（`@echarts/*`）同容器或同父级；这是下游渲染正确性的硬约束。
- 生成管线按几何（bbox + 父子关系）判定结构，不依赖图层命名；但整理命名（`@echarts/*`、`icon-*`、`legend-*` 等）影响人工核对效率和资源导出，仍需保证准确。

## 4. AI 配置

1. 填写公司批准的 OpenAI 兼容接口地址、个人 API Key 和模型名。
2. 启用视觉整理，另填具备图像理解能力的视觉模型，并勾选「导出渲染图并用视觉模型定层级/顺序」。
3. 点击「保存设置（仅存本机）」并确认探测成功。
4. API Key 保存在本机 Figma 插件存储中，不要把 Key 写进共享文件、截图或部门文档；不要共用个人 Key。
5. 只有网关跨域导致 `Failed to fetch` 时才使用 zip 中的本地代理。可选代理需要本机 Node.js 18+；正常直连和所有零 token 工具都不需要 Node 或启动服务。

## 5. Auto Layout 自检

「Auto Layout 自检」为只读本地计算，不会自动设置 Auto Layout。

- `冲突`：已有布局方向与几何判断冲突，需核对对应节点。
- `建议补 AL`：只是候选，不是自动修改指令。
- `重叠`：可能是背景、图表、图例或叠放设计，不要批量改成 Auto Layout。
- `single-child`：单子节点容器通常按规范跳过，不代表布局错误。
- 负 itemSpacing 或重叠区域需先目视确认；不要未经核对批量应用。

## 6. 整理后检查与撤回

**AI 整理 ≠ 正确结构。整理完先按下面清单逐项人工核对，再决定保留还是撤回。**

### 6.1 按开发思维核对结构（最重要）

想象这个组件要用 Vue 代码实现，逐层问「这层对应代码里的什么」：

1. **结构是否对应真实模块**：AI 给的 section 划分是否符合页面的实际功能模块（如「统计区 / 图表区 / 列表区」各归各段）？有没有把两个不同功能的模块揉成一段，或把一个完整模块拆散成平级三块？发现混组/拆散，撤回后手动在 Figma 里调整分组再重跑。
2. **图表是否识别为图表**：柱状图 / 折线图 / 环形图应命名为 `@echarts/bar|line|pie`，**内部不允许残留位图导出**（不应看到 `PNG@2x`）。被误判成 `img-*` / `graphic-*` 的图表，或纯装饰被误升成 `@echarts/*`，都要纠正。
3. **图例必须与图表同容器**：图例（`legend-*`）应归入对应 `@echarts/xxx` 文件夹（或至少与其同父级），**不能**单独留在 section 层、也不能被命名为 `list-*`——下游会把图例当独立列表再渲染一份。图表和图例被拆开的，手动把图例拖回图表容器。
4. **静态资源是否整合**：同一语义的资源应收进同一资源夹——图标统一 `icon-*`（≤40×40，SVG 导出）、内容图 `img-*`、背景 `bg-*`、图表内部结构 `series-*` / `axis-grid`。散落在内容区的同名资源应归位；同一图标出现多个副本的保留一个。
5. **技术栈前缀是否正确**：`@echarts/*` 只给「有 children 的真图表容器」；`@antd/*` 等组件前缀同理。一个裸叶子（无子节点的矢量/矩形）被标成 `@echarts/*` 就是错的。
6. **建议 Frame、慎用 Group**：新容器建议用 Frame 建（可设裁剪、约束，后续能继续编辑布局）；Group 只是视觉捆绑，无法承载布局语义。尤其**重叠内容不要塞进 Group 硬捆**——重叠关系应保留在各自容器内、靠图层顺序（z 序）表达。既有 Group 不必强拆，但整理后新增容器若被建成 Group，建议手动换成 Frame。

### 6.2 通用核对项

1. 根级 `cp-* / header / bg / slot-con` 结构是否符合该组件实际设计；并非每个 section 都要有 header 或 bg。
2. 左右 / 上下内容关系是否保留：不该并排的被并排、不该重叠的被摊开，都要撤回。
3. 关键节点没有被删除、误归父或改坏可见布局。AI 返回的删除操作宁可手动补回，不要侥幸。
4. 文字仍为 TEXT 节点（没被轮廓化或转图）；多行文案没有被拆成多个 TEXT。
5. 对拿不准的结果立即「撤回上次整理」；若之后已继续编辑，撤回可能不再可靠，改用副本重跑。
6. 保存前核对正式稿。不要把一次模型输出视为正确结构的唯一证据。
