# mv-1785691963555-bec4826c 失败原因分析

## 结论
该组件不是在 Figma 获取、视觉分析或代码生成阶段直接失败，而是在 **运行时质量门禁** 连续 3 次未通过后，被系统判定为最终失败。

最终错误来自任务记录：

- `RUNTIME-007`：组件预览存在 HTTP 资源加载错误
- `RUNTIME-010`：组件预览输出 `console.error`

对应任务记录位置：
- `backend-node/data/tasks.json`
- `sessionId = mv-1785691963555-bec4826c`

最终 `error` 字段内容：

```text
运行时质量门禁连续未通过，已达最大修订次数: [RUNTIME-007] 组件预览存在 HTTP 资源加载错误; [RUNTIME-010] 组件预览输出 console.error
```

## 失败链路
1. Figma 数据获取完成
2. 视觉分析完成
3. Vue3 代码生成完成
4. 质量检查完成，但分数偏低，进入后续修订
5. 运行时预览截图阶段检测到资源 404
6. 系统强制回到 `microcode-engineer` 全量修订
7. 连续多轮后，仍然命中同类运行时资源错误
8. 达到最大修订次数后任务失败

## 关键证据
### 第 1 次运行时门禁阻断
日志显示：
- 预览页可打开
- 截图能生成
- 但存在 2 项阻断问题

阻断详情：
- `tabs-icon-43.png` 返回 404
- 对应浏览器 `console.error` 也被记为阻断

### 第 2 次运行时门禁阻断
新增 404 资源：
- `g-7883.png`
- `tabs-icon-43.png`

### 第 3 次运行时门禁阻断
任务最终在同类问题上结束，达到最大修订次数。

## 直接原因
这条任务失败的直接原因不是“组件完全渲染不出来”，而是：

- 组件预览页能打开
- 截图也能产出
- 但运行时门禁把资源 404 和对应 `console.error` 视为 **BLOCK 级问题**
- 因此每一轮都被判定“真实预览检查未通过”

## 补充观察
当前本地 workspace 中这两个资源现在都已经存在：
- `resources/images/g-7883.png`
- `resources/images/tabs-icon-43.png`

这说明当时失败点更像是：

- 某一轮生成后，预览检查发生时资源未正确就位 / 未及时同步 / 路径引用与当时发布状态不一致
- 而不是今天查看时组件目录永久缺图

## 这条任务为什么会拖很久
任务总耗时约 1401 秒，约 23.4 分钟。
主要耗时不是单次报错本身，而是：

- 每次运行时门禁失败后都会触发新一轮修订
- `microcode-engineer` 与 `layout-style-refiner` 的 LLM 调用都比较长
- 于是形成“生成 -> 预览门禁 -> 资源 404 -> 全量修订”的循环

## 当前最合理的归因
**根因类型：Vue3 预览资源发布 / 引用时序问题，最终在运行时门禁被 `RUNTIME-007 + RUNTIME-010` 阻断。**

它不是纯文本质量分数导致失败，也不是 Figma 解析失败，更不是预览路由不可达。

## 建议的下一步
1. 复查 Vue3 质量预览发布时，`index.vue` 引用的图片文件是否在门禁截图前已同步到 `frontend/workspace`。
2. 检查 `workspace-preview-publisher` 是否存在文件同步完成但 Vite 原始读取路径短暂不可见的时序窗口。
3. 对 `Failed to load resource` 这类和已记录 HTTP 404 完全重复的 `console.error`，继续保持去重，避免双重阻断。
4. 对“预览已可见但仅静态资源缺失”的情况，评估是否从 `BLOCK` 降为可修订但不中断整轮的级别。
