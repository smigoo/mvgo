# AI 优化按钮需求可行性分析

## 结论
该需求可行，而且项目里已经具备 70% 以上的基础能力，不需要从零建设。

但建议拆成两期：
1. 第一期做“截图比对 + 分析报告 + 人工确认后再优化”的半自动闭环。
2. 第二期再做“一键自动优化并回写代码”的全自动闭环。

不建议一上来直接做成“点一下就自动优化完成”，因为视觉比对本身可复用现有能力，但自动改代码的风险、成本和误判率都明显更高。

## 现有基础能力

### 1. 预览截图能力：已存在
- 后端已有真实预览截图器，可直接打开组件预览页并用 Puppeteer 截图。
- 参考：`backend-node/src/ai-engine/roles/screenshot-renderer.js`
- 特点：
  - 优先走真实运行时预览页，而不是只截静态 HTML。
  - 已支持 Vue3 和微码两类组件。
  - 已有运行时门禁，能识别预览页加载失败、空白渲染、资源 404、console error 等问题。

### 2. Figma 预览图能力：已存在
- 生成链路里本来就会下载 Figma 预览图 `mc-preview.png`。
- 参考：`backend-node/src/ai-engine/roles/figma-connector.js`
- 已生成组件的 metadata 里也保存了：
  - `figmaFileKey`
  - `figmaNodeId`
  - `figmaWidth`
  - `figmaHeight`
- 参考：`backend-node/src/vue3/vue3.service.ts`、`backend-node/src/phase2/phase2.service.ts`

### 3. 视觉比对能力：已存在
- 后端已有视觉比对器，输入就是：
  - Figma 原图
  - 渲染截图
- 输出已是结构化报告：
  - `overallSimilarity`
  - `issues[]`
  - `pass`
- 参考：`backend-node/src/ai-engine/roles/visual-comparator.js`

### 4. AI 自动修复入口：已存在原型
- 预览页已经有“AI 修复渲染错误”的链路。
- 参考：`frontend/src/views/preview/index.vue`、`backend-node/src/demo/demo.service.ts`
- 这说明“从预览页触发 AI 改代码并回写组件”这件事，在工程上不是新问题。

## 为什么说可行
核心链路实际上已经能拼起来：
1. 在组件详情页增加“AI 优化”按钮。
2. 点击后调用后端任务：
   - 定位当前组件目录
   - 取 Figma 参考图
   - 取当前预览截图
   - 跑视觉比对
   - 生成结构化分析报告
3. 报告展示给用户。
4. 用户确认后，再把“差异报告 + 组件代码上下文”喂给现有 AI 改码链路。
5. 保存后刷新预览，再次截图比对，形成一轮闭环。

所以从系统结构上看，这不是“研究型需求”，而是“工程整合型需求”。

## 真正的难点

### 1. Figma 参考图不一定始终可直接复用
虽然生成阶段会下载 `mc-preview.png`，但“已生成好的组件”未必都稳定保留了这张图的可访问路径。
因此实现时要做双路径：
1. 优先使用组件目录中的本地缓存预览图。
2. 缺失时，根据 `figmaFileKey + figmaNodeId` 重新向 Figma 拉取。

这意味着：
- 没有 Figma Token 时，历史组件分析能力会受限。
- 老数据如果 metadata 不完整，也会降级失败。

### 2. 比对结果容易受运行环境干扰
视觉比对不是简单像素 diff，容易受这些因素影响：
- 预览页背景色不同
- 组件动态数据和 Figma 静态稿不一致
- 字体环境不同
- 图片资源未完全加载
- 视口尺寸和缩放比例不一致

所以这类报告适合做“设计偏差分析”，不适合做“绝对真值判定”。

### 3. 自动优化比分析难很多
“出分析报告”比较稳。
“根据报告自动改代码”风险明显更高，因为模型可能：
- 修了样式但破坏交互
- 为了追相似度删掉真实业务元素
- 把动态绑定写死成静态值
- 在微码 / Vue3 两套目录结构里改错文件

因此自动优化必须加约束：
- 只允许修改样式相关文件或 `index.vue` 的视觉层
- 禁止改接口调用、业务数据结构、事件逻辑
- 修改前做快照
- 修改后自动刷新预览并二次比对
- 提供撤销

## 建议的产品定义

### 版本 A：分析型按钮（推荐先做）
按钮文案：`AI 视觉分析`

点击后执行：
1. 截取当前预览图
2. 获取 Figma 参考图
3. 输出分析报告

报告内容建议包括：
- 综合相似度
- 是否通过
- 高 / 中 / 低问题数量
- 差异列表（颜色、间距、布局、缺失元素、比例、字体）
- 每个问题附带具体修复建议

这个版本价值高、风险低，最适合作为第一版。

### 版本 B：半自动优化（推荐第二步）
在分析报告下增加按钮：`按报告优化`

执行方式：
- 将“差异报告 + 组件源码 + 限制规则”发给现有 AI 改码链路
- 只允许 1 轮优化
- 优化后自动刷新预览并重新对比
- 展示“优化前 vs 优化后”差异
- 用户可撤销

这是最合理的闭环版本。

### 版本 C：全自动优化（不建议直接上）
按钮点击后自动分析、自动修复、自动复检、自动保存。

这个版本能做，但不建议当前阶段直接做，因为：
- 成本最高
- 误改风险最高
- 用户对结果不可控
- 一旦改坏，信任损耗很大

## 更适合挂载的位置
最适合直接挂在组件详情页头部工具栏。
参考位置：`frontend/src/views/components/ComponentDetail.vue`

原因：
- 这里已经有预览 iframe
- 已拿得到 `componentId / groupId / figma metadata`
- 已有刷新预览、源码编辑、AI 修复的上下文
- 用户心理模型也最顺：看预览 -> 点分析 -> 看报告 -> 决定是否优化

## 实现建议

### 前端
在组件详情页增加两个入口：
1. `AI 视觉分析`
2. `按分析优化`（只有分析完成后显示）

报告展示形式建议：
- 右侧抽屉或底部面板
- 不建议 modal，内容会比较长

### 后端
建议新增独立接口，而不是塞进现有渲染报错修复接口：
1. `POST /api/component/:id/visual-analysis`
2. `POST /api/component/:id/visual-optimize`

原因：
- 这是“设计还原度优化”，不是“渲染报错修复”
- 目标、提示词、边界都不同

### 任务模型
建议走异步任务而不是同步请求。
因为它至少包含：
- 截图
- 拉 Figma 图
- 视觉模型分析
- 可选的 AI 改码
- 二次截图与回归

同步接口很容易超时。

## 风险评估

### 可行性
- 分析报告：高
- 半自动优化：中高
- 全自动优化：中

### 主要风险
- Figma Token 缺失或失效
- 历史组件本地预览图缺失
- 视觉模型误判动态内容
- 自动优化误改业务逻辑
- 成本偏高（截图 + 视觉模型 + 改码模型 + 复检）

## 最终建议
建议你把这个需求定义成：

> 为已生成组件增加一个“AI 视觉分析 / 优化”入口，先基于“当前预览截图 vs Figma 参考图”输出结构化偏差报告，再由用户决定是否触发 AI 样式优化。

这是当前代码库里最稳、最容易落地、也最不容易把生成链路搞重的做法。

如果直接问“这个功能是否可行”，答案是：

**可行，而且现有工程基础已经够做第一版。**

但如果问“是否适合一步做到自动优化闭环”，我的建议是：

**能做，但第一版不要这么做。先做分析，再做半自动优化。**
