# 轻量组件生成：用户研究与当前分析摘要

## 一句话结论

现阶段可以确认的是：轻量生成值得进入研究和 MVP 评估，但还不能确认截图、HTML 批量或统一入口哪个应优先。真正需要验证的不是“用户是否喜欢更快”，而是“更快的初版是否减少了总交付成本，并且不会被误当成最终产物”。

## 目前最重要的五个判断

### 1. 核心价值应从“生成更快”改为“更快获得可判断结果”

用户未必只关心代码生成耗时，他们更关心：能否尽早判断方向、是否值得继续投入、哪些地方必须人工修正。因此首个可预览结果、质量边界理解率、从初版到可交付的总时间应同时衡量。

### 2. 轻量模式必须是“有边界的初版”，不能是低配 Full

截图和文档天然缺少完整结构或业务证据；HTML 可能缺脚本、外链资源和组件运行时。Draft/Migrated 不是装饰标签，而是交付风险控制机制。若用户不能正确回答“这个结果能否直接交付”，方案就不能直接扩大范围。

### 3. HTML 批量需求需要行为证据，不应仅凭概念兴趣排 P2

批量是否值得做，至少要知道：每周频率、典型批量规模、文件与文档关联方式、失败后的审核动作、单项失败成本。如果多数用户只是偶尔处理 2–3 个文件，批量编排的优先级可能低于单项质量和迁移报告。

### 4. “统一入口”是待验证的交互假设，不是默认正确答案

输入来源可以统一，但微码与 Vue3 的交付目标、审核责任和接入方式可能不同。研究中应测量误选率、理解时间和后续交付行为；若统一入口提高了选择复杂度，应保留统一基础协议，但允许按角色或目标类型提供预设。

### 5. 速度收益必须与返工和误交付一起计算

建议使用总交付成本衡量：

```text
总交付成本 = 等待时间 + 生成失败重试时间 + Playground 修改时间 + 误交付/返工成本
```

轻量模式只有在该成本下降时才算成功；单纯 P50 更快不代表用户体验更好。

## 研究优先级

| 优先级 | 需要回答的问题 | 研究方式 | 产品影响 |
|---|---|---|---|
| P0 | Draft/Migrated 是否会被误交付 | 任务测试、复述题、结果决策测试 | 质量标签、下载门禁、警告层级 |
| P0 | 截图/文档/HTML 是否真的减少总成本 | 最近任务回放、日志、对比任务 | MVP 输入优先级 |
| P0 | 上传内容的隐私与安全顾虑 | 访谈、警告理解测试 | 数据留存、脱敏、沙箱与提示 |
| P1 | HTML 批量频率和规模 | 访谈、问卷、历史任务日志 | 是否进入 P2 |
| P1 | 微码/Vue3 是否适合统一选择 | 树测试、可用性测试 | 入口信息架构 |
| P1 | 排队、限流、失败恢复是否可理解 | 原型任务测试 | 任务中心状态设计 |
| P1 | 键盘、放大、读屏是否能完成核心任务 | 无障碍可用性测试 | 上线门槛 |

## 研究设计建议

采用三阶段混合方法：

1. **探索**：12–15 名参与者访谈，加入最近一次任务回放；8–10 名参与者做 5 天日记。
2. **验证**：10–12 名参与者做两轮可用性测试，覆盖截图、文档、HTML 单项、批量、Draft 升级 Full 和失败恢复。
3. **量化**：产品内调查 n≥150；结构化问卷建议 n≥200，分组比较需要 n≥300；结合至少 4 周或 300 个有效任务日志。

必须区分：

- 已知事实：来自代码、任务日志和现有系统。
- 用户事实：来自访谈、测试和行为数据。
- 研究假设：尚未验证的产品判断。
- 产品建议：基于证据强度和风险做出的决策。

## 建议的上线判断方式

先建立现有 Figma 流程基线，再按任务风险设置“目标值 + 最小可接受差异 + 95% 置信区间”，不要把 80%、85%、10%、75% 等经验值直接写死为通用门槛。重点判断：

- 轻量路径是否降低总交付成本，而不只是缩短生成等待。
- 用户能否正确判断 Draft/Migrated 的可交付边界。
- 误交付、返工和放弃行为是否控制在预设风险范围。
- 失败/排队任务的恢复表现是否优于现有基线。
- 是否存在 P0 安全、隐私或无障碍阻断。

Draft 探索场景和 Full 生产交付应使用不同门槛。

## 当前不能下的结论

以下内容目前都只是方案假设，不能写成“用户已经证明”：

- 截图+文档一定是最优输入组合。
- HTML 批量一定有足够高频需求。
- 用户一定愿意接受 AI 推断的字段和事件。
- 统一入口一定比分入口更易用。
- 60 秒截图/文档、45 秒 HTML 是用户可接受阈值；这些是产品目标，需用基线和测试校准。

## 推荐下一步

先做“研究准备 + P0 验证”，不要立即进入全量开发：

1. 从现有任务记录建立 Figma 生成耗时、失败、取消、返工和预览行为基线。
2. 招募不同角色用户，优先访谈最近 30 天内真实生产过组件的人。
3. 制作可控原型，确保展示真实的 Draft、Migrated、排队、失败、资源缺失和恢复状态。
4. 先验证质量边界、总交付成本和安全顾虑，再决定 HTML 批量及统一入口的开发顺序。
