## Node 包裹规范：全局响应信封统一（commit a070b69 / 父 a0d7b8f7）

用户指示"继续 node 的包裹规范"，选"全局拦截器统一包+修前端"。但经侦察发现 Node 控制器大量返回扁平 `{success:true,user,...}`、前端混用平铺/嵌套两种读法，纯嵌套包裹会断大量前端读法且无法在此 E2E 全量验证。

**决策：兼容式信封（merged envelope）**——`ResponseEnvelopeInterceptor` 替换 `SourceEnvelopeInterceptor`：
- 所有成功响应补齐 `{success,code:200,message:"ok",data,source:"node"}`；
- 业务字段**平铺保留在顶层**（如 `defaultRoot`/`user`/`list`），使 `res.xxx` 与 `res.data.xxx` 两种前端读法都继续可用 → **零前端破坏性改动**（比用户选项描述的"纯嵌套+扫前端改十余处"更稳）。
- 已带 `data` 字段的响应仅补 source/code/message，不二次包裹；数组/原始值包成 data；跳过 undefined/null/string/Buffer/StreamableFile/可读流(SSE/@Res)。
- 错误响应经 `HttpExceptionFilter`→`ApiResponse.error` 已是规范形+source（验证 401/404 均为 `{success:false,code,message,data:null,source,detail:{path}}`）。

**验证**：nest build 通过；curl `/api/workspace-info`(纯对象)、`/api/models`(带data)、`/api/ai-engine-v2/...`(扁平)、401/404 错误，信封形状全部规范+source。

**提交**：`backend-node` a070b69（仅 response-envelope.interceptor.ts + main.ts；未混入无关改动 ai-engine/graphs、phase2/*）；父 a0d7b8f7 更新指针。**前端子仓库无改动**（兼容式信封）。

**复用经验**：大前端混用读法时统一响应信封，优先用"兼容式信封"（规范字段+平铺字段双留）而非纯嵌套，避免无 E2E 下改崩运行前端。

## dev 环境鉴权 & auth/current 401（已排查）

用户问"dev 下 auth/current 是否也需要鉴权"。结论与修复：

- **dev 下确实需要鉴权（设计如此）**：`GET /api/auth/current` 挂 `@UseGuards(SessionGuard)`（auth.controller.ts:80），守卫按路由挂、不分环境。其本质就是"当前登录用户"，无登录身份必 401。
- **SessionGuard 放行条件**（session.guard.ts）：`raw=1` 静态资源 → `session.userId` 已登录 → `Token` header（先 findOrCreateByPortalToken，失败再 findOrCreateDevUser 兜底）→ 否则 401。
- **dev 免登录旁路 `DEV_AUTO_LOGIN`**：`findOrCreateDevUser` 仅在 `NODE_ENV!=='production' && DEV_AUTO_LOGIN==='true'` 时用任意 `Token` header 自动建本地身份（uid=dev-local，admin 全权限）。`.env.development:50` 已设 `DEV_AUTO_LOGIN=true`，但 **main.ts:14-17 只在 `NODE_ENV` 有值时才加载 `.env.{NODE_ENV}`**，标准 `npm run start:dev`（`nest start --watch`）不设 NODE_ENV → 旁路默认不生效。
- **启用方式**：启动 Node 时显式 `NODE_ENV=development DEV_AUTO_LOGIN=true node dist/main.js` → `curl -H "Token: dev" http://localhost:13030/api/auth/current` 返回 200（dev-local 身份，严格嵌套信封 data.user/group/role/permissions）。
- **本环境后台进程坑（重要）**：用 `& disown` 启动的 Node 会在下一条 Bash 命令时退出（server 进程随 shell 被杀），导致 curl 拿到"上一刻还活着"的实例、内联 env 不稳定。改用 **Bash 工具 `run_in_background:true`** 托管（task `J7g50v`，端口 13030，NODE_ENV=development + DEV_AUTO_LOGIN=true）才稳定常驻。
- 2610 = Vite 前端 dev server，代理 `/api/*` 到 13030（Node）；8080 = Java（当前未起）。

## 重启后端踩坑：tsc incremental 缓存致 dist 不重新编译（已解决）

用户连点"重启前端"，发现 13030 后端 `node dist/main.js` 报 `Cannot find module 'dist/main.js'`（沙箱回收后台进程时把 `dist/` 整个清了）。重新 `npx nest build` / `npx tsc` 都**静默成功（1s 结束、无报错）却不生成 dist/main.js**。

**根因**：`tsconfig.build.json` extends `tsconfig.json`（`incremental: true`），构建信息文件是 **`./tsconfig.build.tsbuildinfo`（在 backend-node 根目录，不在 dist/ 内）**。沙箱清掉 `dist/` 但没清这个 buildinfo → tsc 增量模式读它判定"源码无变更"→ 跳过全部 emit → 无 main.js。

**修复（二选一，已验证）**：
- `rm -f tsconfig.build.tsbuildinfo && npx nest build`（清缓存后正常全量编译）
- 或 `npx tsc -p tsconfig.build.json --incremental false`（强制非增量，直接出 main.js）

**结论**：沙箱回收 dist 后必须清根目录的 `tsconfig.build.tsbuildinfo` 再 build，否则增量缓存会骗过 `nest build`。记此坑避免下次重启重复排查。

## Playground 代码加载崩溃修复（12:44）

用户截图：playground 代码区显示 `// 加载失败: Cannot read properties of undefined (reading 'content')`，要求修好并确保 dev/prod 都正常。

### 根因
后端 `component.controller.ts` 的 `getFileContent`（`GET /api/component/:id/file`）用 `res.json()` 直接返回，**绕过 NestJS 全局响应拦截器**：
```ts
return res.json({ success: true, content })      // 行 281-284，无 data 包装
return res.json({ success: false, error: ... }) // 行 286-289
```
但前端全部按 `data.data.content` / `data.data.error` 访问，`data.data` 为 `undefined` → 崩溃。

**关键点（避免误伤其他调用）**：同一 controller 其他接口（`/files`、`/declare`、保存 `POST /file`、推送、`/auth/current` 等）都用 `return { ... }` 走 NestJS 标准管道，响应被 `ResponseEnvelopeInterceptor` 包成严格嵌套 `{success,code,message,data,source}`，前端 `data.data.xxx` 在这些地方是**正确**的。所以本次只改 `/file` GET 接口的消费点。

### 改动
| 文件 | 位置 | 调用接口 | 修改 |
|---|---|---|---|
| `frontend/src/views/demo/index.vue` | L1370-1379 | `GET /file` | `data.data.content/error` → `data.content/error`（3 处） |
| `frontend/src/views/demo/index.vue` | L1618 | `GET /file` | `data.data.content` → `data.content` |
| `frontend/src/views/demo/index.vue` | L1816-1817 | `GET /file` | `data.data.content` → `data.content`（2 处） |
| `frontend/src/views/components/ComponentDetail.vue` | L472-473 | `GET /file` | `data.data.error/content` → `data.error/content` |
| `frontend/src/views/demo/composables/useFileManager.js` | L83-88 | `GET /file` | `data.data.content/error` → `data.content/error`（3 处） |
| `frontend/src/views/demo/composables/useFileManager.js` | L170-171 | `GET /file` | `data.data.content` → `data.content`（2 处） |

### dev / prod 环境分析
