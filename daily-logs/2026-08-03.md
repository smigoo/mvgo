- **关键证据（扁平化现已冗余）**：
  1. `frontend/src/utils/loadVue3Runtime.js:231` `entryCandidates=['package/index.vue','index.vue']`（package 优先），`resolveRelPath`(286) 专门处理 package 下 SFC 的 `../resources` 解析 → 加载器本就为 package/ 结构而设计。
  2. 后端 `/api/preview`(`preview.controller.ts:36-121`) 是通用文件服务，按 componentDir+filePath 任意路径返回，PROD 探针 `.../package/index.vue?exists=1` 可用。
  3. api-binding `resolveComponentEntry`(`api-binding.service.ts:1083`) candidates=['index.vue','package/index.vue'] 双支持。
  4. 微码分支本就保留 `package/`（生成 component.js import './package/index.vue'），不扁平化，证明系统可在 package/ 结构下正常工作。
- **UI 文件树来源**：`frontend/src/views/demo/composables/useFileManager.js` 经 `/api/component/{id}/files` 取文件列表，按 path 字符串递归建树 → 如实反映 workspace 真实结构（有 package/ 就显示 package/，有根 index.vue 就显示根；两者都在就显示两份）。这是用户截图"双 index.vue"的根因。当前磁盘已确认无 package/ 残留（仅根 index.vue 扁平化态）。
- **结论**：可"全用真实树"。修复=vue3 分支改 `copyDirectoryContents(outputPath, stagingPath)` 保留 package/，与微码一致。低风险。存量组件处理待用户决策（A:旧件不动/新件走真实树；B:批量反向重建 package/）。

## 后端卡慢根因分析：AI 请求网关双重调度死锁（23:15）
- **现象**：layout-reviewer 和 style-mapper 两个 AI 请求从 14:44 发起后卡死近 30 分钟，`elapsedMs` 达 1770 秒远超 `timeoutMs` 180 秒，但 `totalTimedOut` 始终为 0，超时机制从未触发。调度器 `activeCount:2 / maxActive:2` 被占满，后续请求全部排队。
- **根因**：`BaseAgent` 构造函数调用 `attachUnifiedInvoke(this.llm, ...)` 将 `llm.invoke` 替换为内部再调一次 `executeModelRequest` 的包装版本。而 `layout-reviewer` / `style-mapper` 通过 `invokeWithTimeout → invokeLangChainModel → executeModelRequest`（第一层）→ `operation: ({signal}) => llm.invoke(prompt, {signal})` → 被 patch 的 `llm.invoke` → 第二次 `executeModelRequest`（第二层）。第一层占了 2 个 active 槽位，第二层也需要 acquire 但 `activeCount >= limit`（2>=2）永远排不上 → **自死锁**。
- **影响**：系统 load 飙到 14.76，Chrome 86 进程加剧竞争，内存空闲仅 2.1GB。
- **未修改**：用户要求先分析不修改。

## AI 请求网关推荐修复方案（23:19）
- 推荐“单层调度 + 队列可取消”：保留 `attachUnifiedInvoke` 为唯一 `executeModelRequest` 入口；`invokeWithTimeout` 改为通过 `__mvgoRequestOptions` 将 timeout/retry/concurrency/signal/progress 传给已包装的 `llm.invoke`，不再外包一层 `invokeLangChainModel`。
- 同时让 `RequestScheduler.acquire` 接收 `AbortSignal`，排队期间取消时移除队列项并 reject，防止排队请求永久悬挂。
- 不推荐暴露 rawInvoke 或用 AsyncLocalStorage/全局 flag 掩盖嵌套；本次只给建议，未修改代码。

## 超时与调度方案复核（23:28）
- 上述主方向合理，但需校正：当前主要走 `llm.invoke()` 整体响应，网关拿不到首 token/分片事件，暂不适合实施首包/空闲超时；简单 `Promise.race` 后释放槽位可能留下后台 orphan 请求并突破并发限制。
- 新发现配置断点：`layout-reviewer`/`style-mapper` 固定位置参数 180000，虽传入 `options.requestTimeoutMs`，`invokeWithTimeout` 实际未使用；应采用 `options.requestTimeoutMs ?? timeoutMs ?? 默认值`。
- 最优分层：先修单层调度、队列可取消、执行超时从出队后计时；再加任务总预算与按 attempt 调度；最后采集 role/model/input-size 的 P95 后校准，真实流式化后再加首 token/空闲超时。
