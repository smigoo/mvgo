## 二、已定位的差距与根因（本轮 485d724d 实证）

| 差距 | 根因 | 证据 |
|---|---|---|
| **A. 骨架方向错**（纵向堆叠 vs 左 Tab + 右内容） | `container-rebuilder` 的 vertical/horizontal 判定 与/或 装配未遵守 `sec.layout` | 产物 `.c-device-monitor-slot-con{display:flex;flex-direction:column}` |
| **B. Tab 区出现两份** | planner 把同一区域解释两遍：`89:37`（真实 @antd/tab 壳）+ `section-main-content`（臆造语义壳，32 元素）→ LLM 各画一份 | 日志 `filteredCount:0`；产物 TabsSection + MainSection 内嵌 tabs-wrapper |
| **C. 去重失效** | `dedupeDuplicateSections` 只认名字/归属：臆造壳 `sourceNodeIds` 为空 → 跳过归属判定；`type+responsibility` 不同 → 措辞兜底不命中 | section-tree.js:68/97 |
| **D. 内容被挤出视口** | A+B 叠加：column 容器 + 内容翻倍 → 12 张设备卡在视口外 | 截图底部只剩被裁的 Tab 列 |

**不是 CSS 后处理改坏**：09-11 产物 `xfk40oe6` 的 `slot-con` 同样是 column，方向一直如此；差别在子组件拆分粒度与内容量。

## 三、分期执行计划

### P0 —— 取证（必做，1 轮真机 ≈ 4 min）
加临时日志，把"布局识别到底说了什么"打出来，一次性坐实 A/B/C：
1. `container-rebuilder`：每个重建容器的 bbox 与判定结果（vertical/horizontal）
2. `subcomponent-planner`：每个 section 的 `id / type / layout / sourceNodeIds / elementCount / responsibility` + **包围盒**
3. `89:37` 与 `section-main-content` 的**包围盒重叠率**
4. 顶层 slot-con 的 `layout` 判定值（设计稿应为 horizontal）

产出：`P0-取证.md`，明确"判错"还是"没遵守"——决定 P1 修哪里。

### P1 —— 根治重复解释（B+C）
在 `dedupeDuplicateSections` 增加**空间维度兜底**（不依赖名字）：
- 两个 section 包围盒重叠率 > 阈值（初定 60%）→ 判为同一区域的重复解释
- 保留 `elementCount` 更大的一份，把被丢弃者的 `sourceNodeIds` 并入（防信息丢失）
- 阈值先用 P0 实测值校准，写进单一事实源常量

验收：单测（构造重叠/不重叠/含臆造壳三例）+ 真机 `filteredCount > 0`、子组件不再出现两份 tab。

### P2 —— 根治装配方向（A）
按 P0 结论二选一：
- 若**判错**（layout=vertical 但设计稿是 horizontal）→ 修 `container-rebuilder` 的 bbox 方向判定
- 若**判对但没遵守** → 把 `sec.layout` 作为**确定性约束**注入装配：根容器 `flex-direction` 由 layout 事实决定，LLM 自由发挥后由终验链校正（与 root-container-normalizer 同位置）

验收：产物 slot-con 方向与基准图一致（横排：左 Tab 列 + 右内容区）。

### P3 —— 结构自测脚本（可重复验收）
写 `scripts/verify-device-monitor.mjs`（或 spec），对产物直接断言第一节 7 条：
- 解析 `package/index.vue` + `package/components/*.vue` 模板 + `common.less`
- 断言：Tab 列存在且窄 / 切换卡 2 张 / **device-item = 12** / grid 3 列 / 异常数非空 / 6 个 tab 文本 / 12 个设备名
- 输出 PASS/FAIL 逐条表

### P4 —— 视觉自测闭环（与基准图比对）
- 渲染截图 → 用已接入的 vision 模型（`visual-truth-validator` / `vision-figma-cross-validator` 通道）对**结构要素**打分：Tab 列位置、网格 3×4、切换卡数量、缺失区域
- 基准图存 `baseline/`，每轮产物截图与它比对，输出"缺失/错位区域"清单
- **人工终判权在你**：我把每轮截图和 FAIL 项贴给你，你点头才算通过

### P5 —— 稳定性（防偶发回归）
连跑 3 轮（LLM temperature 已 0，但结构仍随机），要求 3 轮全过 P3 结构断言；任一不过则补确定性兜底。

## 四、每期验收纪律

1. 单测：新增/改动必须有 spec，且**端到端**（坏输入 → 修 → 校验通过）
2. 全量 jest：失败集必须与基线**逐字同名同数**（17 suite + 4 test）
3. 真机：至少 1 轮，`degradedFiles=[]`、`BLOCK=0`，且 P3 结构断言全绿
4. 截图：每轮贴给你做视觉终判

## 五、风险与回退

| 风险 | 处置 |
|---|---|
| P1 空间重叠阈值误合并（把真两块合成一块） | 阈值保守起步（60%），且只在"重复解释"场景启用；先 WARN 观察一轮再启用修复 |
| P2 强制方向覆盖作者意图 | 仅在 `sec.layout` 事实明确时生效，事实缺失不动 |
| 单轮 LLM 随机性导致误判修复效果 | P5 连跑 3 轮取稳定结论，不拿单轮下结论 |

## 六、开工顺序

P0（取证）→ P1（去重）→ P2（方向）→ P3（结构断言）→ P4（视觉比对）→ P5（3 轮稳定）

每一步做完贴证据给你，你在关键节点（P0 结论、P2 方向方案）做决策。
