## 排障：生产「新用户首次生成立马排队」（16:05–16:15，只诊断未改码）
**现象**：几个用户刚配完晓界、第一次点生成，立刻进入「在排队」。
**代码链路**：`queue/task-queue.service.ts`（并发槽位模式）+ `phase2.controller.ts:330/382/385` + `vue3.controller.ts:210` + `lite.controller.ts:432/596` + `lite/batch.controller.ts:492`。
**根因 1（主因）**：`TaskQueueService.MAX_CONCURRENT` 默认 **2**（`resolveMaxConcurrent()`，env `TASK_MAX_CONCURRENT`，夹 1–10）。生产若未设该 env，第 3 个并发任务必然 `concurrency_full` 入队。多人同时试用直接撞上。lite / vue3 / phase2 / batch **共用同一队列服务**，槽位是全局的。
**根因 2（放大器：幽灵槽位）**：
- `phase2.controller.ts:330` 判满用 `this.queueService.getRunningCount()`，而 `getRunningCount()`(:213) **不调 `reapStaleRunningTasks()`**；只有 `getAvailableSlots()`(:205) 才清理。**两个计数口径不一致** → 幽灵槽位期间持续误判满槽。
- `phase2.controller.ts:385` `this.phase2Service.startGeneration(...)` **既没 await 也没 .catch**；`phase2.service.ts` 全文**无** `markTaskFailed/markTaskCompleted`。释放只依赖 `progress.service.ts:404 complete()` / `:448 sendError()`。异常路径若没走到二者 → 槽位泄漏。
- `vue3.controller.ts` 同样无释放兜底；**只有 `lite.controller.ts:397/513/525/541` 有**。
- 幽灵回收阈值 `RUNNING_STALE_TIMEOUT_MS = 10min`（:43），靠 5s 定时器 `reconcileWaitingQueue` 触发 → 泄漏后最多卡 10 分钟。
**非因**：配额（新用户 count=0，HOURLY_LIMIT=5 / DAILY_LIMIT=15，不会 `quota_exceeded`）。
**诊断端点**：`GET /api/tasks/queue/stats`（免登录）返回 `{totalQueued, runningCount, maxConcurrent, availableSlots, avgWaitTimeMs, maxWaitTimeMs}`；`GET /api/tasks/queue`（需登录）含快照。若 `runningCount == maxConcurrent` 但实际无任务在跑 → 幽灵占槽。
**修复方向（待授权）**：① 生产 env 设 `TASK_MAX_CONCURRENT=4~6`；② `getRunningCount()` 内部补 `reapStaleRunningTasks()`（或 controller 改用 `getAvailableSlots() <= 0`）；③ phase2/vue3 给 startGeneration 加 `.catch(() => markTaskFailed())` 兜底。
