## 任务号与组件号统一主体分析
- 当前单组件生成没有两个独立业务号：`sessionId` 同时承担任务号、SSE key、任务存储 key、workspace 目录号和前端所称的组件 ID；MongoDB 组件另有 `_id`，通过 `metadata.sessionId` 关联。
- 当前格式：微码 `mc-{timestamp}-{hex8}`，Vue3 `mv-{timestamp}-{hex8}`。所以单组件场景实际上已经是“任务号=组件目录号”。
- 页面批量生成是例外：一个 `page-*` 父任务对应多个 `page-{parentSessionId}-{compKey}` 子任务/组件，不能让父任务号与所有组件号一一同主体。
- 可行的目标模型：先生成无语义主体 `traceId={timestamp}-{hex}`，再派生 `taskId=task-{traceId}`、`componentId=mc-{traceId}` 或 `mv-{traceId}`；页面父任务另用 `page-{traceId}`，每个子组件需增加独立 suffix 或独立主体。
- 不建议直接把现有 `sessionId` 全量改名。应先新增 `taskId/componentId/traceId` 字段，保留旧 `sessionId` 作为内部兼容别名，逐步迁移 SSE、任务持久化、workspace、预览和组件库。
- `ComponentDetail.vue` 当前展示的“组件ID”是 MongoDB `_id`，若要展示业务组件号应改为优先 `metadata.componentId/metadata.sessionId`，数据库 `_id` 只作为记录 ID。
- 推荐分阶段优化：阶段1新增统一 ID 工厂及 `traceId/taskId/componentId` 字段，保持 `sessionId=componentId` 兼容；阶段2修正前端展示和接口返回；阶段3再迁移 SSE/任务存储 key，旧任务只读兼容。重试任务创建新 `taskId`，复用原 `componentId` 仅用于覆盖编辑，重新生成新版本则创建新 `componentId` 并记录 `sourceComponentId/version`。

## 编号识别不清风险审计
- 结论：不能直接切换 `task-*`。当前大量链路把 `sessionId` 同时当任务号和组件目录号；类型判断散落在 `metadata.type`、`target`、`startsWith('mv-')` 和目录搜索中，且存在 `mc-*` 命名的真实 Vue3 历史目录。
- P0：Task 与 Component 无显式映射；重启恢复按 `task.sessionId` 找目录且固定写 Vue3；页面批量只返回 `childSessionId`；断点重试固定跑微码图并默认 `target=microcode`。
- 现存权限风险：组件文件读写仅当 `componentId` 是 Mongo ObjectId 时校验权限；实际 `mc-*`/`mv-*` 目录号会跳过所有权校验。随机后缀不能作为权限边界。
- 现存语义冲突：`/component/download/:componentId` 先按 Mongo ObjectId 鉴权，再把同值当 workspace 目录号打包；匿名预览忽略 `groupId`，先查微码再跨所有 Vue3 group，并允许前缀匹配，存在误命中条件。
- 编号重构前置要求：建立 `resolveComponentRef()` 统一解析器和显式 `target/groupId/componentId/taskId` 映射；所有预览/文件/下载接口按精确三元组定位，前缀只能作为历史兜底并产生日志告警。

## Vue3 预览背景与 CSS 变量失效分析
- 用户反馈 `mc-preview-stage` 写死白色背景，目标组件 `.mv-1785678105587-dc8835d0` 使用 `background: var(--color-bg)` 但 `--color-bg` 无效。

- 分析报告已写入 `/Users/smigoo/工作/mvgo/artifacts/vue3-background-root-cause-2026-08-02.md`，后续修复应优先让 Vue3 根背景脱离不稳定的 CSS 变量链路，并增加“Figma 有根背景但最终 computed background 透明/白底不匹配”的专属校验。
