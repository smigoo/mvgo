# 工坊「端到端自动开发」能力设计

> 起因：把「需求文档 + Figma + Apifox + 技术栈/规范 → 自动拆分功能点 → 详细设计 → 前后端代码 → mock → Git 交付」这件事，做成工坊的一项能力。
> 本文是**实现方案**，不是产物。测试素材（10 篇需求文档 + 2 个 Figma 文件）只用来验证「这条路走不走得通」。
> **输入形态以用户给的 `/Users/smigoo/工作/test` 项目目录为准**（见 §2）。
> 落笔时间 2026-11-04。**未部署、未 commit、未 push。**

---

## 0. 结论先说

**这不是给现有 13 节点管线加节点，而是并列新增一条「项目级」管线。**

现有 `ai-engine-v2` 是**组件级、单产物、固定拓扑**的「视觉 → 一个 .vue」。目标能力是**项目级、多产物**的「项目目录 → 契约 → 多模块前后端 + mock + 交付」。两者不是同一种东西，硬塞会让 `emit` 节点变成 if/else 怪物。

一句话拆解：

| 维度 | 现有 ai-engine-v2 | 目标项目级 |
|---|---|---|
| 输入 | 单个 Figma frame | **一个项目目录**（文档 + 原型 + 现成前后端脚手架 + 外链配置） |
| 产物 | 一个组件目录（`index.vue` + resources） | **往现成工程里补**前端模块 + 后端模块 + OAS + mock |
| **人读产物** | 无 | **需求唯一源 + 前端设计 + 后端设计**（三份 md，见 §3.1） |
| 拓扑 | 13 节点写死常量 | 9 阶段、可跳过、可断点续跑 |
| 真值来源 | Figma（像素可对账） | **契约（OAS）**，Figma 退为视觉参考 |
| 最小重跑粒度 | 整个组件 | **单个端点 / 单个功能点** |
| 交付目标 | 无 | **多仓**（项目里可能不止一个 git 仓） |

## 1. 三个硬事实决定了「怎么加」

这三条是从代码里读出来的，不是推测。

### 事实一：拓扑是常量，规范包改不了
`backend-node/src/ai-engine-v2/pipeline/node-registry.js` 的 `NODES` 表是模块级常量，13 个键写死：
`input-adapter` → `visual-parser` → `layout-reviewer` → `style-mapper` → `code-engineer` → `layout-refiner` → `style-refiner` → `adversarial-checker` → `screenshot-renderer` → `visual-comparator` → `code-structure-validator` → `revision-decision` → `emit`

### 事实二：spec 只能改「怎么生成」，改不了「生成什么、按什么序」
`specs/definitions/vue3-js.json` 的全部字段：`artifacts` / `naming` / `binding` / `events` / `panel` / `style` / `promptInjection` / `validatorRuleSet`。
**没有 `nodes`、没有 `gates`、没有 `tier`。** 用户规范包（`specs/user/*/skill.json`）能做的只有 `baseSpec` + 覆盖上述字段 + 追加 prompt 片段。

⇒ 想靠「传一个 skill 包」实现项目级管线，**架构上不可能**，必须新增管线。

### 事实三：Engineer 白名单只有 2 个，且都是「视觉 → 单组件」语义
`node-registry.js` 的 `ENGINEER_CLASSES = { MicrocodeEngineer, Vue3Engineer }`（配 `specs/skill-loader.js` 的 `ALLOWED_ENGINEER_CLASSES` 双向白名单硬闸）。
两者都是「看图写一个组件」，**没有「按契约写一组模块」的语义**。

⇒ 项目级需要新增 Engineer 类，且必须同步登记白名单（这是**两处齐改**，漏一处即静默失效）。

## 2. 输入形态：项目目录就是容器（S0 的输入协议）

用户给的 `/Users/smigoo/工作/test` 确立了本能力的**输入形态**：不是「上传一堆文件」，而是**给一个项目目录**。S0 的第一件事就是把目录**发现**成一张输入清单。

### 2.1 目录协议（按特征识别，不按名字硬判）

| 位置 | 必需 | 作用 | 缺失时行为 | 本例实测 |
|---|---|---|---|---|
| `docs/**` | **✅ 必需** | 接口 / 功能点真值**主源** | **S0 直接停**：无文档 = 契约无源，不许猜 | `沿江监控运维子系统_需求规格说明书_V1.1.docx`（264,560 字符，V1.1.0，2026-09-15） |
| `html/**` | 🟡 可选 | ① 信息架构 / 视觉锚点 ② **端点候选** ③ 交互参考 | 跳过；S4 无视觉锚点，质量降级但不阻塞 | 5 个 HTML / **8232 行** + `common/` + `libs/`（echarts + vue.global.prod） |
| `frontend/**` | 🟡 可选 | S4 产物**嵌进它**，不新建工程 | 绿地新建（用 spec 默认基座） | `vue3-vite-base`（Vue 3.5 + Vite 5 + ant-design-vue + `microvideo-request`，**带独立 `.git`**） |
| `backend/**` | 🟡 可选 | S5 产物**嵌进它**，不新建工程 | 绿地新建 | `03-...-lite-example-master`（Java 17 + MyBatis-Plus + knife4j，**仅 5 个 java 文件**，**无 `.git`**） |
| `mvgo.project.json` | 🟡 可选 | Figma fileKey / Apifox 地址 / `delivery.branch` / **响应信封口径** 等外链与配置 | 用内置默认，并把「未声明项」计入缺失清单 | **本例缺失（新发现）** |
| `.git/` | 🟡 可选 | S8 交付目标 | S8 前 `git init`，或停下等用户定 | **顶层无 `.git`；只有 `frontend/vue3-vite-base/.git`** |

**发现靠特征，覆盖靠声明。** 识别不能靠目录名——本例 `03-microvideo-framework3.x-lite-example-master` 名字毫无规律。只能靠特征：`pom.xml` + `spring-boot` ⇒ backend、`package.json` 含 `vite` ⇒ frontend、`docs` 下的 `docx/md/pdf` ⇒ 文档、`*.html` 引 `libs/echarts` ⇒ 原型。**`mvgo.project.json` 的显式声明优先于特征探测**（探错了要能改回来）。

### 2.2 这个目录暴露的三条事实（都要改设计）

**事实 A：接口真值有三个来源，不止一个。**

本例实测：原型里**没有任何运行时请求**——`fetch(` / `axios.` / `XMLHttpRequest` / `.then(` 在 5 个 HTML + 3 个 common js 里**全部 0 命中**。
但 `common/service.js` 里**硬编码了 9 个端点路径**（文件首行自注：「服务监测静态原型：截图指标与补充的示例日志，**不连接生产接口**」）：

```
/api/vehicles/mileage/query        /api/toll/exit/query              /api/etc/transactions/query
/api/toll/entry/query              /api/weather/observations/query   /api/trajectory/query
/api/bridge/traffic/query          /api/toll/lanes/traffic/query     /api/province/gantry/traffic/query
```

⇒ 确立**端点三来源**：① 需求文档（主源）② **原型内嵌数据（候选锚点，须交叉验证）** ③ Apifox（后期反接）。
S1 对齐时，原型里的端点要么在文档里找到对应，要么进白名单——**不许因为「它在原型里出现过」就当成真值**：它是截图里的示例数据，不是契约。

**事实 B：S8 的目标可能是「多个仓库」，不是一个。**

顶层无 `.git`；`frontend/vue3-vite-base/` 有自己的 `.git`（remote 指向公司 GitLab，HEAD `fc4546a` main）；`backend/` 只有 `.gitignore` + `.gitlab-ci.yml`，**没有 `.git`**（从压缩包解出来的）。
⇒ S8 不能假设「项目根 = 仓库根」。必须**遍历所有 git 根**（`git rev-parse --show-toplevel`）逐仓提交，并沿用项目既有铁律：**显式列路径、禁 `git add .`、先子仓后主仓**。

**事实 C：这是「存量脚手架」，不是绿地。**

前后端都已存在完整基座（`mirovideo-vue3-vite-base` v2.1.0 / microvideo framework3.x lite 3.1.1），但都是**空壳**：前端 `src/api/` 只有 `test.js`、`views/` 只有 `home/index.vue`；后端只有 5 个 java 文件（`MicroAppliction` / `MybatisPlusConfig` / `XxlJob` / `XxlJobMapper` / `XxlJobController`）。
⇒ S4/S5 的产物形态是 **patch-in-scaffold**：往现成工程里加文件、接现成路由与包结构、用现成的 `microvideo-request` 发请求，**不是从零写工程**。
这直接修正了试跑结论——那 1780 行「外壳」是在**无基座**前提下的产物；**有基座时外壳由基座提供，S4 只产「模块 + 路由 + api 层」**。

⚠️ 配套推论：**原型 HTML 不是 S4 的代码模板**。原型是「单文件 HTML + 全局 `vue.global.prod.js` + 内联 echarts」形态，目标是「Vue3 SFC + Vite + ant-design-vue + microvideo-request」。直接「翻译」原型会产出与基座不兼容的代码。原型的正确用途只有三个：**信息架构锚点 / 端点候选 / 交互行为参考**。

### 2.3 目录自带的冲突项（S2 冻结前必须裁决）

**响应信封口径打架。** 后端基座 `readme.md` 写的是：

```json
{ "code": 200, "message": "响应消息", "detail": "执行细节", "data": {} }
```

`code` 参考 HttpStatus（200 / 201 / 204 / 400 / 401 / 403 / 404 / 405 / 409 / 413 / 429 / 500 / 501 / 503）。
而上游测试素材拍板的口径是 `{ code, message, data }`（**无 `detail`**），且统一 `code:200`。

⇒ **信封形态不能写死**。必须在 `mvgo.project.json` 声明 `response.envelope`（字段名 + `code` 语义），S2 按声明冻结；未声明则**抛给用户选**。写死任何一种，都会让另一类项目拿到错的外壳。

## 3. 九阶段与闸门（S0–S8）

| 阶段 | 名字 | 输入 | 产物 | 是否需要 LLM | 闸门（不过就停） |
|---|---|---|---|---|---|
| **S0** | 输入准入与归一化 | **项目目录**（docs / html / frontend / backend / `mvgo.project.json`） | `sources.json`（sha256、去重、分叉裁决）+ **`project.manifest.json`（坑位识别）+ 缺失清单** | ❌ 纯确定性 | 文档可解析；重复文件已去重；分叉已裁决；**坑位缺失已呈现给用户** |
| **S1** | 多源对齐 | S0 产物 | `alignment.json`（模块 ↔ 画板 ↔ 端点，**端点含三来源置信度**） | 🔸 弱 LLM（只做语义匹配） | 孤儿画板 / 孤儿模块 / **孤儿端点** = 0 或进白名单 |
| **S2** | **契约冻结** | S1 + 文档接口段 | `openapi.local.yaml`（严格 OAS 3.0）+ `conflicts.md` + **`REQUIREMENTS.md`（需求唯一源）** | 🔸 弱 LLM（抽取字段） | **端点齐全；0 悬空 `$ref`；信封 / 分页同源（口径取自项目配置）；文档 ↔ 契约双向差集为空** |
| **S3** | 本地 mock | S2 的 OAS | `mock/`（零依赖，可静态托管前端） | ❌ 确定性 | 端点覆盖 100%；分页真实生效；WS 可连 |
| **S4** | 前端 | S2 + S1 + **基座** | **`FRONTEND-DESIGN.md`（4a）→ patch**：模块 + 路由 + api 层（嵌进 `frontend/`）（4b） | ✅ LLM | **设计先出、端点覆盖 100%、人确认后才生成**；编译过；契约一致性（调用的 path 全在 OAS 内） |
| **S5** | 后端（Java / Spring Boot） | S2 + **基座** | **`BACKEND-DESIGN.md`（5a）→ patch**：controller/service/entity/mapper（嵌进 `backend/`）（5b） | ✅ LLM | **设计先出、端点覆盖 100%、人确认后才生成**；编译过 + 启动可跑 + 数据模型齐 |
| **S6** | 联调对账 | S2/S4/S5 | `reconcile.json`（三份清单差集） | ❌ 确定性 | **差集全为空** |
| **S7** | 反接 Apifox | S2 + Apifox 导出 OAS | `contract-diff.md` | ❌ 确定性 | 差异可解释（新增 / 删除 / 字段变更分类） |
| **S8** | Git 交付 | 全部 + 项目配置 | **逐仓**分支 + 提交 + 交付单 | ❌ 确定性 | 提交路径显式列全，无 `git add .`；先子仓后主仓；**目标分支取配置（默认 `go-dev`）** |

**收敛点只有一个：S2。** S2 之前全是「理解」，S2 之后全是「生产」。生产阶段的任何一路都不许自己发明字段。

### 3.1 三份人读文档：需求唯一源 + 前端设计 + 后端设计

（2026-11-04 追加要求：执行时要出这三份文档）

| 文档 | 落点 | 谁产 | 给谁看 | 回答什么问题 |
|---|---|---|---|---|
| **需求唯一源** `REQUIREMENTS.md` | `.gen/doc/` | **S2**（与契约同一次收敛） | 人评审 + S4/S5 的 prompt | 这个系统要做哪些事；每件事对应哪条端点、哪段文档、哪个画板 |
| **前端设计** `FRONTEND-DESIGN.md` | `.gen/doc/` | **S4a**（生成代码之前） | 人评审 + S4b | 页面 / 路由 / 组件树怎么切；api 层放哪；怎么接进现成基座 |
| **后端设计** `BACKEND-DESIGN.md` | `.gen/doc/` | **S5a**（生成代码之前） | 人评审 + S5b | 包结构 / 表结构 / entity / service / controller 怎么切；怎么接进现成基座 |

**核心定位：它们不是新的真值，是同一份真值的三种视图。** 这一句话决定了后面所有判据。

#### 唯一源 = 「裁决后的需求全集」，不是「所有文档拼起来」

S2 本来就要做抽取与匹配。现在把它的产物从一份变两份：**给机器看的 `openapi.local.yaml`，给人看的 `REQUIREMENTS.md`**——同一次收敛的两个面，这正是「S2 是唯一收敛点」的完整体现。

「唯一」体现在三件事：
1. **多篇 → 一份**：N 篇需求文档（本次实测 10 篇 + 2 组重复 / 分叉）合并成一份
2. **冲突已裁决**：文档之间打架的口径（本次实测 7 类），裁决结果写回本文档 + `conflicts.md`，**未裁决的不许进正文**
3. **带版本与哈希**：头部记 `sourceHashes` 与自身 `sha256`；S4/S5 注入 prompt 时记下这个 hash ⇒ 出问题时能判断「是设计错了，还是代码没按设计写」

#### 硬判据 1：文档 ↔ 契约必须一一对应（第五处对账）

契约现在一共有五处对账：**S6 三处**（前端↔契约 / 契约↔mock / 契约↔后端）+ **S7 一处**（本地契约↔Apifox）+ **S2 一处**（本文档 ↔ 契约）。最后这一处就是第五处，也是**唯一一处「人读产物 ↔ 机器真值」**的对账：

- `REQUIREMENTS.md` 里出现的每个端点，必须能在 OAS `paths` 找到
- OAS 每个 `path`，必须在 `REQUIREMENTS.md` 里有对应条目
- **两边都不得多出**（多出 = 要么有需求没进契约，要么有接口没进需求）

这条是集合差集，机器可判。它堵的是「文档写完就烂掉」这个通病。

#### 硬判据 2：三份文档不许复制字段真值（否则就是漂移源）

这是本项目最痛的教训（**同一事实两处表述，必然有一处先烂**）。所以：

> **字段级真值只存在于契约里。三份文档只写「引用」与「落点」，不写「定义」。**

- `REQUIREMENTS.md` 描述功能点时写：字段见 `openapi.local.yaml#/components/schemas/VehicleMileageQuery`
- 两份设计文档写：`src/api/vehicle.ts` 调用 `GET /api/vehicles/mileage/query`
- **不得出现成片的字段定义表**（响应字段名 / 类型 / 必填的表格）

判据（可 grep 硬判）：**文档里出现的所有 JSON Pointer 必须 100% 可解析，0 悬空**——与契约的「0 悬空 `$ref`」同构。

#### 硬判据 3：设计文档先出，人确认后才生成代码

S4/S5 内部拆成两拍，但**阶段总数不变（仍 9 个）**，也**不新增 LLM 阶段**——原本 S4/S5 就是 ✅ LLM，只是把一次调用拆成两拍：

```
S4 = 4a 产 FRONTEND-DESIGN.md（LLM） → [人确认闸门] → 4b 生成代码（LLM）
S5 = 5a 产 BACKEND-DESIGN.md（LLM）  → [人确认闸门] → 5b 生成代码（LLM）
```

理由很直接：**改设计文档比重写代码便宜一个数量级**。在 4a / 5a 拦下的错，不用等到 4b / 5b 生成完再靠 S6 对账兜。

闸门判据：
- 每个端点必须被某份设计文档覆盖（**端点覆盖 100%**）
- 设计文档里的每个落点文件路径，必须在基座里真实存在或可新建（不许写「假设有个 xxx.ts」）
- **表结构（DDL）只出现在后端设计文档里**；前端要用到的枚举值**必须已进契约**（否则前端生不出类型）

#### 顺序：两份设计可以并行，都只读契约

后端设计定义表结构与实体，前端设计定义页面与 api 层。两者都只从**已冻结的契约**派生，因此**可以并行**——唯一耦合点就是上面那条「前端需要的枚举值必须在契约里」。

## 4. 为什么「只有 2 个阶段需要 LLM」

这是本方案最关键的工程判断。

目标能力听起来像「全 LLM 驱动」，实际上 **9 个阶段（S0–S8）里只有 S4（前端）和 S5（后端）真的需要生成代码**。其余 7 个里，5 个是纯确定性程序，2 个只做抽取与匹配：

- S0 归一化 = 解析 + sha256 + diff（本次实测：`md5`/`shasum` 抓出 2 组重复 / 分叉）
- S1 对齐 = 字符串 / 编码匹配 + 人工白名单兜底
- S2 契约 = 按固定模板填字段（文档里字段名是**已给定**的，不是让模型编）
- S3 mock = OAS → 代码模板
- S6 对账 = 三个集合求差集
- S7 diff = OAS 结构比对
- S8 提交 = git 命令

**收益**：
1. 成本砍掉 ~60%（确定性阶段零 token）
2. 质量可复现（确定性阶段不随机漂移）
3. 失败可定位（S4 错了就是 S4 错，不会怀疑是不是 S0 把它带歪了）

这也直接回应了「成本失控」的风险——真正贵的只有 S4/S5，而 S4/S5 以「单模块 / 单端点」为单元，可以按需只重跑错的那几个。

⚠️ **S4/S5 拆成 4a/4b、5a/5b 后，LLM 调用从 2 次变成 4 次**（见 §3.1）。这不改变「只有 2 个阶段是生产阶段」的判断，但成本要按 4 次调用算。净效果仍是省：4a/5a 的输入只有契约切片 + 基座清单、输出是纯文本设计（token 远小于生成代码）；而被它拦下的错误，原本要等 S4b/S5b 全量生成完、再由 S6 对账发现、再整模块重跑——**一次拦下省的是整个模块的生成成本**。

## 5. 契约是命门：四路同源 + 三处对账

### 为什么 S2 必须是「可被标准工具解析的 OpenAPI 3.0」
契约有四个消费者：

| 消费者 | 拿契约干什么 | 如果不是标准 OAS 会怎样 |
|---|---|---|
| 前端 S4 | 生成调用代码 / TS 类型 | 只能手写，字段名靠猜 |
| 后端 S5 | 生成 controller/service | 同上 |
| mock S3 | 生成假数据 | 同上 |
| **Apifox S7** | **与线上契约 diff** | **接缝直接不成立，整个「后期对接 Apifox」目标落空** |

⇒ 用自定义 JSON 存契约 = 把 S7 这条路自己堵死。这是**不可回退的设计错**，必须在 S2 就锁死。

### 三处对账（S6，全部机器可判）
1. **前端 → 契约**：前端代码里出现的每个 `api.get/post('...')` 路径，必须在 OAS `paths` 里
2. **契约 → mock**：OAS 每个 path 必须在 mock 里有实现
3. **契约 → 后端**：OAS 每个 `method+path` 必须有对应 route handler，且**不得多出**（多出的属未登记接口）

这三条都是集合差集，**不需要 LLM 判断**，是最有性价比的质量投资。

### 加一处：**文档 ↔ 契约**（在 S2 内部做，不在 S6）
4. **`REQUIREMENTS.md` → 契约**：唯一源里的每个端点必须能在 OAS `paths` 找到，OAS 每个 `path` 也必须有对应条目，**两边都不得多出**

这是全部对账里**唯一一处「人读产物 ↔ 机器真值」**的对账（详见 §3.1 硬判据 1）。它必须在 **S2 出契约的同一拍**里做，不能推到 S6——因为 S2 之后一律只从契约派生，此时再发现文档与契约不一致，就得回滚重冻契约。

## 6. 三个真正难的点（不是代码量，是判据）

### 6.1 功能点拆分「没有真值」
视觉链路之所以能自动修，是因为有 Figma 做像素真值、能反复对账。需求拆分**没有真值**——同一个需求拆成 8 个功能点还是 12 个，都可能说得通。

**不要试图判「拆得对不对」，要判「拆得可追溯、可反驳」：**
- 每个功能点必须挂三个锚点：**文档锚点**（文件 + 段号）/ **画板锚点**（fileKey + nodeId）/ **端点锚点**
- 产出「追溯矩阵」并硬性要求：无锚点的功能点 = 0（否则拒），无功能点的画板 = 0 或进白名单
- **冲突不猜**：文档之间口径打架时（本次实测出 7 类），一律抛给用户选，并把选择结果写回 `conflicts.md` 作为「已拍板变更项」

这条也是本次试跑验证过的：我先抛了 4 个决策（响应包装 / 分页 / 缺失模块 / 本轮范围）给用户拍板，然后再开工——**先拍板再生成**是唯一能避免大规模返工的顺序。

### 6.2 前后端一致性不能靠「两边都生成对」
两个独立的生成过程不可能靠巧合对齐。只能靠**同源 + 对账**：
- 同源：S4/S5 的 prompt 都必须注入同一份 OAS 切片（而不是把需求文档再喂一遍）
- 对账：S6 的三处差集必须全空，**不空不许进 S8**

### 6.3 部分失败与单元级重跑
24 个端点里 20 对 4 错是常态。整体重跑有两个问题：贵，且会**覆盖已经对的产物**（尤其产物目录被人工改过时）。

⇒ 最小重跑粒度必须是「单端点 / 单功能点」。产物按单元隔离存盘，重跑只重写该单元。

## 9. 数据与断点续跑

- **不要往 `data/tasks.json` 里塞大文本**——该文件已 223MB 且 `/tasks/recent` 15s 轮询。项目级输入（需求文档全文）必须存产物目录，Task 上只存指针 + 长度。

### 交付分支是配置项，不是常量

`go-dev` 只是**默认值**，必须可被开发该项目的人改掉。三级取值，先命中先用：

| 优先级 | 来源 | 字段 | 说明 |
|---|---|---|---|
| 1 | 任务高级选项 | `deliveryBranch` | 单次生成临时覆盖。与 `extraPrompt` / `userComponentId` 同一套机制 ⇒ **须同步四处齐落**（`TaskMetadata` / `Task` / `createTask` / lite.controller），且 `getTaskStatus` 白名单**必须显式列**（漏写即静默剥离） |

| 3 | 内置默认 | `go-dev` | 都没配时用它；**永不落 `main`** |

⇒ 判据：S8 只读「解析后的分支名」，**任何阶段都不许出现字面量 `'go-dev'`**（出现即改配置无效）。这条可用 grep 硬判。

## 11. 本次试跑给出的证据（用你给的测试素材）

### 实际跑出来的东西
| 项 | 结果 |
|---|---|
| 输入 | 10 篇 md（11 个文件，含 2 组重复/分叉）+ 2 个 Figma 文件共 17 个顶层画板 |
| 产出 | 14 个文件 / 5848 行（契约 1311 行 + mock 1859 行 + 外壳 1780 行 + 对齐/冲突 654 行 + 契约源 244 行） |
| 契约 | 25 端点、79 个 `$ref` **全部可解析、0 悬空**、YAML 无 tab 无奇数缩进 |
| mock | 24 HTTP + 1 WS **覆盖 25/25**；7 项实测全 PASS；**零依赖手写 RFC 6455** 握手 + 掩码解析，6s 内收到推送 |
| 外壳 | Playwright 实测：三列 `440 / 992 / 440`、root `1920×1080` scale `0.833`、4 类图表 SVG 非空、弹窗 params 透传、toast 自动消失 |

**结论：能力可行。瓶颈不在「能不能生成」，在「生成出来对不对、能不能管住」。**

### 试跑暴露的 4 个真实缺陷（每个都对应一条设计决策）

| # | 缺陷 | 证据 | 对应设计 |
|---|---|---|---|
| 1 | **人写契约也会错，且错在三个不同层** | 我手写的契约被独立复核抓出 3 处：响应码分布错（把 D5 归成 `code:0`，实际 D5 是 200，且漏计 D10）、算术错（写成 25 HTTP + 1 WS，实际 24+1）、**出处归属错**（把缺 `sectionNum` 归到 D6，实际是 D2） | ⇒ S2 必须有 `adversarial-checker` 式**独立复核**，且**机器判据只能抓算术和结构，语义归属必须回原文对照** |
| 2 | **并行生成必然漂移** | mock 自己多实现了 1 个契约里没有的 `/operation/monitor/sectionList` | ⇒ S6 对账闸门**不是可选项**；「多出」比「缺失」更危险（缺失会报错，多出会静默扩散） |
| 3 | **阶段间有真实依赖，不能纯并行** | mock 的静态托管指向 `web/`，但 mock 先就绪时 `web/index.html` 还不存在 → `GET /` 404 | ⇒ 阶段依赖图要显式建模；S3 可先于 S4，但**验收**必须等 S4 |
| 4 | **输入从来都不干净** | 11 个文件里 2 组问题：`4.2.2.3` 两文件 sha256 完全相同（逐字节重复）；`4.2.3.1` 两版本已分叉（扁平 `businessConfig` vs `sections[]`，diff 3 段） | ⇒ S0 的去重与分叉裁决**必须前置**，且裁决结果要落盘（不能只在内存里选一个） |

第 1 条尤其值得强调：**契约是人写的、也是人让 AI 写的，而 AI 复核 AI 抓出了 3 处错**。这说明「生成」和「校验」必须是两个独立的、上下文隔离的角色——同一个人/同一个 prompt 自检，等于没检。

### 我给用户的第一个探查结论错了，纠正如下

我最初报「原型 HTML 零接口痕迹」，**这是错的**。准确说法是：

- ✅ **零运行时请求**：`fetch(` / `axios.` / `XMLHttpRequest` / `.then(` 在 5 HTML + 3 JS 里 0 命中
- ❌ **但不是零接口信息**：`common/service.js` + `service-overview.js` 里**硬编码了 9 个 `/api/...` 路径**，以 `{code, name, path, count, duration}` 的**表格展示数据**形式存在

⇒ 我当时的 grep 只查了 `fetch(/axios./url:` 三个模式、且**漏了 `/api/`**，属于「探针不全就下结论」。这正是本项目反复强调的老毛病：**判据必须挂计数行、探针必须覆盖全模式**。已按事实 A 修正设计（端点三来源）。
