## 子项②：2/6 无 vision 缓存成因（已闭环，确定性 bug）

### 日志实锤（`backend-node/server.log`，只读 grep）

```
[03:27:16.109] [WARN] [visual-parser] ⚠️ 视觉分析结果为退化/空结构，跳过缓存，允许后续重试重新调用 Vision {"cacheKey":"vision_GTcJm0DKQvcJvcOZTh5n1l_36:1693_microcode"}   ← fdbb799d
```

### 根因（代码级，形态错位）

`isVisualAnalysisDegraded`（`visual-parser.js:107-112`）读**顶层**：

```js
const secCount = parsed.layout?.sections?.length || parsed.sections?.length || 0
```

但判定对象 `executeResult`（`:4771-4779`）的实际形态是：

```js
{ layoutStructure: analysisResult, charts: [...], interactions: [...], ... }
```

—— sections 埋在 **`layoutStructure.layout.sections`**（`_buildCompleteResult:4533` 把 analysisResult 整个塞进 `layoutStructure` 键），**顶层没有 `layout`/`sections` 键** ⇒ `secCount` **恒 0**。

### 为什么 4/6 有缓存（假救主）

| 组件 | 顶层 sections(sim) | charts | interactions | 判定 | 实际骨架 |
|---|---|---|---|---|---|
| d04b5f2c | 0 | 0 | 1 | 写缓存 ✅ | 1 段（非退化） |
| 40c6e852 | 0 | 0 | 1 | 写缓存 ✅ | 3 段（非退化） |
| c1ac194a | 0 | 1 | 1 | 写缓存 ✅ | 4 段（非退化） |
| af0b0417 | 0 | 0 | 1 | 写缓存 ✅ | 2 段（非退化） |
| **68783bf6** | 0 | 0 | **0** | **误判退化 ❌** | **4 段齐全** |
| **fdbb799d** | 0 | 0 | **0** | **误判退化 ❌** | **1 段 + 24 children** |

有缓存的 4 个 = vision 碰巧返回了 `interactions`/`charts`（`interactions>0` 兜住）；`68783bf6`/`fdbb799d` 是弹窗/详情类静态组件，vision 原始响应 `interactions:[]`、`charts:[]`（`debug-ai-response.txt` 实证）——**静态组件天然三零 ⇒ 必然误判**。

### 连锁后果

1. 拒缓存 ⇒ 每次续跑/重试都重新调 Vision（费用 + 7–15s 时延），且 bypassCache 重试通道（`mc-component-graph-phase2.js:1694`）永远打不破误判循环。
2. `.checkpoint/visual.json`（`saveResult` 落盘）与 `vision-cache/` 事实上分裂为两套存储——误判组件只有前者。
3. 修复方向（P2-C4 前置）：`isVisualAnalysisDegraded` 增加 `parsed.layoutStructure?.layout?.sections` 读取路径（形态归一，非硬编码）；或判定统一改读 `layoutStructure` 包装形态。

### `isLayoutContainerSection` 判据（`section-tree.js:29-37`）

```js
sec.isLayoutContainer === true || (layoutSource==='container-rebuild' && children.length>0)
```

### 根因（两层叠加）

**层1 · 刀66-C 判据 ③b 把 `class` 差异当不可表达 ⇒ 整组 fail-open**（`index-repeat-group-rewrite.js:241/247`）：
三挂载标签的 class 是段高锚（`c-68783b-sech-2/3/4`，各自绑不同 `flex: 0 1 <px>` 段高），**必然逐成员不同** ⇒ `attr-diverges:class` ⇒ v-for 改写整组放弃。而 `class` 恰恰不在 `RESERVED` 白名单（`v-for/key/style/title/icon/items/theme/data-section-id`），也没有像 `data-section-id` 那样的「逐成员不同但可改绑数据字段」通道（`:257`）。

**层2 · fail-open 后的残留形态不闭合**：v-for 没改成 ⇒ index 保持三标签；薄包装段（3/4）自带数据没问题，但**代表段标签上的数据传递没有任何兜底**——契约文本（`iso-template-contract.js`）通篇面向「index 会用 v-for 遍历数据数组」这一预期形态，**没有「若 index 未收成 v-for，代表标签必须自带 :title/:items」的分支指令**；LLM 按「挂载无须传数据」的理解生成空标签（`<ContentSection class=.../>`），系统侧也没有「代表标签缺数据 ⇒ 确定性注入数据数组」的兜底刀。⇒ 三重合力：契约预期形态落空 + 挂载无数据 + 无兜底 = 空壳渲染。

### 佐证

- 该机全 log 仅 1 次刀66-C 触发（本任务），`applied=0` ⇒ 首个可见案例；凡「同构组 + 段高锚 class 不同」的组合都会踩中。
- 段高锚 class 与 A4 真值链路无冲突：骨架 `styles.flexGrow=0.902/figmaHeightPx=161`（战略组）正确，问题只在挂载数据。

### 修复方向（立项材料，本轮不动刀——涉判据变更须六问评审）

按「尊重唯一事实源 + 上游修复 + 无硬编码」三原则，候选方案：

- **方案 R-a（推荐）**：判据 ③b 给 `class` 开「逐成员不同但均为段高锚形态（`*-sech-N`）⇒ 改绑数据字段 `:class="isoItem.sechCls"`」通道（与 `data-section-id` 的 `:257` 同构，零语义猜测——sech-N 与成员顺序的对应关系可由 `sectionGeometries` 确定性派生）；同时契约文本补第 6 条：「若 index 未收成 v-for（fail-open），代表标签必须自带 `:title`/`:items`（数据由系统确定性注入，与兄弟包装同源）」+ 新增兜底刀：fail-open 后系统把三段数据数组以「成员→标签」对应关系**确定性内联**到三个挂载标签（与薄包装渲染同源）。
- **方案 R-b（最小刀）**：只做兜底刀（fail-open 后内联数据），不动判据 ③b。缺点：index 仍是三标签（与用户「vfor 的三个厂商段」裁决相悖），但空壳消除。

两案均须同轮更新：`iso-template-contract.js`（契约文本）、`index-repeat-group-rewrite.js`（判据/兜底）、刀66-C 计数行、四象限（vue3-engineer.js:1149 同链路）、`docs/2026-11-13-门禁全景评审.md` 台账。
