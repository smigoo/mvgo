# B1-S1b 与 A4 回写：相关性 + 优先级分析（2026-11-16 13:2x）

## 一、两者相关吗？

**上游同源，下游分流——「同一根因的两个下游分支」，但受损面和形态不同。**

```
A4 配对错位（根因：vision 段锚落在标题条 h=24 上，节点匹配打分命中薄条）
   │
   ├─ 分支①：vision styles.flexGrow / geometryPx 残留错值（0.078 / 24）
   │     └→ 唯一危险消费路径：buildSectionHeightsMap 的 raw fallback
   │        （pxOfAuthoritative 先查 repaired，查不到才吃 styles.flexGrow）
   │     └→ 触发条件苛刻：planLeaves 对齐失败 + raw 全段有 flexGrow 才走
   │     = **A4 修复值回写刀**（数据卫生，防御性）
   │
   └─ 分支②：planner P0-8 并集已修复出正确的 meta.height（142/175）
         └→ codegen 装配消费 meta.height ✅（主链路已正确）
         └→ 但「宿主高 ≠ 设计高」时 inline 手写 px（intrinsic 形态）留白
         = **B1-S1b 尺寸语义收口刀**（布局语义，根治性）
```

**交叉点（唯一）**：都涉及「段高事实源的一致性」。若 A4 回写刀把
`styles.flexGrow` 同步成 planner 修复值的 Σ=1 量纲，那么
`buildSectionHeightsMap` 无论走主路径还是 fallback 都拿同一份真值——
这**恰好也是 B1-S1b 的前提**（intrinsic 子项比例化的分母 `pbox.h` 同样
来自这段几何事实）。两刀共用「段高唯一事实源」契约，但**改不同文件、
不同链路、互不依赖对方的落地**，可以独立实施、独立回滚。

**结论：相关（同一根因的下游），但不互相阻塞——可并行立项、按风险排序实施。**

## 二、优先级排序

| 维度 | B1-S1b（inline px 收口） | A4 回写（数据卫生） |
|---|---|---|
| **用户可见度** | 🔴 **高**——aca64532 的「空这么高」直接可感知，命中**全部 intrinsic 接管形态的单段组件**（Tab+列表/详情类高频形态） | 🟡 **低**——纯数据卫生，fallback 触发条件苛刻（双失败才走到），当前无已知真机事故 |
| **命中面** | 每个走 intrinsic 接管的产物（高频） | 仅「A4 配错 + planner 修复 + fallback 双失败」三重叠加（低频） |
| **根治 vs 防御** | **根治**（删掉与 B1 目标相反的「留白不拉伸」语义，把 inline 分支拉进 Σ=1 比例世界） | **防御**（错值仍在但无人消费；或标注 superseded） |
| **风险** | 中——改 `buildIntrinsicChildStyle` 输出形态，`flex:0 1 auto` 的「可收缩」语义要保留（防溢出），纯比例化可能破容器小于设计时的表现；须阴阳对照 | 低——只写/标注字段，不改消费逻辑 |
| **验证成本** | 中——需要真机重发 + 宿主不同高度矩阵 | 低——spec 重放即可 |

## 三、建议执行序列

1. **先 B1-S1b**（用户可见、根治、命中高频形态）——但它刀面比 A4 回写大，
   按六问评审走：核心决策点是「比例化 vs 容器锁定设计高」：
   - 方案 α：子项 `flex:<r> 1 0`（Σ=1 与 B1 主形态统一）——宿主高≠设计时
     内容等比拉伸，**不留白但可能纵向变形**；

     变形**，宿主高≠设计时组件整体缩放居中（更像「组件」而非「填充」）；
   - ⚠️ α/β 是产品语义选择（面板填满 vs 设计保真），**建议你裁决**。
2. **后 A4 回写**（低风险小刀，5 行内 + spec）——可搭 B1-S1b 的同一次构建。
