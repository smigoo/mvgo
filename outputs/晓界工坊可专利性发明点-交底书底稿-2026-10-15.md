## 发明点 1：设计源多真值分工协同的组件生成方法

### 1.1 技术领域
UI 代码自动生成，涉及多源异构设计数据与生成模型的约束融合。

### 1.2 现有技术问题
设计稿通常只有一份。但同一产品需同时交付浅色与深色两套主题时，常规做法是人工在深色稿上重画一遍，或对浅色稿做机械反色 —— 前者成本高且两稿易失同步，后者深色语义色（主色、背景层级）几乎必然出错。

### 1.3 核心技术方案
**主副稿分工制**：

| 角色 | 输入 | 承担职责 | 不做什么 |
|---|---|---|---|
| **主稿** | 用户第一填入的链接 | 结构、几何、文案；执行完整 Figma API 分析 + Vision 理解 | — |
| **副稿** | 用户第二填入的链接 | **仅贡献色板** | 不调 `exportImage`、不做结构分析、不进 Vision 模型 |

关键约束（三条，缺一则机制失效）：

1. **同源校验**：两稿解析后若为同一 `nodeId`，判定双真值无意义并阻断
2. **限流保护**：副稿只调 `getNode` 不调 `exportImage`，规避 Figma API 导出限流（并发槽 1、429 冷却 30s 封顶 120s）
3. **fail-closed**：副稿拉取失败**直接阻断**，不静默降级为「仅主稿」——否则用户以为配了双稿实际没生效

派生的**主题分离处理**：设计变量按主题分别存储（`lightDesign` / `darkDesign`），不合并为单一变量表，避免深色主题读到浅色稿色值。

### 1.4 新颖性主张
1. 「主稿管结构几何文案 + 副稿仅管色板」的**职责切分**，而非两稿都做完整分析
2. 副稿仅调结构接口不调导出接口的**限流工程约束**
3. 同源阻断 + 失败阻断的**双向失效保护**

### 1.5 实现证据
| 内容 | 位置 |
|---|---|
| 主副稿解析与错误归类 | `backend-node/src/ai-engine/utils/dual-truth-figma.js:122`（`resolvePrimarySecondary`）、`:140`（同源校验） |
| 副稿拉取（只 getNode） | `backend-node/src/ai-engine/graphs/mc-component-graph-phase2.js#fetchSecondaryFigmaNode` |
| 产物内标记防伪 | `buildCssVarsFile` 确定性写入 `// dualTruth: figma-derived`，LLM 不可伪造 |
| 离线验证脚本 | `npm run check:dual-truth`（根仓）/ `verify:dual-truth` |

### 1.6 风险
- 「主副稿分工」本身接近设计惯例，**新颖性可能不足**；真正可能成立的是**「限流槽约束下的差异化取数策略」+「同源/失败双阻断」**，撰写时应把重心放在这两点
- 需检索：多稿设计输入、主题迁移、design token 双向绑定等方向

## 发明点 2：面向生成式组件的声明契约与可视化重组方法

### 2.1 技术领域
低代码/可视化编辑器的组件资产封装与运行时重组。

### 2.2 现有技术问题
代码生成工具交付的是「一份代码」。交付即定型 —— 换数据源、绑事件、切主题、调布局，都必须回到代码里改，业务人员无法参与。这导致组件在交付后迅速僵化，只能一次性使用。

### 2.3 核心技术方案
**双层产物结构**：

```
微码组件
├── 运行层：component.js / declare.js / package    ← 渲染与逻辑
└── 契约层：declare.json                           ← 可配置维度的外化声明
```

契约层承载 8 类可配置维度（实测 153 份产物覆盖率）：

| 维度 | 契约字段 | 覆盖率 | 配置后效果 |
|---|---|---|---|
| 业务事件 | `businessEvents` | 153/153 = 100% | IDE 内可视化绑定下游动作 |
| 数据源 | `dataSources` | 153/153 = 100% | 替换接口无需改代码 |
| 表单源 | `formSources` | 150/153 = 98% | 表单类组件数据接入 |
| 明暗主题 | `themeConfig` | 152/153 = 99% | 主题统一治理 |
| 布局配置 | `layoutConfig` | 149/153 = 97% | 一套组件多套排布 |
| 业务配置 | `businessConfig` | 146/153 = 95% | 组件级业务参数 |
| 面板键值 | `panelKey` | 136/153 = 89% | 面板型组件挂载 |
| CSS 变量 | `cssVariableConfig` | 134/153 = 88% | 样式变量外部可调 |

**主题描述符内置核心色**：契约的 `themeConfig` 可声明深色主题的三个核心色槽（`colorTextBase` / `colorPrimary` / `colorPrimaryBg`），使主题切换不需要另传样式表。

### 2.4 新颖性主张
1. 「代码 + 声明契约」双层产物，使**可配置维度从代码中剥离**到机器可读的声明结构
2. 契约字段与代码生成阶段的**双向约束**（生成时按契约产出代码，校验时按契约校验产物）
3. 主题核心色槽位**声明式内嵌**于组件契约，而非外部主题表

### 2.5 实现证据
| 内容 | 位置 |
|---|---|
| 契约字段全集 | `frontend/workspace/custom-components/*/declare.json`（153 份实测遍历） |
| 主组件装配器 | `backend-node/src/ai-engine/roles/microcode-engineer.js:2942` `$mcComponentBuilder` |
| 契约 Schema 校验 | `backend-node/src/ai-engine/validators/declare-json-schema-validator.js` |
| IDE 零改造接入 | `frontend/src/router/index.js:4` `import { mcRoutes } from '@microcode/designer'` |
| 双层产物生成 | `microcode-engineer.js`（8800 行）+ `vue3-engineer.js`（2196 行）双引擎 |

### 2.6 风险
- 「声明式组件描述」在低代码领域已有较多先行方案（如 UMDL、Widget JSON 协议），**新颖性风险较高**，须检索
- 更可能成立的是「**由生成式管线自动产出符合该契约的产物**」这一层 —— 即契约是 AI 生成的约束目标而非人工编写的配置格式

## 发明点 3：确定性自愈与多级质量门禁协同的生成代码验证方法

### 3.1 技术领域
程序自动修复与静态验证。

### 3.2 现有技术问题
生成式代码的失败模式高度重复（标签未闭合、围栏夹带、命名不一致、资源漏注入、样式变量漂移）。现有做法要么把这些问题全塞进 prompt 让模型自己注意（不可靠、不可验证），要么生成后再让模型修（引入新的不确定性）。缺一个「确定性、可回归、可开关」的中间层。

### 3.3 核心技术方案
**阶段化确定性修复链**（顺序不可调换）：

| 阶段 | 职责 |
|---|---|
| `CLEAN` 清洗 | 剥离模型输出夹带（围栏、闭合标签后的说明文本、thinking 块）—— 永远最先 |
| `STRUCTURE` 结构 | 标签闭合、裸键引号、双前缀坍缩、虚假换行 |
| `NAMING` 命名 | 实例 ID 前缀剥离、根容器 ID 注入 |
| `RESOURCE` 资源 | import 注入、背景/图标挂载兜底 |
| `STYLE` 样式 | less import、背景图尺寸、变量归一化 |
| `POLISH` 精修 | 插槽保障、头部结构 |

共 **43 条注册修复规则**，每条规则独立 ID，支持通过环境变量 `FIX_<ID_UPPER>=false` **单独回滚**。

**配套对抗性检查器**（9 类专项检查）：面板框架泄漏、内容背景覆盖、微码污染、混合布局、资源利用率、SFC 结构事实、插槽使用、样式覆盖。

### 3.4 新颖性主张
1. **修复阶段顺序不可交换**的编排设计（清洗必须最先，否则后续规则解析的是被围栏污染的文本）
2. **规则级独立开关**（单条规则可关、可回滚，而非整体开/关）
3. **确定性修复 + 对抗性检查成对存在**：前者改代码、后者判合规，职责分离且共用同一套结构事实

### 3.5 实现证据
| 内容 | 位置 |
|---|---|
| 阶段定义与顺序约束 | `backend-node/src/ai-engine/validators/code-fix-pipeline.js:17`（`FIX_PHASE`）、`:37`（`PHASE_ORDER` 注释「顺序即数组顺序，不可调换」） |
| 43 条规则 | `backend-node/src/ai-engine/validators/code-fix-rules.js`（1818 行） |
| 对抗性检查器 | `backend-node/src/ai-engine/roles/adversarial-checker.js`（2170 行，9 类专项检查） |
| 门禁总量 | `backend-node/src/ai-engine/validators/` 下 16 个非 spec 校验器 |

### 3.6 风险
- 「阶段化代码修复」在 AIGC 工具链中已有类似实践，**新颖性中等**
- 需检索：自愈代码生成、AST 级修复、生成后处理流水线

## 发明点 4（备选）：视觉相似度与结构事实双维交叉的保真校验方法

### 4.1 核心方案
两个独立维度的校验合并裁决：

| 维度 | 手段 | 输出 |
|---|---|---|
| **像素/语义相似度** | Figma 原图 + 渲染截图 → Vision AI 逐维度比对（颜色/间距/布局/元素完整性/多余元素/比例/字体 7 维度） | 0-100 相似度 + 分级 issue（high/medium/low）+ 可执行 CSS 修正建议 |
| **结构事实** | 解析产物代码，取真实布局/几何/样式事实 | 与设计真值逐字同源比对 |

**判定规则**：`pass = (相似度 >= 85) AND (无 high 级问题)` —— 双条件同时满足。

**关键设计**：`severity` 分级中明确排除「抗锯齿、字体渲染引擎差异等不可控因素」，并在 prompt 中强制「只报告实际存在的差异，不要为凑数编造问题」—— 这是**对抗假阳性的关键设计**，不是简单的阈值比较。

### 4.2 新颖性主张
1. 「相似度阈值 + 高危问题双条件」的合取判定，而非单一分数阈值
2. **排除项显式声明**（抗锯齿/渲染引擎差异不计），把不可控因素从判定域剔除
3. 输出直接携带**可执行 CSS 建议**，形成「检测→修正→复检」闭环

### 4.3 风险
- 相似度比对本身是成熟做法，**新颖性低**
- 可能成立的是「**排除项驱动的假阳性抑制**」与「**带可执行建议的闭环**」
