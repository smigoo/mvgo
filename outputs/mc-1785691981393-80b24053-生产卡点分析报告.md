# mc-1785691981393-80b24053 生产卡点分析报告

## 1. 结论摘要

该组件从开始到结束共耗时约 **45 分 30 秒（2,730,008 ms）**。主要瓶颈不在截图、浏览器预览或运行时门禁，而在两段串行的 LLM 代码生成链路：

1. **首轮代码生成：21 分 16 秒，占 46.7%**
   - 任务运行时走的是旧路径：`medium` 组件先尝试一次性生成完整 `index.vue`。
   - 完整文件连续截断 3 次，分别耗时约 460.9 秒、249.4 秒、190.3 秒，合计浪费约 **15 分钟**。
   - 之后才降级为 template/script 分段生成。

2. **全量修订及后续链路：约 14 分 59 秒，占 32.9%**
   - 首轮质量检查同时发现 compliance、structural、layout 等多类问题，因此路由到 `microcode-engineer/full`，重新执行全量代码修订。
   - 全量修订 563.4 秒，二次精修 241.5 秒，最终复审 90.4 秒，运行时门禁 3.4 秒。

两部分合计约占总耗时 **79.6%**。截图与运行时门禁两轮合计不足 7 秒，不是性能问题。

最终任务状态为 `completed`，但质量分只有 **45 分**；`runtimeGate=PASS` 只说明代码能够在真实浏览器中运行，不表示设计还原、规范、声明文件和交互质量已经达标。

## 3. 为什么首轮代码生成耗时 21 分钟

### 3.1 任务发生时实际走的旧路径

该任务被判定为 `medium` 复杂度，但当时的运行路径仍然优先让模型一次性生成完整 `index.vue`。日志显示完整文件连续发生三次输出截断：

| 尝试 | 耗时 | 结果 |
|---|---:|---|
| 第 1 次 | 约 460.9 秒 | 输出截断 |
| 第 2 次 | 约 249.4 秒 | 输出截断 |
| 第 3 次 | 约 190.3 秒 | 输出截断 |
| 合计 | **约 900.6 秒** | 三次结果均不可直接使用 |

直到三次失败后，流程才降级为 template/script 分块生成。由于图执行器通过 `await this.executeNode()` 严格串行推进，这 900.6 秒无法与其他节点重叠，全部计入总耗时。

### 3.2 当前源码已经优化，但该任务没有享受到

当前 `microcode-engineer.js` 已增加 `shouldSplitIndexVue()`，`medium` 和 `complex` 组件默认直接拆分：

```js
if (complexity === 'medium') {
  return { split: true, reason: 'medium-default' }
}
```

因此，下一次服务重启后，新任务不应再重复“先整文件尝试三次、再降级分段”的旧路径。按本任务数据估算，这项改动理论上可直接避免约 **15 分钟**的无效等待，但实际节省仍取决于模型响应速度和各分块是否重试。

### 3.3 仍然存在的长尾风险

当前每个分块最多尝试 3 次，每次 Engineer 调用最长允许等待 900 秒：

```js
const maxAttempts = 3
const response = await invokeWithTimeout(
  this.llm,
  p,
  900000,
  'microcode-engineer',
  input.onProgress,
)
```

理论最坏情况下，单个分块可能等待 45 分钟。并且 `Promise.race()` 只结束上层等待，未必真正取消底层模型请求，超时后可能仍占用连接或模型资源。

## 4. 为什么又进入了一轮全量修订

首轮审查并非只有格式或规范问题，而是同时出现：

- `compliance`：微码规范/声明规范问题；
- `structural`：结构、脚本或交互实现问题；
- `layout`：设计还原和布局问题。

当前路由只有在以下条件同时满足时，才允许仅进入轻量布局修订：

1. `runtimeGate=PASS`；
2. 问题仅属于 compliance 类；
3. 没有 structural、layout 等其他类别问题。

本任务不满足“仅规范类问题”，所以正确地进入了 `microcode-engineer/full`。问题不在路由判断本身，而在于：

- 上游 Figma/视觉分析质量不够，首轮产物先天存在多类问题；
- 全量修订会重新触发成本最高的 Engineer；
- 全量修订后又串行执行精修、复审、门禁，增加约 14 分 59 秒；
- `maxIterations=1` 后达到修订上限，即使最终分数仍为 45，也被记为流程完成。

因此，“completed”目前代表图执行结束，不代表质量检查通过。

---

## 5. Figma 获取阶段为什么用了 97 秒

`figma-connector.js` 单次请求超时为 90 秒，并允许最多三次重试。本任务第一次请求等待满 90 秒才失败，第二次很快成功，因此该阶段总耗时约 97.4 秒。

这属于可优化的网络长尾，但仅占总耗时 3.6%，优先级低于代码生成和全量修订。更合理的策略是：

- 缩短首个请求超时；
- 代理与直连采用更早切换或竞争请求；
- 对同一 fileKey/nodeId 缓存成功结果；
- 记录每次重试使用的网络通道和实际耗时。

## 6. 最终质量检查为何与实际代码矛盾

最终 Checker 报告声称缺少：

- `<script setup>`；
- ECharts 初始化；
- Tab 数据联动；
- `<style scoped>`。

但最终 `package/index.vue` 实际包含上述内容，还包含 `ResizeObserver`、资源释放以及 `<style lang="less" scoped>`。这说明最终报告中的部分结论不是可靠的源码事实。

### 6.1 已确认的采样统计缺陷

生成图中使用以下逻辑比较修订前后文件：

```js
const currentFiles = state.generatedFiles || {}
const prevFiles = state.preRefineFiles || {}
```

但两者结构不同：

- `generatedFiles` 是路径数组；
- `preRefineFiles` 是 `{ path: content }` 对象。

因此日志出现：

- `18/18 文件变更`；
- `unchanged: -9`。

直接后果是 `changedFileNames` 将所有真实文件都视为已变更，复审采样优化失效，所有文件均完整发送给模型。它会增加 token 和延迟，但目前没有证据证明它截断了最终 `index.vue`。

### 6.2 更可能的误判来源

最终复审矛盾更可能来自以下情况之一：

1. Checker 输入对应的文件版本与最终发布版本不一致；
2. 模型在长上下文中忽略或混淆了完整 `index.vue`；
3. 质量检查把非确定性 LLM 判断用于可由 AST/字符串解析确定的事实；
4. 复审输入没有快照留档，当前无法精确复现模型当时看到的文件集合。

### 6.3 仍然真实存在的问题

并非所有低分项都是误判。最终 `declare.json` 中：

- `componentName` 仍为 `"80b24053"`，未使用设计标题“环境监测”；
- `eventDataSchema` 仍为空对象。

这些属于真实未修复问题，应继续计入质量评价。

## 7. 优化优先级

### P0：直接减少 15～30 分钟级别浪费

#### P0-1 保持 medium/complex 默认分段生成

当前源码已经实现。下次重启后应通过日志确认新任务直接出现 `medium-default`，不再先尝试完整 `index.vue`。

**预期收益：** 以本任务估算，可避免约 900.6 秒无效调用。

#### P0-2 修复修订文件集合的数据结构

在比较前把 `generatedFiles` 与 `preRefineFiles` 统一转换为 `{ path: content }` 或 `Map<path, content>`，禁止用路径数组与内容对象直接比较，并增加约束：

- `changed + unchanged = total`；
- `unchanged >= 0`；
- changed 文件名必须来自真实文件路径集合。

**预期收益：** 恢复复审采样，降低 token、延迟和模型注意力分散。

#### P0-3 为确定性事实增加 SFC 静态检查

在调用 Checker 前由程序解析：

- 是否存在 `<script setup>`；
- `<style>` 是否包含 `scoped`；
- 是否导入/调用 ECharts；
- 是否存在 `onMounted`、`ResizeObserver`、dispose；
- template 中引用的变量是否在 script 中声明。

LLM 只能评价视觉、语义和设计还原，不得推翻静态解析结果。

**预期收益：** 消除本任务中最明显的误判，避免无意义全量修订。

#### P0-4 限制 Engineer 单次等待和重试预算

建议从“每次 900 秒、每块 3 次”改为总预算机制，例如：

- 首次 300～420 秒；
- 仅对明确可恢复的截断重试一次；
- 第二次自动缩小上下文或继续拆块；
- 同一分块累计预算达到上限后保存中间产物并停止，而不是重复长调用。

**预期收益：** 控制极端长尾，避免单分块理论 45 分钟等待。

### P1：减少不必要的全量重做

#### P1-1 将全量修订拆成目标文件修订

根据问题类别和文件依赖生成 patch plan：

- 样式/layout → 只修 `index.vue` 的 template/style；
- declare/schema → 只修 `declare.json`；
- 资源问题 → 只修资源映射；
- structural → 才进入 script 或完整组件修订。

#### P1-2 保存每一轮 Checker 输入快照

记录：

- 本轮文件路径、内容哈希、字符数；
- changed/unchanged 集合；
- 实际发送给模型的采样内容；
- 模型原始输出；
- 修订前后文件哈希。

这样可以准确判断“模型误判”还是“检查时版本不同”。

#### P1-3 区分流程完成与质量完成

任务状态建议拆分为：

- `completed_passed`：运行时和质量均达到阈值；
- `completed_with_warnings`：可运行，但质量未达标；
- `failed_runtime`：无法运行；
- `failed_generation`：生成过程失败。

本任务应属于 `completed_with_warnings`，不应只显示普通 `completed`。

### P2：网络和可观测性优化

- Figma 首次请求缩短超时并更早切换代理/直连；
- 对 fileKey/nodeId 增加结果缓存；
- 指标中分别记录 LLM 排队、首 token、生成、重试和解析耗时；
- 展示每轮 token、文件字符数和重试原因；
- 对底层 LLM 请求增加可取消能力，避免上层超时后后台请求继续运行。

## 8. 建议实施顺序

1. **先修复 revision 文件集合结构问题**，避免采样和复审输入继续失真。
2. **增加确定性 SFC 检查**，阻止 Checker 对已有标签和代码事实误报。
3. **调整 Engineer 超时与重试预算**，将“固定三次长等待”改成“总预算 + 自动再拆分”。
4. **实施目标文件修订**，避免非必要的全量 Engineer 重跑。
5. **调整任务完成状态语义**，准确呈现“可运行但质量未达标”。
6. 最后再优化 Figma 90 秒网络长尾。

## 9. 最终判断

这个组件慢的根因非常明确：

- **第一根因：** 任务运行时对 medium 组件采用整文件生成，连续三次截断，浪费约 15 分钟；
- **第二根因：** 首轮存在多类质量问题，触发全量 Engineer 修订及完整后处理，又增加约 15 分钟；
- **第三根因：** 图节点串行执行，所有长耗时调用直接累加；
- **第四根因：** revision 变更统计错误和 Checker 非确定性误判，降低了复审效率和可信度；
- **非根因：** Puppeteer 截图与运行时门禁，两轮合计不足 7 秒。

当前源码已通过 medium 默认分段解决第一根因的大部分，但其余三项仍需继续修复。该任务最终能够运行，却没有达到质量要求，应作为“带警告完成”而不是普通成功任务处理。
