## 1. 为什么做（Why）

### 1.1 问题陈述

当前平台的组件预览只有**一种语义：视觉保真**——把 Figma 原始尺寸（`figmaOriginalWidth/Height`）写死成像素，让设计稿 1:1 还原。这对「比对还原度」是正确的，但对「验证组件在不同宽度下会不会崩」几乎没有帮助：

- 想验证 375px 手机宽度下的表现，只能改代码里的写死值 → 改一次预览一次，成本极高且污染源码。
- 生成出来的组件是否带响应式能力（`@media` / `%` / `flex-wrap` / `vw`），**在预览里完全看不出来**——预览恒定在设计稿宽度，媒体查询永远不会命中另一档。

### 1.2 用户是谁、痛在哪

| 角色 | 场景 | 现在的痛 |
|---|---|---|
| 前端开发 | 生成完一个带栅格的图表组件，想知道窄屏会不会挤爆 | 只能改源码试，或开 DevTools 手改 iframe 宽度 |
| 质检 / 验收 | 交付前确认组件在手机端可用 | 无任何手段取证 |
| 产品 | 演示时想当场说明「这个组件是响应式的」 | 做不到 |

### 1.3 目标（Goals）

1. 在**不修改任何组件源码**的前提下，让预览视口宽度可变，从而让组件的响应式规则真实生效。
2. 提供「精确档位」入口（手机/平板/桌面），保证可复现、可对外演示的固定视口。
3. 保留现有视觉保真能力不退化（这是已验证的核心价值，不能为了新功能牺牲）。
4. 拖出的尺寸可复现：同一组件下次打开恢复到上次尺寸。

### 1.4 成功指标

| 指标 | 类型 | 基线 | 目标 |
|---|---|---|---|
| 预览页使用「响应式模式」的会话占比 | 驱动 | 无 | ≥30%（上线 4 周） |
| 因「窄屏布局失效」返工的任务数 | 结果 | 无基线 | 下降 ≥30% |
| 拖拽调尺导致的预览加载失败率 | 健康 | 无 | ≤0.5% |
| 视觉保真模式回归缺陷数 | 健康 | 0 | 0（硬约束，不接受退化） |

> 说明：前两项需要埋点，后两项可用前端日志统计。当前无埋点基建，**上线前至少保证后两项可查**（见 §7）。

## 2. 核心设计决策（本功能成败的关键）

### 2.1 决策一：拆成两种互斥的预览语义，而不是「加个 resize 手柄」

这是整个设计里最重要的一条。现有代码把「视觉保真」和「视口可变」混为一谈，结果是**加手柄一定会踩坑**。

事实依据（`frontend/src/views/preview/index.vue:488-510`）：

```js
const stageStyle = computed(() => {
  if (figmaOriginalWidth.value && figmaOriginalHeight.value) {
    return { width: `${figmaOriginalWidth.value}px`, height: `${figmaOriginalHeight.value}px`, ... }
  }
  ...
})
```

**stage 的宽高被写成固定像素**。外层 iframe 即使变窄，stage 宽度不变 → 内容被裁切 + 横向滚动条 → `window.innerWidth` 变了但**布局视口的可用宽度没变**，媒体查询命不中。

结论：拖拽手柄本身是廉价的，难点全在解开这道尺寸锁。所以设计必须是：

| | **保真模式**（默认，现状） | **响应式模式**（新增） |
|---|---|---|
| stage 宽高 | Figma 原始 px | 容器宽度 100%，高度可配 |
| 缩放方式 | `transform: scale()`（demo 页现状） | 无缩放，1:1 真实像素 |
| 溢出 | 外层滚动 | 内容真实重排 / 真实溢出 |
| 媒体查询 | 恒命中设计稿那一档 | 按拖拽宽度命中 |
| 用途 | 视觉保真比对、截图 | 响应式验证、多端演示 |
| 是否默认 | ✅ 是 | 否，需显式切换 |

**「拖拽调尺」这个动作 = 自动切到响应式模式 + 改容器尺寸**。二者是同一个动作的两面，不做成两个独立开关，避免用户拖了半天发现媒体查询还是不动。

### 2.2 决策二：靠 iframe 元素原生尺寸变化触发重排，不走 postMessage

`views/generate/components.vue:1623-1653` 已经有成熟的 postMessage 通道，容易让人想走这条路。**不需要。**

iframe **元素本身的 width/height 改变，其内部的 `window.innerWidth/innerHeight` 会自动更新、`@media` 会自动重新匹配**——这是浏览器原生行为，跨域与否都成立。

所以同步成本为零，代价是：**iframe 内的组件必须自己正确响应 window resize**（见风险 R1）。

### 2.3 决策三：档位预设与自由拖拽并存，且档位锁定宽度

提供 `375 / 414 / 768 / 1280 / 1440 / Figma 原始` 六个档位。
选中档位时宽度**吸附锁定**（只允许调高度），并给一个「解锁」入口允许微调。理由：对外演示时「刚好 375px」比「大概 380px」有说服力得多。

## 3. 用户故事

> **US-1**　作为前端开发，我生成完组件后想把预览视口拖窄一点，以便确认栅格在窄屏下会不会挤爆，这样我不必为了试一次布局就去改组件源码。

> **US-2**　作为质检，我需要把预览切到 375px 并截图，用于交付前的多端可用性取证，这样我能在报告里给出「已在手机宽度验证过」的证据。

> **US-3**　作为前端开发，我希望把我调好的预览尺寸记住，这样下次打开这个组件不用重新拖一遍。

> **US-4**　作为产品，我要在演示时当场把容器从桌面拖到手机宽度，用实际效果说明组件是响应式的，这样比放 PPT 截图更有说服力。

> **US-5**　作为前端开发，我偶尔要临时把预览拉大看细节，我希望这个能力不被新增的模式开关挡住。

## 4. 功能需求

### FR-1　模式切换（承载全部功能的前提）

| 项 | 规格 |
|---|---|
| 入口 | 预览区工具栏，`保真 / 响应式` 二选一切换（分段控件，非下拉） |
| 默认 | 保真模式 |
| 状态持久化 | 按 `componentId` 存 localStorage；用户本次会话的显式切换优先于历史值 |
| 切换副作用 | 保真→响应式：stage 宽度改为 `100%`，高度取「当前可视高度」；响应式→保真：stage 恢复 `figmaOriginalWidth/Height`，档位选择清空 |
| 切换时机 | **必须在 iframe 加载前完成**。运行中切换走一次 iframe 重建（`src` 不变，靠模式参数触发重渲染即可，不要整页刷新） |

### FR-2　拖拽调尺（响应式模式内）

| 项 | 规格 |
|---|---|
| 手柄位置 | 右、下、右下角（**只增不减**）。左/上手柄不做——那意味着要同时改变 iframe 的定位基准，会与父页面栅格布局打架，收益低复杂度高 |
| 交互 | `mousedown` 捕获 → `mousemove` 更新 → `mouseup` 结束；拖拽中 `body` 设 `userSelect:none` + 对应方向 cursor |
| 实时性 | **必须用 rAF 节流**。既有 demo 页实现（`views/demo/index.vue:2750-2786`）是直接写 ref，实测在拖拽时会有明显掉帧，不复用其写法 |
| 步进 | 建议 10px 一档量化，配合方向键微调（见 FR-5） |
| 边界 | 宽 `≥320px`、高 `≥240px`；上限为父容器可用空间 ×1（超出则父容器滚动，不无限放大） |
| 反馈 | 拖拽中在容器右下角显示实时尺寸气泡 `1280 × 720`，松手后 1.5s 淡出 |

### FR-3　档位预设

| 项 | 规格 |
|---|---|
| 档位 | 手机 375×667 / 手机 414×896 / 平板 768×1024 / 桌面 1280×720 / 桌面 1440×900 / Figma 原始 |
| 选中行为 | 宽高同时应用；宽度进入锁定态（只调高度），提供解锁按钮 |
| 与拖拽关系 | 手动拖拽即视为「自定义」，档位高亮取消，尺寸读数显示 `自定义` |
| 与现有能力复用 | `views/demo/index.vue:2386-2393` 已有 `resolutionOptions`；`views/components/ComponentDetail.vue:438-441` 已有 desktop/tablet/mobile 三档。**档位清单要收敛成单一数据源**，不要三处各留一份（见 §6 风险 R4） |

### FR-4　尺寸持久化与复现

| 项 | 规格 |
|---|---|
| 存储键 | `mvgo:preview-size:<componentId>` |
| 存储内容 | `{ mode, width, height, preset, locked }` |
| 恢复时机 | 预览区初始化时、iframe src 赋值前 |
| 异常兜底 | 读到非法值（宽度 <320、非数字、JSON 损坏）→ 静默回落默认档位，不报错、不白屏 |

### FR-5　键盘与无障碍

手柄需可聚焦（`tabindex="0"`），聚焦后方向键调整尺寸（`Shift+方向键` 加速 10px），`Esc` 取消本次拖拽。`aria-label` 描述方向，尺寸读数用 `aria-live="polite"`。

### FR-6　视口越界可见性（防止「测了但没看见变化」）

响应式模式下，当组件实际渲染高度 > 视口高度时，在容器底部显示一条 `内容超出视口 Npx` 提示（而非静默裁切）。
**理由**：响应式测试的核心价值就是发现溢出；工具本身把溢出藏起来等于废掉价值。保真模式**不加**此提示（那里溢出是正常的）。

## 5. 非目标（Non-goals）

明确不做，避免范围蔓延：

1. **不改组件源码、不改生成管线**。本功能纯属预览层观察工具，不参与门禁判定，不写回产物。
2. **不做真机模拟**。不模拟 DPR、不做触摸事件模拟、不做 UA 伪装。移动端相关的 `hover` / `touch` 分支仍无法验证（见 R2）。
3. **不做 DPR 缩放**。所有尺寸均为 CSS 像素。1x 视口即可支撑响应式验证。
4. **不改造截图链路**。`resources/images/mc-preview.png` 与 `.mc-gen/screenshots/` 仍按现有逻辑生成，不新增「按当前拖拽尺寸截图」的能力（可后续单独立项）。
5. **不做旋转 / 自由布局 / 多容器并排**。
6. **不在响应式模式下做视觉保真判定**。保真模式才是唯一保真判据来源。

## 7. 验收标准

功能验收（必须全过）：

1. 切到响应式模式、拖窄到 375px，**组件内部的 `@media (max-width: 480px)` 分支真实生效**（用一个带断点的测试组件验证，不靠肉眼）。
2. 视觉保真模式**行为与改动前逐像素一致**（改前改后同组件截图 diff 为空）。
3. 含 ECharts 的组件在拖拽后图表重绘，不出现「容器变了图不变」。
4. v4 生成页拖出的高度不被高度上报逻辑覆盖回去。
5. 刷新页面后尺寸恢复；localStorage 被手动改成非法值时不报错、不白屏。

门禁类（三查）：

| 检查 | 方法 |
|---|---|
| 形状量化 | 统计改动涉及的预览页数量、档位清单出现次数（应为 1） |
| 日志留痕 | 模式切换 / 拖拽结束各打一条 info 日志，便于 §1.4 健康指标统计 |
| 离线探针 | 写一个带 `@media` 的最小测试组件，离线断言断点在 375px 下命中 |

**阳性对照**：必须有一个「若探针无效则测试必然失败」的用例，防止测试假绿。

## 8. 风险

| ID | 风险 | 概率 | 影响 | 应对 |
|---|---|---|---|---|
| R1 | 组件未监听 `window.resize`，拖拽后 ECharts / 布局不重绘 | **高** | 高（功能价值归零） | 验收项 3 强制覆盖；如普遍缺失，考虑在预览页宿主侧补一个 resize 广播 |
| R2 | 移动端专属分支（`touch` / `hover` / DPR）仍无法验证 | 高 | 中 | 已在 Non-goals 明确；UI 上加提示，避免用户误以为「375px = 真手机」 |
| R3 | 保真模式回归——stage 尺寸解绑影响大量现有链路 | 中 | **高** | 保真模式保持为默认且代码路径**完全不变**；响应式走新增分支，灰度按页面开关 |
| R4 | 档位清单分散在 3 处，加新档位时漏改 | 中 | 中 | 收敛为单一常量，代码评审检查项 |
| R5 | 与 v4 页高度自适应上报互相覆盖，出现「拖完弹回」 | **高** | 中 | FR-2 实施时必须同时加锁定标志位；验收项 4 专测 |
| R6 | 拖拽时 iframe 连续重排导致掉帧 | 中 | 中 | rAF 节流（FR-2 硬性要求） |
