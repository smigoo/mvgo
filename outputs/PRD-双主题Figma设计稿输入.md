## 1. 问题陈述

### 1.1 用户侧问题

平台当前一个组件只能挂一份 Figma 设计稿链接。产物**结构上**已有 `.theme-light()` / `.theme-dark()` 两个 mixin，但两套色值的来源不对等：

- 有一侧是 Figma 真值
- 另一侧是算法派生（主色沿用 + 中性色反转 + WCAG 兜底）或规范枚举，与设计稿无关

用户要么接受色差，要么去 Playground 手改 —— 而手改部分在下一次重新生成时被覆盖。

### 1.2 现状证据（代码级）

| 事实 | 位置 |
|---|---|
| 生成请求只接受单节点 `fileKey` + `nodeId` | `phase2/dto/generate-phase2.dto.ts:15-20` |
| Lite 路径只接受单个 `figmaUrl` | `lite/dto/generate-lite.dto.ts:38`（**本期不动**） |
| `backgroundBrightness` 单值决定 `defaultTheme` | `style-tokens.js:506-512` |
| light 槽位仅两来源：`figma-extract` / `derive-from-dark` | `style-tokens.js:525-527` |
| dark 槽位恒为枚举三核心 + designVars 附加轨 | `style-tokens.js:530-533` |
| 生成页只 1 个 URL 输入框 + 1 张预览卡 + 1 次 `fetchFigmaPreview` | `generate/component.vue:102-195, 1100-1133` |
| 截图渲染走预览页 URL，**未传 theme 参数** | `screenshot-renderer.js:651-656` |
| 预览页**没有主题切换控件**，只有一条提示文案 | `preview/index.vue:30-36` |

> 后两条是 D4 / D6 的关键取证：**截图不带主题 ⇒ 视觉门禁天然只评一个主题；预览页无切换 ⇒ 用户无法验证第二个主题。** 这两个能力缺口是同一根因的两面。

### 1.3 D2 与「铁律 1」的规范冲突（**已裁定：选 A**）

`style-tokens.js` 文件头「铁律」写明：

> **铁律 1**：dark 核心三变量永远来自规范枚举（M4-10 硬约束），**禁 LLM 生成、禁 Figma 提取**——无论原 UI 明暗

D2 决定「允许 Figma 真值覆盖三核心」，**与铁律 1 直接冲突**。既有铁律 2 的处理方式是「Figma 深色真值作为自定义设计变量额外定义进 dark 槽位，**命名避开框架预设 8 变量**」——即真值只能占自定义名，不能占 `colorTextBase` / `colorPrimary` / `colorPrimaryBg`。

| 选项 | 含义 | 状态 |
|---|---|---|
| **A：真值可占三核心槽位名** | 双真值模式下，Figma 真值直接写入 `colorTextBase` / `colorPrimary` / `colorPrimaryBg` | ✅ **已裁定采用** |
| B：保守 | 保持铁律 1，三核心恒为枚举；真值走 designVars 附加轨 | ✗ 未采用（保真度打折） |
| C：按模式分叉 | 单稿守铁律 1；双真值放宽 | ✗ 未采用（判据分叉复杂度高） |

#### 1.3.1 A 方案的判据落点（代码级核实）

M4-10 判据实现在 `skills/frontend-mc-check/scripts/mc-check.cjs:794-820`，逐字读取：

```
coreVars = CFG.enums.darkThemeCoreVars        // [colorTextBase, colorPrimary, colorPrimaryBg]
colorRules = CFG.enums.darkThemeColorRules    // 白名单：colorTextBase [#ffffff,#F0F0F0] / colorPrimary [#44E4FF] / colorPrimaryBg [#414141,#454545,#474747]
darkVarValues = extractObjectKeyValues(cssVarsContent, 'dark')   // 只读 css-vars.js 的 dark 对象
→ 逐个比对，不在白名单即 colorErrors → M4-10 判 false（error 级）
```

判据配置在 `mc-check-config.json:40-49`。**注意其三个特征**：

| 特征 | 事实 | 对 A 方案的含义 |
|---|---|---|
| 只读 `css-vars.js` | **完全不读 `theme-vars.less`** | 真值落在 `theme-vars.less` 的 `.theme-dark()` 里时，M4-10 根本看不到 ⇒ **只需改 css-vars.js 的 `dark` 块** |
| 白名单是硬编码枚举 | 值不在名单内直接判 error | 真值不可能命中枚举（设计稿主色千变万化）⇒ 必改判据，无绕过空间 |
| 纯文件判定，无任务上下文 | 不读 meta、不读 `dualTruth` 标记 | **判据无法「按模式分叉」** —— C 方案在此判据下不可实现，除非给它注入任务上下文 |

#### 1.3.2 A 方案必须遵守的三条约束

| # | 约束 | 原因 |
|---|---|---|
| C1 | 真值写进 `.theme-dark()` mixin **与** `css-vars.js` 的 `dark` 块 **两处都要写** | M4-10 只看 `css-vars.js`；少一处则「主题真值」与「声明真值」不一致，运行时用一套、门禁查另一套 |
| C2 | 真值**仍禁止写进 `.common()`** | 与 `theme-color-guard.js`（`.common()` 禁颜色槽位名/字面量色值）不冲突，是 D2 的原话要求 |
| C3 | M4-10 判据放宽**必须与生成器同批次上线** | 判据不改 ⇒ 门禁必然拦截生成器；生成器不改 ⇒ 判据改了也无意义 |

#### 1.3.3 ⚠️ A 方案遗留的产品级代价（评审需知情）

M4-10 的原始意图是**平台级一致性**：任何微码组件在深色模式下都用同一套主色/文字色，保证跨组件观感统一、宿主面板配色不冲突。选 A 意味着：

| 代价 | 说明 | 是否可接受 |
|---|---|---|
| **放弃跨组件主色一致性** | 每个组件的深色主色来自各自设计稿，多组件同屏时主色不一致 | 需产品/设计确认（推荐：接受，因为设计稿是唯一真源） |
| **M4-11 联动** | `darkThemeOptionalVars`（scrollbarTrackBg 固定 `#424242`）也受同一机制管辖，需确认是否同步放宽 | 本期**建议不放开**（滚动条与主题无关，无设计稿依据） |
| **宿主面板配色协同** | 组件深色主色若与宿主面板主色冲突，需人工协调 | 依赖项目实际情况，非平台可单方面解决 |

> 上述三点属选 A 的必然代价，已在此明示；如评审不接受，需回退到 B 方案。


### 1.4 适用范围收窄（D7）

| 维度 | 本期做 | 本期不做 | 依据 |
|---|---|---|---|
| 组件类型 | 微码（microcode） | vue3 SFC | 微码才消费 `theme-vars.less` 的 `.theme-light()` / `.theme-dark()` 双 mixin；vue3 走 `buildVue3ThemeVarsLess` 另一套渲染 |
| 档位 | **Max 档** | Lite 档 | `tier-profile.js`：max 含 `screenshot-renderer` + `visual-comparator`（`visualRegression: true`）；**lite 档 `visualRegression: false`**，根本没有评测节点 |

**收窄带来的三重利好**：

1. Lite 档无视觉回归节点 ⇒ D4 的双主题平均分**只需落在一处**（max 档链路），不必处理「lite 无评测却要显示分」的矛盾
2. 截图次数翻倍只影响 max 档（本来就是重档，可接受），lite 档零感知
3. 单稿回归验证只需覆盖 microcode-max 一条路径

**代价**：用户在 Lite 档无法使用本功能。缓解：前端在 Lite 档**隐藏双链接输入**并提示「双主题仅 Max 档支持」，不做无效入口。

## 3. 方案与核心设计：主副稿模型

### 3.1 候选方案对比

| 维度 | A：双链接双真值 | B：Figma Variables | C：单链接 + 派生（现状） |
|---|---|---|---|
| 输入 | 两个节点链接 | 一个链接 + 变量模式 | 一个链接 |
| 色值来源 | 两份设计真值 | 设计系统变量真值 | 一真一派生 |
| 设计侧改动 | 无 | **有**（需变量重构） | 无 |
| 实现成本 | 中 | 高（跨团队） | — |
| 保真度 | 高 | 最高 | 低 |

**选 A 为 P0，B 为 P2，C 保留为单稿路径现状。**

### 3.2 主副稿模型（关键设计）

两份 Figma 节点是两次独立设计，深浅两稿很可能结构不一致（深色版多一个图表、浅色版改过文案）。若两稿都跑完整分析再合并 section 树，产物会取"并集"，谁都不像。

| 角色 | 职责 | 参与范围 |
|---|---|---|
| **主稿（primary）** | 结构、section 顺序、几何尺寸、文案 | 完整 Figma + Vision 分析 |
| **副稿（secondary）** | **只贡献色板与主题专属变量** | 只调 `getNode`，**不调 `exportImage`**、不做结构分析 |

收益：结构一致性天然成立 + Vision 不翻倍 + Figma 导出图仍只 1 次（规避限流槽 `maxConcurrency=1` / 429 冷却 30s 封顶 120s）。

### 3.3 链路对比

```
现状（Max 档）：
  [主稿] → Vision → styleTokens(一真一派生) → 单主题截图 → 单次视觉比对

目标（Max 档）：
  [主稿] → Vision ─────────────┐
  [副稿] → getNode → 色板提取 ──┴→ styleTokens(双真值)
                                    ↓
                  截图 ×2（preview URL 带 theme=light / theme=dark）
                                    ↓
                  视觉比对 ×2（主稿图↔主稿渲染、副稿图↔副稿渲染）
                                    ↓
                  平均分 + 分主题问题清单
```

## 5. 需求详述

### P0（Must-Have）

#### R1 输入层：双链接 + 显式主副选择（Max 档 + 微码）
- Max 档 + 微码类型下，生成页增加第二个链接输入框，标签明确区分「浅色设计稿链接」「深色设计稿链接」
- 第二个可留空（留空 = 单稿模式）
- **主/副稿用单选显式指定，默认预选第一个填入的链接**（D1）
- 两份链接各自独立做 URL 校验 + 防抖预览
- **档位/类型守卫**：Lite 档或 vue3 时不渲染第二输入框

**验收**
- [ ] Given Max + 微码 + 两个合法链接，When 提交，Then 请求体同时携带两份节点信息与主副标记
- [ ] Given Max + 微码 + 只填一个，When 提交，Then 请求体与改动前**逐字节一致**
- [ ] Given **Lite 档**，When 打开生成页，Then **无第二输入框**，且有「双主题仅 Max 档支持」提示
- [ ] Given **vue3 类型**，When 打开生成页，Then **无第二输入框**
- [ ] Given 两链接同一节点，When 提交，Then 前端就地报错，不发请求
- [ ] Given 副稿链接非法，When 填写，Then 仅副稿框标红，主稿不受影响
- [ ] Given 默认状态，When 填入第一个链接，Then 主稿默认选中

#### R2 预览层：双预览 + 双确认
- 两份链接各自渲染预览卡（缩略图 + 节点名 + 尺寸），主稿卡带「主稿」标识
- **两份都确认**才允许点生成
- 副稿预览加载失败 → 卡片内明确报错（不静默）

**验收**
- [ ] Given 副稿预览未确认，When 点生成，Then 按钮禁用并提示"请确认深色设计稿"
- [ ] Given 副稿预览失败，When 查看，Then 卡片显示具体错误原因

#### R3 后端契约：双节点入参
- `GeneratePhase2Dto` 新增可选 `secondaryNode?: { fileKey, nodeId }` 与 `primaryRole?: 'first' | 'second'`
- 均**可选**，缺省行为与现状一致
- `phase2/figma-preview` 支持第二份链接预览
- **Vue3Dto 本期不动**

**验收**
- [ ] Given 不传 secondary，When 生成，Then 产物与改动前无差异（md5 清单 diff 判定）
- [ ] Given 传 secondary，When 生成，Then 主流程无异常

#### R4 事实层：双主题色板注入（**零派生**，依 D8 真值占三核心）
- 主稿与副稿各跑一次 `getNode` → 两份 `figmaNodeData` → `extractFigmaColorPalette` 各一份
- `buildStyleTokens` 扩展入参 `primaryPalette` / `secondaryPalette`
- 双真值模式下：`light` 槽位 ← 浅色稿 palette；`dark` 槽位 ← 深色稿 palette
- **D8：真值可占用 `colorTextBase` / `colorPrimary` / `colorPrimaryBg` 三核心槽位名**
- **派生算法在双真值模式下完全不执行** —— 不能留「真值缺失时仍派生」的分支顺序歧义
- 依 D2/C1：真值**必须两处同写** —— `.theme-dark()` mixin（运行时编译）+ `css-vars.js` 的 `dark` 块（M4-10 唯一校验对象）
- 依 D2/C2：真值**禁止写进 `.common()`**

**验收**
- [ ] Given 双真值，When 生成，Then 日志中 `lightSource` 与 `darkSource` 均为 `figma-extract`
- [ ] Given 双真值，When 生成，Then 产物中不存在「仅一侧由算法生成」的标记
- [ ] Given 双真值，When 检查 `.common()`，Then 无任何颜色槽位/色值（D2/C2）
- [ ] Given 双真值，When 比对 `theme-vars.less#dark` 与 `css-vars.js#dark`，Then 三核心色值**完全一致**（C1）
- [ ] Given 单稿，When 生成，Then 完全走现有分支，三核心仍为枚举值

#### R13 M4-10 判据修订（D8 连带，必与 R4 同批次）
- 修订 `mc-check-config.json` 的 `darkThemeColorRules`，允许三核心在**双真值模式**下取设计稿真值

## 6. Non-Goals

| Non-Goal | 原因 |
|---|---|
| **支持 Lite 档** | D7 裁定本期只做 Max。lite 档无视觉回归节点，双主题平均分无处落地 |
| **支持 vue3 SFC 管线** | D7 裁定。vue3 走 `buildVue3ThemeVarsLess` 另一套渲染，双 mixin 结构不同 |
| 自动从一份稿 AI 推断另一套主题并宣称保真 | 推断就是当前的派生算法，本需求是要**消除**它 |
| 支持 Figma Variables / 模式读取 | 需设计侧重构，跨团队排期不可控 → P2 |
| **副稿失败时自动降级为派生** | **D3 已裁定 fail-closed 阻断**。悄悄降级会让用户误以为拿到的是双真值 |
| 改动既有门禁判据来"放行"双主题产物 | 门禁是质量底线。若被拦，应修产物或修**误伤判定**（M4-10 见 §1.3），不是改判据放行 |
| 双稿结构自动对齐 / 自动合并 | 治标。结构以主稿为准、副稿只管颜色，更可控 |
| 单稿 Max 模式下改变任何现有行为 | 存量工作流零迁移是硬约束 |

| 指标 | 目标 |

### 度量口径提醒

- **双真值率必须同时看两侧**。单侧真值 + 单侧派生是最容易蒙混过关的失败模式。
- **平均分会掩盖单侧灾难**。必须与「最低主题分」一起看：建议同时记录 `min(perTheme.score)`，若 < 60 即使平均分高也需人工复查。
- **分档位统计**。因 D7 收窄，采用率分母必须是 Max 档微码任务，不能混入 lite。

## 10. 推进顺序

| 阶段 | 内容 | 产出 |
|---|---|---|
| S0 | **§1.3.3 遗留代价知情确认**（放弃跨组件主色一致性） | 产品/设计确认记录 |
| S1 | R3 契约 + **证明单稿零回归**（microcode-max） | 单稿产物 md5 与改动前一致 |
| S2 | **R4 + R13 同批次**（生成器与 M4-10 判据） | 两侧均真值，mc-check 通过 |
| S3 | R6 副稿 fail-closed | 4 类错误场景全覆盖 |
| S4 | R1 + R2 前端双输入双确认（含档位守卫） | 双预览可确认，Lite/vue3 无入口 |
| S5 | R5 声明层 + R12 预览切换控件 | 预览可切两主题 |
| S6 | R10 双渲双评 + 平均分 + 分主题问题 | 评分结构落地 |
| S7 | R11 双真值标识 | 列表 + 详情可见 |
| S8 | R7 ~ R9 收口 | 体检、角标、差异报告 |

**关键顺序纪律**

1. **S2 必须把 R4 与 R13 放在同一批次** —— D8 已裁定真值可占三核心，M4-10 判据不改就必然拦截生成器；反之判据先改而生成器未改，等于单稿产物被无端放宽。两者同进同退。
2. **S1 必须用「产物 md5 清单 diff」证明单稿零回归**，再动任何双稿逻辑。这条链路生产在用，回归污染代价远高于多花两天。
3. **S6 放在 S5 之后** —— 先让用户能切、能看见，才有意义去评测两个主题。
4. **S2 须保证 vue3 分支零影响** —— `style-tokens.js` 是双管线共享单一事实源，改动后需单独跑一次 vue3 回归。
5. **R13 的四条验收项是防误伤清单，不是可选项** —— 放宽一个判据时，必须同时证明它没有连带削弱相邻门禁。

## 附：与现有门禁的关系

本需求**只放宽一个判据**，其余一律不动：

| 门禁 | 本期处置 |
|---|---|
| **M4-10**（dark 核心三变量色值枚举） | ⚠️ **唯一放宽项**（D8 / R13）。必须与 R4 同批次 |
| M4-11（dark 可选变量色值 / 滚动条） | **不放开** —— 滚动条色与主题无关，无设计稿依据 |
