**适用对象**：AI Agent（如 Claude）维护或扩展此 Skill  
**最后更新**：2026-08-25

---

## 核心原则

### 1. 理解实际执行者

**错误案例**：创建 `mc-check-full.cjs` 编排 4 步工作流

**问题**：
- 误认为需要 Node 脚本编排
- 实际上 **AI 通过 SKILL.md 已经是编排者**
- 步骤 2（AI 评分）无法在 Node 脚本内完成

**正确理解**：
```
用户调用 /frontend-mc-check
    ↓
AI 读取 SKILL.md
    ↓
AI 自动编排执行 4 步骤
```

**教训**：实施前必问
- **WHO**：谁会使用这个功能？人工、AI、CI/CD？
- **HOW**：在实际场景中如何集成？有无法自动化的步骤？
- **WHY**：为什么需要这个中间层？直接调用底层脚本不行吗？

---

### 2. 避免加载但未使用的资源

**错误案例**：创建 `scoring-schema.json` 并加载，但从未使用

**问题**：
```javascript
const SCHEMA = JSON.parse(fs.readFileSync('scoring-schema.json'))  // 加载了

function validateScore(data) {
  // 手动写了一遍校验逻辑，SCHEMA 从未被使用
}
```

**验证方法**：
```bash
# 检查变量是否真的被使用
grep -n "const SCHEMA" file.js   # 加载位置
grep -n "SCHEMA" file.js         # 使用位置（应该 >1 次）
```

**教训**：实施后立即验证
1. 用 `grep` 检查新文件是否被引用
2. 检查加载的变量是否真正被使用
3. 如果只加载未使用，说明设计有问题

---

### 3. 不要盲从"建议"

**问题**：把审查报告中的"建议"当作"必须执行"

**正确做法**：
- 建议 ≠ 必须
- 实施前重新审视合理性
- 结合实际使用场景验证

## 代码设计原则

### 1. 数据校验必要性判断

**validateScore 是合理的**：
- ✅ 有真实错误来源（AI 生成可能出错）
- ✅ 在数据写入点校验（Fail Fast）
- ✅ 错误提示精确（带路径）
- ✅ 避免污染后续流程

**判断标准**：
1. 谁会产生错误数据？
2. 校验失败后会怎样？
3. 为什么不在后续步骤校验？

### 2. 校验增强方向

**v2.3.1 的正确改进**：

1. **总分一致性** - 防止 AI 计算错误
2. **维度扩展性** - 支持未来 Q6-Q99
3. **Bug 修复** - --init 目录创建

**关键**：基于实际问题改进，不是"看起来应该有"

## 常见错误模式

### 错误 1：创建不必要的中间层

**特征**：看似合理但实际不需要

**案例**：
- mc-check-full.cjs（AI 已是编排者）
- scoring-schema.json（加载但未使用）

**避免**：问"为什么需要这个中间层？"

### 错误 2：文档职责不清

**特征**：内容重复，维护困难

**案例**：
- README.md 写了架构设计
- ARCHITECTURE.md 写了使用示例
- 三个文档都写了评分标准

**避免**：严格遵循职责边界

### 错误 3：项目特定化

**特征**：只能在特定项目使用

**案例**：
- 硬编码路径 `/path/to/mc-component-warehouse-dev`
- 写死工程名称 `Vite 项目`

**避免**：使用通用描述和占位符

## 扩展指南

### 新增检查规则（M1~M5 系列）

1. 在 `mc-check.cjs` 中添加 `checkMX()` 函数
2. 使用 `issue(id, name, passed, message, level)` 生成结果（`level` 缺省 `error`；warning 级显式传 `'warning'`）
3. 更新 `references/checklist.md`
4. **不需要**修改 schema 文件

### 新增评分维度（Q 系列）

1. 在 `SKILL.md` 中定义 Q6 标准
2. `validateScore()` 已支持动态维度（无需改代码）
3. 更新 ARCHITECTURE.md 说明新维度

### 修改文档

**原则**：只改自己职责范围内的

- README.md 改了使用说明 → 不要动 ARCHITECTURE.md
- CHANGELOG.md 记录变更 → 不要重复写设计原理
- SKILL.md 改了执行步骤 → 同步更新其他文档的引用

## 总结

**核心**：
1. 理解实际使用场景 > 实现看似合理的功能
2. 验证真实使用情况 > 假设会被使用
3. 职责边界清晰 > 内容全面但重复
4. 通用性设计 > 项目特定实现

**验证**：
- WHO / HOW / WHY 三问法
- grep 检查引用和使用
- 文档职责边界检查

**文档**：
- README.md = 如何使用
- ARCHITECTURE.md = 如何设计
- CHANGELOG.md = 改了什么
- SKILL.md = AI 如何执行
