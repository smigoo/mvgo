#### 🔴 P0-0 Vision 分区错误：同行的 tabs 与 icons 被拆成垂直 sections（结构根因，最上游）

**Figma 节点树真值**（`.mc-gen/cache/figma-node-data.json`）：

```
[FRAME] cp-环境监测 (420×186)
 ├─ [VECTOR] bg (420×186)                    ← 整体背景
 ├─ [GROUP] header (377×28)                   ← 标题「环境监测」+ 装饰线
 └─ [FRAME] slot-con (380×145)
     ├─ [FRAME] sub-t (380×32, y898)          ← 顶行容器（普通 FRAME，无 layoutMode）
     │   ├─ [GROUP] tabs-list (295×27)        ← 4 个 tab（一氧化碳/能见度/洞内照明/洞外光强）
     │   ├─ [FRAME] tabs-icon (52×24, x1816)  ← 2 个功能图标
     │   └─ [GROUP] num (14×14, x1861)        ← 角标「6」
     └─ [GROUP] @echarts/line (380×113, y930) ← 图表区（下方）
```

**设计上 tabs-list / tabs-icon / num 三者 y 区间完全重叠（898–930），是同一行**（左 tabs、右图标、最右角标），图表在行下方。

**Vision layoutStructure（LLM 输入，`.mc-gen/cache/vision-cache/vision_*.json`）**：

```
layout: vertical-stack
 ├─ header-tabs     (figmaHeightPx 28)  ← 只有 4 个 tab
 ├─ chart-section   (figmaHeightPx 113)
 └─ header-controls (figmaHeightPx 32)  ← 2 图标 + 角标「6」，被拆成独立 section
```

Vision 把顶行拆成了 `header-tabs` 和 `header-controls` 两个**垂直堆叠**的 section → 子组件规划照搬 →  
产物 DOM 变成 `MonitorTypeTabs → MonitorDataChart → FunctionIcons` 三个垂直兄弟 →  
图标组被挤到图表下方独立一行，行内左右关系彻底丢失。

**为什么 Vision 会拆错**：`sub-t` 是普通 FRAME（无 layoutMode），行内关系只能靠 bbox 几何推断  
（y 区间重叠 + x 不相交 = 同行）；vision prompt 的分区 schema 只有 vertical-stack 单向表达，没有  
「行内左右复合」的结构能力。

**次要数据缺陷（同一 Vision 输出）**：

- tab 高度 27/21/12/24 各不相同——取的是各文字 bbox 高度而非统一的 27px 区块高
- `header-tabs` 高 28 vs 真值 32；`header-controls` 高 32 实为整行 sub-t 的高度
- vision summary 判定「浅色风格」——根容器 `#edf4fb` 浅色背景并非臆造（P1-4 主题问题表述需修正）

**修复方向（管线治本）**：分区后增加 Figma bbox 几何校验——两个 section 的 y 区间高度重叠且 x 区间  
不相交时，合并为同行 flex row（可扩展既有 figma-height-ratio.js 的 section 配对机制）；  
vision schema 支持行内左右复合结构表达。

#### 🔴 P0-2 Tab 区块 `height: 100%` + 类名不匹配 → 布局坍塌

**证据**：

- `MonitorTypeTabs.vue:2`（template 根元素）：class 为 `c-env-monitor-tabs-section`（**裸名**）
- `MonitorTypeTabs.vue:68-73`（scoped）：`.c-env-monitor-tabs-section { height: 100%; width: 100%; flex-shrink: 0; }` → 命中 template
- `resources/styles/common.less:13-17`：`.c-env-monitor-kdb60bc8-c-env-monitor-tabs-section { height: 27px; ... }` → **带实例前缀，与 template 裸类名不匹配，`height: 27px` 是死样式**
- 根容器（common.less:1-12）为 `flex-direction: column; height: 100%`（总高 186px）

**类名匹配矩阵**（LLM 生成不一致，三个子组件各不相同）：

| 子组件                     | template 根类                           | scoped 类   | common.less 类 | 实际生效来源                   |
| ----------------------- | ------------------------------------- | ---------- | ------------- | ------------------------ |
| MonitorTypeTabs         | `c-env-monitor-tabs-section`（裸）       | 同裸名 ✅      | 带前缀 ❌         | **scoped（height:100%）**  |
| MonitorDataChart（chunk） | `c-env-monitor-chart-section`（裸）      | 同裸名 ✅      | 带前缀 ❌         | scoped（flex:113 1 0）     |
| FunctionIcons           | `c-env-monitor-…-function-icons`（带前缀） | 裸名 ❌ 不匹配自己 | 带前缀 ✅         | common.less（flex:32 1 0） |

**布局坍塌机制（flex 计算）**：根容器 flex column 高 186px；  
tabs `flex-basis: auto` → 取 `height:100%` = 186px 且 `flex-shrink: 0`；  
chart `flex: 113 1 0`、icons `flex: 32 1 0` 的 basis 均为 0。  
剩余空间 = 186 − 186 − 0 − 0 = **0** → grow（113/32）无空间可分 → **chart 与 icons 高度恒为 0**  
（无论宿主容器多高等式都成立）；echarts 在 0 高容器上不初始化。`width:100%` 在 flex column  
中冗余无害（align-items:stretch 本来就拉伸），杀手只有 `height:100%`。

**根因（管线）**：

1. prompt 已有「禁止对内容区块写死 height:100%」规则但 LLM 违反，L0-B 无对应确定性拦截；
2. **新发现**：CODE-003 只校验 common.less 内 class 带前缀，不校验 template class 与 common.less  
   class 的命中关系 → common.less 里的正确样式（27px）成为永远不生效的死代码。

**修复方向**：

1. L0-B 新增校验——flex column 根容器下，非根内容区块样式含 `height: 100%` 即 BLOCK  
   （对齐既有 FLEX-005 实现方式，复用 `flex-sibling-guard.js` 单一真相源模式）；
2. 新增「template ↔ common.less 类名命中率」校验：common.less 中 class 未在 template 中出现即  
   WARN/BLOCK（检测死样式，防止类名前缀双轨）。

### 1.3 「预览有文件但布局不对」的解释

用户实测：Playground 预览文件齐全、核心症状是布局。结合证据，布局不对是**三层错误叠加**：

3. **比例层（P0-3）**：`flex: 113 1 0` / `flex: 32 1 0` 像素误写 grow，即使有剩余空间比例也错乱。

即使预览层通过「前端加载层自动修复兜底」（既有 #206 机制）补齐了 MonitorDataChart.vue，  
上述三层问题依然存在——文件完整 ≠ 布局正确。另：workspace 真实产物缺 MonitorDataChart.vue（P0-1），

### 6.2 审计揭示的病态结构（为什么会反复打补丁）

当前管线是三层堆叠架构，**每层都在修同一批问题，层与层之间事实源互相矛盾**：

```
prompt 文本规则（靠 LLM 自觉）        ← root-container.md 写错 flex 示例
    ↓ 出错
后处理修复函数（T1-T09 / fix 系列）    ← T2 写 80px，post-process 写 0，互相矛盾
    ↓ 漏过
门禁校验（CODE-001~018+）             ← TEXT-TRUTH 阈值放行，CODE-003 只查前缀
```

实锤的矛盾对（均为本次审计或历史记录发现）：
- `root-container.md`（flex 错误示例）vs `microcode-engineer.js` 09-05 修复段 —— 两个事实源不同步
- T2 `min-height: 80px` vs post-process `min-height: 0` vs chart-standards.md `160/100px` —— 三处口径
- prompt「禁止 height:100%」vs 无门禁 —— 文本约束无强制
- TEXT-TRUTH 阈值（09-04 放宽）vs 文案白名单（#535 加强）—— 两次修改方向相反

**这就是「补丁式修改」的根因**：同一语义在多处表达，修一处漏一处；新规则与旧规则冲突无人发现。

### 6.3 根源方案：从「LLM 生成一切 + 后置修补」翻转为「确定性装配 + LLM 创造」

**核心原则：凡是有真值的东西，不让 LLM 选、不让 LLM 写——由管线确定性装配。**
LLM 只负责它真正需要创造力的部分（交互逻辑、echarts option、事件处理）。

#### 第一层：止血（修正错误事实源，统一口径，不是打补丁）

| 动作 | 内容 |
|---|---|
| F1 | 修 `root-container.md:20` 的 flex 错误示例，与 09-05 修复段对齐；全仓 grep `flex:.*高度` 同类表述清零 |
| F2 | min-height 口径三合一：删掉 post-process 的 `min-height: 0` 注入与 T2 硬编码 80px，统一为「取 Figma 图表区高度 ×0.8」单一出处 |
| F3 | TEXT-TRUTH 分级：标题/标签类核心文案篡改一律 BLOCK（不进 ≤2 阈值），普通文本保留阈值 |
| F4 | visual-parser 兜底重建：行内并列节点（y 重叠+x 不相交）保留为 horizontal 复合结构，禁止拍平 |

#### 第二层：根源（架构翻转，单一事实源 + 装配层）

```
Figma 数据 ──→ Assembly Manifest（单一事实源 JSON）
                ├─ 区块表：尺寸/位置/布局方向（含行内复合）
                ├─ 资源表：变量名→文件→归属区块（唯一绑定）
                ├─ 类名表：区块→class 名（template 与 less 同源生成）
                ├─ 文案表：Figma TEXT 白名单（字面量注入）
                └─ 插槽表：headerSlots 归属（插槽 or 内容区，唯一位置）
                        │
        ┌───────────────┼────────────────┐
   装配层（确定性代码）              LLM（只做创造）
   · 布局 CSS（flex/尺寸/类名）      · 交互逻辑
   · 资源 import + 绑定              · echarts option
   · 文案字面量注入                  · 事件处理
   · headerSlots 落位
```

- **装配清单可 diff、可单测**（纯 JSON + 纯函数），LLM 输出面收窄 → 故障面同步收窄；
- 校验层降级为「最终防线」而非主流程——门禁数量应随装配覆盖**减少**而非增加；
- 迁移顺序（按覆盖面）：① 资源表+装配（治错绑家族）→ ② 布局表+装配（治 flex/双轨/堆叠错）→ ③ 文案表（治臆造）→ ④ 结构表（治行内丢失）。

#### 与「打补丁」的判别标准

| 补丁式（拒绝） | 根源式（采纳） |
|---|---|
| 新增一条 prompt 规则 | 删除 LLM 需要自觉的场景（装配接管） |
| 新增一个后处理 fix 函数 | 修正产生错误的事实源/确定性代码 |
| 新增一个门禁规则 | 让错误在数据结构上不可能发生 |
| 同一语义多处表述 | 单一事实源，多处消费 |

### 7.5 本次新增问题：后处理污染 + 快照冻结不同步

> 适用对象：`mc-max-1788871378450-011998bb / c-device-monitor-yoyz6l2l-011998bb`

#### 7.5.1 现象

- 详情页报 `LESS 编译失败`，报错路径指向 `code-snapshots/r-7395941b-dc6e-471a-963d-95f20eb66ff1/file/package/index.vue:396:1`。
- 当前 workspace 终态 `package/index.vue` 只有 50 行，说明报错来自冻结快照，不是 workspace 当前文件。
- `resources/styles/common.less` 中已经出现分隔文本碎片，样式文件被后处理污染。
- 预览截图与参考图布局不同，但组件并未完全缺结构，更像是终态样式/快照不同步。

#### 7.5.2 根因

1. **`style-class-consolidator` 只保证“合并后括号平衡”，不保证“内容仍纯净”**。当自愈/收敛链反复执行时，普通文本、分隔线、块注释碎片会一起被写进 `common.less`。
2. **`microcode-engineer.writeFiles` 的终态回写与快照冻结不同步**。磁盘上的自愈版已经修好，但 `finalTruthFiles` 仍可能保留自愈前坏版，于是快照冻结的是旧内容，workspace 却是新内容，出现“预览源和 workspace 源分叉”。
3. **`screenshot-renderer` 现在能更稳地分级门禁，但它解决的是渲染阶段阻断，不解决产物生成阶段被污染。**

#### 7.5.3 解决方案

| 优先级 | 方案 | 作用 |
|---|---|---|
| 🔴 P0 | 统一终态落盘后立刻从磁盘回读 `finalTruthWritten`，回写 `finalTruthFiles` | 保证快照 = 磁盘终态，消除冻结坏版本 |
| 🔴 P0 | `common.less` 收敛前增加内容净化校验：分隔线、孤立注释、非 Less 片段直接丢弃或回退 | 防止文本碎片混入样式文件 |
| 🔴 P0 | `style-class-consolidator` 失败时只回退，不做后续自愈叠加 | 防止“回退 + 自愈 + 再收敛”形成坏循环 |
| 🟡 P1 | 快照冻结前做一次 `index.vue/common.less` 语法与长度一致性检查 | 让 snapshot 捕获到的就是最终可发布版本 |
| 🟡 P1 | 预览页和 workspace 产物比对增加 hash / 行数差异告警 | 早发现快照与磁盘分叉 |

#### 7.5.4 验证标准

1. 再生成同类组件，快照 `index.vue` 行号应与 workspace 对齐，不再出现 300+ 行快照、50 行 workspace 的分叉。
2. `common.less` 内不再出现 `==============` 类分隔碎片。
3. 预览截图与参考图的差异只允许来自视觉模型偏差，不允许来自快照/终态不一致。
4. `LESS-COMPILE-001` 仍可作为门禁，但不再频繁由后处理污染触发。
