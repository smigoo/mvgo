## 2. 问题一：FLEX-005 单一事实源未统一

### 2.1 错误表现

```
FLEX-005 兄弟区块 flex-grow 量纲混用
<TunnelChart> → flex:0.978（比例量级）
<BridgeChart> → flex:131（像素量级）
<FlowPrediction> → flex:174（像素量级）
```

同一 `flex-direction: column` 容器内，三个子区块混用了**比例值**（`0.978` ≈ 1）和**像素值**（`131` / `174`）。

### 2.2 根因：策略冲突

**视觉事实层**已同时存在两套量纲（`preview-analysis.json`）：

```
daily-total:      flexGrow=0.683, figmaHeightPx=91
tunnel-chart:    flexGrow=0.978, figmaHeightPx=131
bridge-chart:    flexGrow=0.978, figmaHeightPx=131
vehicle-dist:    flexGrow=1.061, figmaHeightPx=142
flow-prediction: flexGrow=1.300, figmaHeightPx=174
```

**后处理修复层**矛盾（`flex-sibling-guard.js`）：

| 函数 | 方向 | 说明 |
|---|---|---|
| `normalizeFlexSourceConflicts()` | 比例→像素 | 跨文件同 class 冲突时，把比例量级统一到像素量级 |
| `normalizeFlexSiblingScale()` | 像素→1 | 兄弟组混用时，将像素量级改为 `flex: 1 1 0` |

两个函数在 `microcode-engineer.js` 落盘前**依次执行**，但策略相反，导致修复结果不稳定。重试轮间 LLM 输出可能落入其中一种归一形态而另一种不做，结果 L0-B 再检时仍不通过。

### 2.3 治本方案

**原则：Figma 高度是权威真相源。兄弟 flex 单元应从像素高度归一为同一量纲。**

修复步骤：

#### 2.3.1 修复 `normalizeFlexSiblingScale()` 策略（高优）

当前实现把像素量级改为 `flex: 1 1 0`，但文件头注释明确说「严禁把像素量级归一为 1」。策略应改为：

```
同一 flex 父容器内的兄弟组 → 统一使用 figmaHeightPx 像素值作为 flex-grow
```

即：
- `tunnel-chart` height=131 → `flex: 131 1 0`
- `bridge-chart` height=131 → `flex: 131 1 0`  
- `flow-prediction` height=174 → `flex: 174 1 0`

**更改 `normalizeFlexSiblingScale()`**：
1. 基于 figmaHeightPx 像素值做归一，不是改成 `1`
2. 所有兄弟都使用像素值 → 自然同量纲，FLEX-005 不会触发

#### 2.3.2 修复 `normalizeFlexSourceConflicts()` 兼容（中优）

确认它与 2.3.1 策略方向一致：统一用像素量级。如果两者方向仍相反，删掉其中一个。

#### 2.3.3 任务结果保留最终归一值（中优）

L0-B 检测前已经做确定性归一，应该把归一后的值存在 `codeValidationResult` 的 `evidence` 字段，方便排障确认「检测前 vs 后」的值。

### 2.4 验收条件

- [ ] 用第三任务最终 revision 的代码（`flex: 131 1 0` / `flex: 174 1 0`）跑 FLEX-005 检测 → PASS
- [ ] 用视觉事实层的三组像素值构造 mock 产物 → FLEX-005 检测不混报
- [ ] 构造一个真实混用 case（比例 + 像素混合）→ 归一后全部同一量纲

## 3. 问题二：LESS 缺失变量 `inherit` 兜底

### 3.1 错误表现

```less
// theme-vars.less 中由 less-variable-checker.js 自动添加：
@color-tab-default-bg: inherit;   // 自动添加
@color-tab-hover-bg: inherit;     // 自动添加
@fontWeightStrong: inherit;       // 自动添加
@color-stat-card-bg: inherit;     // 自动添加
@colorPrimary: inherit;           // 自动添加
@fontWeightMedium: inherit;       // 自动添加
@colorTextBase: inherit;          // 自动添加
@colorPrimaryBg: inherit;         // 自动添加
```

后果组件中的有效使用：
```less
// TopStatsBar.vue:225
background-color: @color-tab-default-bg;  // → inherit，和设计稿颜色不一致
```

### 3.2 根因：缺失变量推断无真实值

`less-variable-checker.js`（约行 98-110）扫描所有 `.vue`/`.less` 文件找出使用变量，与 `theme-vars.less` 定义变量取差集，缺失的统一写成：

```js
return `  @${v}: inherit; // 自动添加`;
```

这是编译兜底，不是视觉正确修复。LESS 编译能通过，但：
- `inherit` 从祖先元素继承的值**不是 Figma 设计值**
- 文字颜色 `inherit` 可能是黑色（期望白色/渐变）
- 背景颜色 `inherit` 可能是透明（期望半透明主题色）

### 3.3 治本方案

#### 3.3.1 styleTokens → 真实值推断（中优）

Style Mapper 已经生成了 `styleTokens` 结构。缺失变量应按以下优先级赋值：

1. **styleTokens 匹配**：扫描 `styleTokens` 中与变量名语义匹配的 token（如 `color-tab-default-bg` → tokens.tab?.defaultBg）
2. **Figma 颜色源**：从 `figmaNodeData.fills` 或 `resourceDomMapping` 中提取实际颜色
3. **语义规则推断**：从变量名推断用途（如 `@color-tab-*-bg` 用主题 tab bg 色）
4. **结构化告警**：以上都无法推断时 → 输出 WARN 到 `codeValidationResult.warnings`，列出缺失变量和推断失败的 token 路径

**不做纯 `inherit`**。

#### 3.3.2 收集常用缺失变量名 → 预处理白名单（低优）

从历史组件统计常缺变量：

| 变量名 | 预期默认值（dark） | 用途 |
|---|---|---|
| `@color-tab-default-bg` | `rgba(255,255,255,0.05)` | tab 默认背景 |
| `@color-tab-hover-bg` | `rgba(255,255,255,0.1)` | tab hover 背景 |
| `@fontWeightStrong` | `700` | 粗体字重 |
| `@color-stat-card-bg` | `rgba(255,255,255,0.04)` | 统计卡片背景 |

建立 `less-variable-fallback-map.js`，让系统级默认值覆盖 `inherit`。

### 3.4 验收条件

- [ ] 第一任务 `theme-vars.less` 中 `@color-tab-default-bg` 不再是 `inherit`，而是 `rgba(255,255,255,0.05)` 级语义值
- [ ] LESS 编译仍然通过
- [ ] 无法推断时输出结构化 WARN 到 fail reason（不阻断发布）

## 4. 问题三：Runtime latest snapshot 404

### 4.1 错误表现

两个已完成任务（58de1010 completed / 3dc0faa1 failed）的 runtime gate 都报：

```
GET http://127.0.0.1:2610/api/tasks/c-device-monitor-mxj2o4ai-58de1010/code-snapshots/latest → 404
```

URL 中使用的是 `componentId`（`c-device-monitor-mxj2o4ai-58de1010`），而非任务 `sessionId`（`mc-max-1788917080373-58de1010`）。

### 4.2 根因：preview resolver 缺 sessionId 反查

- `frontend/src/views/preview/index.vue` 中 `ensureLatestSnapshot()`：
  ```js
  const sessionId = String(route.query.sessionId || componentId || '')
  ```
  当入口（TaskDetail / WorkflowMonitor）没有传 `sessionId` query 时，fallback 到 `componentId` → API 寻不到任务。
- runtime gate（`screenshot-renderer.js`）以同样的方式构造 preview URL。
- 后端 latest snapshot 接口按任务 `sessionId` 索引，componentId 不匹配。

### 4.3 治本方案

#### 4.3.1 入口传 sessionId（高优）

所有调用 preview 的入口必须传 `sessionId` query：
- TaskDetail → `router.push({ path, query: { sessionId } })`
- WorkflowMonitor → 同上
- PG Playground → 同上
- `screenshot-renderer.js` → 从 `state.sessionId` 取值

#### 4.3.2 后端新增 componentId→sessionId 映射端点（中优）

当 preview resolver 找不到 `sessionId` query 时，用 componentId 查后端：

```
GET /api/tasks/resolve-session?componentId=c-device-monitor-mxj2o4ai-58de1010
→ { sessionId: "mc-max-1788917080373-58de1010" }
```

前端 fallback 到 `/code-snapshots/latest` 前先调 resolve 接口。

#### 4.3.3 runtimeGate latest 404 降级 WARN（低优）

对于 `RUNTIME-007` latest snapshot 404 场景：
- 如果 preview 页面自身能 fallback 到 workspace 源，`RUNTIME-007` 不应阻断发布
- 改为 WARN 而非 BLOCK（只有 workspace 也 404 时才 BLOCK）

### 4.4 验收条件

- [ ] 用真实 sessionId 调用 latest snapshot → 200 返回 revision
- [ ] 用 componentId 调用 resolve-session → 返回 sessionId
- [ ] runtimeGate 在 latest 404 但 workspace 200 时 → WARN（非 BLOCK）

## 5. 问题四：headerSlots 为空 → 视觉结构丢失

### 5.1 错误表现

第三任务 `preview-analysis.json`：

```json
{
  "componentTitle": "流量监测",
  "headerSlots": [],
  "coverageReport": { "covered": 22, "total": 27, "rate": 81 }
}
```

- 覆盖率 81% 但 headerSlots 为空
- 用户截图显示应有大 tab（流量预测 / 交通态势 / …）+ 标题 + `*数据实时更新` 注释
- 视觉分析 `notes` 提到：「设计稿包含设计师注释'*数据实时更新'，已排除」

### 5.2 根因：chrome-section-filter 或 header 验证过于激进

视觉分析的 `headerSlots` 在多个路径被截断：

1. **chrome-section-filter** 把标题栏判断为 `chrome-only` → 不放入业务 section
2. **header 验证**（`validateHeaderSlots`）可能因几何不匹配（标题区域未勾到足够像素阈值）判定「未找到 header 区域」
3. **planner** 接收到的 section 列表不含 header → `headerSlots` 保留空数组
4. **prompt** 看不到 header → 不生成 tab/header UI

视觉事实中 `inlineCompositeRows` 包含 `header-`、`sub-header`、`标题` 节点，说明 Vision 识别到了头部元素，但**在归一层被过滤**了。

### 5.3 治本方案

#### 5.3.1 几何容错增强（高优）

对 `headerSlots` 做**几何容错 + 业务语义复核**：
1. 标题栏高度阈值放宽（当前可能要求 > 30px，但部分 header 只有 20px）
2. 含 `tab` / `header` / `导航` / `title` 等语义词的节点：即使高度不足也保留
3. checkbox：跟踪 `componentTitle` 字段是否也被排除——如果标题被保留但 headerSlots 为空，说明 header 容器级有问题

#### 5.3.2 chrome/content 分流优化（中优）

- `chrome-section-filter` 的输出应保留「被排除的 chrome 节点列表」供排障
- 如果某节点同时出现在 `notes`（排除）和 `inlineCompositeRows`（识别），应有一致性校验
- 文档注释 `*数据实时更新` 不应导致整个 header 区域被排除

#### 5.3.3 headerSlots 下游断点补日志（低优）

在 `visual-parser.js` 的 `_normalizeAnalysisOutput` 和 `chrome-section-filter` 入口加条件日志：

```js
if (headerSlots.length === 0 && analysis.visualElements?.length > 0) {
  logger.warn('[headerSlots] 视觉元素存在但 headerSlots 为空', {
    识别到的标题节点: visualElements.filter(e => /header|title|tab/.test(e.label)),
    被排除节点: excludedTitles,
  });
}
```

### 5.4 验收条件

- [ ] 用第三任务视觉分析重新构建 → headerSlots 至少含 1-2 个 slot（标题 + tab）
- [ ] 含 `title` / `tab` 语义的关键节点不被 chrome-only 排除
- [ ] 文案注释（`*数据实时更新`）不污染 header 区域判定

## 6. 问题五：props 未接线导致 runtime render error

### 6.1 错误表现

第二任务 runtimeGate：

```
RUNTIME-004: 真实预览状态为 render-error
renderError: "Cannot read properties of undefined (reading 'name')"
```

### 6.2 根因：props-wiring-guard 缺跨文件检查

- `props-wiring-guard.js` 检查父组件模板调用子组件时是否传入了 required props
- 但第二任务的 `TabsAndControls.vue` / `ChartArea.vue` 可能在运行时从 props 或 data 中读取了未定义的 `name` 字段
- 可能场景：子组件接收 `chartData` prop，在处理 `chartData.map(item => item.name)` 时 chartData undefined

### 6.3 治本方案

#### 6.3.1 props-wiring-guard 升级（高优）

在 L0-B 前做覆盖数据流的 prop 检查：
1. 子组件 declared props → 父组件模板调用是否传入（现有）
2. 父组件传入的数据源（如 `:chartData="someData"`）→ 检查 `someData` 在 script 中是否定义（新增）
3. **optional chaining 兜底**：子组件对可能 undefined 的 prop 字段使用 `?.` 访问

#### 6.3.2 确定性代码门禁（中优）

对子组件运行时可能 `undefined.name` 的模式做扫描：
```js
// 检测模式：chartData.map(item => item.name)
// 如果 chartData 是 optional prop 且模板未约定其结构
// → 应替换为 chartData?.map(item => item?.name ?? '')
```

### 6.4 验收条件

- [ ] 第二任务重新生成 → runtime render error 不再出现
- [ ] L0-B 新增 props 数据流检查 → 捕获潜在的 undefined 访问

## 7. 问题六：失败任务 result 不完整

### 7.1 错误表现

| 任务 | status | resultKeys |
|---|---|---|
| mc-max-1788917942199-ba330e3e | failed | `["codeValidationResult"]` |
| mc-max-1788917271944-3dc0faa1 | failed | `["runtimeGate"]` |

失败任务只保留了检测阶段的关键字段，缺少：

- `coverageReport`
- `textTruthValidation`
- `subComponentPlan`
- `generationInput.contextManifest`
- `resourceDiagnostics`
- `revision pointers`（candidate / partial / lastGood 的最终 revision）

排障时必须去 checkpoint 和 temp 文件补取证，增加排查成本。

### 7.2 根因：失败路径 result 裁剪过严

`mc-component-graph-phase2.js` 的失败路径只保留了当前节点的最小结果集，没有保留早前计算好的诊断事实。

### 7.3 治本方案

#### 7.3.1 失败路径保留诊断上下文（高优）

在 graph 的 `signalAbort` / `recordFailure` 节点，保留以下字段到 result：

```js
result.coverageReport = state.coverageReport;
result.textTruthValidation = state.textTruthValidation;
result.subComponentPlan = state.subComponentPlan;
result.generationInput = state.generationInput?.contextManifest ? { contextManifest: state.generationInput.contextManifest } : undefined;
result.resourceDiagnostics = state.resourceDiagnostics;
result.revisionPointers = {
  candidate: pointerState.candidate?.revision,
  partial: pointerState.partial?.revision,
  lastGood: pointerState.lastGood?.revision,
};
```

#### 7.3.2 不重复保存生成态文件（低优）

diagnostic 字段都是 JSON 元数据（~1-5KB），不会显著增大 tasks.json。失败任务的总量远小于完成态，空间成本可忽略。

### 7.4 验收条件

- [ ] 构造一个失败任务 → result 包含 coverageReport / textTruthValidation / subComponentPlan
- [ ] result 中 revisionPointers 指向实际存在的 revision
