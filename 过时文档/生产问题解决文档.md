## 2026-09-11

### 问题 1：Figma 导出倍率不统一

**现象**：
- Lite 管线导出 2 倍图（scale=2）
- Phase2/Max 管线导出 1 倍图（scale=1）
- 不同管线导出倍率不一致，导致产物尺寸混乱

**根因**：
- 历史原因：Lite 管线早期使用 2 倍图提升清晰度
- Phase2/Max 管线后来统一改为 1 倍图
- Lite 管线未同步更新

**修复方案**：
统一所有 Figma 导出为 1 倍图（scale=1）

修改位置：
1. `lite.service.ts:1554` — `scale: 2` → `scale: 1`
2. `figma-client.js:75` — 默认 `scale: 2` → `scale: 1`
3. `figma-image-exporter.js:161` — `scale=2` → `scale=1`
4. `figma-connector.js:461` — 默认 `scale: 2` → `scale: 1`
5. `figma-connector.js:1101` — 默认 `scale: 2` → `scale: 1`

同步更新注释和日志（7 处）

**验证结果**：
- ✅ 后端构建成功
- ✅ dist 中所有 scale 默认值为 1
- ✅ 服务重启成功（PID 73621，端口 13030 监听中）
- ✅ 所有管线导出倍率统一为 1 倍

### 问题 2：文件超过单文件限制

**现象**：
- Lite 生成任务失败，错误信息：`文件超过单文件限制：resources/images/mc-preview.png`
- Figma 导出的 PNG 图片超过 2MB 限制

**根因**：
- 快照服务 `task-code-snapshot.service.ts` 对所有文件（包括图片）统一限制 2MB
- Figma 导出的 PNG 即使 1 倍图，大尺寸设计稿也可能 3-8MB
- 图片文件按代码文件标准限制不合理

**修复方案**：
文件：`backend-node/src/tasks/task-code-snapshot.service.ts:69-73`

新增图片文件独立限制：
```typescript
const MAX_FILE_COUNT = 200;
const MAX_SINGLE_FILE_BYTES = 2 * 1024 * 1024;      // 普通文件 2MB
const MAX_TOTAL_BYTES = 20 * 1024 * 1024;            // 总大小 20MB
const MAX_IMAGE_FILE_BYTES = 10 * 1024 * 1024;       // 图片文件 10MB
const IMAGE_EXT_RE = /\.(png|jpg|jpeg|gif|webp|svg)$/i;

// 在文件循环中：
const isImage = IMAGE_EXT_RE.test(path);
const sizeLimit = isImage ? MAX_IMAGE_FILE_BYTES : MAX_SINGLE_FILE_BYTES;

if (content.byteLength > sizeLimit) {
  throw new Error(`文件超过单文件限制：${path} (${(content.byteLength / 1024 / 1024).toFixed(2)}MB > ${(sizeLimit / 1024 / 1024).toFixed(2)}MB)`);
}
```

**验证结果**：
- ✅ 后端构建成功
- ✅ 服务重启成功
- ✅ 图片文件限制提升至 10MB

**当前限制配置**：
| 限制项 | 值 | 说明 |
|--------|-----|------|
| 普通文件单文件限制 | 2MB | 代码文件（.vue/.js/.ts/.json 等） |
| 图片文件单文件限制 | 10MB | PNG/JPG/GIF/WebP/SVG |
| 总大小限制 | 20MB | 所有文件加起来 |
| 文件数量限制 | 200 个 | 单个快照最多 200 个文件 |

### 问题 3：`text.match is not a function` 偶发错误

**现象**：
- Lite 生成任务偶发失败，错误信息：`代码生成失败: text.match is not a function`
- 有时能正常完成，有时失败，无明显规律

**根因**：
- `extractVueCode` 和 `extractMicrocodeOutput` 方法直接对 LLM 返回的 `text` 调用 `.match()`
- LLM 偶尔返回非字符串（对象/数组），导致 `.match()` 报错
- `extractVueCode` 已有类型防护，但 `extractMicrocodeOutput` 没有

**修复方案**：
文件：`backend-node/src/lite/lite.service.ts:2292`

在 `extractMicrocodeOutput` 入口添加类型防护：
```typescript
if (typeof text !== 'string') {
  this.logger.warn(`extractMicrocodeOutput 收到非字符串输入: ${typeof text}`);
  return { vueCode: '', declareJson: null };
}
if (!text) {
  return { vueCode: '', declareJson: null };
}
```

**验证结果**：
- ✅ 后端构建成功
- ✅ dist 中已包含类型防护代码
- ✅ 服务重启成功（PID 73621）

### 问题 4：用户配置的模型故障转移到了开发者的模型池

**现象**：
- 用户只配置了 `z-ai/glm-5.3-flash`，但日志显示切换到了 `qwen3.7-plus`、`deepseek-v4-flash-vision-exp` 等模型
- 这些模型是开发者本人的配置，不应该被用户请求使用
- 用户怀疑"开发者的大模型变成了全局配置硬编码"

**根因**：
- `getMergedAiConfig(userId)` 合并全局配置（`data/ai-config.json`）+ 用户配置
- 当用户只配了 1 个主模型，没有配置 `providers` 池时，`resolveBindingToLegacy` 不会生成 `providers` 字段
- `resolveVisionConfig` / `resolveTextConfig` 发现 `merged.providers` 为空，会回退到 `saved.providers`（从 `data/ai-config.json` 读取的全局配置）
- 全局配置包含开发者的 11 个 provider，导致用户请求的故障转移切换到了开发者的模型池

**修复方案**：
1. `config.service.ts` — `getMergedAiConfig`：当用户有自己的配置时，确保 `providers` 不为 null/undefined，显式设置 `[]`
2. `ai-defaults.js` — `resolveVisionConfig` / `resolveTextConfig`：当 `merged.providers` 是数组（即使是空数组）时，使用 `merged`，不回退到 `saved.providers`（全局配置）

修改位置：
1. `config.service.ts:375-385` — 添加用户配置隔离逻辑
2. `ai-defaults.js:376-382` — vision 配置隔离
3. `ai-defaults.js:443-449` — text 配置隔离

**修复效果**：
- 用户只配了 1 个模型时，故障转移只在用户配置的主模型中切换（通过 `primaryEntry` 注入到供应商池）
- 不会切换到开发者的模型池
- 开发者本人的配置仍然用于开发者自己的请求

**验证结果**：
- ✅ 后端构建成功
- ✅ dist 中已包含用户配置隔离逻辑
- ✅ 服务重启成功（PID 78031，端口 13030 监听中）
