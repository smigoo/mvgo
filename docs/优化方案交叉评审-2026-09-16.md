## 三、三处实质制约（详解）

### 3.1 🔴 核心矛盾：S5「fallback 不掩盖门禁」vs fallback 的存在目的

**问题**：fallback 机制（`generateFallbackCssRule`）**本来就是为"避免重试耗尽"而设计的**——
LLM 漂移 → 门禁 CODE-020 BLOCK → 重试常犯同一错 → 3×BLOCK 耗尽 → 任务失败。
fallback 补 stub 让门禁通过，**牺牲样式正确性换取流程可完成**。

**S5 的诉求**是"不许静默"（让漂移可见）。但如果不加区分地升级为 **BLOCK**，就会**退回"重试耗尽"**——这正是当年引入 fallback 要解决的问题。

**同时 S5 部分抵消 S2**：
- S2 让 stub 补上 `display:flex`（视觉上布局恢复了）
- S5 让门禁识别 stub 标记后报警
- 若 S5 用 BLOCK → 带病产物被拒 → **S2 的"治好"根本没机会落盘**

**调和（必做）**：
1. **S5 只做 WARN，不做 BLOCK**——「可见」而非「阻断」
2. 或：**BLOCK 只对「影响布局的 stub」**（如缺 display/flex 的容器 stub），对「仅装饰属性缺失」的 stub 保持 WARN
3. **S5 必须排在 S9 之后**：先让 LLM 少产生漂移（S9），再让残留漂移可见（S5），否则 S5 会放大重试量
4. 保留 fallback 的"兜底发布"能力（`.preview-source.json` 记录降级原因），**审计可见 ≠ 交付阻断**

### 3.2 🔴 S4「stripDecorSlugTail」修复不完整

**问题**：`componentId = c-max-1789494573361-77f2ae7d-77f2ae7d`
- S4 剥离 13 位时间戳 + 重复尾段后 → `c-max-<8hex>`
- **但语义段仍是 `max`**（从 sessionId 的 `mc-max-` 提取），而真实语义是 `策略类型分布`

**⇒ S4 只解决"双前缀/可剥离性"，不解决"语义段可读性"**。修完仍是 `c-max-xxxx`，而非 `c-strategy-distribution-xxxx`。

**调和（补一步）**：S4 需**同时**确保 `semanticTokenFrom(componentName)` 优先于从 sessionId 提取：
```js
// sanitizeComponentId 内，语义段来源优先级应为：
//   ① displayName / componentName（真实语义，如「策略类型分布」→ strategy-distribution）
//   ② 现有 id 的语义干
//   ③ fallbackToken
// 现状缺失 ① → 退化成从 mc-max- 提取的 max
```
**否则**：S4 上线后，"类名双前缀"消失，但出现"语义段全是 max/lite"的新问题（功能不受影响，可读性差）。

### 3.3 🟡 S6「背景补全」经方案 E 双端生效 → 需 vue3 回归

**问题**：方案 E（已做）把自愈链抽到 `runPreWriteSelfHealing`，**microcode 与 vue3 共用**。
S6 若加进这条链，会**同时作用于 vue3 组件**。

**风险**：vue3 产物的背景挂载语义与微码不同（无 base-panel / 资源注入用 `injectVue3ResourceUrls`），S6 的"补 size/repeat"可能：
- 在 vue3 上补出不符合其设计的样式
- 或与 vue3 已有的 `backgroundSize: 'cover'`（`fixBackgroundImageSize` 产物）冲突

**调和（必做）**：
1. S6 上线前跑 **vue3 产物回归**（不只 microcode）
2. 或：S6 加 `ctx.target` 条件，只在 microcode 生效（但要评估 vue3 是否也需要）

## 四、顺序依赖（改后的落地顺序）

原建议顺序（L3 → L4 → L2）**需要调整**，因为 S5 会放大重试：

| 新顺序 | 方案 | 理由 |
|---|---|---|
| **1** | **S4 + 语义段修复** | 最根本、改动小、无副作用（只对新生成生效） |
| **2** | **S6（+ vue3 回归）** | 直接命中现象，走方案 E 一处双端生效 |
| **3** | **S9（填值不命名）** | 从源头减少漂移 → 为 S5 铺路 |
| **4** | **S5（WARN 版，非 BLOCK）** | 必须在 S9 之后；且只 WARN |
| **5** | S7（保守策略） | 依赖 S6 的自愈链 |
| **6** | S8 | 独立议题 |
| **7** | S10 / 方案 B | 长周期 |

**关键改动**：**S5 从"L2-P0 第 2 位"下调到"第 4 位"**，且明确 **WARN 而非 BLOCK**。

## 五、评审结论

**回答用户问题：是的，有互相制约，共 3 处：**

| 制约 | 严重度 | 处理 |
|---|---|---|
| **S5 不掩盖门禁 ↔ fallback 设计目的**（并部分抵消 S2） | 🔴 核心 | S5 改 **WARN 非 BLOCK**，且**排在 S9 之后**；保留降级发布能力 |
| **S4 只修可剥离性、不修语义段** | 🔴 高 | S4 同时补「语义段优先取 componentName」 |
| **S6 经方案 E 双端生效 → 影响 vue3** | 🟡 中 | S6 上线前补 vue3 回归，或按 target 条件化 |

**不受制约的**（可并行/独立）：
- S1（前端）与全部后端方案
- S6 ↔ S7（互补）
- S8 与 S2（不同属性）
- S10 ↔ S9（递进）

**一句话**：**方案本身方向都正确，但 S5 是"刹车"、S9 是"治源头"——顺序颠倒会让刹车先于治源头生效，反而放大重试。S4 还需补一半（语义段）。**
