## 3. 本轮落地项：T09 headerSlots 结构性文本误注入（f461f30f）

### 7.3 执行纪律与边界

1. 顺序为 **第 1 项证据闭环 → 第 2 项覆盖契约 → 第 3 项注释澄清**；第 4 项只按证据升级。先取证，不因建议顺序直接宣称 P0/P1。

4. 不混淆监控、判定与执行：任务报告聚合端点/判定重放/看板提供可见性与审计；它们不能替代运行时 gate 覆盖，也不能单独证明门禁放行正确。

### 7.4 第 1 项只读核验记录（2026-11-08）

**三项结论**

1. **可达，但现网默认配置无触发实例**：`save` / `run` / `buildDynamicGraph` 三层都没有 gate handler 白名单，构造一份含未知 validator 的自定义 JSON 即可命中；但现有 11 份自定义管线中唯一带 gate 的 `p2-variant-test.json` 因 `engine:'phase2'` 被委托给生产引擎，dynamic 的 gate 分支不会执行。触发需人工写入 JSON 或绕过 UI 直调 API，且需避开 `isPhase2Like` 委托判定。
2. **不属「生产发布质量误放行」**：dynamic 链从不调用 `computeGateScore` / `hasHardPublishBlock`，生产发布走 `phase2Service` 另一条链；dynamic 任务终态由 `executeWorkflow` 硬编码 `success:true`。真实代价是「自定义管线内唯一的校验点被静默跳过 + 节点快照/进度显示虚假通过」，属可观测性与终态协议缺陷，不是发布阻断被绕过。
3. **「1 行 fail-closed」不治本**：把 `:396` 改成 `pass:false` 只改变图内 `_decision`，任务终态仍是 `completed`；且现存条件边标签 `pass/retry` 与路由容错集合不匹配，反而会 fallback 到 `pass` 边。治本出口上移到「拓扑校验」与「终态协议」两层。
