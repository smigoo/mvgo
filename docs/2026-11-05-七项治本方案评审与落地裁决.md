## 3. 本轮落地项：T09 headerSlots 结构性文本误注入（f461f30f）

### 根因（文件:行号 + 真机）

- 真值生产：`visual-parser.js:2645-2657` 识别 title-left 装饰图标组时写 `content: headerChild.content?.title || '装饰图标'`，**把描述性兜底文案塞进 content 字段**。
- 统一出口：`resource-mounter.js#ensureHeaderSlots:2571-2600` 对**每个** slot 取 `String(slot?.content).trim()`，直接 `map(text => '<span …>' + text + '</span>')` → 描述文案变成可见 UI 文本。
- 真机：`c-aiot-dpjh-bsjd-f461f30f/package/index.vue:5` 的 `<span style="display:inline-flex;align-items:center;gap:4px;margin-left:16px;font-size: calc(@fontSize * 0…">` 与 `itemStyle`（:2595-2597）逐字吻合 ⇒ 确认由 T09 注入，非 LLM 自由发挥。

### 修法（治本约束自检）

- 修复点选在**统一出口**（headerSlots → DOM 的唯一注入处），不是某个下游产物兜底。
- 判据**只认结构**：`elementType` 为资源型（icon-group / children 含 `resourceFile`）的 slot 不是文本槽，永不把 `content` 当 UI 文案渲染。
- 无任务 id / 组件名 / 文件名 / 魔法数；不新增守卫（不触 W7 顺序，不触总纲 :115 新守卫门禁）；不改 headerSlots 数据结构 ⇒ planner `hasDeclaredHeaderSlotContent` 零影响（该判据仍以 content 为「宿主是否含插槽事实」的证据，避免连带回归）。
- 计数行：`T09 资源型插槽文本注入拦截 {evaluated, blocked}`，恒 0 也打（可辩驳）。

### 影响面
