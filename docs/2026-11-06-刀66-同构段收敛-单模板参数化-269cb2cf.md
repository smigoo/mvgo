## 1. 背景与归因链

### 1.1 现象
同一页三个语义同构的厂商段（38:3137 战略合作厂商 / 38:3162 优质厂商 / 38:3206 普通厂商），仅厂商数不同（6/12/15），产物却是三副面孔：结构、类名、头部组织、着色规则各不相同。

### 1.2 269cb2cf 补充提示词归因（已完成取证）
| 取证项 | 结论 |
|---|---|
| 提示词是否到达模型 | ✅ 到达。全部 9 个 chunk prompt 含 `## 补充提示词` 区块（`user-addendum.js#buildUserAddendumSection` → `appendGlobalGuidance`），逐字下发 |

### 1.3 机制根因
- 管线按段切块、每段独立一次 LLM 调用；LLM 是概率生成器，「容器怎么套、类名叫什么」属自由发挥区，prompt 铁律管不到。
- 没有任何机制告诉 LLM「你还有两个同构兄弟段」；跨 chunk 一致性无人保证。
- 提示词（prose）压不过蓝图真值（index flex 三档来自各段 Figma 高度差）。
- **结论：跨段一致性必须由代码保证，不能靠提示词求 LLM。**

## 3. 设计（v1：LLM 契约模板 + 确定性薄包装）

### 3.1 交付形态（回应「v-for 的是三个厂商段」）
```
package/components/ContentSection.vue   ← 代表段：参数化模板（props: title/icon/items），LLM 生成一次
package/components/ContentSection3.vue  ← 薄包装：<ContentSection :title="优质厂商" :icon="..." :items="[...]"/>，确定性代码渲染
package/components/ContentSection4.vue  ← 薄包装：同上
index.vue                               ← 零改动（仍引 3 个文件名，回归面最小）
```
- 结构单源：模板只写一次 ⇒ 三段渲染必然一致（等价于段级 v-for 的效果，但不触碰 index.vue 的 LLM 契约）。
- 数据差异：每段 title/icon/items 由 Figma 真值（effectiveSections）确定性提取，以 props 注入。

### 3.2 同构检测（新模块 `utils/isomorphic-section-group.js`）
- 输入：`resolvePlanSections(input)` 顶层段 + 无需 figmaNodeData（v1 只用段树自带事实）。
- 资格判据（全部满足才可入组，任一缺失 ⇒ 不入组，fail-open）：
  1. `header` 存在且含 `title` 字符串 + `styles`；
  2. `body.layout === 'grid'` 且 `gridColumns` 为正整数；
  3. `body.children` 为非空数组，且全部 child 满足：`role === 'label'`、`styles` 为对象、无 `icon/image/charts` 字段（媒体段一票否决）；
  4. 无 `slotCandidate`（不与插槽机制抢段）；
  5. `type` 非 stats/chart 等特化类型（v1 只收 `type == null` 的通用段）。
- 签名（role signature，忽略 title 文本与 children 内容）：`[type, body.layout, gridColumns, headerStylesHash, hasIconControl, childRole, childStylesHash, childFill]` 稳定序列化。
- 分组：同签名段 ≥ `ISO_GROUP_MIN_MEMBERS=2` 成组；代表 = 组内第一个。

### 3.3 段→文件反查
`assignSectionComponentNames(treeSections)` 得 `Map<sectionId, name>` ⇒ `subPath = package/components/${name}.vue`；代表与全部兄弟的 subPath 都必须真实存在于 `subComps` 清单，否则整组放弃（fail-open）。

### 3.4 代表段契约注入（prompt-builder.js）
新导出 `buildIsoTemplateContract(chunk)`，读 `chunk.isoContract`，追加到 `buildChunkMiddle`（挂 `buildSectionIdentityContract` 之后）：
1. 必须声明 props：`title (String, required)` / `icon (String, default '')` / `items (Array<string>, required)`；
2. header 用 `title`+`icon` 渲染（icon 经 props 进来的图片地址直接 `:src`）；body 用 `v-for` 渲染 `items`；
3. 根元素 `v-bind="$attrs"`，**禁止硬编码 data-section-id**（由使用方 fallthrough 注入，包装层会带各段真 id）；
4. **禁止**在本文件 import 任何图片资源、禁止内联本段业务文案数组（文案全部来自 items props）；
5. 本组件会被多个同构兄弟段复用，任何结构/样式差异都会放大 3 份。
- 段身份契约（既有）仍下发本段真值文案 ⇒ 代表段样式/文案真值不受影响。

### 3.5 兄弟段处理（microcode-engineer.js）
- chunk 构建循环：兄弟 subPath 命中 `_isoWrappers` ⇒ `continue`（不进 LLM chunk）。
- 代表 chunk 打 `isoContract`（3.4 契约）+ 代表段 scopedInput 照旧。
- **chunk 池跑完后**新增「刀66 包装写入阶段」：
  1. 取 `allFiles[代表subPath]`，跑 `validateIsoTemplateProps(content)`（props 声明 + title/icon/items 三项齐全 + 无硬编码根 data-section-id）；
  2. 校验通过 ⇒ 对每个兄弟确定性渲染 wrapper（数据 = 该段 effectiveSections 真值：title / controls[0].resourceFile / children[].name），走与刀53 相同的最小修复管线（`_ensureSubComponentStyleAttrs` → `_ensureSubComponentStyleImport` → `injectResourceImports`）后写 `allFiles[subPath]`；
  3. 校验失败或渲染异常 ⇒ **回退**：兄弟段重新组 chunk 进池二次跑（复用 `chunks`+`cursor`+worker 池模式），本组按旧路径出独立组件（零损失）。
