## 3. 根因：R2 与 V-4 判据不对称

### 3.1 决定性证据：同一次运行，R2 已拒修，V-4 照做

`visual.json → layoutStructure.layout.sectionAnchorAudit`：

```json
{
  "judged": 1, "repaired": 0, "phantomRefs": 0, "unrepaired": 1, "siblingCovered": 1,
  "issues": [{
    "sectionId": "38:3260", "anchorId": "38:3260", "kind": "anchor-not-ancestor",
    "refs": ["38:3260", "38:3282"], "missingRefs": [],
    "detail": "锚点 38:3260(GROUP Group 2136638431) 不是其内容 38:3282 的祖先"
  }],
  "fixes": [],
  "unrepairedDetail": [{
    "sectionId": "38:3260", "claimed": "38:3260", "kind": "anchor-not-ancestor",
    "candidateLca": "796:3", "reason": "lca-covers-sibling-sections",
    "coveredAnchors": ["38:3137", "38:3162", "38:3206"]
  }]
}
```

`section-anchor-truth.js#auditSectionAnchors` 的 R2 守卫 `lca-covers-sibling-sections` 判定：
候选 LCA `796:3` 的子树里含**其他段的声明锚点**（`38:3137` / `38:3162` / `38:3206`）⇒ 修了就会吞并三个业务段 ⇒ **拒修**，`repaired: 0`。

而 `section-anchor-scope-auditor.js#auditSectionAnchorScope`（V-4）**没有这道守卫**，只看「父容器下有 2 个同构兄弟 + 有兄弟未覆盖 + 单轴铺满 ≥90%」，于是把锚点改成 `796:3`、段高改成 787。

**两套判据描述的是同一个候选 `796:3`，结论相反 —— 判据不对称才是真因。**

### 3.2 三个叠加缺陷

| # | 缺陷 | 后果 |
|---|---|---|
| ① | `coveredIds` 只算「锚点 + 锚点子树」，不含**段声明的内容节点** | 兄弟卡 `38:3282` 明明写在首段 `body.children` 里，却被判「没人认领」⇒ `uncovered: 1` ⇒ 放行上提 |
| ② | `declaresCollection` 只认顶层/`body` 的 `items` / `headers` | 同样的 `body.children` 声明被无视 ⇒ 事实否决没触发 |
| ③ | 无「目标容器吞并兄弟段」守卫 | 上提到 `796:3` 会把 161/212/265 三个业务段整体吞进首段，无任何阻力 |

即：**段自己已经把两张卡都声明了，审计却认为「只有一张卡、另一张没人要」，于是把范围放大到整个内容槽。**

§3.0 的原始设计意图（「已声明成员清单的段不得上提」）本来就覆盖这个场景，只是清单枚举太窄。

## 4. 修复（`aef58ea`，零硬编码）

全部改动在 `src/ai-engine/utils/section-anchor-scope-auditor.js`，另加一处日志。

### 4.1 新增 `collectDeclaredRefIds(section)`

采集段**声明的内容**节点 id：

- 段顶层：`refs` / `sourceNodeIds` / `nodeIds`
- 三壳（`section` / `section.body` / `section.declaredContent`）：`children` / `items` / `elements` / `internalSubcomponents` / `headers`
- 元素可为字符串或对象（取 `figmaNode` / `figmaNodeId` / `id`），经 `FIGMA_ID_RE` 过滤

并入 `coveredIds` 计算后：`uncovered 1 → 0` ⇒ 命中既有的 `all-peers-covered` 否决 ⇒ 不上提。

### 4.2 新增对称守卫 `covers-sibling-sections`

对齐 R2 的 `lca-covers-sibling-sections`，判据逐条对应：

> 上提目标 `T` 的子树若覆盖**其他段的声明锚点**，且该段**不并入同一目标** ⇒ 撤销上提。

- 并入同一目标 = 合法合并（`2:8438` + `2:8439` → `2:8437` 这类历史收益），**不撤销**
- 撤销时记 `stats.vetoed` / `stats.vetoes[{ sectionId, from, to, reason:'covers-sibling-sections', coveredAnchors }]`
- 新增 `isAncestorId(index, ancestorId, id)`：只吃 `indexFigmaNodes` 的 `parentId` 链，与 R2 `isAncestorOrSelf` 同口径

### 4.3 `targets` 改三阶段

```
① 预采集 anchors / coveredIds
② 只取暂定目标（不再即时累加 stats.promoted）
②-b 统一裁决：逐段检查是否吞并兄弟段 ⇒ 撤销并改写回自身锚点
②-c 再统计 promoted / promotions（只认最终 target !== key 的段）
③ 写回 styles / layoutMetadata
④ 直接返回 { sections, stats }（promoted>0 才走到此处，必有变化）
```

先加后减会让 `stats.promoted` 虚高、`skippedReason` 判错，故改两阶段裁决 + 末位统计。

`skippedReason` 新增取值 `'vetoed-covers-sibling'`（原只有 `'no-narrow-anchor'`）。

### 4.4 日志（`subcomponent-planner.js#applySectionAnchorScopeAudit`）

- INFO 增 `vetoed` 与 `vetoes.slice(0,5)`
- `vetoed > 0` 时额外 `logger.warn`：「段锚点上提被撤销（目标容器吞并其他业务段·对齐 R2 lca-covers-sibling-sections）」

### 4.5 零硬编码

判据只用 Figma 结构化字段：`figmaNode` id 对位、`absoluteBoundingBox` 几何盒、`parentId` 链、段声明清单。**无组件名/段名/尺寸枚举，无写死 flex 值。**
