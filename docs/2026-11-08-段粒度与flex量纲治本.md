## 2. 病灶 A：段粒度过粗（vision 给整块外壳）

`89:40`（407×380 根槽容器）下是 `89:38`（396×65 switch）与 `89:37`（46×317 左竖 tab 条）。
vision 把它当一个段 ⇒ 下游只看到「一个内容区」⇒ LLM 画成一张大卡。

既有 `structure-source` 闸门只判「**锚点是否存在**」（`hasAnchoredContent`）：
`89:40` 是根槽容器、锚点有效 ⇒ 粗粒度骨架直接放行。**锚点存在 ≠ 锚点粒度合理。**

### 判据

段锚点 `A` 判为「过粗容器」，当且仅当其直接子容器中存在 ≥2 个同时满足：

1. 沿垂直方向**依次堆叠**（y 升序，相邻允许 `max(2px, A高×2%)` 重叠）；
2. 堆叠序列**覆盖 `A` 高度 ≥80%**（说明 A 就是这串区块的外壳）；
3. 每个高度 ≥ `A` 高的 10%（排除横向细条）；
4. 每个子树有实质内容（有文本，或节点数 ≥5）。

### 处置

命中 ⇒ 用**既有** `deriveSectionsFromFigmaTree({ document: 锚点节点 })` 局部递归展开
（同一函数、同一判据族，不写第二套结构推导）。多处 `fail-open`：推导空 / 子段数越界 / 子段有锚点解析不了 ⇒ 保留原段。

### 两次踩坑（都是我自己先写错）

| 坑 | 现象 | 修法 |
|---|---|---|
| 要求「铺满宽度 ≥90%」 | `89:37` 仅 46 宽（Figma 把左竖 tab 条的 bbox 报成条宽）⇒ 判据不命中 | 去掉宽度要求，改「垂直覆盖 ≥80%」 |
| 要求「面积 ≥10%」 | `89:37` 面积仅占 9.4% ⇒ 只剩 1 个候选 | 去掉面积约束（高度约束已能排横向细条） |
| 重叠按 1px 判定 | `89:38` 底边 540 vs `89:37` 顶边 538 ⇒ 判不堆叠 | 加 `max(2px, 2%)` 容差 |

真机验证：`89:40 → 89:38 + 89:37`，**与最佳产物 `cbcac19a` 的段树完全一致**；
`89:38` / `89:37` / `2:8419` / `2:8417` 全部正确不命中。

## 3. 病灶 B：规则⑥ 与确定性装配的量纲混用

planner 算对了：`2:8419=0.218 / 89:38=0.473 / 89:37=2.308`（`avg=1` 量纲）。
产物 `index.vue` 却是：`flex: 0.218 / 0.473 / **0.769**`。

- 装配层 `flexItemStyleFromHeights` 写的是**同层归一** `h/Σh`：`30.1/411.9=0.073`、`64.8/411.9=0.157`、`317/411.9=**0.769**`
- 规则⑥ `fixInlineSectionFlex` 用 `sectionHeights`（`avg=1`）覆盖，但只覆盖了前两段
  （第三段是带 `data-section-id` 的 `div`，查不到子组件根 class ⇒ 跳过）
- ⇒ 同一个父容器里 **两套量纲混用** ⇒ 归一后 15% / 32% / 52%，真值应 7% / 16% / 77%
- ⇒ 统计条拉到 121px、内容区只剩 205px（4 行放不下）

### 处置（单一事实源）

规则⑥ 的存在理由是「防 LLM 自由发挥的内联 flex 覆盖 CSS 权威比例」。
**本轮 `<template>` 由确定性装配产出时，装配值本身就是权威（同层归一、Σ=1）⇒ 整条跳过。**

落点：
- `code-fix-rules.js`：`sectionHeights` 注入管线上下文时同时注入 `indexTemplateSource`
  （取 `_indexTemplateFacts.source`）
- `resource-mounter.js`：`ctx.indexTemplateSource === 'deterministic-template'` ⇒ 不调 `fixInlineSectionFlex`，打 INFO 留痕

LLM 模板路径行为**逐字不变**（单测锁定）。

## 7.5 顺序修正：V-4 前移到 `collapseSectionsDeep` 之前（提交 `0a5aed8`）

### 为什么搬

`collapseSectionsDeep` 用段的 `figmaBox` 判几何同构签名来决定折叠成 v-for 的模板。
审计若落在折叠**之后**，折叠器看到的是**未修正**的段树 —— 例如 4 段幻觉里的
`2:8438`（单卡）与 `2:8439`（单卡底图）是两个 117×64 同构段，会被折成错误的模板。
前移后折叠器拿到的是上提过的正确段。

安全性：原始 vision 段形态下 `sectionAnchorKey` 仍可解析（候选序含 `figmaNodeId` / `id`），
且 V-4 只改 `id / sourceNodeIds / 锚点四候选 / 段高`，不动语义字段 ⇒ 形态安全。

### 为什么 V-5 不跟着搬

V-5（过粗下拆）产出的是 **E1 形态段**（无 `body` / `responsibility`），
混入 vision 段树会被 `buildEffectiveSection` 当成「缺内容段」处理。故留在 `effectiveSections` 阶段。

### 实证（用 `be2af6c7` 的 4 段幻觉输入跑真实 `plan()`）

```
[折叠前] 顶层段锚点过窄（单卡/单卡底图被当成整段），已上提到集合容器
  {"from":["2:8419","89:38","2:8438","2:8439"],
   "to":  ["2:8419","89:38","2:8437"]}
flexGrow 已按 Figma 实测高度重新归一 {"id":"2:8419","flexGrow":0.231},{"id":"89:38","flexGrow":0.499},{"id":"2:8437","flexGrow":2.27}
最终 sectionIds = ["2:8419","89:38","2:8437"]，2:8437 h=295 internal=3
```

⇒ 4 段幻觉在**折叠之前**就被纠正，`flexGrow` 直接拿到正确比例。

### 一个诚实的边界：搬家本身不产出 v-for

实测确认：`collapseSectionsDeep` 的 `figmaRoot` **只用于提取文本真值**（`extractTextRuns`），
它只遍历 `sec.children`，**不会从 Figma 展开子结构**。而 vision 从未报出过 12 个卡片段
（本次 `2:8437` 的 `children` 为空）⇒ 折叠器没有输入，搬家前后都不会产出 12 卡 v-for。

离线实验：手工注入 `2:8437` 的 12 个 Figma 子卡后，折叠器**能**正确产出
`2:8438-list`（`type=grid`、`collapsed=true`、`items=12`），但 `_vforData` 仍空（文本真值需另接）。
⇒ 若要实现确定性 v-for，还需「网格段 Figma children 注入 + `_vforData` 真值接入」两步，属独立立项。

## 7.6 卡内布局与文字颜色对齐（提交 `7755b04` + `95054ed`）

### 根因 A：`itemSkeleton` 被透传白名单剥掉（`7755b04`）

planner 已从 Figma 几何推导出卡内骨架（日志 `itemSkeleton 已从 Figma 几何确定性推导 count:1`）：

```json
{"textDirection":"column","gapPx":4,"texts":["摄像机","(2/484)"],
 "icon":{"widthPx":27,"heightPx":32},"iconPosition":"left"}
```

`section-tree.js:1473/1546` 消费它，能生成完整的「H3 硬骨架 DOM 模板」下发给 LLM。
但 `generation-context-assembler` 的白名单没有 `itemSkeleton` ⇒ 被剥成 `undefined`
（`droppedKeys` 里能看到它）。**与 `internalGeometry` 完全同族，第二个断点。**

处置：白名单放行 + `normalizeItemSkeleton`（只留 `textDirection / gapPx / texts / icon{w,h} /
iconPosition`，非法值丢弃，缺 `textDirection` 或 `texts` 空则不产键）+ 4 例单测。

修复后 prompt 实测输出（`formatSectionTreeForPrompt` 实跑）：

```
- `2:8437` — 网格卡片布局区，布局 grid，含 51 个元素，
  ⚠️卡内骨架（H 契约，禁止改写）：文本列纵向堆叠（label 上 value 下，flex-direction: column），
  icon 固定 27×32px，文本项 [摄像机 / (2/484)]
  ▼ 卡内骨架模板（H 契约·照抄结构，只替换变量绑定，禁止改结构/类名/方向）：
  <div v-for="item in ..." class="<卡容器类>">
    <div class="<卡容器类>-icon"><img :src="item.icon" style="width: 27px; height: 32px;" /></div>
    <div class="<卡容器类>-text" style="display: flex; flex-direction: column; gap: 4px;">
      <span>{{ item.label }}</span><span>{{ item.value }}</span>
    </div>
  </div>
```

### 根因 B：网格卡是刀53 接管产物，绕过 LLM（`95054ed`）

日志实锤：`刀 53 确定性子组件已落盘: CardGrid.vue {"kind":"grid","sectionId":"2:8437"}`
—— 该组件由 `folded-grid-section-takeover` 确定性生成，**LLM 的模板被整体替换**，
所以根因 A 的 prompt 修复对这条路径无效。

模板原本固定：

```html
<div class="...-card" :style="...">      <!-- CSS: display:flex（默认 row） -->
  <img ... />
  <span v-for="(t, ti) in it.runs">{{ t.text }}</span>
</div>
```

⇒ `icon + 名称 + 数值` 必然横排。

处置：`cardTruth` 从 runs 几何判定方向（新增 `textDir` / `stackGap`）：

- `x 起点差 ≤ 2px` 且 `y 严格递增` ⇒ `column`，`stackGap = 平均 (y_i − (y_{i-1}+h_{i-1}))`
- 其余（单文本 / y 相同 / x 未对齐）⇒ `row`，**逐字保持旧结构**

模板：**全部卡一致为 column** 才包一层 `<div class="-text" style="display:flex;flex-direction:column;gap:Xpx">`；
CSS 同步加 `-text { min-width: 0; }`。混排/无方向 ⇒ 不猜，产物逐字不变。
