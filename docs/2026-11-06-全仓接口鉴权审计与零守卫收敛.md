## 二、判据与口径（含一次自我纠正，务必先读）

### 2.1 为什么必须逐方法检查

全仓 `grep APP_GUARD` **零命中** ⇒ **没有全局守卫**。守卫只能逐类/逐方法声明，**漏挂即匿名可达**，且不会报错、不影响功能自测。

### 2.2 🔴 上一版结论 `83 条零守卫` 是错的

上一版扫描脚本判「类级守卫」时只取 `lines[@Controller … class声明]` 之间的行，**漏掉了写在 `@Controller` 上方**的 `@UseGuards`：

```ts
@UseGuards(SessionGuard)   // ← 上一版没读到这一行
@Controller('workflows')
export class WorkflowController {}
```

本仓这种写法占多数（`workflow` / `admin-page-generator` 等而 `announcement` 是写在下方）。漏读的后果是把 **整个类已受保护的 60 条路由**误判为匿名，并据此得出「`/api/admin/generate` 匿名可达」这类**假高危**。

修正口径后：

```
total=294  guarded=277  UNGUARDED=17
```

**教训（写进判据）**：任何安全审计脚本，必须先对「已知有守卫的文件」做一次阳性对照，确认它能判为「有守卫」；否则假阳性会指导出错误的修复动作（本轮差点给已受保护的 admin 端点重复叠加守卫）。

### 2.3 正确口径

- **类级守卫** = `@Controller` **上方**紧邻装饰器块 + `@Controller` 到 `class` 声明之间（两种写法都吃）
- **方法级守卫** = 路由装饰器**上下两侧**连续的装饰器块，遇非装饰器非注释行立即停（不吃方法体）
  —— 本仓两种顺序并存：`e.g. apifox` 是「路由在上、守卫在下」，`tasks` 是「路由在上、守卫紧邻在下」

## 九、追加处置：`apifox/record` 落库带 `ownerId`（用户裁决后）

### 9.1 缺陷链（三段，缺一段都不会有症状）

```
SKILL.md 步骤 5 → body.userId
  → RecordApifoxDto 未声明该字段
  → 全局 ValidationPipe({ whitelist: true }) 静默剥离（不报错、不打日志）
  → recordTask 落库 task 无 ownerId
  → listMine 的 `|| !t.ownerId` ⇒ 记录对所有登录用户可见
  → assertTaskOwner 的 `if (ownerId && task.ownerId && …)` 对这些记录空转
```

`ApifoxTask.ownerId` 字段**本就存在**（`apifox.service.ts:29`，注释「所有者用户 ID（用于隔离 history 列表）」）⇒ 属「设计已有、写入通路被掐」，不是缺设计。

### 9.2 修法（三处，缺一不可）

| # | 文件 | 改动 |
|---|---|---|
| ① | `apifox/dto/record-apifox.dto.ts` | 声明 `ownerId?` 与 `userId?`（`@IsOptional() @IsString()`），让 whitelist 不再剥离；保留两个字段名是因为 SKILL.md 已发布、改文档覆盖不到用户手里的旧副本 |
| ② | `apifox/apifox.controller.ts` | `record` 挂 `@UseGuards(OptionalSessionGuard)` + `@OptionalUser()`：该守卫**永不阻断**（Skill 无 token 照旧放行），但浏览器带 `Token` 头调用时能顺手拿到**权威**会话身份 |
| ③ | `apifox/apifox.service.ts` | 新增纯函数 `normalizeOwnerId`（形态归一）+ `mergeTaskRecord`（幂等合并），`recordTask` 改为纯读 → 纯合并 → 写的薄壳 |

取值优先级（唯一实现处 `ApifoxController.record`）：**会话身份 > `body.ownerId` > `body.userId`**。
会话身份优先的理由：有 `Token` 的调用方无法把自己的记录伪造成他人归属。

### 9.3 🔴 为什么 `default-user` 不能落库（本轮最大隐性坑）

`SKILL.md` 把 `userId` 缺省值写成 `default-user`，而「真实归属」的唯一形态是
`session.guard.ts:50` 写入的 `user._id.toString()`（24 位十六进制 ObjectId）。

若把调用方自报值原样写进 `ownerId`，`listMine(真实userId)` 的两个条件
（`t.ownerId === ownerId` / `!t.ownerId`）**都不成立** ⇒ 该记录对**所有人（含作者本人）**
永久不可见，比原来的「所有人可见」更坏，而且没有任何报错。

⇒ `normalizeOwnerId` 只接受 ObjectId 形态：形态不符的值**不落库**（保持旧口径「公共可见」），
并打一条 warn 日志（`忽略非法 ownerId="default-user"（taskId=…）`）让漂移可观测。
刻意**不查库**：查库会把 `recordTask` 变成异步并引入 mongoose CastError 分支，
而形态不符的值本来就不可能是本系统的用户 ID。也刻意**不做名字白名单**（禁 `default-user` 硬编码）。

### 9.4 存量无主记录：保留兜底，不翻脸

`listMine` 的 `|| !t.ownerId` **保留**（`apifox.service.ts` 已就地写明理由）：
2026-11-06 之前 Skill 通路落库的记录全都没有 ownerId，若改成严格相等，
这批历史记录会对**所有人（含作者）同时消失** —— 不可逆的可见性事故。
所以策略是「旧无主记录保持可见 + 新记录必须带 ownerId」，严格性靠「不再产生新无主记录」收敛。
**若要收紧历史数据**，正确顺序是：先一次性回填（把无主 task 归到具体用户）→ 再删兜底。

### 9.5 判据与阳性对照（`src/apifox/apifox-owner.spec.ts`，13 passed）

四层断言，每层都做了「改坏必红」的阳性对照：

| 层 | 断言 | 阳性对照（实测） |
|---|---|---|
| 根因 | 真实 `ValidationPipe({whitelist:true})` 下 `userId`/`ownerId` 不再被剥离 | 删掉 DTO 的 `userId` 声明 ⇒ `✕ userId（SKILL.md 实际发送的字段名）不再被剥离` |
| 白名单仍生效 | 未声明字段 `evil` 照旧被剥离 | 若有人把 `whitelist` 改 false 来「让字段通过」⇒ 本断言红 |
| 归一 | `default-user`/空串/非字符串 → `undefined` | — |
| 合并 | 二次登记不抹掉已有 `ownerId`，保留首次 `createdAt` | 改成朴素 `{...old,...next}` ⇒ `✕ 本次没算出归属时保留原 ownerId 与首次创建时间` |
| 优先级 | 会话 > `ownerId` > `userId`；无归属显式回 `null` | — |

### 9.6 判据口径同步（`guard-coverage.spec.ts` 必须一起改）

`record` 现在挂了 `OptionalSessionGuard`，但覆盖判据原先「出现 `@UseGuards` 即算已阻断」——
若不改，白名单会假腐化（红在「白名单已过期条目」）。新增口径：

> 「守卫」指**真正阻断匿名请求**的守卫；`OptionalSessionGuard` 只解析身份永不阻断，**不算**。
> 判据问的是「匿名能否打到业务代码」，不是「是否出现过 `@UseGuards`」——
> 否则给匿名端点挂个空守卫就能骗过本 spec。

实现在 `NON_BLOCKING_GUARDS` + `extractGuardNames`（支持跨行与嵌套括号）。
阳性对照：把 `NON_BLOCKING_GUARDS` 改坏 ⇒ `✕ 零守卫集合 === 已定性白名单`，
诊断精确指向 `apifox/apifox.controller.ts::Post /apifox/record`。

## 十、追加处置：三块新功能的用户级数据隔离（ownerId）

用户裁决：**「新增的录音会议、项目级生成都是需要 ownerId 的，每个人独立；lab 生成任务也是」**。

先把「开关」与「归属」的关系钉死，否则后面每一条都容易读错：

> **DevOnly 开关 ≠ 归属。** 开关（`isV3ProjectExposed()` / `isLiteLabExposed()`）管的是
> 「这个环境**暴露不暴露**这个功能」；归属管的是「暴露之后**谁能看谁的**」。
> 生产把开关关掉只能说「现在摸不到」——一旦有人为了上线把开关打开，**归属是唯一防线**。
> 所以「生产 404 所以不用管归属」是错的口径。

### 10.1 审计矩阵（改前 → 改后）

| 功能 | 归属落库 | 读路径隔离 | 守卫 | 本轮结论 |
|---|---|---|---|---|

### 10.2 v3 项目级生成：把 12 处重复前置收敛成「唯一入口」

文件：`backend-node/src/ai-engine-v3/project/project-pipeline.service.ts`、`api/project-pipeline.controller.ts`

**（1）根因是「没有身份，就没有可过滤的维度」。** 原设计注释写着「M1 不消耗模型额度、不落用户资产 ⇒ 不挂
`SessionGuard`」。这句话在 S3/S4（生成代码）落地后已不成立：`data/project-runs/<runId>/` 里**就是**用户资产；
而「不知道调用者是谁」在数学上就**不可能**做隔离——无身份的过滤等价于不过滤。

**（2）三条设计约束（改之前先读懂，否则会踩可见性事故）：**

| # | 约束 | 不遵守的后果 |
|---|---|---|
| ① | 归一只认**平台用户 ID 形态**（24 hex，即 `session.guard.ts` 写入的 `user._id.toString()`）；其余（空串 / 前端自造 `default-user` / 脏值）**不落库** | 落一个假 ownerId ⇒ 这条运行对**所有人（含作者）**同时不可见，且**零报错**——比不隔离更坏 |
| ② | **存量运行无 `ownerId` ⇒ 仍然可见**（legacy 分支） | 改严格相等 ⇒ 本功能 11-06 之前的历史运行对作者本人也消失，属不可逆可见性事故。要收紧必须先一次性回填再删兜底 |
| ③ | **越权一律 404 而非 403** | 403 等于承认「这个 runId 存在、只是不给你看」，与 dev-only「不暴露存在性」口径冲突 |

**（3）单一入口 `resolveRunDir(runId, userId)`（形态校验 + 存在性 + 归属校验三合一）。**
本文件原先有 **12 处逐字相同**的 `assertRunId(runId) + path.join(RUNS_ROOT, runId) + existsSync`。
若把归属校验散着加，必然出现「新加的方法忘了校验」——那正是权限漏洞的经典成因。
现在**任何**读写单个运行的路径都必须过本方法（拿不到 `dir` 即编译期可见），替换后残留裸
`this.assertRunId(runId);` 仅 2 处（`resolveRunDir` 内部 + `readDecisions`）。

```ts
const OWNER_ID_RX = /^[0-9a-fA-F]{24}$/;
export function normalizeProjectOwner(userId?: unknown): string | undefined {
  if (typeof userId !== 'string') return undefined;
  const value = userId.trim();
  return OWNER_ID_RX.test(value) ? value : undefined;   // 见约束 ①：不合形态宁可不落
}

private resolveRunDir(runId: string, userId?: string): string {
  this.assertRunId(runId);
  const dir = path.join(RUNS_ROOT, runId);
  if (!fs.existsSync(dir)) throw new NotFoundException(`运行不存在：${runId}`);
  const owner = normalizeProjectOwner(this.readRunMeta(dir)?.ownerId);
  if (owner && owner !== normalizeProjectOwner(userId)) {
    this.logger.warn(`[owner] 拒绝访问 runId=${runId}：归属不一致（caller=${userId ?? 'anonymous'}）`);
    throw new NotFoundException(`运行不存在：${runId}`);   // 见约束 ③
  }
  return dir;                                            // 见约束 ②
}
```

统一改走该入口的方法（14 个）：`freeze` / `generate` / `generateVue` / `generateZip` / `getUnits` /
`inspectRun` / `readArtifact` / `listGeneratedFiles` / `deleteRun` / `saveDecisions` / `getBinding` /
`setBinding` / `getEmbeds` / `setEmbeds`。其中 `readArtifact`、`listGeneratedFiles` 改前**只有** `assertRunId`
（即「知道 runId 即可读产物」），本轮一并补上归属校验与 `userId?` 形参。

**（4）`listRuns` 的过滤必须早于排序截断。**
改成「先排序 → 取前 30 → 再按归属过滤」会得到一个极隐蔽的症状：**列表里看不到自己刚跑的那条**
（被别人的运行挤出了 top-30）。正确顺序是 `filter(归属) → sort(createdAt desc) → slice(0,30)`。

**（5）控制器：写端点 8 处补 `@UseGuards(SessionGuard)`。**
`scan` / `freeze` / `generate` / `generate-vue` / `decisions` / `delete` / `set-binding` / `set-embeds`；
读端点保持 `OptionalSessionGuard`（只解析身份不阻断），由 service 按归属过滤。
类注释整体改写为「DevOnly 管暴露、归属管可见性」双轨说明，并保留原文作对照。

### 10.3 lab 生成任务：缺口只在 `report` / `artifact` 两条读路径

文件：`backend-node/src/lite-lab/api/lite-lab.service.ts`、`lite-lab.controller.ts`

归属在**建任务**时就已存在：`run(dto, userId)` → `createTask(sessionId, { …, userId }, 'running')`。
缺口是两条读路径：

```ts
// 改前：两个方法都没有身份参数，内部 locateOutputPath 遍历所有 group 目录
getReport(sessionId: string)
getArtifact(sessionId: string, relPath: string)
```

⇒ **任何知道 sessionId 的人都能读到别人的回填报告与回填后代码**。sessionId 虽然随机，
但它会出现在前端 URL / 日志 / 分享截图里，等于一次「知道 ID 即可读全部」。

修法：新增单一入口 `assertLabAccess(sessionId, userId)`，`getReport(sessionId, userId?)`、
`getArtifact(sessionId, relPath, userId?)` 首行调用。

```ts
private assertLabAccess(sessionId: string, userId?: string): void {
  const task = this.tasksService.getTask(sessionId) as any;
  const owner = typeof task?.userId === 'string' ? task.userId.trim() : '';
  if (!owner) return;                             // ① 存量/无主任务放行（见下）
  if (owner !== (userId ?? '').trim()) {
    this.logger.warn(`[lite-lab][owner] 拒绝访问 sessionId=${sessionId}：归属不一致（caller=${userId ?? 'anonymous'}）`);
    throw Object.assign(new Error(`任务 ${sessionId} 不存在`), { status: 404 });   // ② 404 不暴露存在性
  }
}
```

🔴 **刻意不在本模块再引一份 owner 正则**（与 10.2 的取舍刚好相反，值得说明）：
`project-pipeline` 的 `ownerId` 可以来自 **DTO 入参**，是外部输入 ⇒ 必须收敛形态；
而 lab 任务的 `userId` 是**我方自己在 `createTask` 时写入的**，不是外部入参 ⇒
再引一份形态判据只会多一处会漂移的真相源。

🔴 **为什么 `report`/`artifact` 不改成 `SessionGuard`，只加 service 侧校验**：
`artifact` 是 `<img src>` 加载的，浏览器带不了自定义 Header，前端只能把 token 拼进 **query**
（见 `frontend/src/api/lite-lab.ts#labArtifactUrl`）；`resolveSessionFromRequest` 的 `query.token`
分支已覆盖该形态，身份能拿到。若这里改挂 `SessionGuard`，那些**不经过前端拼 token** 的场景
（新标签页直开图片、本地 curl 调试）会从 404 变 401，与「只读端点不阻断」的既有分工相悖。
控制器对应的两处改动就是把 `req?.session?.userId` 透传给 service。

### 11.6 🔴 一个工具/流程教训：破坏性重命名 × 构建读到「写中途」的快照

本轮把 `export const INDEX_KEY` 改成 `export function draftIndexKey()` 时，前端构建报
「`draft-store.js` does not provide an export named 'INDEX_KEY'」。当时的归因是
「并行会话实时重构」，**归因错了**：真实成因是
**`vite build` 在读文件那一刻取快照**，而写入方（本会话的重构）还没写完 `index.vue`
⇒ 构建读到「新 `draft-store.js` + 旧 `index.vue`」的不一致组合，模块图必然断。

| 教训 | 做法 |
|---|---|
| 纯 JS 无类型检查，**破坏性重命名只有构建期才暴露** | 重命名 ESM 具名导出后**立刻在同一轮**跑一次构建，别等下次 |
| 「构建失败」不等于「磁盘当前状态是坏的」 | 先 `npm run build:safe` 复跑一次；仍红再去查引用，避免按过期快照找根因 |
| 并行会话是**可能**的归因，但不能当默认归因 | 用证据（mtime + 引用方 import 行 + 构建结果）而不是「同一分钟 ⇒ 一定是别人」 |

复核结果：全前端 `INDEX_KEY|CONSENT_INDEX_KEY|CONSENT_CURRENT_KEY|RETENTION_AUDIT_KEY` **零命中**，
`index.vue` 已是 `import { createDraftStore, listSaved, STORAGE_PREFIX, draftIndexKey }`，
`npm run build:safe` → **EXIT=0（34.05s, ✓ built）**，产物仅 `dist/static/js/index-*.js` 含 `mvgo.meeting.draft.`，**无**旧无前缀索引键。

> 同轮的另一个「待修」曾被我记为「`index.vue` 的 `watch` 命中 TDZ」——**复验后不成立**：
> 该 `watch` 位于依赖的 `const store` / `storeTick` / `savedIndex` **之后**（L2735 > L2685/2686/2691），
> 且依赖后置函数的副作用已用 `nextTick(refreshStoreForOwner)` 延迟。**未改动。**
