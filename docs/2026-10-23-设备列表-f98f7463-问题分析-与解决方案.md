  ③ **非法 id**：section id 不在 figma 索引里 ⇒ 报 `syntheticSectionId`。

- 落点：`utils/inline-row-assembler.js` 增加 `regroupStatRowSiblings(sections, figmaRoot)`，在 effectiveSections 落定后、`assessStatRowConfidence` 之前调用；命中后按刀 53 家族方式**整文件确定性渲染**（跳过 LLM chunk，复用 `FG_TAKEOVER_CLASS_RX` 豁免链）。

### 3.3【P0】表格结构崩 + 表头丢失 + 设备名列双渲染（= 用户看到的「多个 icon」）

**现象**：表格挤成一团、没有表头；设备名称列出现**两遍**，图标因此翻倍（8+8=16）。

**证据**：
- `CardGrid.vue:2` `data-section-id="43:4812-list"`（合成 id）——真值 `43:4812` 只是「电量」列，产物却把**4 列数据全塞进去**；

- `CardGrid.vue` 无表头 ⇒ `43:4787/4814/4833/4852`（设备名称/电量/速度(m/s)/启用状态）**全部丢失**；
- `ContentSection4.vue`（section `43:4785` = 设备名称列）被「1/离线」stat 卡顶替 ⇒ 设备名列在表格里**整体丢失**；
- `ContentSection5.vue`（section `43:4869` = 页脚「运行中」图例）却渲染了「表头：设备名称 + 8 行 icon+名称」（`:3-15`）⇒ **设备名列在页脚位置被重渲染一遍**，这是「多个 icon」的直接来源；同时页脚图例丢失；
- `ContentSection6.vue`（section `43:4875` = 「离线」图例）把**两个图例都渲染了**（`:4-11`）⇒ 图例重复。

**根因**：`grid-list-layout-contract.js` 只覆盖「grid/list」形态，**没有「列式表格」契约**（日志里 4 个 section 全是 `grid:noGridContract`）；且「表头属于哪个组件」没有判据 ⇒ LLM 自由拆分。

**方案 C（表格契约 + 整表接管）**
- 判据 `detectTableSection(section, figmaIndex)`：子树内存在 ≥2 个**同构列容器**（同宽 ±2、同高 ±2、x 严格递增），每列 = 1 个表头 TEXT（y 最小）+ N≥2 个数据 TEXT，且**跨列数据行数一致** ⇒ 产出 `tableContract { columns: [{ x, width, header, cells: [...] }] }`。
  > ⚠️ **2026-10-23 实测更正**：「同宽 ±2」在本单**恒不成立**——真值 4 列宽是
  > **179 / 98 / 98 / 98**（首列与其余差 81px）。落地判据改为：
  > **同高 ±2 + 同 y ±2（同一行带）+ x 严格递增（允许 ≤2px 咬合）+ 各列 TEXT 数相同且 ≥3
  > + 跨列逐行 y 对齐 ±2**，列宽各自记录、渲染时按 `width/列宽和` 转百分比。
  > 另加一条硬条件：**父容器的全部直接子项都必须在同一行带**（否则「行数不同的列」
  > 被高度过滤掉后，剩余列仍会被误判成表格 —— 离线单测实锤）。
- 落点：`utils/grid-list-layout-contract.js` 内新增（与该文件的 `buildGridContract` / `judgeGridContract` 同族，保持判据族单一来源）；命中后扩刀 53 家族 `detectTableLeaf`，整组件由真值确定性渲染：行 `display:flex`，列 `flex:0 0 <width/total>%`，表头行与数据行分别渲染（表头不再单独拆组件）。
- 阳性对照：本单 `43:4784` ⇒ 4 列，宽比 37.9% / 20.6% / 20.6% / 20.9%，表头 4 个，数据 8 行；渲染后设备名 icon **恰好 8 个**。
- 阴性对照：`43:4892`（3 列但每列仅 2 文本、无多行网格）必须判否 ⇒ 交给方案 B。
- 日志：`tableContract: {evaluated, hits, skipped}`。

### 3.4【P1】状态列中英混写直出 `disabled`

**证据**：`CardGrid.vue:44` `{ … status: 'disabled', … }`（其余 7 行是中文「启用」），`:27` 用 `row.status === 'disabled'` 判色。真值 `43:4862` = 「禁用」fs14 fw500 rgb(255,115,0)。

**根因**：内容守卫只判「是否借用 / 是否重复」，**不判「字面量是否等于 Figma 真值文本」**；「启用/禁用」被 LLM 转成了英文枚举，且被用作判色键名。

**方案 D（字面量漂移判据）**
- 判据（不猜语义，可证伪）：产物中出现的**纯 ASCII 单词字面量**（`/^[A-Za-z][A-Za-z0-9_-]*$/`）若同时满足 ① **不属于**该 section 的 Figma 文本全集；② **出现在 `:class` 三元条件 / 状态映射的键位**（即参与渲染分支）⇒ 报 `literalDrift`，确定性替换为真值文本（**连同判色分支的键名一并改**，否则替换后颜色失效——这是本条最容易做漏的一步）。
- 落点：`utils/section-content-guard.js#checkSectionContent` 新增 issue 类 + `healLiteralDrift`（沿用「保守改 + `validateSfc` 回退」口径）。
- 阳性对照：本单 `disabled` ∉ {启用, 禁用} 且参与 `row.status === 'disabled'` ⇒ 报 1 条并自愈为「禁用」+ 橙色键。
- 阴性对照：`1.20` / `92` / `m/s` 属真值文本 ⇒ **不得报**；`flex` / `nowrap`（CSS 值，不参与文本渲染）⇒ 不得报。

- `frontend/src/components/@mv-business-panels/default-panel/index.vue:14 / :34`：**无条件**渲染 `<div class="header-title">{{ componentName }}</div>`，且另提供 `title-left` / `title-right` / `header-right` 槽位。

⇒ chrome 标题 + header-right 里的 Figma 标题 = **两个标题**。

**根因**：`panel-chrome-misplacement.js`（刀 42-B）只管「面板装饰三件套（background/border-radius/box-shadow）被搬到子元素」，**不管槽位归属** ⇒ 标题塞进 `header-right` 无任何判据拦截。

**方案 E（槽位归属判据）**
- 判据：若某 slot 目标组件（此处 `HeaderSection`）满足 ① 其 `data-section-id` 对应 Figma 子树**恰含 1 个 TEXT**；② 该 TEXT 与 `componentName` / 面板标题**相同或高度相似**；③ 该 slot 名是 `header-right`（非 `title-left`）⇒ 判定「面板标题被塞进 header-right」，改为挂 `title-left`，并把 chrome 的 `componentName` 标题让位（由 `panelKey` 侧约定，不在产物内重复渲染）。
- 落点：`utils/panel-chrome-misplacement.js` 扩 `healPanelTitleSlot`（与刀 42-B 同族、同挂载点 `pre-write-self-healing.js`，不新增挂载点）。
- 阳性对照：本单 `HeaderSection`（1 TEXT「具身机器人设备列表」）⇒ 命中并改挂 `title-left`。
- 阴性对照：header-right 里放的是**关闭按钮 / 图例 / 筛选器**（0 TEXT 或文本与标题无关）⇒ 不得改。

### 3.6【P1·横切】守卫算出 8+8 却**零自愈**

**证据**：`server.log`（01:27:32）
```
内容映射守卫发现问题（…已留痕）
{"memberOrderIssues":0,"duplicateTextIssues":8,"borrowedTextIssues":8,"borrowedAssetIssues":1,"techStackTagViolations":0}
```
其后**没有任何**「高置信重复文本已确定性自愈」/「借用证据已确定性处置」日志（对比 10-22 10:14:41 那单确实有自愈日志）⇒ 本单 heal **全部 no-op**，缺陷原样发货。

**根因（可复现）**：`section-content-guard.js:597 removeStaticTextNode` 的正则只认**标签之间纯静态文本**（`>[\s]*TEXT[\s]*<`）。本单所有错装文本都是**动态形态**：
- `ContentSection3.vue` → `{{ statLabel }}` / `ref('运行中')`；
- `ContentSection5.vue` → `{{ item.name }}`（v-for）；
- `CardGrid.vue` → `{{ row.status }}`；
⇒ `cleaned === null` ⇒ `healDuplicateTextIssues:313/314/325` 逐条 `continue`，`healBorrowedEvidence` 同理。

**方案 F（文本删除形态扩维）**
- 把 `removeStaticTextNode` 升级为 `removeTextBinding`，支持三类：**① 静态纯文本**（现状）；**② `{{ expr }}` Mustache 整段**（要求 expr 是简单标识符或 `.` 路径，删除后同步删 script 里对应 `ref/const` 声明，避免「声明未使用」硬闸）；**③ 数组字面量里的整行数据对象**（仅当该行所有文本均属非归属 section；单行部分命中 ⇒ 跳过，不猜）。仍沿用「`validateSfc` 引入新错误即回退」+「删引用与剪 import 同处完成」两条既有铁律。
- 定位：**兜底**而非主路径——方案 B/C 做成后，这些组件根本不会被 LLM 生成。故建议排在 B、C 之后。
- 阳性对照：`ContentSection3.vue` 的 `{{ statLabel }}` + `ref('运行中')` 应被判为可删（其文本 owner = `43:4898`，已由 `ContentSection.vue` 正确渲染）；`CardGrid.vue` 的 `{{ row.name }}` 行在 C 生效后不再出现。
- 阴性对照：`ContentDetail.vue` 的「点击查看详情」（owner = `807:2-tail-text` 自身）⇒ 不得删。
