## 三、根因遗漏（方案未覆盖）

### 3.1 f68aedb6 的真实失败面比方案描述的更宽

日志实证（`server.log:5440-5500`）：

```
[CODE-022] 资源变量未挂载：package/index.vue import 了 1 个资源变量
           但模板/脚本 0 处引用（icon1）。资源使用率: 86%
[CODE-025-WARN] 资源契约提示（7 项）：
           bg1 / bg2 / bg3 / icon1 未在资源事实源登记（可能命名漂移）
```

**与方案描述的偏差**：

| 方案描述 | 实证 | 偏差 |
|---------|------|------|
| "import 了 7 个资源变量但模板 0 处引用" | **仅 1 个未引用（`icon1`），7 个中 6 个已用（使用率 86%）** | 🔴 严重夸大 |
| 未提及 CODE-025 | `bg1/bg2/bg3/icon1` 与 `resourceDomMapping` 事实源**脱节** | 🔴 根因遗漏 |

**CODE-025 才是要害**：LLM 自行编造了 `bg1/bg2/bg3/icon1` 变量名，而资源事实源（`resourceDomMapping.assignedVarName`）登记的是另一套名字。这正是"根因 1 事实源分散"的**新实例**，方案却只在图表/section 两处举例，漏了资源这一处。

### 3.2 资源"不显示"的直接原因，方案完全没覆盖

`package/index.vue` 实际写法：

```javascript
import bg1 from '../resources/images/bg-125.png'   // Vite 下是 URL 字符串
const statsData = ref([
  { icon: icon3.value, bgImage: bg1.value }        // ← .value 误用
])
```

`import` 静态资源在 Vite 下返回 **URL 字符串（非 ref）**，`icon3.value` / `bg1.value` 恒为 `undefined`
→ `:src="item.icon"` 拿到 `undefined` → **图片不渲染**

**这才是用户截图里"布局、资源都没有出现"的直接原因**，而非 CODE-022。
CODE-022 只是恰好因 `icon1` 未引用而 BLOCK 了任务——**即便删掉 `icon1` 让门禁通过，6 个已 import 的资源照样显示不出来**。

> 现行门禁中**没有任何一条**拦截 `.value` 误用。这是纯盲区。

### 方案 D：资源变量确定性挂载 — 🔴 自相矛盾

方案 D 给了两条路径：

1. **"启用 `pruneUnmountedResourceImports`（删除未使用的 import）"**
2. 确定性挂载

🔴 **第 1 条正是用户批评的"打补丁"原型**：
- 它让**门禁通过**，但**资源该显示的位置依旧空白**
- 视觉问题原样保留，只是不再 BLOCK
- 与治理目标"拒绝打补丁、要根源修复"**直接冲突**

**实证补刀**：f68aedb6 走的是 `vue3-engineer`，而 `pruneUnmountedResourceImports` **只在 `microcode-engineer` 调用（:6670），Vue3 链路完全没接**。
若照方案 D 第 1 条执行 → 删掉 `icon1` → 门禁过 → **6 个资源仍因 `.value` 误用不显示** → 用户看到的现象**毫无改善**。

**修订**：第 1 条降级为"临时止血"并**显式标注副作用**（只过门禁、不修视觉）；主路径必须是第 2 条确定性挂载 + **新增 `.value` 误用拦截**。

## 五、缺失的最高优先级方案（方案 E）

### 🔴 方案通篇未识别的机制性原因：双链路不同源

实证：`Vue3Engineer` 的 `writeFiles` 继承自 `microcode-engineer.js:4205`，但 **execute 自愈链在 `vue3-engineer.js:1769` 被绕过**：

| 自愈能力 | microcode-engineer | vue3-engineer |
|---------|-------------------|---------------|
| `pruneUnmountedResourceImports`（CODE-022 修复） | ✅ :6670 | 🔴 **未调用** |
| 其余落盘前自愈链 | ✅ | 🔴 逐一待核 |

**这就是"反反复复出各种问题"的机制性答案**：
> 微码链路每补一个修复器，Vue3 链路**不会自动获得**——同一个 bug 在双端反复复发，团队却在单端不断"治本"。

### 方案 E：双链路自愈链同源化（建议列为 P0）

**目标**：`vue3-engineer` 与 `microcode-engineer` 共用同一套落盘前自愈/校验链，消除"补一端漏一端"。

**实施**：
1. 抽 `runPreWriteSelfHealing(files, ctx)` 公共函数（从 `microcode-engineer.execute` 的落盘前段落抽出）
2. 两个 engineer 的 execute **均调用**该函数
3. 新增守卫时**只加一处**，双端同时生效

**收益**：
- 成本最低（纯重构，无新逻辑）
- 直接消灭"同类 bug 双端复发"这一最大痛点
- 为后续方案 A/B/D 铺路（届时改一处即双端生效）

**建议优先级**：**P0，且排在方案 A/B/C/D 之前**

## 九、追加实锤：`mc-max-1789491376201-24254234`（布局全纵向）

### 9.1 症状

设备监测组件，布局几乎全部纵向、同行元素变垂直排列、各占 100% 宽度。

### 9.2 代码级根因（可复现，非猜测）

**vision 已识别正确布局方向**（`visual.json` layoutStructure）：

| section id | vision `layout` | 应为 |
|-----------|----------------|------|
| `switch-section` | `horizontal` | `display:flex; flex-direction:row` |
| `8439`（设备网格） | `grid` | `display:grid` |

**产物 `common.less` 实际缺 `display:flex` 的容器**：

| 类名 | 现状 | 缺失 |
|------|------|------|
| `.c-device-monitor-switch` | `flex:0.339 1 0; min-height:0; gap:8px; width:100%` | 🔴 无 `display:flex` → 两卡片纵排 |
| `.c-device-monitor-header-stats` | `width:100%; min-height:0` | 🔴 无 `display:flex` → 三统计项纵排 |
| `.c-device-monitor-tabs-section` | `width:100%; min-height:0` | 🔴 无 `display:flex` → 左 nav + 右 grid 纵排 |
| `.c-device-monitor-active/default` | `align-items:center; gap:10px`（无 display） | 🔴 align-items/gap 在 block 下无效 |

**根因链条**（`utils/figma-section-heights.js`）：

1. `buildSectionLayoutFacts`（:186）**已经算出** `{ display, flexDirection, flexGrow, gridColumns }`：
   ```js
   const display = hasGrid || layout === 'grid' ? 'grid' : 'flex';
   const flexDirection = layout === 'horizontal' ? 'row' : 'column';
   ```
2. 但真正写回产物的 `buildSectionHeightsMap`（:224）**只消费 `flexGrow`**，`display`/`flexDirection` 字段**被丢弃**。
3. 该文件注释（:175-176）**自己承认了这个缺口**：
   > 「都是『LLM 写 grid-template-* 却漏 display:grid』『子组件根漏 display:flex』的事后修补。与其事后猜，不如把布局事实（display / gridColumns / flexDirection / flexGrow / 高度）接管」

→ **这是"半成品治本"的典型形态**：识别了问题、建了事实表，但消费端只接了一半（flexGrow 接了，display/flexDirection 没接）。

### 9.3 是否被原方案覆盖？

**部分覆盖，但错判了优先级和改法**：

| 原方案表述 | 判定 |
|-----------|------|
| 方案 A "规则⑤补 display:flex 注入" | ✅ 方向对，但被列为 P1 |
| "新增注入逻辑" | 🔴 **错**——不用新增，`buildSectionLayoutFacts` 已产出 display/flexDirection，只需**接上 `buildSectionHeightsMap` 的消费**，改动更小 |
| 未识别"半成品治本"形态 | 🔴 遗漏——这是比"规则缺 display:flex"更本质的形态 |

### 9.4 避免影响其他生成面的硬约束（治本前必须满足）

1. **唯一事实源**：display/flexDirection 只从 `buildSectionLayoutFacts` 读，方向跟随 facts —— `horizontal→row`、`vertical→column`、`grid→grid`。**绝不盲目补 `row`**（会破坏 slot-con 这类本来就是 column 的容器）。
2. **只注入 section 根容器**：不动 section 内部 item 级 DOM（tabs 项、卡片、行内 label/value 等），避免破坏 R2 序 4 尚未接管的 item 契约。
3. **幂等 + 不覆盖**：目标容器已声明 `display` 时跳过（LLM 正确写的不动）。
4. **fail-open**：`buildSectionLayoutFacts` 对齐失败返回 null 时，**零注入、绝不猜**。
5. **上线前全语料离线重放审计**：用 `mvgo-deterministic-replay-triage` 跑近 30 天语料，确认不误伤 column/grid 布局；新增「注入前后 display/flexDirection 一致性」回归用例。

### 9.5 优先级修正

原方案把"规则⑤补 display:flex"列 P1。鉴于本组件 + `acf9c8ac` + 记忆中的 `228b63d5` **连续 3 个设备监测组件同一处中招**，且根因是"已建事实表、消费端没接"这种低风险高收益改动，**应提升为 P0**，与"方案 E 双链路同源化"并列第一批落地。
