## 二、五条根因线

### L1 预览层：微码子组件 LESS 未预编译 → 组件加载整体失败

**现象**：`找不到文件: less`（dcc8b98d）/「一片蓝色」（3912b7b3）

**根因链**：
1. 微码子组件（`package/components/*.vue`）带 `<style lang="less" scoped>` + `@import '../../resources/styles/index.less'`
2. 微码预览路径（`frontend/src/views/preview/index.vue` 的 `loadProd`）**只剥 `index.vue` 的 `<style>`，子组件未处理**
3. vue3-sfc-loader 遇 `lang="less"` 调 `getFile('less')` 拉编译器 → dev/prod 都无该资源 → 404
4. → 组件加载整体失败（报友好错误 / 或只剩 base-panel 蓝色背景）

**对照**：Vue3 路径（`loadVue3Runtime.js`）**有** `precompileVueLess`（注释明写"避免 getFile('less')"）→ 微码路径是修了一半的历史遗留。

**被否决的两个"显而易见"修法**（全语料审计）：
- ❌ 剥掉所有 `.vue` 的 style：225 个组件 / 988 个子组件 style 块中，**2555 个类名的私有样式不在 common.less** → 会丢样式
- ❌ 去掉 `lang="less"` 当纯 CSS：**202 个块有 less 变量、421 个有嵌套、338 个有 `&`** → 解析失败

**✅ 已落地**：
| 文件 | 改动 |
|---|---|
| `frontend/src/utils/loadVue3Runtime.js` | `precompileVueLess` 加 `export` |
| `frontend/src/views/preview/index.vue` | 导入 `precompileVueLess` + `import('less')` + `getFile` 里 `precompileVueLess(src, less, \`${base}/${rel}\`)` |

**验收**：`npm run build:safe` 通过；预览微码组件不再报 less；子组件样式完整。

**⚠️ 待部署生产**（用户报的 dcc8b98d 是生产实例）。

### L2 样式层：模板类名 ↔ 样式类名漂移（G 类）

**现象**：布局失效（24254234「全纵向」）/ 背景错位、尺寸不对（5ed7a5f8）/ 双前缀（77f2ae7d）

**根因链**（4 层，24254234 已实锤）：
1. **LLM 两次独立命名**：子组件块（写模板）与 style 块（写 common.less）是两次独立 LLM 调用，各自命名
2. **清单已注入但 LLM 未遵守**：`extractTemplateClassNames` 的清单确实注入样式块 prompt（含"禁止重命名"铁律），实测 LLM 未遵守
3. **R4 对齐覆盖不到**：`normalizeClassNameDialect` 的 R4 只覆盖「有修饰符锚点 + 候选基名以 `${base}-` 开头」，处理不了"完全无前缀交集"
4. **fallback 遮掉告警**：`generateFallbackCssRule` 补 stub（只含 elementStyleMap 布局属性）→ stub 落地后 CODE-020 反查命中 → 不再报警 → 带病发布

**5ed7a5f8 的具体表现**（6 个死样式，其中 3 个恰是正确解）：
| 问题 | 死样式（正确解） | 模板实际 |
|---|---|---|
| tab 无背景 | `tabs-list`（295×27 浅蓝渐变 = bg1） | `.c-env-monitor-tab`（fallback stub） |
| icon 大小不对 | `icon-container`（24×24） | 裸 `.c-env-monitor-icon`（14px） |
| 图表无外层高度 | `chart-section`（flex:1 + min-height:0） | `.c-env-monitor-chart`（fallback stub） |

**优化方案**：
| 优先级 | 方案 | 改动面 |
|---|---|---|
| **P0** | **fallback 不得掩盖门禁**：stub 显式标记 `/* [自动修复-stub] */`，CODE-020/C3/C4 识别标记后**仍报警** | 小，立即做 |
| P1 | **样式块「填值不命名」**：管线用 classNamesList 确定性生成 common.less 空规则骨架，LLM 只填值 | 中 |
| P2 | 类名由 DOM 事实源确定性生成 / R4 扩展（须全语料误伤审计） | 大 |

**关联文档**：`docs/类名漂移根因与治理方案-2026-09-16.md`

### L3 命名层：E/F 类复发 —— 13 位时间戳绕过 `stripDecorSlugTail`

**现象**（77f2ae7d）：
```
componentId:    c-max-1789494573361-77f2ae7d-77f2ae7d   ← 13位ts + 尾段重复 + 语义段丢失(=max)
componentName:  策略类型分布                              ← 真实语义
meta.checkpoint: 同脏值（已固化）
businessEvents: ['c-max-…-onload', '77f2ae-onload']      ← 双轨
common.less:    class 双前缀 c-max-1789…-c-77f2ae-*（且有两套类名，单前缀成死样式）
```

**根因**：**同一概念两处实现，一处漏**
| 实现 | 位置 | 认 13 位时间戳？ |
|---|---|---|
| `namingRank`（S2 补丁） | `component-naming.js` | ✅ `EMBEDDED_TASK_ID_RE = /\d{13}/` |
| **`stripDecorSlugTail`（刀 8b）** | `component-naming.js` | ❌ 只认 8 位 `…-<slug8>-<hex8>` / `…-<slug8>` |

⇒ `sanitizeComponentId` 的剥离步骤返回原样 → 语义段退化成 `max`（从 `mc-max-` 提取）→ `c-max-…`。
**刀 9 的收敛点接对了，但剥离函数漏了这个形态。**

**优化方案（P0）**：`stripDecorSlugTail` 补 13 位时间戳形态，**复用 `EMBEDDED_TASK_ID_RE`**（与 `namingRank` 同源，杜绝二次漂移）：
```js
// 形态①′：…-<13位ts>-<hex8>（可多段）
const mTs = s.match(/^(.*?)-(\d{13})(?:-([0-9a-f]{8}))?$/i);
if (mTs) return mTs[3] ? `${mTs[1]}-${mTs[3]}` : mTs[1];
```
**改前必须全语料审计**：`ls workspace/custom-components | grep -cE '^c-.+-[0-9]{13}-'`，确认命中集都是真脏 id、正常 `c-<语义>-<8hex>` 不被误伤。

**注意**：这条线是 77f2ae7d 的**最根本原因**——它导致 class 双前缀 → CSS 选择器全部不命中 → 布局退回默认流。

### L4 资源层：mountTarget 错位 + 背景 `:style` 不完整

**现象**（5ed7a5f8）：
- ① tab 内背景没出现 → 资源 `mountTarget: "tabs-list"` 在模板不存在（模板类名是 `tab`）→ bg1 错挂到 `.c-env-monitor-tabs-icon`
- ② tab-item--active 背景重复+位置不对 → 模板 `:style` **只有 `backgroundImage`**，缺 `backgroundSize/Repeat/Position` → 原尺寸平铺

**对照**：`.c-env-monitor-tabs-icon` 的 `:style` 是**系统注入**（完整含 size/position/repeat）；tab-item 的是 **LLM 手写**（不完整）。

**现有机制缺口**：`fixBackgroundImageSize`（`post-process.js:223`）**只管「已是 px 尺寸 → cover」，完全不管「缺失」**。

**优化方案**：
| 优先级 | 方案 | 说明 |
|---|---|---|
| **P0** | **背景 `:style` 补全自愈**：扫描产物 `:style` 含 `backgroundImage` 但缺 `backgroundSize`/`backgroundRepeat` → 补 `'100% 100%'` + `'no-repeat'` | 走 `runPreWriteSelfHealing` 只加一处；直接命中现象 ② |
| P1 | **mountTarget 校验**：资源挂载前校验 mountTarget 是否在模板类名集合中；不存在则按 `bgRole`/section 归属回退 | 命中现象 ① |

### L5 图表层：真值 doughnut → 产物 pie + 空数据 + 笛卡尔残留

**现象**（77f2ae7d）：设计 `doughnut` + 8 图例，产物：
```js
grid: {...}, xAxis: { type:'category', data:[...] }, yAxis: { type:'value' },   // ← 笛卡尔坐标残留（饼图/环形图不需要）
series: [{ name: "交通事故, 车辆故障, ...", type: 'pie', data: [] }]            // ← pie 而非 doughnut；data 为空
// 缺：legend / radius / center / 背景
```

**根因**：图表生成链未按视觉真值（doughnut + 图例清单）生成，且**残留了笛卡尔坐标系模板**、`data` 未填充。

**优化方案（P1，独立议题）**：
1. **图表类型强约束**：`resolveEchartsType` 已有归一化，但产物仍出 `pie` → 检查强约束是否覆盖"环形图与饼图"的区分（`doughnut` ↔ `radius: ['40%','70%']`）
2. **坐标系清理**：饼/环/雷达等非笛卡尔图表**禁止**输出 `xAxis`/`yAxis`/`grid`
3. **data 填充**：从视觉真值/`seriesColors` 生成数据占位，禁止 `data: []`
4. **图例**：`legend` 必须按真值清单生成，且位置支持"两边"布局（`orient: 'vertical'` ×2 或 `legend.left/right`）

## 四、共性结论（"反反复复"的机制性答案）

本轮 4 个组件的 6 类问题，**没有一个是"LLM 能力不足"**，全部是**管线机制问题**，且集中在三种形态：

| 形态 | 实例 | 本质 |
|------|------|------|
| **治本做了一半** | L1（Vue3 有 less 预编译，微码没有）；L2（`buildSectionLayoutFacts` 产 display 但消费端只接一半） | 双链路/双消费点不同步 |
| **同一概念两处实现，一处漏** | L3（`namingRank` 认 13 位 ts，`stripDecorSlugTail` 不认） | 违反"单一事实源" |
| **补丁掩盖根源** | L2 层 4（fallback stub 遮掉 CODE-020）；L4（错挂后无校验） | 修好了告警，没修好问题 |

⇒ **治理原则**（本轮已多次验证）：
1. **同一概念只允许一处实现**（L3 是最新反例）
2. **补丁不得掩盖告警**（L2 层 4）
3. **新增守卫必须同时下线一个旧补丁**（对抗补丁层膨胀）
