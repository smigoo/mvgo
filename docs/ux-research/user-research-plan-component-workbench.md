# 组件生成工作台用户研究计划

> 研究对象：mvgo 项目 `/generate/components` 组件生成工作台
> 研究目的：深入了解目标用户需求、痛点和行为模式，为界面信息架构与交互优化提供证据支持
> 版本：v1.0
> 日期：2026-08-13

---

## 1. 研究目标

### 1.1 核心问题

1. 用户在使用组件生成工作台时，主要目标是什么？（生成新组件、复用历史组件、调试已有组件等）
2. 当前三栏布局（左侧配置 / 中央舞台 / 右侧历史）是否符合用户心智模型？
3. 左侧配置面板的信息密度和步骤顺序是否清晰？用户是否会产生困惑？
4. 中央「工作流」卡片对新手和老手分别有什么价值？是否存在信息冗余？
5. 用户在生成过程中最关注哪些信息？（进度、日志、预览、错误、耗时等）
6. 任务完成后，用户如何找到、下载、预览或继续调试生成的组件？
7. 不同角色（前端开发、设计师、产品经理）对组件生成工具的期望有何差异？

### 1.2 业务影响

- 优化 `/generate/components` 页面的任务完成率和首次使用成功率
- 降低用户在配置阶段的操作错误和犹豫时间
- 提升生成结果的可发现性和可复用性
- 为后续「任务详情页」与「生成工作台」的视觉一致性提供用户依据

## 2. 研究方法

采用 **混合研究方法（Mixed Methods）**，结合定性与定量数据，确保发现既有深度又有统计支撑。

| 方法 | 目的 | 样本量 | 时长 | 产出 |
|---|---|---|---|---|
 **可用性测试（ moderated ）** | 观察真实用户完成任务的全过程，发现操作障碍和认知困惑 | 8-10 人 | 45-60 min/人 | 任务完成率、错误率、用时、行为观察记录 |
| **结构化访谈** | 深入了解用户目标、使用场景、痛点和期望 | 与可用性测试合并进行 | 15-20 min | 用户原话、需求优先级 |
| **问卷调研（SUS + 自定义量表）** | 量化用户满意度、易学性和任务效率感知 | 30-50 人 | 5-10 min/人 | SUS 评分、NPS、任务难度评分 |
| **日志分析/行为数据** | 了解实际使用中的高频路径、弃用点和停留时长 | 现有用户数据 | 持续 | 热力图、漏斗分析、按钮点击率 |
| **启发式评估** | 由 UX 专家基于尼尔森十大可用性原则快速排查问题 | 2-3 名专家 | 2-3 小时 | 问题清单、严重程度评级 |

### 2.1 方法选择理由

- **可用性测试 + 访谈**：直接观察行为并追问原因，适合探索当前界面的具体问题。
- **问卷**：扩大样本，验证定性发现的普遍性。
- **行为数据**：补充真实场景下的使用模式，避免研究环境偏差。
- **启发式评估**：低成本、高效率，在研究正式开展前快速定位明显问题。

## 3. 参与者招募

### 3.1 目标用户画像

#### 主要用户：前端开发工程师
- **角色特征**：负责将设计稿或需求转化为 Vue3 / 微码组件
- **使用频率**：每周多次
- **核心目标**：快速生成可用、规范的组件代码，减少重复劳动
- **技术熟练度**：中高

#### 次要用户：UI/UX 设计师
- **角色特征**：提供设计稿，需要验证设计能否被正确还原
- **使用频率**：每周 1-3 次
- **核心目标**：确认组件生成结果与设计稿一致
- **技术熟练度**：中

#### 潜在用户：产品经理 / 业务方
- **角色特征**：需要快速验证想法或查看组件效果
- **使用频率**：不定期
- **核心目标**：低门槛地看到可运行的组件原型
- **技术熟练度**：低中

### 3.2 样本规模与分组

| 组别 | 人数 | 招募标准 |
|---|---|---|
| 有经验用户（1 个月以上） | 4-5 人 | 已使用 mvgo 或类似组件生成工具 |
| 新手用户（首次使用） | 4-5 人 | 前端开发或设计师，未使用过 mvgo |
| 跨角色用户 | 2-3 人 | 设计师或产品经理 |

**总计：10-13 人参与深度研究，30-50 人参与问卷调研。**

### 3.3 招募渠道

- 公司内部前端/设计团队
- 参与过 mvgo 项目的早期用户
- 通过飞书/钉钉/企业微信发布招募启事
- 如有必要，可联系外部 Vue 前端开发者社区

### 3.4 筛选问题

1. 您的日常工作是否涉及前端组件开发或 UI 设计？
2. 您是否使用过 AI 辅助代码生成工具（如 GitHub Copilot、Cursor、v0 等）？
3. 您是否使用过 Figma 或类似设计协作工具？
4. 您每周大约需要将多少个设计稿转化为前端组件？
5. 您是否愿意参与 1 小时的屏幕共享会话并被录制？

## 4. 研究场景与任务设计

### 4.1 测试环境

- 在测试设备上打开 mvgo `/generate/components` 页面
- 使用真实可用的 Figma 链接和示例截图
- 后端接口可用，允许真实生成（或准备已完成的 mock 任务）
- 屏幕录制 + 眼动追踪（可选）+ 出声思维法（Think Aloud）

### 4.2 任务场景

#### 任务 1：首次生成一个 Vue3 Lite 组件（15 min）
**场景**：你收到一张设计稿截图，需要让系统帮你生成一个 Vue3 Lite 组件。
**指令**：请使用这个页面，从截图生成一个 Vue3 Lite 组件。
**观察重点**：
- 用户是否能快速理解左侧配置项的含义和顺序
- 用户是否会阅读中间「工作流」卡片
- 用户在上传截图、选择规格、点击生成时的犹豫点和错误
- 用户对生成按钮状态和文案的理解

#### 任务 2：使用 Figma 链接生成微码 Max 组件（15 min）
**场景**：设计师给了你 Figma 文件链接，需要生成一个微码 Max 组件。
**指令**：请使用这个页面，从 Figma 链接生成一个微码 Max 组件。
**观察重点**：
- Figma 来源切换是否自然
- 用户对「微码 / Vue3」、「Lite / Max」概念的理解
- 用户如何处理 Figma 链接粘贴、节点选择等步骤
- 错误提示的可理解性

#### 任务 3：查看生成进度并定位问题（10 min）
**场景**：你之前提交了一个生成任务，现在回来看进度。
**指令**：请找到刚才的任务，查看它的进度、日志和错误信息（如果有）。
**观察重点**：
- 用户是否能从右侧历史面板找到目标任务
- 用户对进度条、时间线、日志 tab 的关注优先级
- 错误状态的可发现性和可理解性
- 用户是否知道如何重试或取消

#### 任务 4：下载并使用生成结果（10 min）
**场景**：任务已经完成，你需要获取生成的组件代码。
**指令**：请下载或预览刚才生成的组件。
**观察重点**：
- 完成态信息的可发现性
- 下载、预览、Playground 跳转的操作路径是否清晰
- 用户对「ZIP 下载」vs「Playground 调试」的选择偏好

#### 任务 5：探索历史任务（5 min）
**场景**：你想看看过去生成的组件，找一份之前的代码复用。
**指令**：请找到你最近生成过的一个组件。
**观察重点**：
- 右侧历史面板的扫描效率
- 用户通过名称、状态、时间定位任务的策略
- 历史任务的可达性和可操作性

### 4.3 任务后访谈问题

1. 你觉得这个页面最想帮你完成什么？
2. 第一次打开时，你首先注意到了哪个区域？
3. 左侧配置和中间「工作流」卡片，你更依赖哪一个？为什么？
4. 有没有哪个步骤让你感到困惑或需要反复确认？
5. 你觉得哪些信息是多余的，哪些信息缺失？
6. 生成过程中你最关心什么？进度、日志、耗时还是结果？
7. 如果你可以改一个东西，你会改什么？
8. 你会把这个工具推荐给同事吗？为什么？

## 5. 数据收集与分析

### 5.1 定量指标

| 指标 | 定义 | 目标基线 |
|---|---|---|
| 任务完成率 | 在无明显协助下完成任务的用户比例 | ≥ 80% |
| 平均任务用时 | 从阅读任务到完成的时间 | 记录基准值 |
| 错误数 | 用户在任务中的误操作、错误选择次数 | 记录基准值 |
| SUS 评分 | 系统可用性量表，0-100 分 | ≥ 70 分 |
| NPS | 净推荐值 | ≥ 30 |
| 任务难度评分 | 1-7 分，1=非常容易 | ≤ 3 分 |
| 信息冗余感知 | 1-7 分，1=完全不冗余 | 记录基准值 |

### 5.2 定性分析

- **主题分析法（Thematic Analysis）**：对访谈和出声思维记录进行编码，提取重复出现的行为模式、痛点和期望。
- **旅程地图（Journey Map）**：绘制用户从打开页面到获取结果的完整流程，标注情绪高点、低点和摩擦点。
- **亲和图（Affinity Diagram）**：将观察发现按主题归类（如配置理解、进度认知、结果查找等）。
- **问题严重程度评级**：
  - **P0（严重）**：导致任务失败或用户放弃
  - **P1（重要）**：显著降低效率或满意度
  - **P2（一般）**：可优化，影响较小
  - **P3（建议）**：未来可考虑

### 5.3 数据三角验证

- 对比可用性测试观察、问卷数据、行为日志三者是否一致
- 如发现不一致，深入访谈追问原因
- 优先处理被多种数据源共同验证的问题

## 6. 研究产出

### 6.1 核心交付物

1. **用户研究报告**（Markdown / Word）
   - 研究目标与方法
   - 用户画像
   - 关键发现与痛点
   - 设计建议与优先级
   - 成功指标与后续追踪计划

2. **可用性问题清单**
   - 问题描述
   - 影响用户/任务
   - 严重程度
   - 复现步骤
   - 建议方案

3. **用户旅程地图**
   - 阶段划分
   - 用户行为
   - 情绪曲线
   - 痛点与机会点

4. **设计优化建议**（可直接进入迭代）
   - 信息架构调整
   - 交互流程优化
   - 文案与标签优化
   - 视觉层级建议

### 6.2 初步假设（待验证）

基于当前截图和已有认知，提出以下假设，供研究验证：

1. **假设 A**：中间「工作流」卡片对新手有价值，但对有经验的用户是冗余信息，会降低操作效率。
2. **假设 B**：左侧配置面板的步骤顺序不够明显，新手用户需要更多引导。
3. **假设 C**：用户更希望中央区域作为「素材上传区」或「结果预览区」，而非流程说明区。
4. **假设 D**：右侧历史面板在组件数量多时需要更强的筛选和搜索能力。
5. **假设 E**：生成过程中的日志信息对技术用户重要，但对设计师等非技术用户造成认知负担。

## 8. 伦理与隐私

- 所有参与者在会话开始前签署知情同意书
- 屏幕录制仅用于研究分析，不对外公开
- 匿名化处理所有个人信息和公司敏感数据
- 研究报告中对用户原话做去标识化处理
- 研究数据存储在公司内部安全位置，访问权限受限
