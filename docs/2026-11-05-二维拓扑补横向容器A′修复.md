## 1. 根因证据链（Phase 2）

### D1 · A′ 在真实 vision 形态下**一次都没执行过**

产物缓存 `.mc-gen/cache/debug-ai-response.txt` 顶层键：

```
[generatedAt, stage, componentName, componentTitle, analysisModel, sourceImage,
 summary, layout, styles, interactions, charts, doNotInvent, notes]
layoutStructure: undefined
```

- `parseAnalysisResult` → `normalizeFields:1048` 仅在 `!result.layout && result.layoutStructure` 时映射；真实响应**有** `layout`、**无** `layoutStructure` ⇒ `parsed.layoutStructure === undefined`。
- `visual-parser.js:1763` 守卫 `if (parsed.layoutStructure && parsed.layoutStructure.layout)` ⇒ **恒 false** ⇒ `:1774 rebuildSlotConContainers(...)` **从未被调用**。
- `layoutStructure` 壳是 `analyze()` 返回时才包装的（`visual-parser.js:4157` `layoutStructure: analysisResult`），时间点**晚于** `_postProcessAnalysis`（`:814`）。

⇒ 日志 `vision-structure-guard {injected:0}` 的语义是「没有重建」，不是「重建结果被丢弃」。

**假绿温床**：`container-rebuilder.realdata.spec.ts:23/40/57` 的夹具是 `visual.layoutStructure.layout` —— 这个形态在 vision 主路径上不存在，单测绿 ≠ 生产生效。

**第二道门**：A′ 整段嵌在 `if (inlineRows.length)` 内 ⇒ 组件若没有横向行可合并（`inlineRows=0`），A′ 同样不执行。与 D1 同性质。

### D2 · 方向判据入参形状错，横向被**反向**处理

| 环节 | 现场 |
|---|---|
| `container-rebuilder.js:64-68` | `byId.get(id)`（索引记录，**带 `bbox`**）→ `.map(getBBox)` → 压成 `{x,y,w,h}` |
| `flex-direction-inferrer.js:23` | `siblings.filter(n => n.absoluteBoundingBox || n.bbox)` |
| 结果 | 压平后 `bbox` 丢失 ⇒ 全被过滤 ⇒ `boxes.length < 2` ⇒ **恒返回 `'vertical'`** |
| `container-rebuilder.js:70` | `if (inferFlexDirection(memberBoxes) === 'horizontal') continue` ⇒ **永不成立** |

后果**不是**「横向容器被跳过」，而是**横向容器照样被包成 `layout:'vertical'`** —— 把左右并列写成上下堆叠，正是本单要修的 bug 形态。

> 首版影响面审计脚本犯了同一错，输出「横向 = 0」是假阴性（已修正口径）。

### D3 · 注释承诺「横向交给 merger」，而 merger 在该开关下是 no-op

`container-rebuilder.js:62-63` 声称横向容器交给 merger。但两个调用点（`visual-parser.js:1759` / `:1764`）都传 `preserveVisionStructure: true`，而 `inline-row-merger.js:338-340` 在此开关下只做 `{ ...layout, sections: sections.slice() }` 浅拷贝 —— **零结构改动**。

⇒ 横向容器的父子关系「无人生还」，这才是 `effectiveSections` 只剩 3 段平级、`rootLayoutFacts.sectionRoots=3`、最终 `flex-direction: column` 的完整链条。

### 真机链路复算（c-device-monitor-38f97905）

```
2:8417 cp-设备监测
├─ 2:8419 header GROUP (388×30)        → 顶层 section（type=stats，跨行合并了 89:38）
└─ 89:40 slot-con FRAME (407×380)
   ├─ 89:38 switch FRAME (396×65)      → 不在顶层（被并进 2:8419.sourceNodeIds）
   └─ 89:37 @antd/tab FRAME            → 不在顶层
      ├─ 89:39 tabs FRAME (46×317)     → 顶层 section
      └─ 2:8437 cons GROUP (367×295)   → 顶层 section
```

- `89:37` 候选条件 `kids.every(secIds.has)` **成立**（`89:39` / `2:8437` 均在顶层）⇒ 修好 D1 就会进候选；但 D2 会把这对**左右并列**子节点包成 `vertical`。
- `89:40` 因 `89:38` / `89:37` 都不在顶层 ⇒ `allChildrenInSections = false` ⇒ 从一开始不进候选（本次不改这一条，见 §6）。

## 3. 修法（Phase 4 · 三处，一条链）

### D1 · `visual-parser.js`

1. **把 A′ 移出 `if (inlineRows.length)`**（放到该块之后、幻觉剔除之前，与 `:1798` 注释声明的「必须在 container-rebuild 之后」对齐），使其无条件执行（有 `figmaData` 时）。
2. **守卫改为按实际形态解析**，与 `:1596 _overrideVisionDimensionsWithFigma` 的既有多形态写法对齐（不新起第二套）：
   ```js
   if (parsed.layoutStructure && parsed.layoutStructure.layout) { ...重建并回写... }
   if (parsed.layout) { ...重建并回写... }
   ```
   两处分别重建（纯函数、幂等），**不做对象身份合并** —— 避免强行统一 `parsed.layout` 与 `layoutStructure.layout` 引发的隐性副作用；因两处入参同源、函数纯净，内容必然一致，`||` 短路读哪个都对。
3. **补计数行**（治理铁律：零命中也要打）`🛡️ A′ 容器层级重建·已评估`，带 `slots / containers / horizontal / vertical / members` 分解。

### D2 · `container-rebuilder.js`

1. 方向判据喂**原始节点/索引记录**（带 `bbox`），不再喂压平盒子。
2. 删除 `continue`，横向产出 `layout: 'horizontal'`，children 按 `bbox.x` 升序（纵向仍按 `y`）。
3. `role` 保持 `content-container`、`layoutSource` 保持 `container-rebuild`（`isLayoutContainerSection` 的唯一判据来源，不改契约）。

### D3 · 注释与承诺对齐

`container-rebuilder.js` 头注释与 `:62-63` 局部注释改为「横向/纵向都由本函数重建，方向由共享 primitive 裁决」，删除「交给 merger」的错误承诺。
