## 一、问题概述

### 1.1 三个典型案例

| 任务 ID | 类型 | 表面症状 | 真实失败原因 | 产物可见性 |
|---------|------|---------|-------------|-----------|
| `mc-max-1789490645947-e6f8687e` | 微码 | "所有解析策略失败" | DO-NOT-INVENT-CHART-MOUNT-MISSING（LLM 写了 echarts 代码但缺 `<div ref="chartRef">`） | 被 BLOCK 拦截 |
| `mc-max-1789490669448-acf9c8ac` | 微码 | tabs 纵排、颜色失效 | 规则⑤只注入 flexGrow 不注入 `display:flex` + scoped style 颜色覆盖 common.less | 降级发布（视觉异常） |
| `mv-max-1789490989951-f68aedb6` | Vue3 | 布局资源完全没出现 | CODE-022（LLM import 了 7 个资源变量但模板 0 处引用） | 被 BLOCK 拦截 |

### 1.2 共同特征

- **检测有效但不修复**：门禁成功拦截问题，但只拦不修 → 重试耗尽 → 任务失败
- **后处理规则不完整**：规则⑤只处理 flexGrow，遗漏 `display:flex` 等必要属性
- **LLM 遗漏高频复发**：图表挂载点、资源变量挂载、布局属性声明——同类遗漏反复出现
- **日志误导**：`all_strategies_failed` 是中间重试噪音，真实失败原因被掩盖

## 二、根因分析（深层问题）

### 2.1 量化"打补丁"规模

| 维度 | 数量 | 说明 |
|------|------|------|
| 修复器文件 | 31 个 | `backend-node/src/ai-engine/utils/` 下 `*fix*.js` / `*heal*.js` / `*ensure*.js` |
| 校验器文件 | 17 个 | `backend-node/src/ai-engine/validators/` 下 `*.js` |
| 月度 commit | 88+ | 近 30 天管线相关提交 |
| 重复门禁 | 3 类 | DO-NOT-INVENT / CODE-022 / FLEX-003 反复命中 |

**结论**：管线已进入"补丁层 > 生成层"的失控状态。

### 2.2 深层根因

#### 根因 1：事实源分散

- **sectionLayoutFacts**（display/gridColumns/flexDirection/flexGrow）与 **code-generator 的 resolvePlanSections** 不同源
- **资源变量注入**（resource-import-guard.js）与 **LLM 生成的 import 声明** 两套逻辑
- **图表声明**（vision JSON 的 seriesColors）与 **LLM 生成的 echarts 代码** 两套逻辑

→ 同一概念多处实现 → 一致性靠校验器兜底 → 校验器越加越多 → 补丁层膨胀

#### 根因 2：LLM 承担确定性判断

- **图表挂载点**：LLM 决定是否写 `<div ref="chartRef">`（确定性需求，应由管线注入）
- **资源变量挂载**：LLM 决定如何在模板中使用 `bg1` / `icon1`（确定性需求，应由管线注入）
- **布局属性**：LLM 决定是否写 `display: flex`（确定性需求，应由 sectionLayoutFacts 注入）

→ LLM 遗漏 → 门禁拦截 → 重试常犯同一错 → 耗尽

#### 根因 3：fail-open vs fail-loud 混乱

- **fail-open**：静默降级（如 `all_strategies_failed` 后 recoverFilesFromRawText 兜底）
- **fail-loud**：明确报错（如 DO-NOT-INVENT BLOCK）

→ 中间状态不可观测 → 日志误导 → 排障困难

#### 根因 4：后处理规则不完整

- **规则⑤**（resource-mounter.js）：只注入 flexGrow，遗漏 `display:flex` / `flex-direction`
- **主题切换**：`.common()` 颜色变量覆盖 `.theme-*()` mixin（LESS mixin 变量不覆盖 caller 已有同名变量）
- **scoped style**：子组件 scoped style 颜色变量覆盖 common.less

→ 规则只处理部分场景 → 遗漏场景复发 → 加新规则 → 补丁层膨胀

## 三、治理方案（根源性修复）

### 方案 A：Section 树单一事实源（治根因 1）

**目标**：section 的 display / flexDirection / flexGrow / gridColumns 只从 sectionLayoutFacts 读取，消除 code-generator 与 resource-mounter 的双源问题。

**实施步骤**：

1. **统一数据源**：
   - `buildSectionHeightsMap` / `alignSectionClasses` / `resolvePlanSections` 全部从 `sectionLayoutFacts` 读取
   - 删除 `code-generator.js` 中的 `resolvePlanSections` 冗余逻辑

2. **确定性注入**：
   - 当 `flexDirection === 'row'` 时，规则⑤自动补 `display: flex`
   - 当 `flexGrow` 存在时，规则⑤自动补 `min-height: 0`（flex 子项必要属性）

3. **验收标准**：
   - `acf9c8ac` 的 tabs 横向布局正常（无需手动补 `display: flex`）
   - 高度比例与 declare.json 一致（无冗余切片）

**预计工作量**：3-5 天  
**风险**：中（需回归测试所有 section 类型）

---

### 方案 B：图表声明式化（治根因 2）

**目标**：LLM 只声明 `{ sectionId, type, series, colors }`，由确定性渲染器写 echarts 代码，消除 LLM 遗漏挂载点的问题。

**实施步骤**：

1. **图表声明 schema**：
   ```json
   {
     "sectionId": "chart-1",
     "type": "pie",
     "radius": ["55%", "75%"],
     "series": ["危化品车", "重型货车", "超高车辆"],
     "colors": ["#ff4d4f", "#1990ff", "#fa8c16"]
   }
   ```

2. **确定性渲染器**：
   - 新增 `chart-renderer.js`：读取图表声明 → 生成 echarts 代码 + `<div ref="chartRef">` 挂载点
   - 删除 `injectEchartsFallback`（不再需要兜底）

3. **与高度比例 dedupe 协调**：
   - chart 叶子必须明确 `flexGrow` + 排他 `sourceNodeIds`
   - 否则 `buildSectionHeightsMap` fail-open → `flex: 1` 平分

**验收标准**：
- `e6f8687e` 的环形图正常显示（无需 LLM 写 `<div ref="chartRef">`）
- 图表系列数与 vision 一致（无膨胀/遗漏）

**预计工作量**：5-7 天  
**风险**：高（需重构图表生成链路）

---

### 方案 C：fail-open → fail-loud（治根因 3）

**目标**：所有降级路径必须可观测，消除中间状态不可见的问题。

**实施步骤**：

1. **统一降级日志格式**：
   ```javascript
   logger.warn('降级发布', {
     reason: 'DO-NOT-INVENT-CHART-MOUNT-MISSING',
     fallback: 'recoverFilesFromRawText',
     originalError: err.message,
     taskId: state.taskId
   });
   ```

2. **修复 error-humanizer.js 文案错映射**：
   - 新增 DO-NOT-INVENT 专属分支：`/禁止臆造校验未通过/` → "图表/资源声明不完整，需重新生成"
   - 不再匹配到"视觉分析失败或降级"

3. **日志查询工具**：
   - 新增 `query-task-logs.js <taskId>`：按 session ID 聚合所有相关日志（含重试噪音）
   - 输出：真实失败原因 + 重试次数 + 降级路径

**验收标准**：
- `e6f8687e` 的日志直接显示"DO-NOT-INVENT-CHART-MOUNT-MISSING"，无 `all_strategies_failed` 噪音
- 排障时间从 30 分钟降至 5 分钟

**预计工作量**：1-2 天  
**风险**：低（纯日志改造）

---

### 方案 D：资源变量确定性挂载（治根因 2）

**目标**：LLM import 资源变量后，管线自动在模板中挂载，消除 CODE-022 问题。

**实施步骤**：

1. **启用 `pruneUnmountedResourceImports` 修复器**：
   - 当前已实现（`resource-import-guard.js:1154`），但未启用
   - 落盘前扫描：import 后 0 引用的资源变量 → 确定性删除

2. **或：确定性挂载**：
   - 新增 `mount-resource-vars.js`：扫描 `resourceDomMapping` → 自动在模板中插入 `:style="{ backgroundImage: url(bg1) }"`
   - 需 LLM 在 prompt 中声明资源用途（背景/图标/装饰）

3. **验收标准**：
   - `f68aedb6` 的 7 个资源变量全部挂载（或自动删除未使用的）
   - CODE-022 门禁通过率从 0% 提升至 95%+

**预计工作量**：2-3 天  
**风险**：中（需确认资源用途声明的准确性）

## 七、总结

**核心问题**：管线已进入"补丁层 > 生成层"的失控状态，根因是事实源分散 + LLM 承担确定性判断。

**治理方向**：
1. **单一事实源**：section 布局、资源变量、图表声明——每个概念只允许一处实现
2. **确定性注入**：LLM 只负责创意性内容（文案/颜色/布局比例），确定性内容（挂载点/布局属性/资源引用）由管线注入
3. **可观测降级**：所有降级路径必须 fail-loud，消除中间状态不可见

**预期效果**：
- 校验器数量从 17 降至 10 以下
- 修复器数量从 31 降至 20 以下
- 组件生成通过率从 70% 提升至 90%+
- 排障时间从 30 分钟降至 5 分钟
