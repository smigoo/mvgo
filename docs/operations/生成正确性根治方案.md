# 生成正确性根治方案（静态图放错 + 布局方向错乱）

> 目标：让「资源图片放错位置」和「上下布局变左右」这两类错误在**任何环境、任何组件类型**下都不再发生。
> 核心原则：把「LLM 自由发挥」改成「系统确定性」——编号与布局方向都由系统在源头固化，LLM 只读不计算。

---

## 一、根因总结

### 1.1 静态图放错（资源编号错位）

**现象**：LLM 在模板里写 `bg1`，系统注入的 `bg1` 却是另一张图，导致图片错位。

**根因**：变量名的「位置编号」（`bg1` / `icon1` / `img1`）在**两个下游各自重新计算**，且过滤口径不一致：

| 环节 | 文件 | 编号方式 |
|------|------|----------|
| prompt 侧（LLM 看到什么） | `resource-mapping-formatter.js` `formatResourceMapping` | 微码模式 `filterPanelResources: true`，**先过滤面板级资源再编号** |
| 注入侧（系统注入什么） | `resource-import-guard.js` `buildVarToMapping` | **不过滤**面板级资源，直接对所有 `success` 资源编号 |

两条链路算出的 `bg1` 指向不同图片 → 错位。

**本质**：`bg1` 这类「位置编号」没有在 mapping 生成时**固化**，而是在两个下游**运行时各自推导**，一旦任何一边的过滤/排序条件不同就漂移。

### 1.2 上下布局变左右（flex 方向缺失）

**现象**：设计稿中 Traffic Trend 与 Vehicle Distribution 应上下堆叠，实际渲染成左右并排。

**根因有三层**：

1. **`display: flex` 未写 `flex-direction`**：CSS 默认值是 `row`（横向）。LLM 生成的 `index.css` 里存在大量只写 `display: flex` 却漏掉 `flex-direction: column` 的规则（如 `.c-traffic-monitor-chart-section`），于是横向排列。
2. **微码 prompt 未注入 Figma `layoutMode` 树**：Vue3 管线已把 `figmaNodeData`（含每个容器的 `layoutMode: HORIZONTAL/VERTICAL`）注入 prompt 作为「flex-direction 的权威依据」（`vue3-engineer.js` L483-491），但**微码管线没有**——LLM 只能靠散落各处的示例猜，猜错就漏写。
3. **幽灵样式：`index.css` 与 scoped 样式类名不一致**：`component.js` 引入编译产物 `index.css`（全局、非 scoped），而 `index.vue` 的 scoped style 又 `@import index.less`，两套选择器类名对不上（`-chart-section` vs `-content`），互相干扰。

### 1.3 附带发现：LESS Grid 被编译丢失

LESS 中 `.c-trend-chart-section` 用 `display: grid; grid-template-areas: ...`，但 `less.render` 编译出的 `index.css` 里变成了 `display: flex; flex-direction: column`。Grid 布局在编译环节丢失，属独立 bug（需排查 less 版本/语法兼容），本方案先记录、后续单独处理。

---

## 二、治本原则

| 原则 | 含义 |
|------|------|
| **单一事实源** | 资源变量名（`assignedVarName`）在 mapping 生成时一次性固化，下游只读不计算 |
| **确定性兜底** | 写盘前用确定性代码补全缺失的 `flex-direction`，不依赖 LLM 自觉 |
| **过滤不编号** | 「是否展示给 LLM」与「变量名编号」彻底解耦，过滤绝不改变编号 |

---

## 三、方案一：资源变量名单一事实源（治静态图放错）

### 3.1 改动点 1：`figma-connector.js` `_buildResourceDomMapping`

在 mapping 生成阶段，为每条资源**一次性分配 `assignedVarName`**，并显式标记 `isPanelResource`：

```js
// 在 traverse 完成后、返回 mappings 之前：
// 1) 标记面板级资源（与 filterPanelResources 的正则口径统一）
const isPanel = (m) => {
  const figmaPath = m.figmaPath || ''
  const name = m.name || ''
  if (/^[^/]+\/(bg|background|header|panel-header|title-bar)$/i.test(figmaPath)) return true
  if (/^(bg|background|header|panel-header|title-bar)$/i.test(name)) return true
  return false
}
for (const m of mappings) m.isPanelResource = isPanel(m)

// 2) 对「非面板资源 + success」按角色 + traverse 稳定顺序，固化 assignedVarName
const roleIndex = { bg: 0, icon: 0, img: 0 }
for (const m of mappings) {
  if (m.isPanelResource || m.downloadStatus !== 'success') continue
  const role = m.previewAnalysisRole === 'image' ? 'img' : m.previewAnalysisRole
  if (!roleIndex.hasOwnProperty(role)) continue
  roleIndex[role]++
  // semanticVarName 优先（已全局去重），否则用固化位置编号
  m.assignedVarName = m.semanticVarName || `${role}${roleIndex[role]}`
}
```

**要点**：
- 编号在**过滤之前**、基于「非面板资源的 success 全集」稳定排序（traverse 顺序 = Figma 树顺序，天然稳定）。
- `assignedVarName` 写进 `resource-dom-mapping.json`，落盘后任何环境/任何类型读到的是同一份编号。
- 面板资源不占编号位（业务组件本就不该引用面板级 bg/header）。

### 3.2 改动点 2：`resource-import-guard.js` `buildVarToMapping`

注入端**不再自己编号**，改为读 `assignedVarName`：

```js
function buildVarToMapping(resourceDomMapping) {
  const available = (resourceDomMapping || []).filter(m =>
    m.downloadStatus === 'success' && !m.isPanelResource)
  const varToMapping = new Map()
  for (const m of available) {
    // 优先读固化编号；老 mapping 无此字段时回退到旧逻辑（semanticVarName 或按角色编号）
    const key = m.assignedVarName || m.semanticVarName || null
    if (key) varToMapping.set(key, m)
  }
  // 兼容老 mapping：若无 assignedVarName，回退按角色顺序编号（与旧行为一致）
  if (!(resourceDomMapping || []).some(m => m.assignedVarName)) {
    const bgMappings = available.filter(m => m.previewAnalysisRole === 'bg')
    const iconMappings = available.filter(m => m.previewAnalysisRole === 'icon')
    const imgMappings = available.filter(m => m.previewAnalysisRole === 'img' || m.previewAnalysisRole === 'image')
    bgMappings.forEach((m, i) => varToMapping.set(`bg${i + 1}`, m))
    iconMappings.forEach((m, i) => varToMapping.set(`icon${i + 1}`, m))
    imgMappings.forEach((m, i) => varToMapping.set(`img${i + 1}`, m))
  }
  available.forEach(m => { if (m.semanticVarName) varToMapping.set(m.semanticVarName, m) })
  return { available, varToMapping }
}
```

### 3.3 改动点 3：`resource-mapping-formatter.js` `formatResourceMapping`

prompt 侧展示变量名时，**优先读 `assignedVarName`**，不再用 `index + 1`：

```js
// 原：const varName = mapping.semanticVarName || `bg${index + 1}`
// 改：const varName = mapping.assignedVarName || mapping.semanticVarName || `bg${index + 1}`
```

`filterPanelResources` 保留，但仅用于「决定是否展示该条目」，不再影响编号（编号已在源头固化）。

### 3.4 验证

单测（`resource-import-guard.spec.ts` / 新增 `resource-mapping-formatter.spec.ts`）：

1. 构造含面板级 bg + 2 个业务 bg 的 mapping，断言：
   - `buildVarToMapping` 产出的 `bg1` 与 `formatResourceMapping`（`filterPanelResources: true`）产出的 `bg1` 指向**同一条记录**。
2. 断言 `filterPanelResources` 前后，业务资源的 `assignedVarName` 不改变。
3. 断言旧 mapping（无 `assignedVarName` 字段）走回退逻辑，行为与现状一致（不破坏已生成组件）。

## 四、方案二：flex 方向确定性（治上下变左右）

双保险：**prompt 注入权威依据 + 写盘前确定性兜底**。

### 4.1 改动点 1：微码 prompt 注入 `figmaNodeData` 的 `layoutMode` 树

对齐 `vue3-engineer.js` L483-491 的成熟做法，在 `microcode-engineer.js` 的 prompt 中注入：

```
## Figma 节点布局方向（layoutMode — flex-direction 的权威依据）
逐节点比对：节点标注 HORIZONTAL → 该容器必须 flex-direction: row；
          节点标注 VERTICAL → 该容器必须 flex-direction: column。
【铁律】任何 display: flex 的容器都必须显式写 flex-direction，禁止省略（省略默认 row）。
```

### 4.2 改动点 2：写盘前确定性补全（兜底）

在 `css-sanitizer.js` 新增 `ensureFlexDirection`，扫描所有 `display: flex` / `display:flex` 且**无 `flex-direction`** 的规则，自动补 `flex-direction: column`：

- 有 Figma `layoutMode` 数据可精确匹配时，按 `HORIZONTAL→row` / `VERTICAL→column` 补。
- 无数据时，**默认补 `column`**（面板类 UI 纵向堆叠是绝对多数，且「icon+text 横向」这类小块 LLM 通常会显式写 row，反而不易漏），并输出告警日志供质量门禁追踪。

将该函数挂到**所有写盘路径**（与 `repairScopedThirdPartySelectors` 同模式）：
- `microcode-engineer.js` 的 sanitize 链
- `diff-engine.js` L230 附近
- `vue3-engineer.js` L684 附近
- `layout-responsive-graph.js` L129 附近

### 4.3 验证

单测：构造含 `display: flex` 无 `flex-direction` 的 CSS，断言补全为 `column`；含 `flex-direction: row` 的不改动；含 `display: grid` 的不动。

## 五、方案三：消除幽灵样式（治类名不一致）

`component.js` 目前 `import './resources/styles/index.css'`（全局编译产物），而 `index.vue` scoped 又 `@import index.less`。两套选择器类名不一致是「幽灵样式」根源。

**改动**：统一为**单一入口**——

- `index.css` 只作为 Vite 加载需要（`less` 文件会被 Vite 拦截，见 `microcode-engineer.js` L5378 注释），因此 `component.js` 的 import 保留，但需保证 `index.css` 与 `index.less` 内容同源（都由同一份 `common.less` 编译而来）。
- 关键约束：**禁止 `index.css` 中出现 scoped 模板未使用的类名**。写盘前校验 `index.css` 的选择器集合是 `index.vue` 模板使用类名的子集（或至少两者不冲突），发现游离类名即告警。

> 简化版：若验证「`index.css` 仅含 theme 变量 + common.less 编译产物，且类名与模板严格一致」成本过高，可先做最小改动——删除 `component.js` 中对 `index.css` 的 import（scoped 的 `@import index.less` 已覆盖全部样式），观察预览是否正常。此改动需在单测环境验证后再上线。

## 六、实施顺序

| 顺序 | 方案 | 风险 | 依赖 |
|------|------|------|------|
| 1 | 方案一（变量名单一事实源） | 中（涉及注入端核心） | 需兼容老 mapping 回退 |
| 2 | 方案二（flex 方向兜底） | 低（纯增量补全） | 无 |
| 3 | 方案三（幽灵样式） | 低 | 需单测验证样式不缺失 |

每步改完：
1. `npm run build`（nest build 才是真入口）编译通过。
2. grep 确认关键符号定义存在（`assignedVarName`、`ensureFlexDirection` 各只有 1 处定义 + N 处调用）。
3. 相关单测通过。

## 七、回退策略

- 方案一：`buildVarToMapping` 保留了「无 `assignedVarName` 时回退旧编号」分支，一旦发现问题，删除 mapping 生成侧的 `assignedVarName` 赋值即可完全回退到旧行为。
- 方案二：`ensureFlexDirection` 是独立函数，可单点移除。
- 方案三：`component.js` 的 import 一行即可恢复。
