# 架构评估：事实树基线四阶段 vs 现行 vision 驱动管线

日期：2026-11-06 ｜ 性质：架构方向评估（用户提案评审，未实施）

## 用户提案（四阶段）
1. 输入快照与视觉事实树：Figma 可见节点/几何/样式/资源+渲染图存不可变事实，**Vision 不决定数值**；
2. 确定性视觉基线：容器/TEXT/IMAGE/普通矢量先行，无 Auto Layout 允许 absolute，先画对；
3. 真实渲染门禁：DOM 带 data-figma-id，比对缺失/额外节点、bbox、计算样式、像素差；
4. 等价语义重构：基线通过后再做 Flex/列表/组件拆分/动态逻辑，重构不得改变视觉。

| absolute 兜底 | 强推 flex 还原，Figma 非专业文件无 Auto Layout 时 LLM 只能猜 | 段契约复读（刀70）、纵排/间距错 |

**结论：提案的前两步（事实树+数值去 vision 化）能消除约一半的病灶族**——凡是

（Figma 节点树自带 absoluteBoundingBox/fills/strokes/layoutMode，无需 vision 猜）。

## 二、与现行管线的根本差异

- 现行：vision 看渲染图 → layoutStructure 段树（语义单元）→ 段接管（fg-list/statrow）
  + LLM 自由生成 → 写盘守卫兜底 → 粗粒度像素门禁（VISUAL-002 score，WARN 不阻断）。
- 提案：Figma 事实树（节点单元）→ 确定性 absolute 渲染（画对）→ 节点级门禁 →
  等价重构（语义化）。
- **差异本质**：语义识别前置（现行）vs 视觉正确前置（提案）。现行管线在「识别错」
  时全线崩溃且难以自证；提案把「画对」变成可独立验证的基线，语义化是后续等价变换。

## 三、冲突与代价（必须诚实）

1. **架构替换非增量**：段规划/接管渲染器/折叠器/几十把守卫都围绕 vision 段树建。
   基线法需要新写「Figma 树→absolute DOM」确定性渲染器——新管线级工作量。
2. **absolute 与弹性容器目标冲突**：组件挂大屏 portlet（尺寸不定），absolute 只能保证
   **原稿尺寸**下画对；「重构不改变视觉」只能定义为「原稿尺寸下像素等价」，
   弹性化仍需第 4 步的 Flex 重构，且弹性下无像素等价可守（需改为几何比例等价判据）。
3. **图表/交互在基线阶段只能降级为快照**：echarts 真值、tab 交互在 absolute 基线里
   无法表达——第 4 步恢复，期间产物「能看不能用」。需产品侧接受。
4. **vision 不该全废**：数值去 vision 化正确，但「这是 tab/列表/表格」的语义标签
   vision 有真实价值（fe2b79ed 的 interactions.tab-switch 识别很准，是消费侧断链）。
   正确定位：**vision 只产语义标签挂到节点 id，数值一律以 Figma 快照为准**。
5. **现有资产可迁移**：resource-mounter/背景四件套（刀70 T4）、text-runs 真值、
   fg-list 模板可转为事实树渲染原语，不是全推倒。

## 四、落地路径建议（门禁先行，生成路径渐进切换）

- **Phase 0（立即可做，不动生成路径）**：Figma 节点级渲染门禁——DOM 带 data-figma-id
  （接管模板已有 data-section-id 可扩展），渲染后与 Figma 可见节点做
  「缺失/额外/bbox」对照，**缺失即 BLOCK**。直接防「底部消失」族。
- **Phase 1**：输入快照事实树——Figma 节点树落不可变 snapshot（.checkpoint/figma.json
  雏形已存在），vision 输出仅允许挂语义标签；所有几何/样式取值一律 snapshot。
  此步直接解 038b65ae 整族（vision 无 box 不再是问题）。
- **Phase 2**：确定性基线渲染器（容器/TEXT/IMAGE/矢量→absolute DOM）作为**裁判**，
  与现行管线产物像素 diff——先当对照组，不替代生成。
- **Phase 3**：基线稳定后评估生成路径切换到「基线+等价重构」。

**收益/成本比**：Phase 0+1 以两把刀的成本拿到提案 60% 收益（缺失节点门禁 +
数值去 vision 化）；Phase 2/3 是架构替换，需单独立项与排期。

## 附：具体工程方案评审（用户提供的 P0-P5 设计，04:39）

### 方案的真正增量（现行管线缺的「可证性」）
1. **hash 自证**：figmaRawHash/designImageHash 任务结束不变 +「Vision 开关数值不变」硬验收；
2. **编译确定性**：同一 IR 两次编译产物 hash 一致、全程无 LLM；
3. **四层门禁**：结构覆盖（missing/extra/ambiguous）→ 几何（bbox 零偏差）→ 计算样式 →
   RGBA 逐像素（现行 VISUAL-002 是 256×256 亮度直方图，对位移不敏感）；
4. **UNVERIFIED 三态**：字体/渲染缺失不得判 PASS 也不判 FAIL（现行门禁无此态）；
5. **重构事务单点回滚**：失败只回滚 flex-2:7889，不整页重试（现行 incremental_fix 是整页重试）。

### 内部矛盾与隐藏成本（全量采纳的风险）
1. **「等价重构 bbox 不变」与弹性 portlet 矛盾**：mvgo 组件挂弹性容器，Flex 化的目的
   就是适配不同容器尺寸——**容器尺寸变化时 bbox 必然变**。门禁若只在原稿尺寸视口跑，
   弹性行为就无门禁覆盖，回到「弹性下错布局无判据」的现状。方案未给弹性等价判据。
2. **平台壳隔离未闭环**：P2 禁 transform scale，但「平台壳负责承载和缩放」——组件实际
   运行尺寸≠原稿尺寸时的呈现机制（缩放？重排？）方案未回答。
3. **TEXT 像素级一致被低估**：Figma lineHeightPx/letterSpacing/autoResize 与 CSS line box
   差异是业界深坑，「严格模式零偏差」成本极高。
4. **两套并行维护**：新支路走通后，旧段规划/折叠器/守卫群变维护负担，方案未提退役节奏。
5. **动态数据主流程未展开**：基线是静态快照，接真实 API 后视觉必变——门禁只能覆盖
   静态快照，与 mvgo「API 绑定」主价值的关系未展开。

### 裁决：裁剪采纳（三部件先行，P1 暂缓）
| 部件 | 处置 | 理由 |
|---|---|---|
| **P0 快照 IR**（fidelity/ 不可变 input + hash + Render Node） | **采纳先行** | 低成本高价值：「数值以 Figma 为准」立刻有载体；vision 降级为语义标签；直接解 038b65ae 族 |
| **P2 结构覆盖层**（data-figma-id + missing/extra/ambiguous + BLOCK） | **采纳先行** | 不需等 baseline compiler，现行接管模板已带 data-section-id 可扩展；直接防「底部消失」族 |
| **P4 重构事务单点回滚** | **思想采纳** | 现行整页重试改事务化，降回归面 |
| **P1 absolute 基线编译器** | **暂缓** | 与弹性 portlet 冲突最大、TEXT 成本最高、与 fg-list 接管渲染器职责重叠；要验证「先画对」先做 P3 单点试点而非全量 |
| P2 几何/计算样式/RGBA 全量 | 随 P3 试点评估 | 视口固定原稿尺寸才有意义，弹性场景需另立判据 |

### 验证指标（决定是否续投 baseline）
P0+P2 上线后跑 2 周：**缺失节点拦截率**（应拦下 0f0468b7 类事故）、
**误拦率**（ambiguous/extra 假阳性）、**门禁可执行率**（UNVERIFIED 占比）。
达标再议 baseline compiler；不达标先修判据而非扩架构。
