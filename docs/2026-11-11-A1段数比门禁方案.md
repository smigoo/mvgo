**分界线：>10 个组件无一合格。**规划层日志（417bde2c 实测）：
`子组件规划完成 {"rawSectionsCount":2,"effectiveSectionsCount":2,"leafSectionsCount":26,"minFiles":28,...}`
——vision 只有 2 段，E1/拆分链把叶子炸到 **26 个**（minFiles=28 ⇒ 34 个 .vue），规划器自己就知道要 28 个文件，但没有任何闸门质疑这个数。

## 根因（文件：行号）

`subcomponent-planner.js:3444` `plan()` 的返回完全基于 `leafSections.length`，**没有「段数 vs 真值」合理性校验**：
- `:2542` 既有 `structure-source` 计数行已输出 `visionSections=1 figmaTop=3`（2026-11-10 刀1，纯观测）——文档 `2026-11-10-结构来源可视化与文本重叠门禁.md` 明确写了「为『段数过低触发重分析』判据留数据基线（本轮只观测不收紧）」；
- 爆炸的放大器在 `deriveNestedSections`（section-tree.js:2508，深度 ≤2 层全拆叶子）+ `shouldSplitInternally` 复杂度拆分，但产物组件数（≈minFiles）从未与任何真值比对照。

**查重结论**：续接 2026-11-10 方案预留的「段数合理性」方向（该文档刀1 已埋观测点），不是另起炉灶；`2026-11-08-段粒度与flex量纲治本.md` 治的是「段高量纲」，与本刀（段数）正交。

## 修法（单一闸门，两层动作）

新增纯函数 `auditSectionCountRatio`（放 `utils/section-plan-coverage.js`，与既有 coverage 判据同域）：

```
输入: { leafSections: N, figmaTop: T, visionSections: V }
基准 base = max(T, V)            // 真值段数：Figma 顶层业务段 或 vision 段，取大者
ratio = N / base
阈值: SECTION_COUNT_RATIO_LIMIT = 4   // 命名常量；依据=今日分布（合格 max=8/base≈3 ⇒ 2.7；爆炸 26/3≈8.7）
```

接线点 `subcomponent-planner.js` plan() 返回前（`:3440` reason 计算旁）：
- **ratio ≤ 4**：放行（现有行为不变），计数行 `🛡️ section-count-ratio：N/base=ratio verdict=pass`（恒打，0 也打）；
- **ratio > 4 且 ≤ 8**：**裁剪**——按 `elementCount` 降序保留 top-N（N = base×4），被裁段合并进最近祖先容器段（保持内容不丢），计数行 `verdict=trimmed trimmed=X`；
- **ratio > 8**：**BLOCK**（抛 `SECTION_COUNT_RATIO_BLOCKED`，带 N/base/ratio/top10 段清单），同 L0-B 硬闸形态（`_l0HardBlock` 通道既有消费）。

判据纪律：
- 零硬编码：`figmaTop` 复用 `:2536-2541` 既有口径（单一事实源），`visionSections` 复用 `sections.length`；
- 计数行恒打（含 pass），改验分离：spec 用 fixture 断言，真机验收看计数行；
- 阳性：417bde2c 形态（26 叶/2 段）必 BLOCK；阴性：0fa7f33d 形态（4 叶/3 段）必 pass。
