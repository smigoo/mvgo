# 段树「根节点当段」与 R11-B 失效 · 根因记录

> 日期：2026-11-10 · 状态：**根因已定位，修法待裁决（未实施）**
> 触发样本：`mc-max-1794274231287-45b0eceb`（环境监测 2:7879）— 用户截图：图表在上、tab 被挤到中间、图例散落

---

## 1. 根因 A：vision 段树把「组件根节点」当业务段

**证据链（全部离线可复现，不依赖并发日志）**

`c-env-monitor-45b0eceb/.checkpoint/analysis.json` → `subComponentPlan.effectiveSections`：

| 序 | 段 id | layout | type |
|---|---|---|---|
| 1 | `2:7879` | vertical | **chart** |
| 2 | `89:42` | horizontal | tabs |
| 3 | `chart-2:7898` | null | chart |

而 Figma 真实顶层结构是：

```
2:7879 (root, 420×186)
  ├─ 2:7880 VECTOR bg      y=865 h=186
  ├─ 2:7881 GROUP  header  y=875 h=28
  └─ 89:41  FRAME slot-con y=898 h=145
```

**问题**：第 1 段 id `2:7879` **就是组件根节点本身**，vision 把整张设计稿标成了 `type=chart`。产物因此生成 `ChartSection(flex:0.562) + TabsSection(0.097) + ChartChart(0.341)` —— 首段吃掉 56% 高度，tab 被压到中间，与用户截图完全一致。

**为什么既有判据没拦住**

`subcomponent-planner.js:285-289`：

```js
function isVisionComponentRootAnchor(sec, figmaRoot, siblingCount) {
  const rootId = String(figmaRoot?.id ?? '');
  return siblingCount > 1 && !!rootId && sectionAnchorKey(sec) === rootId;
}
```

注释明确「只在同层存在多个段时判错；单段组件以根节点为锚点仍合法」。而**单组件设计稿的根是唯一顶层节点** ⇒ `siblingCount=1` ⇒ 判据恒 false ⇒ 根被当作普通业务段进入装配。

**修法三选一（需裁决）**

| 方案 | 做法 | 风险 |
|---|---|---|
| **A1 丢弃根段** | 段树出口过滤 `id === rootId` 的段 | 标题/背景可能随根段一起丢（本例 header `2:7881` 在根段内） |
| **A2 展开根段** | 用根的 children（bg/header/slot）替换该段 | 需要 vision 段里带 children；本例 3 段是**平铺**的，无 children，展开无数据可用 |
| **A3 vision 层禁止** | 在 visual-parser 的 schema/prompt 里明确「段必须是 root 的子节点，禁止 root 自身」 | 治本但影响面大（vision schema 是全链路契约） |

**推荐 A3**（问题产生处），A1 作为出口兜底。**不做 A2**（本例无数据）。

## 2. 根因 B：R11-B 在 45b0eceb 上零执行

**证据**：离线对该产物跑 `relocateStrayTemplateRoots` → `changed=true`，`moved=["<div class="c-env-monitor-slot-con-tabs"..."]`；但磁盘 `index.vue` 首行仍是：

```html
<template>      <div class="c-env-monitor-slot-con-tabs" style="display:flex;gap:8px;...">
  ...
  <base-panel panelKey="default-panel">   ← base-panel 在后面
```

且 R11-A / R11-B 在该时间窗**日志均 0 条**。

**已排除**：R11-B 代码位置（`microcode-engineer.js:9632`）不在条件分支内，正常流可达；relocator 本身对该形态有效。

**待查**（两条都指向「中间层把成果吃掉」）：
1. `finalTruthFiles` 的 key 形态是否与 `p === 'package/index.vue'` 匹配（可能带前缀或只有 basename）；
2. 45b0eceb 是否走了另一条写盘路径（不经 execute 的 R11-B 段）。

**方法论教训**：`server.log` 并发下**不能按时间窗归因**——前一轮我把 `1:2426/1:2435`（另一任务的 `MainSection.vue`/`c-109c43-*`）当成重点车辆的段树，得出过错误结论。判据类结论必须用**离线重放**（产物 + analysis.json 固定输入）复核。
