# A4 高度比例「写而不消费」治理方案（2026-11-03）

## 一、背景

三个真机产物（均 `gitHash=2980bd7`，11:01 重启后生成）复现同一类病灶：**vision sections 的高度比例与 Figma 真值不符，产物表现为区块等高/等分、间距异常**。

| 任务         | 组件              | figma 根下                                   | sections | A4 写入         | 产物表现                 |
| ---------- | --------------- | ------------------------------------------ | -------- | ------------- | -------------------- |
| `c46c2631` | 重点车辆监测 (2:7952) | `[bg, header(28), slot(86)]`               | 2        | ✅ 0.492/1.508 | `flex:1` 写死（比例未消费）   |
| `7396124c` | 合作厂商 (38:3134)  | `[bg, header(10), slot-icon(787, 9 kids)]` | 4        | ❌ 0           | 三等分/内容撑高             |
| `eefcd3df` | 设备详情 (36:1693)  | `[bg, header(10), slot-icon(493, 9 kids)]` | 3        | ❌ 0           | 三等分 `flex:1.000/1/1` |

## 二、根因（消费链三处断点，均已定位到文件+行号）

### 断点① A4 触发面过窄

`figma-height-ratio.js` `applyFigmaSectionRatios` 的 ① 分支只读 `section.figmaNode || section.figmaNodeId`：

- 合作厂商/设备详情的根下内容容器名为 **`slot-icon`**，不匹配 `WRAPPER_RE=/^(slot-con|slot|frame|container|group|wrapper|panel)$/i`（精确匹配，`slot-icon`≠`slot`）⇒ `collectSectionRegions` 只得 2 个 region；
- 复合展开把 `slot-icon` 展开成 **9 个图元** ⇒ `pairRegions=10` ≠ sections 数（4/3）⇒ `orderMatched=[]` ⇒ 写入 0（实测 `applyFigmaSectionRatios` 返回 0）。

而合作厂商的 4 个 `sections.id` **恰好就是 figma 节点 id**（`38:3260/38:3137/38:3162/38:3206`），本可 1:1 直配，却因不读 `section.id` 而浪费。

### 断点② 执行顺序错位

`visual-parser.js:1467` 执行 A4，而锚点修复（写 `figmaAnchorId`）在 `1469` 的 `_normalizeAnalysisOutput` 内 ⇒ **A4 永远拿不到 R7 产出的 `figmaAnchorId`**。

### 断点③ 消费端数量校验过严

`figma-section-heights.js:388`：

```js
if (tags.length < 2 || tags.length !== orderedSections.length) return null;
```

重点车辆监测 A4 已写对比例（rawSections=2），但产物 `index.vue` 只有 **1 个大写子组件标签**（`<ContentSection>`；标题栏 section 未生成组件、tab 被提到 `base-panel` 外）⇒ `tags=1 ≠ 2` ⇒ `buildSectionHeightsMap` 返回 null ⇒ `fixInlineSectionFlex`（`resource-mounter.js:3111`）不改 ⇒ 产物 `flex:1` 写死。

**铁证**：`flexGrow`/`figmaHeightPx` 在两个 chunk prompt 中 grep **0 次** ⇒ LLM 看不到比例；唯一消费点是 resource-mounter 规则⑥，被断点③挡死。

## 三、实施记录（Loop 1–3 已完成，Loop 4 未实施）

> 三个 Loop 均遵循「治本非产物直改 + 可辩驳判据 + 阳性对照 + 真机日志计数行」纪律；
> 每个 Loop 的真机验证都用真实样本（`.checkpoint/figma.json` + `visual.json` + `context-shadow.json`）跑过，非仅单测。

### Loop 1（P0）A4 锚点候选增加 `section.id` 直配 —— ✅ 已实施

- **位置**：`figma-height-ratio.js` `applyFigmaSectionRatios`，新增 ①-β 分支 + stats out param；`visual-parser.js:1773` `_applyFigmaElementHeightRatios` 透传 stats 并打日志计数行（`A4 元素级高度比例已应用 { count, sectionStats }`）。
- **优先级**：`figmaNode/figmaNodeId` 直命中 > **根下直配（②-α）** > **`section.id` 直配（①-β）** > 顺序配对（②）。
  - 根下直配必须先于 id 直配：重点车辆监测的 `sections.id` 指向**内部子节点**（`2:7959` 小标题 28px、`136:122` sub-header 24px），若 id 直配优先会得到 28/24（错），而根下直配得 28/86（对）。
- **判据**：`figmaNodes.find(n => n._id === String(section.id))` 且 `effectiveH > 0`；**全部命中才采纳**（≥2 防孤例），有任一项未命中即整体放弃走原路径（语义 id 如 `attributes-section` 天然不命中）。
- **真机结果**：合作厂商 `[76,161,212,265]`，`stats.idDirect=4`（改前为 0）；flexGrow `[0.426,0.902,1.188,1.485]` 与 planner 修复值逐项一致。
- **测试**：`figma-height-ratio.spec.ts` 新增 3 例（阳性/阴性/顺序保护），家族 35/35 全绿。

### Loop 2（P0）`buildSectionHeightsMap` 单一内容段容错 —— ✅ 已实施（方案修订）

- **位置**：`figma-section-heights.js` 两处：
  1. `planLeaves.length >= 2` → `>= 1`（plan.effectiveSections 已由 planner 滤除 header，「计划里只剩 1 个内容段」是合法形态）；
  2. `:388` `if (tags.length < 2 || tags.length !== orderedSections.length)` → `if (tags.length !== orderedSections.length)`。
- **方案修订说明**：原计划「`tags === orderedSections-1` 且首项为 header 类则剥 header」未采用——`orderedSections.length === 1` 只可能来自 `planLeaves.length === 1`（raw fallback 长度恒 === rawSections.length ≥ 2；plan 路径长度必须 === planLeaves.length），因此「唯一标签 ↔ 唯一 plan leaf」是**严格相等校验的自然结果**，无需引入名字判据；数量仍必须严格相等（tags 2 ≠ plan 1 → fail-open 不猜）。
- **真机结果（端到端）**：重点车辆监测 `buildSectionHeightsMap` → `{ 'c-vehicle-monitor-content-section': 1.508 }`，`fixInlineSectionFlex` 把产物内联 `flex:1;min-height:0;` 改写为 `flex: 1.508 1 0;`（改前映射为 null、内联原样透传）。
- **测试**：`figma-section-heights.spec.ts` 新增 4 例（阳性/阴性 A 数量不等/阴性 B 量纲缺失/边界 C 单文件路径仍 fail-open），家族 21/21 全绿。

### Loop 3（P1）复合展开后再归并 —— ✅ 已实施（方案修订：WRAPPER_RE 不放松）

- **评估结论**：原计划「WRAPPER_RE 支持 `slot-*` 前缀」**不可行**——`slot-当日总流量` / `slot-车型分布` / `slot-流量预测` 等业务名 slot 自身就是 section（e1432017 复合展开契约，既有 spec 用例锁定），blanket 前缀匹配会把该用例整体打挂。
- **真正机制**：不是 WRAPPER_RE 匹配问题，是**顺序问题**——`mergeVisualRows` 只在复合展开**前**跑（`:512`，那时 regions=2 < sections，条件不成立），展开后 regions 已是图元级（10 个）却永远失去归并机会 → 10≠4/3 → fail-open 写入 0。
- **修法（Fix B）**：复合展开 + 剥离循环结束后，若 `pairRegions.length > restSections.length`，按**同一判据**（恰好相等才采纳）再跑一次 `mergeVisualRows`；不采纳则原样退回 1:1 跳过（不猜）。`mergeVisualRows` 为纯函数，二次调用零副作用。
- **真机结果**：设备详情 `[98,135,193]`（`stats.order=3`、`idDirectMiss=3`），**改前为 0**；合作厂商在语义 id 隔离下同路径得 `[76,161,212,265]`，与 Loop 1 ①-β 结果**逐项一致**（两条独立路径互为交叉验证）。
- **测试**：`figma-height-ratio.spec.ts` 改写设备详情用例（阴性→阳性）+ 新增归并不对齐阴性 + 合作厂商 ② 路径隔离交叉验证，家族 35/35 全绿。
