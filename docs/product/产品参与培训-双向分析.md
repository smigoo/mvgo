> 日期：2026-09-01

## 一、产品物料如何帮助我们生产（平台已有功能 + 可规划需求）

### 1.1 现状盘点：产品侧已有的"物料"

| 物料类型 | 具体内容 | 当前平台对接状态 | 价值 |
|---------|---------|----------------|-----|
| **Figma 设计稿** | 组件/页面设计、Auto Layout、样式变量、命名规范 | ✅ 已对接（Figma Connector + Vision 解析） | 最高——直接驱动组件生成 |
| **APIFOX 接口目录** | 接口定义、入参/出参、mock 数据 | ✅ 已对接（API 生成 + 组件接口绑定） | 高——自动生成 service 层 |
| **需求文档/PRD** | 功能描述、业务规则、交互说明 | ✅ 已对接（文档驱动组件生成管线） | 中高——驱动 Lite 生成 + 接口生成 |
| **组件规范文档** | 微码 declare.json / css-vars.js / 一体化扩展点 | ⚠️ 部分对接（管线内置规范，但无产品侧输入入口） | 高——决定生成质量 |
| **用户研究/反馈** | 访谈记录、NPS、使用痛点 | ❌ 未对接 | 中——指导管线优化方向 |
| **竞品分析** | 功能对比、定位分析 | ❌ 未对接 | 低——间接影响 |
| **业务线需求池** | 各业务线组件需求、优先级 | ❌ 未对接 | 中——指导共享库建设 |

### 1.2 已能直接利用的产品物料（立即可用）

#### ① Figma 设计稿 → 组件生成（P7/P11 已覆盖）

**产品侧需要做的：**
- 设计稿图层命名规范（`bg-*`、`icon-*` 等），确保 Figma Connector 能正确解析
- Auto Layout 属性完整（`layoutMode`/`primaryAxisSizing`/`counterAxisSizing`），避免 `pruneRedundantFields()` 误删
- 组件级设计稿标注尺寸、颜色、间距真值（Vision 解析 fallback 不可靠）

**平台已有能力：**
- Figma URL 粘贴 → 自动解析节点树 + 下载资源 → Vision 视觉解析 → Layout Reviewer 审查 → Style Mapper 样式映射 → Vue3/Microcode Engineer 生成
- 资源映射 `downloadStatus` 契约保证"已下载=已引用"
- 质量门禁 L0-B 自动校验规范/编译/结构

**产品参与培训的价值：**
- 产品了解 Figma 规范后，能在设计阶段就规避"生成不出来"的问题
- 产品可推动设计团队统一 Figma 命名规范，提升全团队生成成功率

#### ② APIFOX 接口目录 → 接口生成 + 组件绑定（P22 已覆盖）

**产品侧需要做的：**
- 维护 APIFOX 目录的完整性（接口定义、字段类型、枚举值）
- 需求文档中明确标注"需要对接哪些接口"

**平台已有能力：**
- API 接口生成页：绑定 APIFOX 目录 → 自动生成 service 函数 + 类型定义 + mock 数据
- 组件生成时自动注入 APIFOX 字段映射（ApiBindingWizard）
- 下载的 `.ts`/`.js` 文件可直接拷贝进工程

**产品参与培训的价值：**
- 产品了解 APIFOX 对接流程后，能在需求阶段就准备好接口定义
- 减少"组件生成了但接口没对齐"的联调返工

#### ③ 需求文档 → Lite快速生成 + 文档驱动管线

**产品侧需要做的：**
- 需求文档结构化（模块划分、字段说明、交互说明）
- 提供页面截图或低保真原型

**平台已有能力：**
- Lite 模式：截图/需求 → 秒级出简单布局 + 基础交互 + 图表
- 文档驱动管线：doc → microcode config → component code
- 需求文档拆分 → 多组件批量生成（Page Generator）

**产品参与培训的价值：**
- 产品可用 Lite 模式快速验证需求可行性，再决定是否投入完整版
- 产品写需求时就能预判"哪些能生成、哪些需要手写"

### 1.3 可规划的需求（产品参与后能推动的）

#### 需求 1：产品规范输入入口（P0）

**痛点：** 微码规范（declare.json / css-vars.js / 业务事件/状态配置）目前只有开发知道，产品不了解、也无法参与定义。

**方案：**
- 在平台增加「规范配置」入口，产品可上传/编辑组件规范文档
- 规范文档结构化（字段名、类型、默认值、业务含义）
- 生成管线读取规范文档，自动注入 declare.json / css-vars.js

**产品价值：** 产品定义的规范直接变成生成产物，减少"开发理解偏差"
**工程成本：** 前端入口 + 后端解析 + 管线集成，约 3 人周

#### 需求 2：需求池 → 组件需求映射（P1）

**痛点：** 各业务线的需求分散在 Jira/飞书/微信，平台不知道"哪些组件是高频需求"。

**方案：**
- 产品侧维护"组件需求池"（需求描述、业务线、优先级、使用场景）
- 平台分析需求池，识别高频模式，沉淀为共享模板
- 需求池与平台任务中心打通（需求 → 生成任务 → 产物关联）

**产品价值：** 需求直接驱动组件库建设，平台产能聚焦高价值组件
**工程成本：** 需求池管理页 + 任务关联 + 分析看板，约 5 人周

#### 需求 3：用户研究反馈 → 管线优化闭环（P1）

**痛点：** 管线质量问题（还原度不足/门禁 BLOCK/生成失败）只有开发知道，产品不了解用户真实痛点。

**方案：**
- 平台暴露"生成质量数据"（成功率、BLOCK 原因、重试次数、用户评分）
- 产品侧可查看所有质量指标，识别"用户最痛的点"
- 产品驱动管线优化优先级（数据驱动，而非开发自嗨）

**产品价值：** 产品用数据决定管线优化方向，避免"修了没人用的问题"
**工程成本：** 质量数据埋点 + 看板页，约 2 人周

#### 需求 4：PRD → 组件生成需求拆解（P2）

**痛点：** 产品写的 PRD 是"业务语言"，开发/平台需要"技术语言"（组件名、字段、接口）。

**方案：**
- 产品上传 PRD → 平台 AI 自动拆解为"组件需求清单"（组件名、类型、输入源、接口绑定）
- 产品确认拆解结果 → 一键批量生成
- 拆解规则可配置（按业务线/模块/优先级）

**产品价值：** 产品写的 PRD 直接变成生成任务，减少"翻译成本"
**工程成本：** AI 拆解引擎 + 确认交互 + 批量生成，约 8 人周

## 二、如何帮助产品用我们的平台（需求设计）

### 2.1 产品使用平台的典型场景

| 场景 | 产品角色 | 平台能力 | 当前支持度 | 需要补充 |
|-----|---------|---------|----------|---------|
| **验证设计可行性** | 产品看 Figma 稿，想知道"这个能不能生成" | Lite快速生成 | ⚠️ 有，但产品不知道 | 培训 + 引导 |
| **确认接口对接** | 产品写需求，需要知道"组件需要哪些接口" | APIFOX 绑定 + 接口生成 | ✅ 已有 | 产品侧 APIFOX 维护规范 |
| **验收生成产物** | 产品看生成的组件，确认"还原度/功能对不对" | Playground 预览 + 质量门禁 | ⚠️ 有，但产品不会用 | 产品视角的验收指引 |
| **提组件需求** | 产品想要一个新组件，不知道去哪提 | 无（目前只有开发知道平台） | ❌ 缺失 | 需求提交入口 |
| **跟踪组件状态** | 产品想知道"我提的组件生成到哪了" | 任务中心 | ⚠️ 有，但面向开发 | 产品视角的任务看板 |
| **复用已有组件** | 产品想知道"有没有现成的组件可以用" | 共享组件库 | ⚠️ 有，但无搜索/浏览 | 组件库目录页 |

### 2.2 产品视角的需求设计

#### 需求 A：产品专属入口页（P0）

**目标：** 产品登录后看到的不是"开发者界面"，而是"产品工作台"。

**功能：**
- **我的需求**：我提交的组件需求列表（状态：待生成/生成中/已完成/需修改）
- **组件库浏览**：按业务线/模块/类型浏览已有组件（搜索 + 标签过滤）
- **质量看板**：各业务线组件生成成功率、BLOCK 原因分布、用户评分
- **快速生成**：Lite 模式快捷入口（贴截图/需求 → 秒级预览）

**界面草图：**
```
┌─────────────────────────────────────────────┐
│  感智晓界工坊 · 产品工作台                    │
├──────────────┬──────────────────────────────┤
│  我的需求     │  快速生成                     │
│  ┌─────────┐ │  ┌─────────────────────────┐ │
│  │ 待生成 3 │ │  │ [贴 Figma URL / 截图]    │ │
│  │ 生成中 1 │ │  │ [需求文档]               │ │
│  │ 已完成 5 │ │  │ [开始生成]               │ │
│  └─────────┘ │  └─────────────────────────┘ │
│              │                              │
│  组件库      │  质量看板                     │
│  ┌─────────┐ │  ┌─────────────────────────┐ │
│  │ 图表类 8 │ │  │ 成功率 78% ████████░░   │ │
│  │ 表单类 5 │ │  │ BLOCK 原因:             │ │
│  │ 布局类 3 │ │  │ · LESS 编译 32%         │ │
│  │ [搜索]   │ │  │ · 规范违规 28%          │ │
│  └─────────┘ │  │ · 资源缺失 18%          │ │
│              │  └─────────────────────────┘ │
└──────────────┴──────────────────────────────┘
```

**与开发版差异：**
| 维度 | 开发版（当前） | 产品版（新增） |
|-----|-------------|-------------|
| 入口 | 组件生成页（技术导向） | 产品工作台（业务导向） |
| 任务中心 | 技术日志、报错行列 | 状态卡片、业务语言描述 |
| 组件库 | workspace 目录（文件级） | 可视化目录（卡片级） |
| 质量门禁 | 报错详情、代码上下文 | 成功率、BLOCK 原因分布 |

**工程成本：** 前端工作台页 + 后端需求管理 API + 组件库目录页，约 5 人周

#### 需求 B：需求提交表单（P0）

**目标：** 产品有一个标准入口提交"我要一个新组件"。

**表单字段：**
| 字段 | 类型 | 说明 |
|-----|------|-----|
| 组件名称 | text | 中文/英文，≤ 20 字 |
| 业务线 | select | 下拉选择（隧道/设备/流量/...） |
| 组件类型 | radio | 图表/表单/布局/弹窗/其他 |
| 输入源 | radio | Figma URL / 截图 / 需求文档 / 无（从零设计） |
| 功能描述 | textarea | 组件要干什么（业务语言即可） |
| 接口需求 | text | 需要对接哪些接口（可选，留空则产品侧不填） |
| 优先级 | radio | P0 紧急 / P1 重要 / P2 一般 |
| 期望交付时间 | date | 可选 |

**提交后流程：**
1. 平台创建生成任务（状态：待生成）
2. 开发确认需求（可补充技术细节）
3. 平台执行生成（状态：生成中）
4. 生成完成 → 产品验收（状态：已完成 / 需修改）
5. 需修改 → 退回平台重新生成 / 开发手动修复

**工程成本：** 表单页 + 任务状态机 + 通知机制，约 3 人周

#### 需求 C：产品视角的验收指引（P1）

**目标：** 产品拿到生成产物后，知道"看什么、怎么判"。

**内容：**
- **还原度检查清单**（5 项）：
  1. 布局结构是否与 Figma 一致（网格/间距/对齐）
  2. 颜色/字体是否与设计稿一致
  3. 图标/背景图是否完整加载
  4. 图表数据是否占位正确（不关心真实数据，关心结构）
  5. 交互元素是否可见（按钮/tab/输入框）

- **功能检查清单**（3 项）：
  1. 接口字段是否绑定（看 Playground 网络请求）
  2. 数据展示是否正确（mock 数据 vs 真实数据）
  3. 响应式是否生效（拖拽窗口看布局变化）

- **不合格处理方式**：
  - 还原度问题 → 平台重新生成（附 Figma 修正）
  - 功能问题 → 开发介入（接口对接/逻辑修复）
  - 规范问题 → 平台自动修复（门禁重试）

**工程成本：** 指引文档 + 验收页 UI，约 1 人周

#### 需求 D：组件库可视化目录（P1）

**目标：** 产品/开发都能快速找到"有没有现成组件"。

**功能：**
- 卡片式展示（组件名 + 缩略图 + 业务线 + 类型标签）
- 搜索（名称/描述）+ 过滤（业务线/类型/状态）
- 详情页（组件代码预览 + declare.json + 使用示例）
- "基于此组件生成"按钮（复制 + 微调）

**工程成本：** 组件库页 + 缩略图生成 + 搜索索引，约 4 人周

#### 需求 E：培训 deck 产品版（P0，本次可交付）

**目标：** 现有培训 deck 面向开发，需要一版面向产品。

**差异点：**
| 维度 | 开发版（现有） | 产品版（新增） |
|-----|-------------|-------------|
| 核心概念 | 微码/Vue3/一体化技术规范 | 平台能力边界（能生成什么/不能生成什么） |
| 使用流程 | 技术步骤（贴 URL → 选类型 → 生成） | 业务场景（验证设计 → 提需求 → 验收） |
| 质量门禁 | 报错详情、代码上下文 | 成功率、BLOCK 原因、产品怎么处理 |
| 接口对接 | APIFOX 配置、字段映射 | 产品侧需要准备什么（接口定义/字段说明） |
| Playground | Monaco 编辑器、代码修改 | 预览验证、验收 checklist |
| 交付 | Git 推送、产物集成 | 验收标准、不合格处理流程 |

**工程成本：** 培训 deck 产品版 HTML（复制现有 deck 改写内容），约 0.5 人周

## 四、优先级总结

### 4.1 短期可交付（本次培训前后，1-2 周）

| 需求 | 优先级 | 成本 | 价值 |
|-----|-------|-----|-----|
| 培训 deck 产品版 | P0 | 0.5 人周 | 产品听懂、知道能干什么 |
| 产品侧 Figma 规范文档 | P0 | 0.5 人周 | 提升生成成功率 |
| 产品侧 APIFOX 维护规范 | P1 | 0.5 人周 | 减少接口联调返工 |

### 4.2 中期规划（1-2 个月）

| 需求 | 优先级 | 成本 | 价值 |
|-----|-------|-----|-----|
| 产品工作台（需求管理 + 快速生成） | P0 | 5 人周 | 产品专属入口，降低使用门槛 |
| 需求提交表单 | P0 | 3 人周 | 标准化需求提交流程 |
| 产品验收指引 | P1 | 1 人周 | 产品知道"怎么验收" |
| 组件库可视化目录 | P1 | 4 人周 | 减少重复开发 |

### 4.3 长期演进（3-6 个月）
