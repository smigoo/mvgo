# 工作台功能迁移与易用性 PRD

> 版本：v1.1 · 2026-09-30
> 范围：`/workbench` 工作台（对话式 AI 组件开发入口）
> 状态：R1-R23 已全部落地（未部署）· 待部署验证

---

## 1. 背景与目标

### 1.1 现状问题

| # | 问题 | 影响 |
|---|------|------|
| 1 | 工作台 10 个对话工具里 6 个是假实现（返回写死/空壳），用户以为能用却拿不到真结果 | 信任崩塌，工作台沦为「演示壳」 |
| 2 | 6 个假工具对应的后端服务其实已存在（统计/修改器/Apifox/工作流），只是没桥接 | 能力闲置，做了却没接线 |
| 3 | 生成完成后不写回「当前组件 id」，后续「改它/绑它/下它」没有锚点 | 用户被迫手动复制 sessionId |
| 4 | 首屏无引导，用户不知道「能干嘛、怎么开始」 | 上手门槛高，留存差 |
| 5 | 生成过程进度不可见、失败只报裸错误无法重试 | 挫败感强，反复打断 |
| 6 | 网站上已有成熟功能（组件库/任务中心/接口生成）与工作台割裂，无法跳转衔接 | 能力孤岛，用户来回切换 |

### 1.2 设计目标

- **能力闭环**：6 个假工具全部接真后端，工作台从「演示壳」变「真工具」。
- **产物稳定**：生成结果写回会话上下文，后续操作有明确锚点。
- **降门槛**：首屏引导 + 上下文感知 + 进度可见 + 失败可重试 + 结果可续做。
- **能力衔接**：工作台与网站既有功能打通，第二档能力通过跳转完成。

### 1.3 核心原则

```
能力闭环 = 每个对话工具背后都有真服务，杜绝假实现
单一锚点 = 会话始终知道「当前在操作哪个组件」
渐进引导 = 用户第一次进来就知道能干嘛、点哪、结果是什么
失败可解释 = 任何失败都给出原因 + 下一步建议 + 一键重试
```

## 4. 阶段一：能力闭环（R1-R6）

> 目标：把 6 个假工具全部桥接到真实后端服务，杜绝写死与空壳。

### R1 统计查询落地 ✅（本版本已实现）

- **用户故事**：作为用户，我想问「我这周生成了多少组件、成功率多少」，就能拿到我自己的真实统计，而不是写死的数字。
- **实现要点**：`get_generation_stats` 调用 `TaskStatsService.myDashboard(userId, filter)`，时间范围映射 `today/week/month/all` → `custom(今日)/week/d30/custom(全部)`，返回 `overview{totalTasks, completedTasks, failedTasks, successRate, avgDurationMs, totalTokens, totalCost}` + `windowLabel`。
- **验收标准**：
  - 对话返回真实统计卡，非写死 47/42/3/2。
  - 成功率/耗时/token/成本来自真实 overview。
  - 无任务时返回 0 与「—」，不报错。

### R2 组件修改落地

- **用户故事**：作为用户，我想在对话里说「把标题改成蓝色、加个圆角」，就能直接改当前组件。
- **实现要点**：`modify_component` 桥接 `DemoService`（Playground 自然语言修改器），复用 LangGraph 修改链路。
- **验收标准**：对话发出修改指令 → 返回修改结果（新代码/新预览）→ 预览可刷新看到变化。

### R3 API 绑定落地

- **用户故事**：作为用户，我想说「给这个组件绑定设备监控接口」，就能把数据 slot 绑到后端 API。
- **实现要点**：`bind_api_to_component` 桥接 `ApifoxService`，复用 ApiBindingWizard 的绑定逻辑（Apifox 目录绑定 + device monitor API）。
- **验收标准**：对话触发绑定 → 返回绑定结果 → 组件数据源生效。

### R4 工作流执行落地

- **用户故事**：作为用户，我想执行一个预设工作流/配方，对话就能真跑并返回进度。
- **实现要点**：`execute_workflow` 桥接 `WorkflowService`，返回真实执行状态与进度。
- **验收标准**：传入 workflowId → 真实执行 → 返回 status + 可查询进度。

### R5 GitLab 交付落地

- **用户故事**：作为用户，我想说「把这个组件交付到 GitLab」，就能真提交代码。
- **实现要点**：`push_to_gitlab` 桥接 GitLab 交付服务（含质量门禁），返回 MR/commit 链接。
- **验收标准**：对话触发交付 → 返回真实 commit/MR 链接。

### R6 批量生成落地

- **用户故事**：作为用户，我想一次提交多个截图/Figma 链接批量生成组件。
- **实现要点**：`batch_generate` 循环调用截图/Figma 生成工具，返回批量进度卡。
- **验收标准**：多个输入 → 多个真实任务排队 → 返回 batchId + 进度可查询。

## 5. 阶段二：产物稳定（R7）

### R7 当前组件 id 回写

- **用户故事**：作为用户，我生成完组件后，想直接说「改这个组件」「绑定这个组件」，而不用手动复制 sessionId。
- **实现要点**：生成工具成功返回后，把 `componentId`/`sessionId` 写回工作台会话上下文（currentComponentId），后续 `modify/bind/push` 默认作用于它。
- **验收标准**：
  - 生成完成后，后续「改/绑/下」指令无需显式传 id 即可命中当前组件。
  - 切换组件后锚点跟随更新。

## 6. 阶段三：降门槛（R8-R12）

### R8 首屏引导

- **用户故事**：作为新用户，我第一次进来就能看懂「能干嘛、怎么开始」。
- **实现要点**：欢迎语 + 4 个真工具快捷入口卡片（从截图生成/从 Figma 生成/查组件/查任务）。
- **验收标准**：首屏有可见入口，点击即触发对应工具，无需打字。

### R9 上下文感知

- **用户故事**：作为用户，我不想重复输入「刚才那个组件」。
- **实现要点**：自动带入最近生成的组件与最近任务，作为对话上下文提示。
- **验收标准**：提到「刚才的组件」时能正确命中。

### R10 进度可见

- **用户故事**：作为用户，生成过程中我想看到进度，而不是干等。
- **实现要点**：复用 SSE 进度链路，展示阶段提示 + 进度条。
- **验收标准**：生成中实时展示阶段与进度，完成后自动刷新。

### R11 失败可解释可重试

- **用户故事**：作为用户，失败时我想知道原因，并能一键重试。
- **实现要点**：失败返回「原因 + 下一步建议 + 重试」卡片，而非裸报错。
- **验收标准**：任何失败都有可读原因与重试入口。

### R12 结果可续做

- **用户故事**：作为用户，生成完成后我想直接续做「改样式/绑 API/下代码/再来一个」。
- **实现要点**：生成结果卡附带续做动作按钮。
- **验收标准**：结果卡有续做按钮，点击进入对应动作。

## 13. 阶段七：产物信任（R19-R20）

> 目标：复用后端**已存在**的视觉对照、质量门禁、快照版本能力，接进结果卡，建立「生成结果可信可追溯」的心智。核心是接线 + 补少量小接口，不重造业务逻辑。

### R19 结果卡「体检」徽章 ✅（已落地）

- **用户故事**：作为用户，生成完组件后，我想一眼看到「还原度多少、过没过门禁」，而不是盲目相信结果。
- **实现要点**：
  - 结果卡 completed 态加「体检」动作（复用 R12 的 `emit('action')` 链路）。
  - 前端调两个**已有接口**：
    - `POST /api/component/:id/analyze-visual`（`ComponentAnalysisService#analyzeComponent`）→ `visual.overallSimilarity` + `visual.issues[]` + `recommendation.nextStep`。
    - `POST /api/tasks/:sid/code-snapshots/:rev/validate`（`SnapshotQualityService#validateRevision`）→ `pass` + `blockCount` + `issues[]`（含 `file/line/column/snippet`）。
  - 徽章展示：`视觉相似度 X%` + `门禁 pass / block N`；点击展开 issues，复用行列号 + 代码片段定位。
- **复用**：`ComponentAnalysisService`、`SnapshotQualityService`（零后端业务改动）。
- **缺口**：仅前端接线。⚠️ `analyze-visual` 需请求传视觉模型配置（`config.visionApiKey`），工作台调用时从 `toolCredentials` / `userAiConfig` 读取，缺则友好提示「去配置视觉模型」而非裸报错。
- **验收标准**：
  - 结果卡有「体检」入口，点击展示还原度百分比 + 门禁结论。
  - issues 可展开、可定位到文件与行列。
  - 缺视觉模型配置时给出引导文案，不报裸 500。

### R20 版本历史 + 一键回滚 ✅（已落地）

- **用户故事**：作为用户，我「改样式」改坏了，能退回上一版，而不是不敢改。
- **实现要点**：
  - 结果卡「历史」动作 → 版本列表 → 选版本 diff（复用 RightPanel 已有「版本历史对比」交互）→ 一键回滚。
  - 复用快照机制（`TaskCodeSnapshotService` 的 `getLatestManifest/getManifest/edit`）。
  - 补 **2 个小接口**：
    - `GET /api/tasks/:sid/code-snapshots/revisions`：列出该 session 全部 revision（时间倒序 + manifest 摘要）。
    - `POST /api/tasks/:sid/code-snapshots/:rev/rollback`：把指定 revision 置为当前指针，仅任务本人可操作。
- **验收标准**：
  - 版本列表可见（时间 + 摘要）。
  - 两版本可 diff 对比。
  - 回滚后当前产物/预览切到目标版本，指针持久化。

## 14. 阶段八：交付与复用（R21）

### R21 组件发布到公共池 + 交付统一入口 ✅（已落地）

- **用户故事**：作为用户，我想一键把组件发布给团队复用，或推到 GitLab，而不是在多个入口来回切换。
- **实现要点**：
  - 把 R12 的「下代码」升级为「交付」动作，弹层二选一：
    - **发布到公共组件池**：调 `POST /api/component/:id/publish`（`ComponentService#publishComponent`，已有 `visibility/sharedAt`）。
    - **推送到 GitLab**：复用 R5 `push_to_gitlab`。
  - 发布成功返回可分享预览链接（复用 schema `shared/sharedWith` 预留字段，补公开预览 URL 生成）。
  - 支持 `unpublish` 下架（已有 `POST /api/component/:id/unpublish`）。
- **验收标准**：
  - 结果卡「交付」弹层可选择发布 / 推送。
  - 发布后返回可分享链接，团队可访问。
  - 可下架，个人副本保留。

## 15. 阶段九：体验增强（R22-R23）

### R22 生成完成通知 + 消息编辑重发 ✅（已落地）

- **用户故事**：作为用户，生成耗时 3-4 分钟，我切走后想在完成时收到提醒；打错参数想改一个字重发。
- **实现要点**：
  - **通知**：复用现有 1.5s 轮询（`/api/tasks/status/:sid`），状态到 completed/failed 时触发浏览器 `Notification API`（纯前端，无后端）。
  - **编辑重发**：用户消息气泡加「编辑」→ 回填输入框改参数重发（复用 `sendMessage`）。
- **验收标准**：
  - 后台生成完成时收到浏览器通知（授权后）。
  - 用户消息可编辑重发。

### R23 结果反馈（👍/👎，数据飞轮） ✅（已落地）

- **用户故事**：作为用户，我点 👍/👎 表达结果好坏，平台据此越用越准。
- **实现要点**：
  - 结果卡加 👍/👎 反馈入口。
  - 补反馈落库接口，写入（组件、版本、反馈类型、可选备注）。
  - 喂给 self-optimizer / 8 维评分引擎做自我优化（对应演进路线「数据飞轮」）。
- **验收标准**：
  - 结果卡可点 👍/👎，状态持久化。
  - 反馈数据可被评分引擎消费（字段对齐）。

## 16. 执行顺序（Now / Next / Later）

```
【Done】 R1-R23 能力闭环 + 易用性 + 产物信任 + 交付复用 + 体验增强（已落地，未部署）
【Next】 部署验证：重启后端（:13030）+ 刷新前端，逐项冒烟 R19-R23
```

> 每个需求独立可验收、独立可回滚，按序号依次执行，逐步验证后再进入下一项。
> R19-R23 的原则是「复用已有后端能力优先，接线优先于造新」：R19 复用 analyze-visual + validate（零后端业务改动）；R20 补 listRevisions/rollback 两接口（快照 last-good 指针重定向）；R21 复用 publish（补 sessionId→组件 _id 反查）；R22 纯前端（Notification + 编辑回填）；R23 补 1 个反馈落库接口（按月聚合 JSON）。
