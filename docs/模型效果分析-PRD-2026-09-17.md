- 作者：产品通
- 日期：2026-09-17
- 状态：P0 + P1 + P2 全部完成（2026-09-17）
- 关联模块：用户管理（UsersView）、生成管线（token-usage / usage-export / tasks）

---

## 1. 问题陈述

平台接入了多家模型供应商（claude / gpt / qwen / deepseek / gemini / glm / minimax / kimi 等），同一能力存在多个候选模型，且**同一个模型可能挂在不同 baseURL（具体代理）上**，效果和速度可能不同。管理员目前面临两个无法回答的问题：

> 1. 哪个模型（具体代理 baseURL）效果好、速度快？
> 2. 所有用户的任务明细（谁、什么时候、用什么模型、成功失败、耗时）在哪看？

不解决此问题的代价：模型选型拍脑袋、成本失控无法归因、供应商/端点切换无数据支撑、用户行为无法全局复盘，平台「大模型路由降成本」的演进方向（方向 2）无法落地。

**数据现状（实测 2026-09-17，423 任务）**：

| 数据源 | 数量 | 关键字段 | 缺口 |
|---|---|---|---|
| `token_usages`（Mongo）| 727 条 | model / token / duration / sessionId | **无 userId、无 baseURL** |
| `tasks.json` configSnapshot | 361/423 | textModel / visionModel / textBaseURL / visionBaseURL / status / duration / userId | 含失败任务 |
| `tasks.json` completionModels | 250/423 | textModel / visionModel | **仅成功任务** |
| 快照 manifest.files | — | path / size / lines（文件数、行数）| 旧快照可能缺 lines |
| `components`（Mongo）| 239 | taskId（=sessionId，1:1）→ 组件数 | — |

**实测效果数据（configSnapshot 归因）**：

```
按模型成功率：   deepseek-v4-flash 87% · qwen3.7-plus 77% · claude-opus-4-8 68% · claude-sonnet-5 66% · gpt-4o 0%
按代理成功率：   api.deepseek.com 87% · dashscope compatible-mode 77% · code1 claude/ultra 68% · code1 claude/super 66%
```

结论：**「效果好」就是成功率，且模型间、代理间都有显著区分度**，是有效的选型依据。

**现有接口缺口**：`GET /api/tasks` 注释声称「admin 可查看全部」，但实现 `if (userId) return task.userId === userId` 总是按当前用户过滤，admin 并未真正看全部（注释与实现不符）。底层 `getAllTasks` 已支持「userId 为空返回全部」，仅缺 admin 入口。

## 2. 目标

**用户目标**：
1. 管理员能查看**所有用户的任务日志**（明细：谁、何时、模型、baseURL、token、文件数、行数、耗时、成功失败）。
2. 管理员能对比每个「模型 × 代理」的**效果（成功率）**和**速度（耗时 p50/p90）**。
3. 管理员能按时间窗过滤，观察效果/速度/用量的变化趋势。

**业务目标**：
1. 支撑「大模型路由降成本」决策（数据飞轮第一环）。
2. 让效果（成功率）、速度（耗时）、成本（token）都能归因到模型和代理两个维度。
3. 全局任务复盘能力（所有用户行为可观测）。

**成功标准**：管理员能在 30 秒内回答「哪个模型 + 哪个代理效果最好、最快」，以及「某个用户最近在用什么模型、成功率如何」。

---

## 3. 非目标（Non-goals）

1. **不做质量评分**：成功率 + 失败分类是本模块的「效果」代理指标，不引入视觉还原度打分等重质量体系（后续可挂 `qualityGate` 钩子）。
2. **不做「单模型独占贡献」拆分**：一个组件由 text+vision 协作产出，不拆贡献比例（见 §6）。
3. **baseURL 不独立成页**：作为「模型 × 代理」聚合视图的一部分（不是 hover 下钻）。
4. **不做用户抽屉里的「生成耗时」**：耗时是「模型 × 任务」的属性，不是「人」的属性，从用户抽屉移除。
5. **不做任务明细的写操作**：任务日志只读，不在此模块做任务重试/删除（复用 TaskDetail 现有能力）。
6. **不阻塞在历史数据精确回填**：历史 token 记录无法精确到「调用级」baseURL，接受任务粒度回填（见 §8）。

## 4. 用户故事

- 作为**平台管理员**，我希望查看所有用户的任务日志，以便全局复盘谁在何时用什么模型做了什么。
- 作为**平台管理员**，我希望对比每个「模型 × 代理」的成功率和耗时 p50/p90，以便选型与降成本。
- 作为**平台管理员**，我希望看到每个模型/代理的 token 量、代码文件数、代码行数、已用时间，以便评估产出效率。
- 作为**平台管理员**，我希望区分「质量失败 vs 环境失败」，以便把失败正确归因到模型而不是环境。
- 作为**平台管理员**，我希望按时间窗过滤，观察模型效果/速度的变化趋势。
- 作为**平台管理员**，我希望在用户抽屉里看到这个人的组件/接口产出与常用配置（baseURL/模型），而不是耗时，以便快速了解用户画像。

**边界与空态**：
- 无数据时显示空态提示。
- 旧快照缺 lines 时，代码行数显示 `-`，不误导为 0。
- 样本量 < 3 的模型/代理，成功率标注「样本不足」，避免小样本误判。

## 5. 模块结构（两个视图）

管理员「任务统计」模块，一个入口两个 tab，共用同一份任务台账（tasks.json）：

```
任务统计（管理员，新入口）
├── Tab 1：任务日志（明细）
│     所有用户任务列表，每行一个任务：
│     用户 · 时间 · 类型 · 模型(text/vision) · baseURL · token · 文件数 · 行数 · 耗时 · 成功/失败
└── Tab 2：模型效果对比（聚合）
      模型 × 代理，每行：
      模型 · baseURL · 成功率 · 耗时 p50/p90 · token 量 · 文件数 · 行数 · 组件数
```

两个视图的关系：**任务日志 = 事实表明细，模型对比 = 在明细上聚合**，口径一致（见 §6）。

## 6. 归因规则与口径（核心定义）

### 6.1 归因数据源（生命线）

**必须用 `configSnapshot`（配置级快照）归因模型和 baseURL**，不能用 `completionModels`。

> 陷阱：`completionModels` 只记录「实际完成调用的模型」，失败任务没有该字段 → 用它归因，失败样本被静默丢弃，成功率虚高到 100%（已实测）。`configSnapshot` 是任务配置快照，无论成败都有，是唯一正确的效果归因源。

### 6.2 组件产出归因

一个任务 = 一次生成 = 1 组件，记到「该任务实际调用的模型去重集合」，语义为**「参与产出」**：

```
任务 A：text=sonnet-5 + vision=opus-4-8  → sonnet-5 参与 +1，opus-4-8 参与 +1
任务 B：unified 同模型                    → 该模型 +1（去重）
```

### 6.3 口径差异（必须标注）

| 指标 | 归因粒度 | 是否重叠 |
|---|---|---|
| token 量 | **调用级精确**（token_usages.model）| 无重叠 |
| 代码文件数 / 行数 | **任务级参与**（快照产出）| text/vision 有重叠 |

> 后果：token 是「它实际消耗的」，文件/行数是「它参与的」。界面列头需 tooltip 标注口径，避免用户困惑「为什么所有模型行数之和 ≠ 总行数」。

### 6.4 效果（成功率）定义

- 成功率 = `completed ÷ (completed + failed)`，**排除 cancelled**。
- **失败必须分类**（否则冤枉模型）：

| 类别 | 示例（实测 147 失败）| 归因 |
|---|---|---|
| 质量失败 | 质量检查未通过（44）、输出截断（5）| 归模型 |
| 环境失败 | 图片格式（16）、服务重启（12）、API Key（9）、超时（2）| 不归模型 |
| 其他 | 管线 bug（如 collectLeafSections 未定义）| 不归模型 |

- 界面同时展示「总成功率」和「质量失败率（排除环境失败后的更准效果）」。

### 6.5 速度定义

耗时用 **p50 / p90**（非均值，避免长尾任务拉偏），数据源 `tasks.duration`（墙钟，含排队）。

## 7. 需求

### P0（必须，最小可用版本）

| 编号 | 需求 | 验收标准 |
|---|---|---|
| R1 | **任务日志（所有用户明细）**：管理员查看全部用户任务列表 | Given 管理员登录，When 打开任务统计，Then 看到所有用户的任务，每行含：用户/时间/模型/baseURL/token/文件数/行数/耗时/成功失败 |

| 编号 | 需求 | 验收标准 | 状态 |
|---|---|---|---|
| R6 | 失败分类展示（质量失败 vs 环境失败）| 每行可下钻看失败原因分类；model-compare 加「质量成功率」排除环境/其他失败 | ✅ |

> P1 实现说明：失败分类用关键词正则（环境→质量→其他 优先级）对 `task.error` 分类；时间窗后端 `task-stats.service` 复用 `resolveWindows`/`inWindow`，两个接口均接受 `?preset=&from=&to=`；R9 为纯前端客户端筛选，无后端改动。

### P2（治本 + 回填 + 趋势）— 已实现 2026-09-17

| 编号 | 需求 | 说明 | 状态 |
|---|---|---|---|
| R10 | `recordUsage` 补记 `userId` + `baseURL` | 让新 token 记录自带归属与端点，精确到调用级 | ✅ |

| R12 | 效果趋势（按时间维度画成功率/耗时曲线）| 观察模型稳定性 | ✅ |

> P2 实现说明：
> - **R10**：`token-usage.schema.ts` 加 `userId`/`baseURL` 可选字段；`token-tracker.service.ts` 的 `recordUsage()` 持久化新字段；`lite.service.ts`/`vue3.service.ts`/`phase2.service.ts` 三处调用点传参；`task-stats.service.ts` 的 `modelCompare()` 升级为三维聚合键 `(model, baseURL)`，使用 `$ifNull` 兼容历史数据。

> - **R12**：新增 `GET /api/task-stats/trends` 端点，支持按天/按周粒度聚合成功率/耗时/token/任务量；前端新增「效果趋势」Tab，用 SVG 折线图展示，支持悬停查看详情。

## 9. 成功指标

- **领先指标**：管理员打开任务统计模块的频率。
- **可观测结果**：30 秒内回答「哪个模型+代理效果最好、最快」；30 秒内定位「某用户最近的任务与模型」。
- **滞后指标**：降成本决策是否基于本模块（运营复盘确认）。
