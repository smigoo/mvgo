## 序 7 修改方案（先行，因为它是序 6 颜色接管的验收依赖）

> 逻辑依赖：颜色接管改完，怎么证明「颜色对了」？唯一办法是**渲染产物 vs 设计稿做像素比对**。所以序 7 是序 6 的验收前置。当前 BLOCK=0 ≠ 视觉正确，正因缺这道门禁。

### 7-A 渲染产物 vs 设计稿 · 像素级比对（核心，可独立落地）

**新增** `utils/render-fidelity-gate.js`（纯函数 + 可单测），复用 sharp：

```
compareRenderedVsDesign({ renderedPath, designPath }) → {
  score: 0~1,          // 结构相似度（SSIM 或分块直方图差）
  verdict: 'pass'|'warn'|'block',
  diffRegions: [...],  // 差异集中区域（供定位）
}
```

事实源：
- `renderedPath` = `*-rendered.png`（screenshot-renderer 已产出）
- `designPath` = `previewImage`（Figma 预览图，graph 里 `state.previewImage` 已有，`renderScreenshot` 已用它取 viewport 尺寸）

比对方法（**降级优先，不引入重依赖**）：
1. 两图 resize 到同一宽高（如 256×N），`removeAlpha` 后逐块（8×8）算亮度直方图差。
2. `score = 1 - 平均块差`。阈值分档：`≥0.85 pass`、`0.6~0.85 warn`、`<0.6 block`。
3. 只对「渲染非全白」（复用 `analyzeScreenshotPixels.blank` 判定）才比对；空白渲染直接 BLOCK（已有 RUNTIME-012）。

**接入点**：`screenshot-renderer.js#renderScreenshot` 的 `finalizePreviewResult` 里，`renderedImage` 非空且 `designPath` 存在时追加比对结果到 `runtimeGate.issues`（新 id：`VISUAL-001` 元素级差 / `VISUAL-002` 像素级差）。

**验收**：真机重生成后，`component-meta.json` 出现 `visualFidelity` 字段，好样本 pass、差样本（若有颜色/布局崩）warn/block。

### 7-B 元素级比对（阶段 D 完整版，可延后）

在 7-A 基础上，用 `*-rendered.png` 与 vision 的 section bbox 做元素级对账：
- 渲染截图中检测到的「视觉块」（边缘/连通域）数量 ≈ vision 识别的 section 数；
- 差距过大 → `VISUAL-003` 结构缺失。

此步依赖渲染截图质量稳定，建议 7-A 跑通真机后再做。

## 序 6 修改方案（颜色接管）

> 前提：序 6 的目标是「删 M5-10/THEME-\*」这类颜色后处理。但删后处理必须满足「颜色已由 assembler 确定性生成」——否则删了门禁，颜色错误/数据键类名化立即复发。分三步走，**每步可独立验收，且只有前一步归零才进入下一步**。

### 6-A 建 nodeId→fills 确定性事实源（提取层，已有 80% 底座）

现状 `_extractVisualMeta` 只对「资源节点」挂 `visualMeta.fillsSummary`。要「按 nodeId 绑定颜色」，需把**业务节点**（TEXT/FRAME 的非资源节点）也纳入。

**新增** `figma-connector.js#buildNodeColorIndex(figmaNodeData)`：
- 遍历所有节点，产出 `Map<nodeId, { fillsSummary, textColor, bgColor }>`。
- 复用现有 `_rgbaToHex` / `_gradientAngleDeg` / `_extractVisualMeta`，**不重复实现颜色算法**。
- 纯数据索引，供 assembler 消费。

### 6-B 颜色确定性装配（生成时接管，核心难点）

参考阶段 B 的 `healStatRowMemberPairing`（写盘前结构层接管）先例，新增 `roles/microcode/color-assembler.js`：

```
assembleNodeColors({ effectiveSections, nodeColorIndex, files }) →
  { files, applied: [...], diagnostics: [...] }
```

规则（宽进严出，不满足即 no-op）：
1. 对每个 section，取其 `sourceNodeIds` → 从 `nodeColorIndex` 取该 section 的**文本色/背景色**真值。
2. 若 section 的文本色/背景色在产物 `<style>` 里是「槽位外字面量」→ 改为 `var(--colorX, <真值>)`（microcode）或 `@colorX`（vue3）。
3. 只处理「确定性可映射」的颜色（section 根 + 明确子元素），不猜嵌套。

**关键：这一步的「删 M5-10/THEME-\*」是最终目标，但必须 6-A + 6-B 真机归零（THEME 门禁连续 N 个样本 0 违规）后才删，否则按治理方案铁律「删探测器早于观测归零」违反纪律。**

### 6-C 删后处理（收敛，最后一步）

前置：6-B 真机连续样本 THEME-COLOR 违规 = 0。
执行：
1. 删 `theme-color-guard.js` 的调用（`code-structure-validator.js` L0-B 出口）。
2. 删 `file-writer.js#healSlotHexToVarRefs` / `healPresetLiteralDecls`（槽位 hex 变量化自愈）——它们被 6-B 取代。
3. 删 `code-healer.js` 里 THEME-SLOT-COLOR / THEME-PRESET-OVERRIDE 自愈。
4. 门禁/规则总数净下降（删减法收敛指标）。

## 风险与边界

1. **像素比对阈值需真机标定**：不同设计稿复杂度的合理分数区间未知，上线前用 162 份历史产物标定（好样本 vs 差样本分数分布），禁止拍脑袋定 0.85/0.6。
2. **颜色接管的「删」必须后置**：6-C 是删减法收敛动作，绝不能 6-A/6-B 未归零就删 THEME-*，否则颜色错误立即复发（历史实锤：删探测器早于观测归零）。
3. **颜色语义映射是本仓最难的确定性缺口**：Figma 的绝对色值（#333）如何映射到「主题槽位」（colorTextBase），目前靠 `theme-vars.less` 反查。6-B 若做不到 100% 确定性映射，就只对「可确定」的部分接管、其余保留 LLM + 门禁，**禁止半确定性混合**。
