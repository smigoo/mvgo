# 大屏布局快速生成 · 体验方案

> 2026-09-30 · 针对现有 `/screen` 大屏布局模块的体验重构方案
> 配套可交互原型：`outputs/screen-layout-ux-prototype.html`

---

## 一、问题诊断

对照 `frontend/src/views/screen-layout/` 与 `backend-node/src/screen-layout/` 的实际实现：

| # | 现象 | 代码位置 | 根因 |
|---|------|---------|------|
| 1 | 必须先摆好坐标，AI 才有用 | `screen-layout.controller.ts` 只暴露 `download` / `analyze-spatial` / `analyze-responsive` | **入口方向反了**：接口以「已设计好的 ScreenLayout」为输入，自然语言入口完全缺失 |
| 2 | 要懂「自适应模式」「gridSize」「snapToGrid」 | `index.vue:106-113`、`types/screen-layout.ts:7-19` | **实现细节当成了用户参数**，暴露层次错误 |
| 3 | 「XY 都自适应」做不到 | `types/screen-layout.ts:12` `outputScaleMode: contain \| fillWidth \| fillHeight \| none` | **能力缺口**：四种模式没有一种能双轴独立自适应 |
| 4 | 生成完看不到效果 | `download-responsive/:sessionId` 返回 ZIP | **反馈回路断在最后一米**，对比主线组件生成有预览，这里没有 |
| 5 | 改一句话要回编辑器重拖 | 无增量修改接口 | **无迭代闭环** |

### 最根本的一条：两套自适应哲学并存且互不相通

- `canvas.outputScaleMode` —— **整体缩放派**（把 1920×1080 画布缩放到容器）
- `layout-responsive-prompt.md` —— **流式布局派**（`fr` + `clamp()` + `minmax(0,1fr)` + 断点）

生成规则已经在往流式走了，UI 面板还停在整体缩放。用户看到的选择器和最后拿到的代码不是一回事 —— 这是困惑的总根源。

## 二、五种适配策略选型表

设计稿 16:9 投到 21:9 超宽屏的实际表现：

| 策略 | 实现 | 结果 | 变形 | 适用场景 |
|------|------|------|------|---------|
| `contain` | `scale(min(sw,sh))` | 等比铺满，留黑边 | 否 | 设计感优先，可接受黑边 |
| `cover` | `scale(max(sw,sh))` | 等比放大，裁掉边缘 | 否 | 有满屏背景图 |
| `stretch` | `scaleX(sw) scaleY(sh)` | 完全铺满 | **是** | 几乎不用（圆变椭圆、字变扁） |
| **`fluid`** | `fr` + `minmax(0,1fr)` + `clamp()` | 骨架弹性伸缩 | 否 | **推荐，默认** |
| **`hybrid`** | 骨架 fluid + 卡片 `aspect-ratio` 锁比 | 间隙吃掉多余空间 | 否 | **最稳**，图表类必选 |

**核心结论**：用户说的「XY 都自适应」，90% 想要的是 `fluid` / `hybrid`，而不是字面意义上的 `stretch`。UI 上**不应该出现 `stretch` 这个技术选项**，而应该问「窗口变形时你希望发生什么」。

## 三、参数契约：AI 生成大屏必须知道的六类参数

| # | 类别 | 参数 | 作用 | 缺失时默认 | 是否反问用户 |
|---|------|------|------|-----------|-------------|
| 1 | 基准 | `designWidth` / `designHeight` | 换算比例、判定是否变形 | 1920×1080 | 否，默认值 |
| 2 | **适配策略** | `fitMode` | **决定变形与否** | `fluid` | **是**（用图示选项，不用术语） |
| 3 | 骨架 | `columns[].fr`、`zones[].fr` | 空间怎么分 | 三列经典 | 否，给一版可改 |
| 4 | 固定区 | `header` / `footer` 是否启用、高度 | 决定剩余空间 | 无头尾 | 否 |
| 5 | 间隙 | `gap` / `padding` | **吃掉多余空间的关键** | `clamp()` 自适应 | 否 |
| 6 | **兜底** | `overflow`、`minW/minH`、图表是否锁比 | **极端比例时怎么办** | 隐藏滚动 + 最小尺寸 | **是**（仅极端比例时问） |

**关键洞察：只有第 2 和第 6 类值得打断用户。其余四类一律给默认值 + 高亮可改。** 追问次数直接决定体验好坏 —— 每多问一句，流失一批用户。

## 四、用户话术 → 参数映射表

| 用户说 | 解析为 | 处理要点 |
|--------|--------|---------|
| 「1920×1080」 | `design: {w, h}` | ⚠️ 这是**基准设计稿**，不是最终显示尺寸 |
| 「自适应」 | `fitMode: fluid` | 99% 情况的正解，无需追问 |
| 「铺满别留黑边」 | `fitMode: cover` 或 `stretch` | 提示：cover 裁边 / stretch 会变形 |
| 「保持比例」「别变形」 | `fitMode: contain` | 提示会留黑边 |
| 「左边两栏右边两栏」 | ⚠️ **歧义** | 见下方歧义处理原则 |
| 「左边窄一点」 | 列 `fr` 权重 | 1 : 1.5 之类 |
| 「有头部」 | `header.enabled` | 高度给默认值 |
| 「上下三块」 | 单列纵向 3 段 | |

### 歧义处理原则（体验关键）

「左边两栏右边两栏」至少有两种合理解读：
- **A**：左右各成一组，左组内上下 2 格、右组内上下 2 格（2 大列）
- **B**：左 2 列 + 右 2 列，共 4 列

**不要弹窗追问。** 正确做法是：

1. 按最可能的理解（A）立即渲染
2. 在参数区写清「我这样理解了：左右各成一组，左 2 区 + 右 2 区」
3. 旁边放一个「换一种理解」按钮，一键切到 B

用户看到结果不对会自己点切换，比回答一个问题快得多。**把追问变成可逆的一次点击。**

## 五、目标交互：描述 → 预览 → 迭代

```
说一句话  →  线框秒出  →  拖动验证 / 继续说话改  →  出真组件
 (输入)      (<50ms)      (实时)                  (慢速，但用户已确认结构)
```

四个设计要点：

1. **线框先行，代码后置** —— 结构确认用纯 CSS 渲染（毫秒级），结构对了再花时间生成真组件。现有 `index.vue:80-97` 已有 wireframe 雏形，可放大利用。
2. **实时拉伸验证器（杀手锏）** —— 预览容器可拖动改变比例，实时看布局怎么响应。附常用分辨率预设（16:9 / 21:9 / 4:3 / 竖屏 / 拼接屏）。把抽象参数变成可感知体验。
3. **自然语言增量修改** —— 「左边改成三等分」「头部矮一点」「给右边加个底栏」→ 直接改 DSL → 线框实时更新，不回编辑器。
4. **参数渐进披露** —— 默认只露 4 项（设计尺寸、适配策略、分区结构、间距），`gridSize` / `snapToGrid` / `editorZoom` 收进「高级」。
