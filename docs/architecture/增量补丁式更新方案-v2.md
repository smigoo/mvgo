# 增量补丁式更新方案 v2

> 版本：v2（2026-09-01）
> 定位：本文是「生成链路增量治理」的**唯一权威实施文档**，取代并吸收 v1 讨论稿与
> `multi-agent-migration-plan.md` 的三阶段骨架。v2 依据真实代码逐行核对，修正了 v1 的
> 三处偏差：① 契约治理打偏靶、② 增量补丁缺落点、③ 快照机制重复造轮子。

---

## 1. 背景与问题

当前 Phase2 生成链路存在两类问题：

| 类别 | 症状 | 影响 |
|------|------|------|
| **契约失败** | 分块 LLM 返回 JSON 缺少 `files` 字段，解析后直接抛错 | 整个 Phase 2 中断，已生成的前序成果作废 |
| **覆盖式写入** | 标准文件/样式按整包重写，前序正确内容被无意覆盖 | 内容越改越丢、同名样式源冲突 |

---

## 2. 根因（基于真实代码逐行核对）

### 2.1 契约失败的真实根因：解析失败不重试（不是"缺校验"）

`files` 契约的**硬校验其实已经存在**：

- `code-parser.js:177-215`：对「空 files」做了 `#B` 修复，把 `robustJSONParse` 返回的
  空对象 `{ files: {} }` 判定为「未解析到产物」，走兜底恢复，恢复不了就
  `throw new Error('LLM 返回的 JSON 缺少 files 字段')`（`code-parser.js:214`）。

**真正的漏洞在调用侧**：`code-generator.js:803` 调用 `parseCodeOutput(...)` 抛错后，
`generateSingleChunk` 的重试循环（`code-generator.js:547-990`）**只重试四类错误**：

| 重试类型 | 代码位置 |
|---|---|
| `empty_output`（空串） | `code-generator.js:789-801` |
| `max_tokens`（截断） | `code-generator.js:844-845`、`550-594` |
| `truncation`（标签未闭合） | `code-generator.js:847-860` |
| `semantics`（脚本语义） | `code-generator.js:864-907` |

**`parse_failure`（缺 files / 解析失败）不在重试清单里**。异常直接向上冒泡 →
`Phase 2 Figma阶段失败`，不重试、不降级、不换 provider。

> 实锤：`mc-max-1788272805835-1e2fe5ad` 在 `22:39:40` 报
> `Failed to parse code output: LLM 返回的 JSON 缺少 files 字段`，随后直接挂掉，
> 没有任何重试动作。

**结论**：不是"再加一道 files 校验"，而是"把解析失败纳入可重试错误集合"。

### 2.2 覆盖式写入的真实落点

覆盖式写入集中在以下 4 个真实写盘点：

| 覆盖点 | 位置 | 现状 |
|---|---|---|
| `writeFiles` 幂等覆盖 | `microcode-engineer.js:3454`（转发 `microcodeWriter.writeFiles`） | 同名文件直接覆盖，唯一跳过 `isUserPatched` |
| 最小样式骨架预写 | `microcode-engineer.js:329`（`_buildBootstrapStyleFiles`，定义在 `3397`） | 每次生成重新构建骨架 |
| 标准文件补充 | `microcode-engineer.js:5224-5245`（`standardFiles` → `writeFiles`） | 覆盖式回填 `component.js`/`declare.js`/`index.less`/themes |
| `allFiles` 聚合 | `microcode-engineer.js:1330/1367/1391/1422/1474/1490/1543` | 大量 `Object.assign(allFiles, ...)` 整块合并 |

> 说明：`Object.assign(allFiles, ...)` 是**内存态合并**，本身不算"落盘覆盖"；真正的
> 覆盖发生在 `writeFiles` 把内存态整体 flush 到磁盘时。增量治理要同时管住这两层：
> 内存态合并的字段边界 + 落盘的 patch 化。

### 2.3 快照机制的重复造轮子风险

项目里**已经有**完整的快照/断点续跑机制，v1 的 `SnapshotService` 若另起炉灶会打架：

- `onFilesReady → createCandidate` 候选快照
- `temp-components/.task-code-snapshots/{sessionId}/revisions/{revision}/`
- checkpoint/resume（`💾 Checkpoint 已保存`）
- 断点续跑（`🔄 断点续跑: 已恢复 N 个已生成文件`）

**结论**：`SnapshotService` 的正确做法是**收编/统一**现有机制，不是新建一套。

### 2.4 ⭐ 用户痛点「一会儿一小部分、之前的不见了」的直接成因：候选快照回退

> **这是本次方案最关键的发现**。前面的「覆盖式写入」讨论的是**磁盘产物**，
> 而用户实际看到的是**预览/代码 Tab**——它读的是**候选快照**，不是磁盘。
> 两者是不同层次的问题，此前混在一起讨论导致打偏靶。

**现场**：`microcode-engineer.js`（改动前 1188-1199 行）与 `vue3-engineer.js:440`：

```
const runChunk = async (chunk, middleBuilder) => {
  const res = await this._generateSingleChunk(...)
  if (res.files && Object.keys(res.files).length > 0) {
    await input.onFilesReady({
      stage: 'microcode-engineer',
      files: { ...allFiles, ...res.files },   // ← ① 推送：调用时刻求值
    })
  }
  return res
}
// ← runChunk 之外才有 ② 合并（1330 / 1367 / ... 行的 Object.assign）
```

**根因**：① 的 `{ ...allFiles, ...res.files }` 是**调用时刻求值**的，而 ② 的合并发生在
`runChunk` **返回之后**。两者之间隔着 `await` 边界——而子组件是**并行**生成的
（`genSubComponents`，并发 2~3）。交错时序：

| 时刻 | 动作 | 候选 revision 内容 |
|---|---|---|
| t1 | worker A：runChunk 推送（`allFiles` 还是 `{}`） | revision₁ = `{ A }` |
| t2 | worker B：runChunk 推送（`allFiles` 仍未被合并 A） | revision₂ = `{ B }` ← **A 丢了** |
| t3 | caller A：`Object.assign(allFiles, A)` | — |
| t4 | caller B：`Object.assign(allFiles, B)` | — |

而 `phase2.service.ts:614-686` 的 `createCandidate` **每次都把候选指针指向最新 revision**。
于是预览/代码 Tab 从「含 A」回退成「只剩 B」——正是用户描述的
「一会儿一小部分、之前的不见了」。

**修复**：把「合并」前移到「推送」之前，两者原子地放在一起：

```
先 Object.assign(allFiles, resFiles)   // ① 合并
再 onFilesReady({ files: { ...allFiles } })  // ② 推送累积全量
```

**为什么这比 4 个覆盖点更优先**：覆盖点治理的是「磁盘文件被同名覆盖」（**可恢复**，
产物最终一致）；快照回退治理的是「用户在生成过程中看到的产物倒退」（**体验直接受损**，
且中途退出会拿到残缺产物）。故单列为 **P0.5**。

**实证取证**（`backend-node/scripts/diagnose-snapshot-regression.mjs`，2026-09-01 跑 31 个历史任务）：

| 指标 | 数值 |
|---|---|
| 有回退的任务 | **13 / 31** |
| 回退事件总数 | 20 |
| **亚秒级（<1s，并行交错）** | **14** ← 本根因，Slice2 已修 |
| 同轮（1~60s） | 3 |
| 跨重试轮（>60s，多为孤儿剪枝，属预期） | 3 |
| 累计丢失文件 | 44 个，100% 是 `package/components/*.vue` 子组件 |

典型形态：`counts: 8,9,9,10,11,12,13,14,15,18,18,18,18,18,**14**,15,15,...`
—— 累积到 18 后突然掉回 14，丢失 `BridgeHourlyChart.vue / TunnelHourlyChart.vue / VehicleTypeDistribution.vue`
等多个子组件，间隔仅 **0.2~0.7 秒**（并行 worker 几乎同时完成）。

> **⚠️ 取证方法上的一次自我纠错（务必记住）**：revision 目录名是 **UUID**，
> **字母序 ≠ 时间序**。第一版探针按字母序统计，得出「29/31 任务有回退、文件数在 8~18
> 之间反复横跳」的**错误结论**；改用 `mtime` 排序后真实数字是 13/31，且丢失集中在亚秒窗口。
> **用错排序会得出完全相反的判断**。诊断脚本内已用醒目注释锁死这条。

**已排除的两个错误假设**（避免重复 v1 打偏靶，记录在案）：
1. 覆盖点 1（`standardFiles`）剩余价值小 —— `prompt-builder.js:674` 已要求 LLM 不输出
   `index.less`，且 `isUserPatched` 保护已存在。
2. 前端 `fileLifecycle` 渲染 —— `TaskDetail.vue:3348-3349` 只消费 `phase` + `summary`，
   **未使用** `files` 数组，前端不是嫌疑。

## 4. P0：解析失败纳入重试（契约治理修正版）

### 4.1 目标
让「分块解析失败 / 缺 files」成为**可重试错误**，重试时换 provider 并携带错误上下文，
而不是让异常直接穿透杀死整个 Phase 2。

### 4.2 改动点

> **✅ 已于 2026-09-01 落地**（TDD RED→GREEN，build + jest + 重启探活全绿）

**文件**：`backend-node/src/ai-engine/roles/microcode/code-generator.js`

1. 在 `generateSingleChunk` 的 `lastErrType` 类型集合中新增 `'parse_failure'`。
2. 把 `code-generator.js:809` 的 `parseCodeOutput(...)` 调用包进 `try/catch`，
   catch 到解析失败时：
   - 设置 `lastErrType = 'parse_failure'`
   - 设置 `lastErr = error?.message`
   - 满足 `attempt < maxAttempts` 且 `Date.now() - chunkBudgetStart < CHUNK_BUDGET_MS` 时 `continue` 重试
3. 在 `buildRetryPrompt`（`utils/retry-prompt.js:26`）中新增 `parse_failure` 分支。

> ⚠️ **透传链预警（排查踩坑，可复用）**：`code-generator.js:18` 的 `buildRetryPrompt` 导入自
> `./prompt-builder.js`，而 `prompt-builder.js:1675` 只是 `utils/retry-prompt.js` 的
> **透传包装**（`import { buildRetryPrompt as buildRetryPromptBase }`）。
> 改 `utils/retry-prompt.js` 即可生效，但**必须先确认这条透传链**，否则会误判"改了没生效"。

### 4.3 兜底（重试耗尽后）—— 对 v2 原方案的修正

**v2 原文假设**：复用「保留最后产物 + `_degraded` 标记」的降级路径（对齐 truncation/semantics）。

**实测不成立，实现改为抛准确错误**。原因：`parse_failure` 与 truncation/semantics 有本质区别——

| 错误类型 | 解析是否成功 | 是否有可用产物 | 兜底策略 |
|---|---|---|---|
| `truncation` / `semantics` | ✅ 成功 | ✅ 有（内容不完整但可救） | 保留产物 + `_degraded` 降级 |
| **`parse_failure`** | ❌ 失败 | ❌ **无** | 抛准确错误 |

`parseCodeOutput` 在抛错前**已内部尝试过** `recoverFilesFromRawText`（从 ```vue 围栏重建文件）
兜底恢复并失败，说明原始文本里确实没有任何可恢复产物。此时"保留最后产物"是**无米之炊**——
没有 files 可保，若强行降级只会产出空 files，反而在下游造成更难排查的静默失败。

⇒ 重试耗尽后抛 `LLM 输出无法解析为合规 JSON（...），已重试 N 次仍无产物`，
**而不是**误报成"输出被截断或语义不完整"（原第 992 行通用错误）。

### 4.6 行为级验证（证明"真的会重试"，而非只测了纯函数）

纯函数单测（`buildRetryPrompt`）无法证明「LLM 输出缺 files 时真的会重试」。
故补 `code-generator.parse-failure.spec.ts`——mock LLM 返回非法输出，断言完整行为链：

| 用例 | 断言 |
|---|---|
| 缺 files → 重试 | `invokeWithTimeout` 被调用 **2 次**（而非异常直接穿透） |
| 重试 prompt 正确 | 第 2 次调用的 prompt 含 `files` / `JSON` / `重新输出` |
| 错误信息准确 | 含「无法解析」，且**不含**「输出被截断或语义不完整」（旧行为会误报） |
| 对照组 | 合规输出正常返回、仅调用 1 次，**不误触发重试** |

**⭐ 反向验证（关键方法）**：此 spec 是在实现**之后**补写的，必须证明它「不是永远通过的无效测试」。
做法：备份 → 把 catch 里的 `continue` 临时改成 `throw`（模拟改动前）→ 重跑 → **3 个用例失败**
（对照组仍通过，符合预期）→ 恢复 → diff 为空 + 探针 0 处 → 重跑 4 passed。
⇒ **凡是在实现之后补写的测试，都应做一次反向验证**，否则可能埋下"无效守护"。

**⚠️ 可复用：jest CJS 模式下测 ESM 依赖链的 mock 模板**
`code-generator.js` 依赖链中有 5 个模块顶层使用 `import.meta`，直接 import 会让套件加载失败
（与既有 13 个套件失败同一根因），必须全部 `jest.mock` 拦截：
`backend-root.js`（**须提供 `logsDir`**，否则 `logger.js:8` 的 `join(undefined,…)` 抛错）、
`prompt-loader.js`、`resource-import-guard.js`、`sfc-semantics.js`、`provider-pool.js`。
排错口诀：报错栈里 `at Object.<anonymous> (xxx.js:1:1)` 的 `xxx` 就是下一个要 mock 的模块。

## 5. P1：落点级增量补丁

### 5.1 目标
把「标准文件补齐 / 样式骨架 / 同名文件写盘」从"整包覆盖"改成"只 patch 命中块"。

### 5.2 改动点（锚定 4 个覆盖点）

| # | 覆盖点 | 增量改造 | 状态 |
|---|---|---|---|
| 1 | `microcode-engineer.js:5224` 标准文件补齐 | 写前读现有内容，标准文件（`component.js`/`declare.js`/`index.less`/themes）只 patch 变化的块；用户编辑过的文件（`isUserPatched`）一律跳过 | ⬜ 待启动 |

| 3 | `microcode/file-writer.js:690`（经 `microcode-engineer.js:3454` 转发） | 增加「写前 diff」：同名文件内容未变化则跳过（减少无意义重写 + 保留 mtime）；变化则应用 patch | ✅ **Slice1 已落地**（2026-09-01） |
| 4 | `microcode-engineer.js:1330/1367/...` `Object.assign` | 统一为「带边界校验的 merge」：同名 key 冲突时按「LLM 产出 > 骨架 > 空」的优先级收敛，并记录 merge 决策到 debug | ⛔ **已被既有机制覆盖**（见 5.2.3） |

#### 5.2.1 Slice1 落地记录（tracer bullet）

**改动**：`microcode/file-writer.js`
- 新增纯函数 `shouldSkipWrite(fullPath, content)`（:339）：返回 `{ skip, reason }`，
  reason ∈ `absent` / `identical` / `differs` / `read_error`。
- 在 `writeFiles` 的 `isUserPatched` 检查之后、`writeFileSync` 之前接线（:722）：
  内容字节级全等 → 跳过写盘；否则照常写入。

**保守优先契约（关键设计决策）**：**只在全等时跳过**，文件不存在 / 内容不同 / 读取异常
一律照常写入。绝不允许因增量优化而丢失产物——这是本切片最大的风险点，用契约锁死。

**⚠️ 接线时必须注意的 R1 一致性陷阱**：跳过写盘时**仍需回写内存** `files[relativePath] = sanitizedContent`。
因为磁盘上已是 sanitizedContent，若内存 map 停留在本轮 `content`，二者会分叉——
这正是 R1（`file-writer.js:708`）已修复的「分叉点①」，增量改造不能把它重新引入。

**⚠️ 测试编写的陷阱（本次踩坑，务必记住）**：

真实 bug 依赖「推送在 runChunk 内、合并在 runChunk 外且中间隔 await 边界」。
必须用 `simulateWorker` 忠实复刻该模式，并用 `Promise.all` 并发：

```ts
async function simulateWorker(pusher, allFiles, resFiles, pushed) {
  await pusher({ allFiles, resFiles, onFilesReady: async (d) => { pushed.push(d) }, ... })
  await Promise.resolve()          // ← runChunk 返回与 caller 合并之间的 await 边界
  Object.assign(allFiles, resFiles) // ← runChunk 之外的合并
}
```

#### 5.2.2b Slice2b：运行时不变量监控（高水位回退告警）

**为什么需要**：单元测试只能证明「我改的那个函数是对的」，证明不了「线上真的不再回退」。
加一个常驻监控，把「我相信修好了」变成「日志会告诉我们」。

**实现**（`chunk-snapshot-pusher.js`）：用 `WeakMap` 以 `allFiles`（每次 generation 一个稳定
对象引用）为键，记录**上次推送的文件集合**；每次推送前比对，发现丢失即 `logger.warn`
（非阻断），payload 含 `from` / `to` / `missing` / `hint`。

两个设计决策：
1. **用 WeakMap 而非模块级变量**：不同 generation 天然隔离（不会把上个任务的集合当基线），
   且 `allFiles` 被 GC 时条目自动释放，无内存泄漏。
2. **比「上次推送集合」而非「历史最大集合」**：后者在发生一次**合法**剪枝后，会对后续
   每次推送都重复告警，迅速退化成无人看的噪声；前者只在真正回退的那一跳告警一次。

**噪声预期**：`_pruneOrphanSubComponents`（孤儿剪枝）之后的首次推送会告警一次，属**预期**——
故 payload 的 `hint` 里写明这一点，避免后人误判为新 bug。

## 5.5 P4（新增）：精修范围收窄 —— 「增量修改」的第一个真实断点

> 本轮在做「增量修改」链路调研时发现的一个**意图在传递途中被丢掉**的 bug，
> 与「增量变多」（P0.5）互补：前者解决「产物不该回退」，本节解决「修改不该越界」。

### 5.5.1 问题

`phase2.controller.ts:192` 的 `refine` 接受 `refineType ∈ {layout, style, both}`，
但 `phase2.service.ts` 的 `executeRefine` **只用 `refineType` 决定「跑哪个 refiner」，
没有把它翻译成 refiner 的 `_reviseTarget`**：

```ts
// 改前（phase2.service.ts:1341 / 1366）—— 两处都没传 _reviseTarget
await refiner.execute({ figmaNodeData, layoutStructure, outputPath, generatedFiles, target, onProgress })
```

两个 refiner 的默认值都是 `_reviseTarget = 'full'`：

| refiner | 默认值 | 精修范围随 `_reviseTarget` 变化的位置 |
|---|---|---|
| `layout-refiner.js` | `:337` `'full'` | `:357-364`：`layout` →「仅布局修正（间距/对齐/flex）」；`stylistic` →「轻量检查」 |
| `style-refiner.js` | `:454` `'full'` | `:72-76`：`scopeInstruction` 按 `stylistic` / `layout` 分别收窄 |

**后果**：
- 用户选「仅布局」→ LayoutRefiner 仍按 `全面精修` 跑 → **顺手动了样式**
- 用户选「仅样式」→ StyleRefiner 仍按 `全面精修` 跑 → **顺手重排了结构**

即：**用户选的精修类型在传递途中被静默丢弃，实际永远是「全面精修」**。
这正是「为什么不是增量修改」的直接表现之一。

### 5.5.2 修复

新增纯函数 `src/phase2/refine-target.js`：`resolveRefineTarget(refineType)`。

| refineType | `_reviseTarget` | 语义 |
|---|---|---|
| `layout` | `layout` | 仅布局修正，不动样式 |
| `style` | `stylistic` | 仅样式修正，不动布局 |
| `both` | `full` | 两类都改，无法收窄（正确行为） |

在 `executeRefine` 计算一次，透传给 **LayoutRefiner（:1359）与 StyleRefiner（:1386）** 两处。

**保守优先契约**：未知 / 缺失 / 非法值一律回退 `'full'`（最宽范围）。
理由：**收窄过当会导致「该改的没改」**，这种错误比「多改了一点」更隐蔽、更难发现；
宁可多改，不可漏改。

### 6.6 ⚠️ 收编本身引入的 P0 回归（2026-09-02 实锤，已修）

**诚实记录**：6.3 的收编在首次真实生成时**让整个 Node 进程崩溃**（HTTP 000，不是 500）。

```
TypeError: Cannot read properties of undefined (reading 'log')
    at warn (dist/ai-engine/logger/logger.js:265)       ← logger 内部 this.log(...)
    at saveCheckpoint (dist/ai-engine/utils/save-checkpoint.js:78)
    at Object.handler (dist/.../mc-component-graph-phase2.js:586)
```

**根因**：收编时把方法抽成裸引用，丢了 `this`。

```js
const warn = logger && typeof logger.warn === 'function' ? logger.warn : null;  // ❌
const warn = logger && typeof logger.warn === 'function'
  ? (...args) => logger.warn(...args) : null;                                   // ✅
```

原实现是 `logger.warn(...)` 直接调用，`this` 天然绑定；收编时为了"避免重复取属性"
改成了抽变量 —— **看似等价的改写，引入了致命的语义差异**。同类隐患共 3 处，另两处在
`chunk-snapshot-pusher.js:64`（一旦触发回退告警同样会崩），已一并修复。

**⭐ 最贵的教训：9 个用例全绿，却没挡住这次崩溃。**

测试替身是 `{ info: jest.fn(), warn: jest.fn() }` —— 普通对象方法**不依赖 this**，
裸引用照样调得通。这比"没写测试"更危险：**有测试反而提供了虚假信心**。

**守则（已写入排障 skill）**：
1. 凡「会被抽成变量传递 / 延迟调用」的回调或方法，测试替身必须**复现真实实现的 this 依赖**
   （用类实例，内部 `this.log(...)`）；
2. 补完必须做**反向验证**：撤回实现 → 新用例必须失败，且报错与生产崩溃逐字一致。
   本次反向验证结果：撤回后 `2 failed / 18 passed`，报错 `Cannot read properties of
   undefined (reading 'log')`，与生产完全一致。**没做反向验证的修复等于没修。**

**对「收编」这件事的启示**：合并两个"逐字节相同"的实现，风险不在被合并的代码本身，
而在**合并过程中引入的新包装层**。所以收编后必须：
① 用生产等价的输入（而非简化 mock）做 dist 级冒烟；
