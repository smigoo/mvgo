# 管理后台功能需求文档

> 版本：v1.0 · 2026-09-17
> 范围：`/admin/*` 三个页面（用户管理 / 数据分析 / 系统日志）
> 状态：待评审

---

## 1. 背景与目标

### 1.1 现状问题

| # | 问题 | 影响 |
|---|------|------|
| 1 | 「任务日志」与「操作日志」名字相似，概念不同（业务层 vs 系统层） | 管理员混淆入口 |
| 2 | 用户统计出现在两个地方（任务统计 Tab4 + 用户管理列表） | 不知道去哪看 |
| 3 | 用户管理页面职责过载（CRUD + 配置审计 + 使用统计 + 导出） | 信息密度过高 |
| 4 | 耗时/Token 用绝对值展示，无法跨任务/跨用户公平比较 | 模型选型缺乏效率视角 |
| 5 | 导航扁平无层次，3 个 Tab 平铺顶栏 | 缺乏「管理后台」整体感 |

### 1.2 设计目标

- **职责清晰**：三个页面各管一件事——谁在用 / 做得怎样 / 系统发生了什么
- **效率优先**：所有成本指标归一为「单位产出成本」，支持公平比较
- **数据不重复**：同一份数据只在一个地方展示，其他地方引用

### 1.3 核心原则

```
用户管理 = 谁在系统里 + 他们怎么样（人 + 配置 + 效率）
数据分析 = 任务和模型的效果（任务明细 + 模型对比 + 趋势）
系统日志 = 系统发生了什么（HTTP 审计流水）
```

## 4. 页面二：数据分析

**路由**：`/admin/task-stats`（路由不变，显示名改为「数据分析」）
**定位**：任务明细 + 模型效果对比 + 趋势分析

### 4.1 页面结构

```
┌─ 共享时间窗 ────────────────────────────────────────────┐
│  时间预设(全部/本周/30天/60天/自定义) | 刷新               │
└──────────────────────────────────────────────────────────┘

[任务明细] [模型效果对比] [趋势分析]
```

### 4.2 Tab 1：任务明细（原「任务日志」）

**改名理由**：与「系统日志」区分，明确是组件生成任务的业务流水。

| 功能 | 说明 |
|------|------|
| 时间窗 | 全部 / 本周 / 近30天 / 近60天 / 自定义 |
| 筛选 | 按用户（支持用户名搜索）、按模型名、按状态 |
| 表格列 | 时间 / 组件名 / 用户 / 类型(微码/Vue3) / 状态 / 模型 / Token·行数 / 耗时 / 失败原因 |
| 分页 | 20 / 50 / 100 |
| 失败分类 | 质量（红）/ 环境（橙）/ 其他（灰） |

**后端接口**：`GET /api/task-stats/tasks?preset=&from=&to=`

### 4.3 Tab 2：模型效果对比

#### 4.3.1 图表区（取任务数 Top 6 模型）

| 图表 | 指标 | 方向 | 说明 |
|------|------|------|------|
| 成功率对比 | 成功率 % | 越高越好 | 带最佳标注 |
| 效率对比（耗时） | **每百行耗时（秒）** | 越小越好 | 替代原来的绝对 P50 |
| 效率对比（Token） | **每百行 Token（K）** | 越小越好 | 替代原来的绝对总量 |

#### 4.3.2 详细数据表（折叠面板）

| 列 | 说明 | 改动 |
|----|------|------|
| 类型 | 文本 / 视觉 | 不变 |
| 模型 | 模型名 | 不变 |
| 成功率 | completed / (completed + failed) | 不变 |
| 质量成功率 | 排除环境/其他失败 | 不变 |
| **每百行耗时** | `durationMs / lineCount × 100 / 1000` 秒 | **新增** |
| **每百行 Token** | `totalTokens / lineCount × 100 / 1000` K | **新增** |
| 失败分解 | 质量 / 环境 / 其他 | 不变 |
| 样本 | 任务数 + 样本不足标注 | 不变 |

**后端接口**：`GET /api/task-stats/model-compare?preset=&from=&to=`
**后端改动**：返回新增 `secPer100Lines` + `tokenKPer100Lines` 字段

### 4.4 Tab 3：趋势分析（原「历史表现」）

| 功能 | 说明 | 改动 |
|------|------|------|
| 粒度 | 按天 / 按周 | 不变 |
| 指标选项 | 成功率 / **每百行耗时** / **每百行Token** / 任务数量 | 耗时和Token改为效率指标 |
| 图表 | SVG 折线图 + 面积填充 + 80%参考线（成功率时） | 不变 |
| 解读说明 | 根据指标显示白话解释 | 更新文案 |

**后端接口**：`GET /api/task-stats/trends?preset=&metric=&granularity=`
**后端改动**：metric 新增 `secPer100Lines` / `tokenKPer100Lines` 选项

### 4.5 移除的功能

| 原功能 | 去向 |
|--------|------|
| Tab 4「用户统计」 | 合并到「用户管理」页面 |

## 6. 效率指标定义

### 6.1 核心公式

```
每百行耗时(秒) = durationMs / lineCount × 100 / 1000
  例：185000ms / 1986行 × 100 / 1000 = 9.3 秒/百行

每百行Token(K) = totalTokens / lineCount × 100 / 1000
  例：24000 / 1986行 × 100 / 1000 = 1.21K token/百行
```

### 6.2 聚合规则

| 场景 | 聚合方式 |
|------|---------|
| 模型对比 | 先收集所有成功任务的 (duration, lineCount, tokens)，再算 P50/P90 |
| 用户统计 | 同上，按用户分组 |
| 趋势分析 | 按时间桶（天/周）分组，桶内算 P50 |
| 部门汇总 | 按部门分组，部门内所有用户任务合并计算 |

### 6.3 边界处理

| 情况 | 处理 |
|------|------|
| lineCount = 0 或缺失 | 该任务不参与效率计算，但参与成功率/任务数计算 |
| 仅有 duration 无 lineCount | 显示「-」，标注「无行数数据」 |
| 所有任务都无 lineCount | 效率指标整体显示「-」 |

### 6.4 数据来源

| 字段 | 来源 |
|------|------|
| durationMs | tasks.json → task.duration |
| lineCount | 快照 manifest → files[].lines 求和 |
| totalTokens | token_usages 按 sessionId 聚合 |

## 9. 验收标准

| 场景 | 预期 |
|------|------|
| 管理员打开顶栏 | 看到「系统日志 / 用户管理 / 数据分析」三个 Tab |
| 进入「用户管理」 | 顶部有部门汇总卡片，列表含效率列（每百行耗时/Token） |
| 进入「数据分析 → 模型效果对比」 | 图表显示效率指标（每百行耗时/Token），非绝对值 |
| 进入「数据分析 → 趋势分析」 | 可选「每百行耗时」「每百行Token」指标 |
| 进入「系统日志」 | 看到 HTTP 审计流水，与「数据分析」无混淆 |
| 模型 A 做 2000 行 / 100 秒 / 20K token | 每百行耗时 5 秒，每百行 Token 1K |
| 模型 B 做 500 行 / 80 秒 / 15K token | 每百行耗时 16 秒，每百行 Token 3K → 效率低于 A |

## 10. 不做的事

| 事项 | 理由 |
|------|------|
| 改路由路径 | 避免书签失效，仅改显示名 |
| 合并三个页面为一个 | 职责不同，合并反而增加认知负担 |
| 操作日志增加业务语义 | 系统日志保持纯粹的系统层审计 |
| 用户管理增加任务明细 | 任务明细在数据分析，用户管理只看聚合 |
