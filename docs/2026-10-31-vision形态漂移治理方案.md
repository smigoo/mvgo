# Vision 形态漂移治理方案（2026-10-31 · 最终版）

> 目标：消灭「vision 输出形态漂移 → 下游判据漏认 → 视觉缺陷」问题类。
> 从**追形态打补丁**转为**归一收拢 + 显式事实协议 + 形态回归库**。
> 依据：2026-10-31 当天 4 单真机事故（8200b273 / a100e890 / 4851eedd / 769789af）+ 此前 56445358 / bc38e1e6 等。
> 修订：已并入影响面评审与「与既有机制关系」对表结论（见第六章），D/A/C 三处交付物定义已按对表结论修订。

---

## 一、问题定性（为什么必须治理而非继续打补丁）

### 1.1 元问题

vision 分析是 LLM 自由输出，**同一结构语义存在 N 种合法声明形态**；下游判据（白名单、角色标签、关键词表）按形态逐个认，每撞一个新形态就补一个分支。补丁分散在 4+ 个文件，修一层漏一层。

### 1.2 当天实证：同一"统计右值"语义已撞出 4 种形态

| 形态 | 事故单 | 漏认点 |
|---|---|---|
| `item.stats[]` 数组 | 8200b273 | 归一器只认 `valueGroup.elements` |
| `item.valueGroup.elements`（value+label 相邻对） | 8200b273 | —（已修） |
| `item.value.parts + item.offline.parts` | 696105e8 | —（已修） |
| `item.value.elements[].parts[]`（number+unit 角色对） | 769789af | `Object.values(value)` 拆出垃圾条目静默跳过 |

### 1.3 其余热点（同型风险）

| 热点 | 形态数 | 分散位置 |
|---|---|---|
| 表格表头契约 | 4（headers / tableStyle.headers / body.children[].headers / 按列 header） | `declaredTableHeaders` + 装配器 `normalizeTableHeaderContract` |
| section 类型推导 | 关键词表与语义 id 前缀冲突（`footer-summary`→stats） | `deriveSectionType` |
| header 定性 | 4 来源（显式 type / 关键词 / chrome 剥离 / 几何兜底） | planner + `header-geometry-fallback` |
| footer 高度 | 3 来源（figmaHeightPx / 锚点 LCA / 文本锚），且要求 type==='footer' | `resolveFooterTextRowBox` |
| 装配器白名单二段丢失 | analysis 对 ≠ generationInput 对（表头/body/layoutMetadata 各丢过） | `normalizeSectionNode` |
| 兜底覆盖显式事实 | `headerRelation:'no-header'` 被几何兜底翻案 | `applyHeaderGeometryFallback`（已修首例） |

**结论**：继续加分支的边际成本递增（每单一次真机事故 + 一轮修复 + 一轮回归），且无法保证下一个形态不漏。

## 二、治理方案总览（5 个 Phase）

```
Phase B 显式事实协议 ──┐
Phase C 形态回归库 ────┼── 先行止血（小切口、每步可独立验收）
Phase D 出口契约门禁 ──┘
Phase A 结构归一收拢 ──── 治本主干（大手术，C 是它的安全网）
Phase E 拒绝原因聚合 ──── 配套观测
```

## Phase B：显式事实协议「只填沉默、不翻案」

**原则**：任何兜底 / 几何推断 / 自愈机制，执行前必须先检查 vision 是否已就**同一问题**显式发言；发言 ⇒ 只能填沉默，禁止翻案。

### 适用边界（评审定界，两条硬边界）

1. **只约束「结构语义判定类」兜底**（header 定性、section 类型、footer 高度、角色/插槽归属等——它们可能**推翻** vision 的显式结论）；
   **不约束「产物清洗类」自愈**（刀53h、刀7 等对产物的确定性清理——它们不参与语义判定，无"翻案"可言，不得被协议拖慢或误伤）。
2. **只在 vision 骨架路径生效**（E1 骨架=Figma 树的 figma 逃生门路径下，结构本身来自 Figma，vision 没有"发言权"，协议不适用）。

### 交付物
1. `src/ai-engine/utils/vision-facts.js`（新，**词表收拢而非新增**）：
   - `declaredHeaderRelation(sec)` → `'no-header' | 'title-itself' | ... | null`
   - `declaredSectionType(sec)`、`declaredControl(sec)`、`declaredRole(sec)`
   - 统一"vision 显式发言"读取口径（含 `styles`/`style`、`role`/`type`/`control`、id 前缀的优先级注释）
   - 🔴 **评审约束**：既有角色词表已有 **3 份**（takeover 的 `roleOf`+`ROLE_*_SET`、header fallback 的 `businessTypes/businessRoles`、type-derive 的 `TYPE_KEYWORDS`+`INLINE_HEADING_RE`）。`vision-facts.js` 必须把 3 份词表**吸收收拢为单一来源**，原处改为引用（或薄壳 re-export）；**禁止并列新增第 4 份**，否则 split-brain 风险 +1。
2. 接线改造（每处兜底一个前置闸门，仅第 1 类边界内的兜底）：
   - `applyHeaderGeometryFallback`：候选段有 `headerRelation` 声明 ⇒ 跳过（4851eedd 已修，改为读 vision-facts）
   - `resolveFooterTextRowBox`、`resolveVisionSectionBox`：段已带 `figmaHeightPx` 时已有守卫，补 `headerRelation`/`role` 发言检查
3. **接线判据 spec**（防新兜底绕过）：扫源码断言每个 `applyXxxFallback` / 兜底函数调用点都消费 `vision-facts`；新兜底不接线 ⇒ spec 红

### 验收
- 现有 4851eedd 3 条判据保持绿
- 变异测试：摘除任一接线 ⇒ 判据变红
- 真实 checkpoint 回放：4851eedd / a100e890 产物结构不变

## Phase C：形态回归库 + 标签扰动测试

**原则**：每次真机事故的 vision 形态固化为 fixture；判据必须在**所有已知形态 + 任意标签扰动**下结论一致（或显式 fail-open）。

### 交付物
1. `src/ai-engine/utils/__tests__/vision-form-regression.spec.ts` + `__fixtures__/vision-forms/`：
   - fixture 按语义命名（非任务号）：`stat-value-elements-container.json`、`stat-value-group-pairs.json`、`table-column-headers.json`、`semantic-footer-id.json`、`header-relation-no-header.json` 等
   - 每形态记录：来源任务、vision 原始片段（最小化）、期望的管线结论（类型 / stats 条数 / 表头数组 / footer 高度 / 是否进插槽）
2. **两段式断言**：
   - 形态断言：fixture → 装配器 → `resolvePlanSections` → 归一器/接管器/模板，结论与记录一致
   - **标签扰动断言**：自动生成变体（删 `role`、`type` 置 null、数字 id ↔ 语义 id、`styles`↔`style`、`items`↔`children`），核心结论不得翻转；不可判定时必须显式 fail-open（计数日志留痕），**禁止静默产出空壳**
3. 首批入库形态：今天 4 单 + 56445358（整表 388）+ e99a736f（语义 table-section）≥ 10 个

### 与既有 per-刀 spec 的分工（评审定界，避免 fixture 双份漂移）
- **归形态库（C）**：跨形态不变量（同一语义 N 形态结论一致）+ 标签扰动一致性 + fail-open 显式化——这些判据横跨多个刀，只在这里写一份。
- **留在各刀 spec**：单形态的具体数值断言（如 769789af 双条真值 px 字号、4851eedd 闸门变异验证）——各刀 spec 是行为契约的最终权威，**不迁移、不复写**。
- fixture 单一来源在 `__fixtures__/vision-forms/`，各刀 spec 若需引用形态样本，引用同一 fixture 文件，禁止各自复制。

### 验收
- 全部形态阳性 + 扰动阴性通过
- 此后每个新形态事故 = 加 1 fixture + 修归一器 1 处（不再动 4 个文件）

## Phase D：vision 出口契约门禁（先观测、后阻断）

**原则**：形态漏网在管线最前段暴露，而不是最后一环变成视觉 bug。

### 定位（评审修订）：接入既有审计家族，不另起体系

既有 vision 审计链已有 7 个成员：`vision-anchor-validator`、`vision-figma-cross-validator`、`plan-body-child-id-audit`、`section-plan-coverage`、`section-coverage-guard`、`manifest-auditor`、`node-size-validator`。
本 Phase 交付物**作为该家族的新成员**挂在 visual-parser 出口链，输出契约对齐家族既有 `{ evaluated, missing, conflicts }` 结构；**禁止另起一套并行审计体系**。

### 交付物（拆为两个可独立回滚的子步）

**D1：audit 观测（纯代码，先上）**
1. `src/ai-engine/utils/vision-contract-audit.js`（新，纯函数，家族新成员）：
   - 检查项：每顶层段是否有类型/角色可判定；`headerRelation` 是否声明；统计对是否 value+label 成组；表头是否 ≥2 且成列完整；数值/文本是否有样式真值
   - 输出：`{ evaluated, missing:[], conflicts:[] }`，调用方只记日志 + 写入 `.checkpoint/contract-audit.json`（**不阻断**，先跑两周看数据）

**D2：prompt 增补（唯一的故意行为变更，独立成步）**
2. prompt 侧收敛（`structure-examples` 模块）：把规范形态写进 few-shot——value 容器、按列表头、`footer-*` 语义 id、`headerRelation` 必填——让 vision 输出向规范靠（治源头）
   - 🔴 **评审护栏**：D2 独立提交、独立灰度、可独立回滚；**禁止与任何代码改动同批合入**，否则线上行为变化无法归因。
3. 两周后按 missing 率决定是否升级为软阻断（重解析一次）

### 验收
- 对当天 4 单 checkpoint 跑 audit：能精确标出各自缺失项（回放判据）
- 正常历史组件 audit 误报率 < 5%（抽样 20 个 checkpoint 验证）

## Phase A：结构语义归一层（治本主干）

**原则**：同一语义只在一处识别；下游只读规范结论。

### 交付物
1. `src/ai-engine/utils/section-semantics.js`（新，单一事实源）：
   - `canonicalSectionType(sec)`：显式 type > id 结构前缀（`footer-*` / `header-*` / `table-*`）> 结构角色契约（control/role=table、stat 结构、content.elements value 结构）> 关键词表（最后兜底）
     - 关键词表直接消费 `vision-facts.js` 收拢后的单一词表，**不在本模块复制任何词表**（与 Phase B 同一约束）
   - `canonicalTableHeaders(sec)`：4 形态收拢（现 `declaredTableHeaders` 整体迁入）
   - `canonicalItemStats(item)`：5+ 统计形态收拢（现 `normListItem` 统计轨迁入），返回 `[{v,l,vc,vfs,vfw,lc,lfs}]`
   - `canonicalHeaderRelation(sec)`、`isBusinessContent(sec)`（现 `hasBusinessContent` 迁入）
2. 🔴 **双轨同源（评审强制）**：`items` 解释现有两条轨——`repeated-section-collapser`（E1 几何优先）与 takeover `normListItem`。迁移后**两轨必须同读 `canonicalItemStats`**，只允许 E1 几何优先这一个差异点存在；任何一方私有补形态分支 ⇒ 迁移失败。验收时对两轨跑同一组 fixture（C 形态库）结论必须一致。
3. 消费者迁移（逐个、每步两态回归）：
   - `subcomponent-planner`（类型推导、header 兜底、footer 高度）
   - `generation-context-assembler`（表头契约透传读归一层）
   - `folded-grid-section-takeover`（normListItem / detectTableLeaf）
   - `repeated-section-collapser`（items 解释轨，双轨同源另一半）
   - `header-geometry-fallback`、`section-type-derive`（退化为薄壳 re-export，过渡期保留）
4. 迁移护栏：
   - Phase C 形态库全绿为前置条件
   - 🔴 **vue3 管线接管 spec 补齐为前置**：`collectFoldedGridTakeover` 被 vue3-engineer(:769)/vue3-prompt/orphan-style-rule-guard 共用，但 vue3 侧无独立接管 spec；A 动刀前必须先补齐 vue3 接管行为 spec（否则迁移回归对 vue3 管线是盲区）
   - 每迁移一个消费者：专项两态对账 + 全量 FAIL 集合 diff 为空
   - 最终对存量组件 checkpoint（实测 295 个，`workspace/custom-components/*/.checkpoint`）做离线重放产物快照对照（diff 为空 = 零行为漂移）

### 验收
- 形态库全绿 + 存量产物快照零 diff
- 新形态事故的修复动作 = 只改 `section-semantics.js` 一处 + 1 fixture

## 六、与既有生成机制的关系（评审对表结论）

### 6.1 三处重复风险及收拢决定

| # | 既有机制 | 重复点 | 收拢决定 |
|---|---|---|---|
| 1 | vision 审计家族已有 7 成员（anchor-validator / figma-cross-validator / plan-body-child-id-audit / section-plan-coverage / section-coverage-guard / manifest-auditor / node-size-validator） | Phase D 若另起体系 = 第 8 套并行审计 | D 作为家族**新成员**接入 visual-parser 出口链，输出契约对齐 `{evaluated, missing, conflicts}` |
| 2 | 角色词表已有 3 份（`roleOf`+`ROLE_*_SET` / `businessTypes`+`businessRoles` / `TYPE_KEYWORDS`+`INLINE_HEADING_RE`） | B/A 若新建词表 = 第 4 份 split-brain | `vision-facts.js` **吸收收拢** 3 份为单一来源，原处 re-export；spec 断言无新增词表常量 |
| 3 | items 解释双轨（collapser 几何优先轨 + takeover `normListItem` 轨） | A 若只迁一侧 = 双轨继续漂移 | 两轨同读 `canonicalItemStats`，唯一允许差异 = E1 几何优先；同一 fixture 组断言两轨一致 |

### 6.2 两处边界写明

| # | 边界 | 结论 |
|---|---|---|
| 1 | B 协议 vs 产物清洗类自愈（刀53h / 刀7） | 不冲突但必须定界：协议只约束**结构语义判定类**兜底（可能翻案 vision 的）；清洗类不接线、不减速 |
| 2 | B 协议 vs E1 逃生门（骨架=Figma 树路径） | 协议只在 **vision 骨架路径**生效；figma 逃生门下结构来自 Figma，vision 无发言权，协议不适用 |

### 6.3 四处一致性确认（无矛盾，仅记录优先级链）

| # | 对照项 | 确认结论 |
|---|---|---|
| 1 | B「不翻案」vs 刀5c 显式 type 优先级 | 同向：协议把「显式发言优先」前推到所有兜底，是刀5c 链条的泛化，无冲突 |
| 2 | A id 结构前缀 vs 刀5a 教训（形态校验误杀合成 id） | 前缀匹配**不做形态校验**（刀33 教训：合成 id `43:4791-list` 会变空键 fail-closed），只在归一层做匹配不校验合法性 |
| 3 | C 形态库 vs 各刀 per-刀 spec | 分工明确（见 Phase C「分工」节）：跨形态/扰动归 C，单形态数值断言留各刀 spec，fixture 单一来源 |
| 4 | D2 prompt 规范 vs LLM 可配置（模型不硬编码） | prompt 增补只改 `structure-examples` few-shot 模板，不触碰任何 provider/模型配置，与「LLM 由用户配置」原则无冲突 |
