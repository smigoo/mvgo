### 2.3 根因：两个判据不同构（memory「同判据 ≥2 份 = 事故温床」再犯）

`src/ai-engine/utils/style-class-consolidator.js:477`

```js
/** 括号平衡校验（防止把残缺块写进 common.less） */
function isBalanced(less = '') {
  let depth = 0;
  for (const ch of String(less)) {
    if (ch === '{') depth += 1;
    else if (ch === '}') depth -= 1;
    if (depth < 0) return false;
  }
  return depth === 0;
}
```

**只数 `{}`，完全不数圆括号。** 而 `less-compile-gate.js:572-580` 数的是圆括号：

```js
const pOpens  = (cleaned.match(/\(/g) || []).length
const pCloses = (cleaned.match(/\)/g) || []).length
if (pOpens !== pCloses) { /* LESS-WRITE-004 */ }
```

⇒ **合并器把「大括号平衡但圆括号缺 1」的文本放行写进 common.less，写盘门禁立刻拒绝。**

对照证据：11:45:13 那三轮合并器**自己**报过  
`[style-class-consolidator] 合并后 LESS 括号不平衡，已回退（不改动 common.less）`  
说明它具备「检出→回退」能力 —— 只是判据缺圆括号这一维，在本例中没能触发。

### 2.4 为什么「跳过」会变成「兜底覆盖」（二级放大）

`file-writer.js:951-998` 的降级链：

```js
if (!_lessGate.ok) {
  let _hasLastGood = false;
  try {
    const _absPath = join(outputPath, relativePath);
    const _disk = existsSync(_absPath) ? readFileSync(_absPath, 'utf-8') : '';
    _hasLastGood = _disk.trim().length > 0 && !_disk.includes('模型输出为空时自动补齐');
  } catch { _hasLastGood = false; }
  if (!_hasLastGood) {
    const _retry = gateStandaloneLessWrite(rebalanceBlockComments(sanitizedContent), relativePath);
    if (_retry.ok) { /* 降级落盘 */ }
    else { skippedFiles.push(relativePath); continue; }   // ← 本例走这里
  } else { skippedFiles.push(relativePath); continue; }
}
```

两个缺口：

1. **`_hasLastGood` 只查磁盘，不查分块缓存**。本例磁盘上是空的/兜底，但 `.mc-gen/cache/code-chunks/17-...` 里躺着一份 `gate ok: true` 的 641 行合格版本 —— 有可回退的 good 版本，却没被使用。
2. **`rebalanceOrphanCloseParens`（`less-compile-gate.js:470`）按设计只抹「孤立 `)`」，不补「缺失 `(`」**（注释明确写「不猜位置补」）。所以「缺 1 个 `(`」这条路径**没有任何自愈出口**。

跳过之后，`code-validator.js:2242-2267`：

```js
const commonLessPath = 'resources/styles/common.less';
if (!files[commonLessPath] || files[commonLessPath].trim().length < 10) {
  fixedFiles[commonLessPath] = `// 通用样式（common.less 兜底模板 - 模型输出为空时自动补齐） ...`;
}
```

⇒ **静默把 641 行样式换成 15 行兜底**，日志只有一条 WARN，任务仍标记成功。这是本组件「几乎无样式」的直接成因。

### 2.5 待查清的一点（诚实标注）

门禁报的括号总数（30 / 24 / 25 / 32 / 27）**与现存 chunk 17 的 26 均不相等**，且逐轮变化。推论：

- 门禁判的是**合并后的中间态**（chunk 26 + 子组件样式 24 = 50 也不等于 30，说明合并器已做过滤）；
- 被判文本**未留档**，无法逐字复核。

**这本身是一条诊断能力缺口**（详见 §六 G6）：门禁判定为坏时，应把被判文本落盘为 `*.rejected.less`。

最可能的缺 `)` 来源：`mergeIntoCommonLess` 提取声明时对**多行 `linear-gradient(`** 不安全 —— 产物里有两处该写法（`ContentSection5.vue:26-31`、chunk17 `:236`/`:552`）：

```less
background: linear-gradient(
  180deg,
  rgba(212, 227, 254, 0.4) 0%,
  ...
);
```

若提取按「行 = 声明」处理，`linear-gradient(` 首行被当无分号声明，后续行（含 `)`）被丢弃 → 圆括号必然失衡。**需加阳性对照单测**。

## 四、P0-3：「模块内部布局」（用户点名 ②）

### 4.1 flex 比例算错（可精确定量）

真值（`796:3 slot-icon` = 604×787，y 相对根）：

| 段       | 节点                       | 真值高 | 真值占比                | **产物 flex** | 偏差           |
| ------- | ------------------------ | --- | ------------------- | ----------- | ------------ |
| 顶部两统计卡行 | `38:3260` + `38:3282` 并排 | 76  | 76/787 = **0.0966** | **0.192**   | **×1.99** 🔴 |
| 战略合作厂商卡 | `38:3137`                | 161 | 0.2046              | 0.204       | ✓            |
| 优质厂商卡   | `38:3162`                | 212 | 0.2694              | 0.268       | ✓            |
| 普通厂商卡   | `38:3206`                | 265 | 0.3367              | 0.335       | ✓            |

**反推模型**：令 `h₁ = 152`（**两张并排卡 76+76 相加**），`Σh = 152+161+212+265 = 790`：

```
152/790 = 0.19240  →  0.192  ✓
161/790 = 0.20380  →  0.204  ✓
212/790 = 0.26835  →  0.268  ✓
265/790 = 0.33544  →  0.335  ✓
```

**四个值全部命中** ⇒ 结论确定：LLM 用 `flex_i = 段高 / Σ段高`，但对**行内并排（row）的子项取了高度之和**，而不是取 `max`。

**危害**：顶部统计卡实际高度 = `0.192 × 787 ≈ 151px`，真值 76px ⇒ 截图里顶部区被撑掉近 2 倍高度，下方三卡被压缩。

**正确算法**：`行内高 = max(子项高)` = 76；`flex_i = h_i / (Σh + Σgap)`。

function isBalanced(less = '') {
  let depth = 0;
  for (const ch of String(less)) {
    if (ch === '{') depth += 1;
    else if (ch === '}') depth -= 1;
    if (depth < 0) return false;

  // 新增：圆括号维度（与 less-compile-gate LESS-WRITE-004 同构）
