## A. 硬伤（修订后方可授权开工）

### A1 🔴 G1「退役最大补丁簇」是伪目标：含死代码 + 边界未定义

**核对结果：**

| 模块 | 行数 | 接线现状（实测） |
|---|---|---|
| `utils/chart-container-guard.js` | 155 | ✅ 已接线 `microcode-engineer.js:191`、`vue3-engineer.js:52`（双刀，:7440/:1453） |
| `utils/chart-type-guard.js` | 1210 | ✅ 已接线 `microcode-engineer.js:238`、`vue3-engineer.js:54`、`code-healer.js:33` |
| `utils/echarts-init-guard.js` | 339 | ✅ 已接线 `artifact-invariants.js:28`、`code-structure-validator.js:42` |
| **`utils/chart-resize-healer.js`** | **131** | ❌ **全仓零调用点 = 死代码** |
| **`utils/chart-section.js`** | **319** | ❌ **`injectChartSectionIfMissing`/`detectChartSignal`/`collectEchartsNodes` 零调用点 = 死代码** |

- G1 宣传的「最大补丁簇 ~1500 行」，其中 **450 行是死代码**（约占 30%），退役它不需要 2 周取证、不需要 shadow 验证、不需要 `hit=0`，属于**立即零风险清算**。方案把它和新 kind 接管捆在一起等 2 周，是排期浪费。
- 更关键：**接管器 `utils/folded-grid-section-takeover.js` 全文 0 处 `chart`**（`grep -ni chart` 空），kind 白名单 `FG_TAKEOVER_CLASS_RX`（`:91`）为 `header|grid|kvgrid|text|icon|statrow|table|legend|list|footer|regions` 共 11 项，**无 chart**。
- 而接管的工作粒度是**段级**（命中段 → 确定性组件，见总纲 §1「命中 → 确定性模板（不进 chunk LLM）」）。图表在真实产物里往往是**段内区块**（`test`：`chart-section` 与 `tabs` 同段共存，`code-generator.js:1253` 实锤 facts 顺序 `tabs(89:42) → chart-section`）。
- ⇒ **方案未定义「chart 接管为整段，还是接管为段内叶子」**。若为叶子，则 `folded-grid-section-takeover` 的段级登记制（三处 kind 登记 + R6 段级对账）不能直接套用，G1 的工作量远大于文档描述；若为整段，需先解决「同段 tabs + chart 混排」的拆分，属新设计。

**修订要求**：G1 拆为 G1a（死代码清算，零风险，立即可做）/ G1b（chart 接管，须先提交「段级 vs 段内叶子」边界设计）。

### A2 🔴 接管 ≠ 跳过 LLM：现状是「LLM 生成 → 整体覆盖」

**证据**：确定性装配由 `microcode-engineer.js:2589` / `:2634` 调用 `_applyDeterministicIndexTemplate`（`:4417`），后者调 `microcodeGenerator.applyDeterministicIndexTemplate`（`code-generator.js:1272`），动作是 `findRootTemplateBlock` 定位 `<template>` 块后**整体替换**（`:1297-1300`）。同时 `code-generator.js:1253` 注释自述：确定性装配**历史上只挂 complex 分支**，simple/medium 的 `index.vue` 由 LLM 整文件生成。

- ⇒ 当前「确定性接管」是**生成后覆盖**形态：LLM 仍然产出 template（消耗 token、产生失败面），随后被丢弃替换。方案 §2/G0 及 G4 反复使用「接管 = 不进 chunk LLM」「engineer 瘦身为 chunk 生成 + 槽位接线」，**与实现不符**。
- 后果：G4 终态（LLM 不再产出布局 DOM）**缺少让 LLM 不产出 template 的机制**——光靠覆盖做不到「减量」，token 成本与生成失败面不会下降，方案的「净删 2.5 万行」是以「LLM 不再写这些代码」为前提的，而这个前提没有对应设计。
- ⇒ 须新增 **G1.5 生成前置化**：把确定性装配从事后替换提前为 prompt 契约（该段不做 template 输出）或 chunk 边界划分。

### A3 🔴 G1 声称的 R6 安全网对 chart 不成立，N1 被错误地列为删除对象

- G1 写「R6 `declaredUnconsumed` 对账保证不丢声明内容」。但总纲 §5 明确 R6-2 口径 = **`declaredTextMass` 文本量守恒**（收集 text/texts/characters/name/value/label/title，值形态过滤色值/路径/var）。
- **图表数据的对账对象是数值序列，不是文本**——`chart-spec.js:22` 甚至设有红线「数值/文本数据键禁止混入 chartSpec，归 chartDataHints / node TEXT 单源」。
- ⇒ 若按方案推进，chart 接管后**数值丢失无人对账**（这正是历史 N1「数字字面量差集剥离」想解决的问题）。
- ⇒ 修订：G1 必须先新增 **chart 数值守恒判据**（chartSpec/hints 数值集合 ↔ 产物 series 数值集合差集为空），**承接 N1 思路**而非如方案 §G3 那样直接把它列为退役候选。

### A4 🟡 G0.1「禁止静默」前提与代码不符，且措辞会诱导高危改法

- 方案：后处理链 catch「禁止静默」。
- 实测：`pre-write-self-healing.js` 约 30 处 catch（`:351/392/460/486/532/554/576/600/632/659/727/786/828/878/1016/1049/1081/1117/1145/1165/1189/1209/1231/1288/1345/1391/1422/1507`），抽查 `:460`、`:486`、`:786` **均已** `logger?.warn?.('🛡️ …（fail-open）', { error })`。mc-engineer 后处理区（>6800）37 处 catch，逐 pass 分布（`n1err`/`n2err`/`n3err`/`n4bErr`/`n5err`/`ctErr`/`axisErr`/`postErr`…），空 catch 仅 3 处（`:3590/:7294/:8758`）。
- ⇒ 现状不是「静默吞错」，而是**留痕但不聚合、不进任务 warning、不落计数行**。G0.1 的价值应重述为「聚合 + 报警升级」。
- ⚠️ 风险提示：若实施者按「禁止静默」字面理解去改 fail-closed，一次补丁异常会导致整单失败——**风险远大于收益**。须在方案中显式写入「**禁止改成 fail-closed，仅新增观测**」。
- 另缺一项：catch 虽逐 pass，但异常若发生在共享变量赋值处（历史上 `microcode-engineer.js:6907` 注释实锤的 `input is not defined` 即发生在 execute 级）仍会「一炸停链」。建议 G0.1 补 **阶段级 try + 阶段名计数**，使失败定位到阶段而非整链。

## B. 设计缺口（影响根治承诺，须补设计）

### B1 🔴 布局区（补丁体量绝对多数）无根治设计，G2 实为新增补丁

- 权属矩阵自述：布局（flex 方向/尺寸/间距）由 **chunk LLM 主笔**，纠偏方为 V8/V9 几何注入、刀16、FLEX-001~005、刀28/30/50 —— 方案自认「全部实锤布局事故在此区」。
- 而 G2 的全部内容是「守卫写入值打 provenance 标 + V6/W4 只剥 LLM 原始值」。这是**给剥离器加判据**，即**再新增一个补丁维度**，与 G0.3「新守卫默认拒绝、须论证为何不能是接管 kind」直接冲突。
- 关键事实：**布局编译所需的真值已经齐了**——`figma-node-layout-facts.js`（`buildNodeLayoutFacts`）已被 `design-facts-compiler.js:1` 消费，V8 `layout-facts-injector`（`code-validator.js:2657`）与 V9 `ITEM-FACTS-INJECT`（`:2723`）已在用 `nodeLayoutFacts`/`itemFacts` **补缺失**（总纲 §4-2「事实只补缺」）。
- ⇒ 既然「事实已足以判缺失并注入」，就足以**直接求解生成**。缺的不是数据，是**求解器**。建议 G2 重定义为「**布局编译化**」：消费既有 layoutFacts 直接产出 flex/grid 契约，provenance 打标降级为该阶段副产物（而非独立目标）。

### B2 🟡 方案查重只查了 docs，漏认在仓的 IR 雏形

- 方案 §0 查重口径为「docs/ 全量 grep」，得出「无既有 IR/编译器」；但**代码里已有**：

| 模块 | 行数 | 性质 |
|---|---|---|
| `src/ai-engine/context/design-facts-compiler.js` | 202 | 真值 → 结构化 `designFacts`（含 `normalizeCharts`、`legend.owner: 'unresolved'`） |
| `src/ai-engine/context/generation-context-assembler.js` | 403 | 裁决事实装配（信任等级 + 问题清单） |
| `src/ai-engine/context/context-conflict-resolver.js` | 134 | 来源冲突裁决 |
| `src/ai-engine/context/generation-context-shadow.js` | 108 | 影子对照 |

- 即：**「真值 → 结构化中间表示」这一层已经存在**，`designFacts.{root, charts, provenance}` 就是 IR 雏形。方案一边声称「不引入平行 IR 层」，一边也没认领这层——导致 G1 chart 槽位、G3 真值槽位都**没有指定落点**。
- 建议：明确 **designFacts 为 IR 载体**；G1 的图例归属问题可直接落 `designFacts.charts[].legend.owner`（现值为 `'unresolved'`，正是待接管对象），G3 文本/数字槽位落 `designFacts` 对应域。查重口径需补「代码查重」并重跑。

### B3 🔴 退役判据 `hit=0` 对跨段补丁结构性不可达（方案最大逻辑漏洞）

- 方案退役机制：补丁「连续 N 单 hit=0」→ 删除修补动作。
- 但 FLEX-001~005、V6 dedup、V8/V9 注入、W4 刀23 这些是**跨段落/跨全产物**运行的补丁，其 hit 由**布局区**决定；而 G2 不打散布局区的 LLM 主笔地位（见 B1），⇒ **这些补丁的 hit 永远不会归零** ⇒ 退役路径自我阻断。
- 直接后果：方案预期的「3.4 万行 → 6~8 千行」中，除 chart 簇的少数项（且实际可退役量因 A1 缩水）外，**其余 ~2.9 万行没有任何可执行的退役路径** —— 「净删 2.5 万行」缺乏支撑。
- 另：G1 判据「chart 相关 BLOCK 计数行归零」当前**无口径**——G0.2 只聚合计数据，BLOCK 未按子系统分类。所幸 `gate-score.js:14-18` 已有四维映射（结构/资源/类名/语义）可复用。
- ⇒ 修订：① 明确「**不可退役簇**」清单（列出必须等布局编译化落地才可退役的补丁），避免用不可达判据自欺；② G0.2 扩展 BLOCK 维度归类；③ 定义 N 与 M（建议 N≥20 单 / M≥10 单，且需覆盖含 chart 与不含 chart 两类任务）。

### B4 🟡 影子验证已有资源未指定

- 仓内已有 `dual-truth-score.js`（双主题评分，`DEFAULT_LOW_SCORE_THRESHOLD = 60`，同时产出 minScore 防「单侧灾难」被平均分掩盖）、`gate-score.js`、`quality-score-v1.js`。
- 方案 §3 只写「shadow 对比（接管产物 vs 现链产物 component-meta 视觉分/门禁计数）」，未指定用哪个、阈值多少、连续多少单。
- ⇒ 建议补齐：shadow 判据 = `dual-truth minScore ≥ 基线` **且** `gate-score ≥ 基线`，连续 M 单；`quality-score-v1.js` 只引用其纯函数、不改实现（与「并行 WIP 隔离」不冲突）。

### B5 🟡 G0.3 价值被低估，应提级

- G0.3（新守卫默认拒绝、须论证「为何不能是接管 kind」）是方案中**唯一的增量治理手段**——G0.1/G0.2 都只管存量观测。当前被放在 A 档末尾且只改文档。
- 建议提级并加硬约束：新增修补型守卫须同时提交「退役判据」（何时可删），否则不合并。
