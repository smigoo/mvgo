# 工坊可开发功能需求 · 首批清单

> 日期：2026-11-04
> 状态：需求清单，未开工
> 前提：工坊定位为「buddy 的后台之一」——放弃 L1 入口层 / L2 编排层，守住 L3 判据层 / L4 事实层。
> 承接：A2A 支持度核查 → API vs A2A 对比 → 入口外移后的价值论证 → 砍掉工坊的反向成本 → 研发类转型 → 操作位置趋同 → 不可替代性加固，共七轮讨论。

---

## 0. 前提修正（重要）

「产物出生证明（合格证）」此前被列为高壁垒主攻项，**排序错误**。它的本质是**出口**（一张被格式化的声明），不是**资产**。实测确认三层分离：

| 层 | 内容 | Buddy 侧复制难度 |
|---|---|---|
| L1 格式层 | provenance 有哪些字段 | 零成本，一个 skill |
| L2 证据层 | 每个字段的**值**从哪来 | 需真值源才能填 |
| L3 可复验层 | 第三方能否**独立查证** | 需外部可查锚点 |

**一张自己签的证明 = 自证清白 = 零价值。** 合格证有价值的前提是：它每一栏都指向一个**工坊之外可独立获取的事实**。

⇒ 修正后的选型法则：**加出口稀释壁垒，加事实源深度才加固壁垒。** 下面的清单按此重排。

## 1. P0 · 对外接入硬前置

### 1.1 v2 接入任务队列

- **目标**：v2 目前零引用 `TaskQueueService`（实测 `grep -rn "TaskQueueService" src/ai-engine-v2/` 返回空），并发完全不受控。buddy 一旦作为后台高频调用，会直接打爆模型额度。
- **落点**：`src/queue/task-queue.service.ts`（889 行，已被 `queue.module.ts` 导出）。实测可用 API：
  - `getAvailableSlots(userId?)` :260 — 入队前判断
  - `registerRunning(sessionId, userId?)` :304 — 占位
  - `dequeue(sessionId)` :502 — 释放（**注意：不是 `releaseSlot`，此名不存在**）
  - 辅助：`getRunningCount(userId?)` :273、`isRunning(sessionId)` :296
- **落点文件**：`src/ai-engine-v2/api/v2-pipeline.service.ts` — 构造器注入；`generate` 入口加 `getAvailableSlots` 分支；`runGeneration` 的 `finally` 补 `dequeue`。
- **验收**：并发提交 3 个 v2 任务，超配额的那个进入 `queued` 而非直接开跑；`getRunningCount` 与 `pm2` 实际在跑任务数一致。

### 1.2 服务间鉴权

- **目标**：buddy 作为服务调用工坊时，目前只能**转发某个真实用户的 token**。实测 `src/auth/session.guard.ts:22-60` 的三条身份路径全是「人」的概念：`session.userId` / 门户 `token` / 开发态兜底。全库 grep `apiKey|serviceToken|X-Service` 的 30 处命中**全部是 LLM provider 密钥**，零处调用方身份。
- **落点**：新增 `src/auth/service.guard.ts` + `service-identity.schema.ts`。凭据走**无状态**（HMAC 签名 / 预共享密钥 + 时间戳 + nonce），**不能依赖 express-session** —— `session.guard.ts:72-73` 注释已明说内存 session 重启后失效。
- **附带**：调用方身份需落审计（谁在什么时候发起了哪次生成），这是后续限流与追责的前提。
- **验收**：服务身份不携带任何用户 session 即可通过鉴权；重启后凭据仍有效；无凭据请求 401；审计表有记录。

### 1.3 任务报告聚合端点

- **目标**：buddy 拿到 `taskId` 后需要一次读到判决，而不是自己去 `result` 里翻嵌套字段。这是 1.2 之后的第一个业务出口，也是后续看板/出生证明的共用数据源。
- **落点**：`GET /api/tasks/:sid/report`，把 `result` 内的 `finalQualityScore` / `runtimeGate` / `visualComparisonReport` / `issueCategories` 提为顶层。
- **验收**：单次请求即可回答「这个任务合格吗、差在哪、证据在哪」，无需二次请求。

## 2. P1 · 事实源深度（真壁垒所在）

### 2.1 事实锚点外露（可复验性）

- **目标**：让声明**可被第三方独立查证**，这是 L3 层的唯一实现方式。
- **锚点清单**（每一栏都必须能被外部独立获取）：
  - `figmaFileKey` + `figmaNodeId` + `figmaVersion` → 任何人调 Figma API 可验
  - `artifactsHash`（sha256 of 全部产物文件）→ 任何人拿产物可算
  - `specId` + `specVersion` + `rulesetVersion` + `tierId` → 判定依据可定位
  - `modelProviderId` + `model` + `llmCallCount` → 调用日志可查
- **验收**：把这张锚点表交给一个不信任工坊的第三方，它能**不依赖工坊**地验证其中每一条。

### 2.2 判定可重放

- **目标**：同一份产物 + 同一个 `rulesetVersion`，任何时候重跑都必须得到同一个判决。**不可重放的判定等于不可验证的声明。**
- **落点**：复用现有 `:rev/validate` 只重跑门禁的路径；补齐 `rulesetVersion` 版本标记（现在规则集改动无留痕）。
- **验收**：取一个历史产物，用当时的 `rulesetVersion` 重跑，`pass/fail` 与文件/行/类名定位**逐字一致**。

### 2.3 失败案例库

- **目标**：把「已付的学费」固定资产化。前 7 个刀（16b/17/33/53/54/55/7c）都是学费，不入库就要重交。
- **数据独占性**：失败样本是 Figma 解析失败 / 门禁 BLOCK / 修订耗尽 —— **这些事实只有工坊有**，buddy 侧产生不了。这是本清单里唯一偏「真资产」的一项。
- **触发点三处**：`configurable-pipeline.js:548-555`（修订耗尽）、`rejected` 快照落库处、`runtimeGate` 双 BLOCK 处。
- **落点**：`backend-node/data/failure-cases/`（append-only，独立于 `.mc-gen` 缓存）。**只写不读，零依赖，今天就能开始积累。**
- **验收**：每次修订耗尽自动产生一条记录，含 `{spec版本, tierId, 命中规则id, 触发条件, 输入特征, 最终裁决}`。

## 3. P2 · 出口与运营

### 3.1 判据误报率看板

- **目标**：统计每条规则（46 条 `CODE-*`/`FLEX-*`/`COMP-*` + TEXT-TRUTH + visual-trust）的命中 / 被人工推翻 / 被后续修订轮次自行消除比例。这是「判据自己也要被判据约束」的元能力。
- **依赖**：1.3 报告端点（先有聚合数据）。
- **落点**：`code-snapshots/*` 的 revision 序列 + 修订回环数据旁挂 `rule-stats.json`。
- **验收**：能列出误报率最高的 5 条规则，并支持把规则降级为 warning 或加豁免。

### 3.2 裁定权变更留痕

- **目标**：谁能改规则、谁能定基线、改的时间与影响范围，全部留痕。**「合格」的定义权是最后一个不可让渡项**（见七轮讨论的结论），留痕是它的运维保障。
- **落点**：`spec-registry` 已有版本概念，扩展到规则集与基线；变更需记录「影响哪些已交付产物」。
- **验收**：任意一次规则/基线变更，能反查受影响的历史产物清单。

## 4. P3 · 既有缺陷修正

### 4.1 修订耗尽判定修正

- **现状**：`src/ai-engine-v2/pipeline/configurable-pipeline.js:548-555` —— 修订轮次耗尽后被判定为 `_decision:'pass'`，任务状态仍是 `completed`，**无法与「真达标」区分**。这是 max 自动化的阻断性缺陷。
- **落点**：`verdict` 枚举化（`pass` / `pass_degraded` / `fail`），任务状态补 `completed_degraded`。
- **验收**：修订耗尽的任务不再出现在「达标」统计里；报告端点能区分两类完成。

### 4.2 生产放行决策

- **现状实测**：`src/ai-engine-v2/api/v2-pipeline.controller.ts:40-46` 全部端点被 `DevOnlyGuard` 覆盖 ⇒ **生产环境统一 404**。`src/ai-engine-v2/api/dev-only.guard.ts:12-17` 的 `isV2Exposed()` 已支持 `AI_ENGINE_V2_ENABLED` 显式放行。
- **结论**：能力（开关）已存在，本项**不是开发任务，是决策任务** —— 需要明确生产放行策略：全量放行 / 仅内部服务身份放行 / 仅指定端点放行。
- **建议**：与 1.2 服务间鉴权绑定 —— 生产只对服务身份开放 `generate` 与 `report`，`catalog`/`preview`/`health` 维持 dev-only。

## 6. 验收总判据

**「不可替代性」只有一个度量方式**：把工坊拿掉，让 buddy 团队列出「我们必须自己做的功能清单」。

- 这份清单**变长** → 做对了
- 这份清单**变短**（工坊把能力以更易复制的形式吐了出去）→ 做反了

按前述估算，这份清单当前约 **23–34 人月**。

**反面清单（明确不做）**：

| 不做 | 理由 |
|---|---|
| 在线 IDE | 重资产，且属 L1 入口层，buddy 自己做更快 |
| 更多档位 | 档位不是壁垒，判据才是 |
| 更多出口 / 报表 | 出口越多越像 skill，越容易被复制 |
| 数据后台 / 模型网关 | 无状态替换品，碰了只分散精力 |
