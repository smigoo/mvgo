## 2. 新发现（F1~F4）

### F1 🔴 G0.2 不是纯观测：component-meta 写入契约是双形态，判据③结构性不可达

**现象**：方案 G0.2 拟把 `patchHitReport` 写入 component-meta.json 并判「每单存在」。实测该文件**至少 10+ 写入点，分两类形态**：

| 形态 | 位置 | 对新增字段的影响 |
|---|---|---|
| **全量覆写** | `component-meta.util.ts:32-67`（`JSON.stringify` 固定 5 字段 → `writeFile` 写两处 workspace）、`lite/lite.service.ts:676`、`:3565`（自拼 JSON 全量写） | **抹掉**此前写入的任何字段 |
| read-modify-write merge | `mc-spec/mc-spec.service.ts:490-505`、`graphs/mc-component-graph-vue3.js:1695/:1905/:2008`、`graphs/mc-component-graph-phase2.js:3285/:3537/:3667` | 保留既有字段 |

**关键时序证据**：`vue3/vue3.service.ts:313` 在生成结束后**无条件调用** `saveComponentMeta(...)`（S10，注释「无条件写入，避免 ApiBindingWizard 404」）。若 report 在 graph 层先写，随后被 util 全量覆写抹除 ⇒ 判据③「每单 component-meta 中存在 patchHitReport」**结构性不可达**，属与评审 B3 同型的「假绿」。

**连带影响**：
- 若在 util 加字段，需改 `saveComponentMeta` 函数签名，并给全部调用点（`vue3.service.ts:313` 等）传值；
- lite 链路 2 处独立全量写入必须同步补字段，否则 Lite 单永远缺 report（双端形态不同）；
- 前端 `ApiBindingWizard` 读取该文件（util 头注释自述 dev/prod 两条 fetch 路径），字段新增向后兼容但**写入契约变更**属共享契约改动。

**修订要求（CR9）**：① 落盘收敛为**单一 merge 出口**（或 3 个全量覆写点统一补字段，「0 也落盘」）；② 判据③改为「**最终产物** component-meta.json 中存在」；③ 阳性对照须覆盖「先写 report → 后续全量覆写 → 字段仍在」的顺序链；④ **G0.2 从 A 档提至 B 档**。评审意见 C5「聚合落盘无新机制需求」据此作废。
