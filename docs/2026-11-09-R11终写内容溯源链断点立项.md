## 2. 根因（文件:行号 + 真机证据）

**断点位置**：`src/ai-engine/roles/microcode-engineer.js:9586-9600`

```js
let _revertedSemanticFiles = 0;
for (const [fp, fc] of Object.entries(finalTruthFiles)) {
  if (!fp.endsWith('.vue') || typeof fc !== 'string') continue;
  const _sem = validateVueScriptSemantics(fc, fp, {});        // ← 空 options
  if (_sem.issues && _sem.issues.length > 0) {
    const _before = allFiles[fp];                              // ← healing 之前的原始分块
    if (typeof _before === 'string' && _before !== fc) {
      finalTruthFiles[fp] = _before;                           // ← 整文件回退
      _revertedSemanticFiles++;
    }
  }
}
```

三个事实：

1. **`allFiles` 是 `:909` 起的原始分块累积**（`:962/:986/:990` 写入），远早于 `:9484` 的 healing 链，更早于 `:9518` 子组件 import 补齐、`:9534` 类名前缀、`:9559` 根容器归一。⇒ 一旦回退，**该文件本轮所有确定性自愈全部作废**（R9-b 改写、R10 归位、背景补全、FLEX 归一…）。
2. **判据上下文缺失**：`validateVueScriptSemantics(fc, fp, {})` 传空 options。该函数在别处调用时会带 import 白名单 / less 变量等上下文（见 `file-writer.js` 同名调用），空 options 下等于「用最严形态扫一遍」，假阳性面最大。
3. **真机实证**：R10 轮 `11bd56c1` 的 healing 归位版 6371 字符 vs 磁盘终写 6370 字符、md5 不同，且磁盘版仍是「tabs 块在 base-panel 之外」的形态 ⇒ 归位被此分支回退。这正是上一轮 R10「已修但不生效」的机制。

**为什么当年这么写**：2026-09-02 该段的目标是校验 `fixedFiles` 的覆写（AI 修复轮产物），回退源当时只有 `allFiles` 一个候选。2026-09-16 healing 链并入后，`finalTruthFiles` 的内容来源从「allFiles+fixedFiles」变成「allFiles+fixedFiles+healing」，但**回退源没有跟着演进** ⇒ 语义漂移。

## 3. 治本方案（三个候选，建议 A）

| 方案 | 做法 | 评价 |
|---|---|---|
| **A（建议）** | 回退源改为「healing 输出的同文件版本」：在 `:9502` 处另存 `const healedFiles = _healed.files`，`:9590` 改 `const _before = healedFiles[fp] ?? allFiles[fp]` | 语义最小改动、单一事实源清晰（healed → finalTruth，跨跳只隔 import 补齐/类名/根归一，均幂等）；缺点：仍会丢掉 `:9518/:9534/:9559` 三步（可接受——那三步是确定性补全，若触发语义问题本身就是判据 bug） |
| B | 命中 issues 时**定点修复**而非整文件回退（只删/改出问题的引用） | 最强，但要为每类 issue 设计修复器，工作量与风险都大 |
| C | 把该重校验整体移到 healing **之前**（恢复其原始语义：只验 `fixedFiles` 覆写） | 位置最干净，但等于放弃「healing 后终态语义校验」——healing 自身可能引入语义问题（R10 归位就会移动节点），等于失去兜底 |

**建议 A + 计数行**：

- `🛡️ 覆写后语义校验回退: file=… from=healed|allFiles issues=<n>`（恒打，命中才打 revert 分支）
- 判据：`from=allFiles` 出现 ⇒ healing 版本语义不过，说明 healing 有 bug（应回查该 pass），**不是让回退静默吃掉**
- **阳性对照要求**：必须构造一个「healing 归位后触发语义 issue」的样本，验证 A 方案下回退源是 healed 版而非原始分块（避免又变成「改的人和验的人同正则」）
- **阴性对照**：无 issue 的文件零改动（`reverted=0`）

## 3.5 真机补充证据（2026-11-09 13:49-13:57 回放，restart 后新代码生效）

三发确定性回放（`after-review2.jsonl`）后核对产物，发现 R10 **运行时 0 命中**而磁盘仍为游离形态：

| 证据 | 值 |
|---|---|
| `server.log` 窗口 05:49-05:57 内 `R10 修复` 行 | **0 条**（同窗口 `R9-b` 也是 0，`R2 终裁快照校验` 有 14 条） |
| healing 是否执行 | 执行了（`patchHitReport.selfHealing` 有 `resourceInject=1 / writebackFixed=2 / sectionFlexTruthFixed=1` 等非零） |
| 离线对**同一磁盘文件**跑 relocator | `changed=true, moved=1`（会归位） |
| 磁盘终写 `1b3f78c2/package/index.vue` | `base-panel` 在 idx 664，之前仍是 `div.c-vehicle-monitor-slot-con-tabs`（v-for tabs 行） |

⇒ **healing 看到的 index 内容 ≠ 落盘 index 内容**（否则 R10 必命中）。这不能再归因于「LLM 随机漂移」，而是内容来源分叉，两条候选机制：

- **(a) 语义校验回退**（§2 主机制）：本次窗口内 `覆写后语义校验命中` 为 0 条，说明**不是**这条触发的（该日志只在命中时打，0 条即未命中）。
- **(b) 后置 pass 注入**（新发现，优先）：`刀66-C「index 段级 v-for 改写」` 位于 `generateCode` 内、**在 execute 的 healing（:9484）之后**执行（见 `patch-chain-coverage.spec.ts` 对该 catch 的登记注释「generateCode 内、包装写入之后」）。它把 tabs 行写进 index 时**没有再过 healing 的 R10** ⇒ 游离根在 R10 之后才出现。

**结论修正**：R10/R9-b 这类 healing 阶段守卫的**生效前提**是「自己是终态最后一关」；当前链上至少还有 `刀66-C` 在它之后写 index。所以 R11 的第一修法不是改回退源，而是**把 R10 挂到终态出口**（或让 66-C 之后重跑 R10，幂等纯函数可安全重跑）。

**验收方式同步修正**：R10 是否生效不能只看日志行，必须以「磁盘终写 index 的 `base-panel` 是否为首元素」为判据（落盘事实），日志仅作归因线索。
