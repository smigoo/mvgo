# 类名漂移根因与治理方案

**日期**：2026-09-16
**触发案例**：`mc-max-1789491376201-24254234`（设备监测，布局全纵向）
**分析方法**：真机 chunk 原始产物离线重放（未落盘、未被 fallback 污染）
**结论**：**三层补丁嵌套**——LLM 自由命名（不可控）→ R4 对齐（覆盖不全）→ fallback stub（遮掉告警）

---

## 一、症状

`c-device-monitor-24254234` 产物 `common.less` 里存在**两套互不交集的类名**：

| 来源 | 类名 |
|------|------|
| **模板**（SwitchSection.vue / index.vue） | `switch`、`active`、`default`、`bg`、`icon`、`active-content`、`default-content`、`active-title`、`default-title`、`line1`、`line2`、`line-label`、`line-value` |
| **样式**（common.less 原生） | `switch-wrapper`、`switch-item`、`switch-title`、`switch-label`、`switch-value`、`switch-icon`、`switch-content`、`switch-stats`、`switch-stat-row` |

**交集仅为 `c-device-monitor-` 前缀**——模板的每个 class 在样式里都不存在，反之亦然。

后果链：模板 class 无样式 → `_validateClassNames` 报 15 个 forward mismatch → fallback 补残缺 stub（缺 `display:flex`）→ 布局全纵向。

---

## 二、根因溯源（三层，全部离线实锤）

### 层 1：LLM 分块生成「两次独立命名」

分块结构（`chunk-meta.json`）：

| chunk | 文件 | segmentType |
|-------|------|-------------|
| 6 | `package/components/SwitchSection.vue` | `component`（写模板 + scoped style） |
| 9 | `resources/styles/common.less` | `style`（写样式） |

**模板块与样式块是两次独立的 LLM 调用**，各自命名 → 同一元素落到两套基名。

**实锤（chunk 原始产物对比）**：
- `6-package_components_SwitchSection.vue` 模板根：`class="c-device-monitor-switch"`
- `9-resources_styles_common.less` 根规则：`.c-device-monitor-switch-wrapper {`

### 层 2：类名清单「已注入但 LLM 未遵守」

管线**确实**注入了统一类名清单（`microcode-engineer.js:1961` `_extractTemplateClassNames` → `prompt-builder.js:2407` 硬约束段）：

> 「以下是从所有已生成的 Vue 模板中程序化提取的 class 名完整列表。你必须在 common.less 中为**每一个** class 生成对应的 CSS 规则……❌ 禁止重命名 class」

**离线验证**（用 chunk 产物跑 `extractTemplateClassNames`）：

```
清单总数: 31
含 switch 类名: c-device-monitor-active, c-device-monitor-active-content,
              c-device-monitor-active-title, c-device-monitor-default,
              c-device-monitor-default-content, c-device-monitor-default-title,
              c-device-monitor-switch
```

⇒ **LLM 拿到了含 `switch`/`active`/`default` 的完整清单，但样式块仍写 `switch-wrapper`**。这是 prompt 约束力问题（软弱约束、无强制）。

### 层 3：R4 跨侧对齐「覆盖不到这种漂移」

`class-dialect-normalizer.js:planCrossSideBaseAlignment`（刀 12，已识别同类缺陷）的判据：

| 判据 | 要求 | 本案例 | 结果 |
|------|------|--------|------|
| ① | 样式侧已有同名基类 → 不动 | `switch` 在原生样式侧无 | 继续 |
| ② | **锚点 = 元素上的修饰符后缀**；无锚点 → 不动 | `switch` 元素单 class，**无修饰符** | 🔴 **拒绝** |
| ③ | 候选样式基名以 `${base}-` 开头（前缀扩展） | `active` 与 `switch-item` **无前缀关系** | 🔴 **拒绝** |
| ④ | 候选唯一才改写 | — | — |

**离线验证**（用 chunk 产物跑 `normalizeClassNameDialect`）：

```
changes 数: 3
[ { SwitchSection.vue: is-active → c-device-monitor-default--active },
  { TabsSection.vue: active → c-device-monitor-tab-item--active },
  { common.less: active → c-device-monitor-tab-item--active } ]
```

⇒ **R4 只对齐了 3 处修饰符类，完全没有处理 `switch` ↔ `switch-wrapper` 的基名漂移**。

**R4 的设计边界**：它只能处理「同源基名 + 后缀扩展」（如 `tab` → `tab-item`），**处理不了 LLM 两次独立命名产生的"完全无前缀交集"漂移**。

### 层 4：fallback stub「遮掉告警」

`_validateClassNames` 检测到 15 个 forward mismatch 后，用 `generateFallbackCssRule`（`code-validator.js:377`）从 `elementStyleMap` 生成 stub：

- stub **只含** elementStyleMap 提供的属性（`flexGrow` / `minHeight` / `gap` / `width`）
- **不含** `display:flex`（elementStyleMap 无布局方向信息）
- stub 追加到 common.less 后，**CODE-020 反查（模板 class → CSS 定义）此时已命中 stub** → **不再报警**

⇒ 漂移被"修复"掩盖，产物带病发布。

---

## 三、为什么「补 display」只是治标

本轮已落地的 `fallback 段补 display`（`microcode-engineer.js` fallback 追加后补 display/flex-direction）**治的只是层 4 的一个症状**：

- ✅ 残缺 stub 补上了 `display:flex` → 布局不再纵排
- ❌ **真病未除**：模板 `switch` 与样式 `switch-wrapper` 仍是两套类名 → 设计样式（背景色/圆角/内边距/字重/激活态底色）**永不生效**（与刀 12 注释描述的历史事故 `mc-1789305950498-6a45b6f2` 同源）

---

## 四、治理方案（按删减法原则，治本 → 治标）

### 方案 1（P1，治本）— 样式块「填值不命名」

**现状**：LLM 在样式块自由决定 class 名 + 填属性值。

**改法**：管线把 `classNamesList` 作为**骨架**，确定性生成 common.less 的**空规则块**：

```less
.c-device-monitor-switch { /* LLM 只填这里 */ }
.c-device-monitor-active { /* ... */ }
```

LLM **只填属性值**，禁止新增/改名（prompt 已有铁律，此处改为**结构强制**）。

**收益**：从结构上消除"样式块自命名"这一漂移源。
**成本**：中等（需改 prompt + 骨架注入 + 校验）。
**风险控制**：LLM 可能删块 → 需门禁「清单内 class 必须全部存在」。

### 方案 2（P2，治本，最彻底）— 类名由 DOM 事实源确定性生成

即删减法方向：LLM 只声明语义（section/DOM 结构），类名由 `class-facts` / `classname-contract` 事实源**确定性生成**，模板块与样式块共用同一份。

**收益**：彻底消除命名自由 → 漂移归零。
**成本**：最大（触及架构层）。

### 方案 3（P2，治标+兜底）— R4 扩展

给 R4 增加「无锚点元素」的跨侧对齐：用元素在 section 中的**位置/层级**匹配（而非基名前缀）。

**风险**：位置匹配可能误配 → **必须做全语料离线误伤审计**（`mvgo-deterministic-replay-triage`）。

### 方案 4（P0，门禁，防带病发布）— fallback 不得掩盖门禁 ⭐

**现状**：fallback stub 让 CODE-020 反查命中 → 漂移静默消失。

**改法**：
1. fallback stub **显式标记**（如 `/* [自动修复-stub] 仅兜底布局属性，设计样式缺失 */`）
2. CODE-020 / 类名契约门禁（C3/C4）**识别标记** → **仍报警**（BLOCK 或至少 WARN）
3. 或：`_validateClassNames` 的 forward mismatch **在补 stub 前**先落一条可观测告警（含漂移类名对照）

**收益**：漂移**可见**，不再带病发布；成本最低，可立即做。
**这是防止"补丁掩盖根源"的最后一道闸**，优先级最高。

---

## 五、避免影响其他生成面的硬约束

1. **门禁标记必须向后兼容**：历史产物无标记 → 行为不变；只有新产生的 stub 带标记。
2. **骨架注入只对 common.less**，不动 scoped style（子组件自带样式有自己的生命周期）。
3. **R4 扩展必须先全语料离线差分审计**，只报命中内容、人工确认无误伤才上线。
4. **不得删除 fallback 机制**：它是"避免重试耗尽"的必要兜底 → 目标是"不掩盖"，不是"取消"。
5. **新增门禁必须配「下线一个旧补丁」**（过程约束，对抗补丁层膨胀）。

---

## 六、推荐落地顺序

| 优先级 | 方案 | 理由 |
|--------|------|------|
| **P0** | 方案 4 门禁不掩盖 | 成本最低、收益最直接：让漂移可见，立即止血 |
| **P1** | 方案 1 样式块填值不命名 | 消除主漂移源，中等成本 |
| P2 | 方案 2 确定性类名 / 方案 3 R4 扩展 | 更彻底，改动大，需长周期 |

---

## 七、与既有工作的关系

- **刀 12（2026-09-13）**：已识别「模板/样式两次独立调用 → 同一元素两个基名」，但 R4 只覆盖「同源基名 + 后缀扩展」→ 本案例是**超出 R4 判据边界**的新形态（完全无前缀交集）。
- **本轮 fallback 补 display**：治层 4 的一个症状（布局纵排），**不治命名漂移**。
- **方案 4 与前两者的区别**：刀 12 与 fallback 都是"让管线自己修好"；方案 4 是"修不好时**不许静默**"。三者互补，不是替代。
