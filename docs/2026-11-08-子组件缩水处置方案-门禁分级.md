## 1. 现状与缺口

| 环节 | 现状 |
|---|---|
| planner | `effectiveSections=2` + `internalSubcomponents=3` → `minFiles=5` |
| prompt | `microcode-engineer.js:1064` 要求 5 个独立子组件文件，「数量不得缩减」 |
| 模型 | 实际只落 3 个（`StatsSection` / `MainSection` / index） |
| 已补判据 | `subcomponent-coverage.js` → 写盘出口打 `🧩 子组件覆盖度: expected=5 generated=3 missing=2 …` |
| **缺口** | 判据结果只进日志，**不进 `result.issues`** ⇒ 不进 `gateScore`、不触发 `retryGuidance`、不被 `WARN_ESCALATION_POLICY` 管理、任务仍 `completed` |

一句话：**现在能看见了，但没人管。**

## 2. 可复用的既有机制（不另造）

| 机制 | 位置 | 作用 |
|---|---|---|
| WARN→BLOCK 逐 id 策略表 | `utils/gate-severity.js#WARN_ESCALATION_POLICY` | 连续 ≥N 轮未愈合 ⇒ 按 action 处置；带 `MVGO_GATE_*` 开关 |
| 软失败评分 | `mc-component-graph-phase2.js:5516` `computeGateScore(result.issues)` | 0-100 分 + 维度拆解，挂 `result.gateScore` |
| 重试指导 | `:5530` `_l0CodeRetryGuidance = retryGuidance` | 文本注入下一轮 prompt |
| 局部重做 | `:5534` `_reviseFiles` ← `resolveTargetFilesFromIssues` | 按 `issue.file` 只重做受影响文件 |
| 重试预算 | `:5524` `codeValidatorRetryCount`，条件边 `<= l0MaxRetry` | 失败才 +1、通过即重置 |

⇒ 覆盖度只需要变成**一条 issue**，上面五条自动全部生效。

## 3. 四档处置路径

| 档 | 做法 | 收益 | 代价 / 风险 | 建议 |
|---|---|---|---|---|
| **0（已做）** | 只打计数行 | 可观测 | 任务仍 `completed`，用户看不到差别 | 保留作为基线 |
| **1** | 生成 `WARN` issue（`SUBCOMP-001`）+ `retryGuidance` 追加缺失清单 | 模型**下一轮有机会补**；进 `gateScore`；进 `failOpenEvents` 留痕 | 多跑一轮生成（成本 ↑）；若模型仍不补，产物照旧 | ✅ **推荐第一步** |
| **2** | 档 1 + 在 `WARN_ESCALATION_POLICY` 注册 `SUBCOMP-001: {action:'BLOCK', rationale}` | 连续 2 轮不愈合 ⇒ fail-closed，杜绝带病出厂 | BLOCK = **该轮一个组件都不产出**；用户是拿截图迭代的，可能更难受 | ✅ **推荐第二步**（可随时用 `MVGO_GATE_ESCALATE_BLOCK_IDS` 关掉） |
| **3** | 直接 BLOCK（首轮就拦） | 最严格 | 首次生成就失败，没有补救机会；存量任务大面积变 failed | ❌ 不推荐 |

### 为什么不是档 3

`gate-severity.js` 头注释已经把这条写死：「BLOCK 会 fail-closed —— 该轮一个组件都不产出。对『产物带此缺陷但仍可迭代』的判据，fail-closed 比带病出厂更差」。子组件缩水属于「结构不完整但主壳可看」，符合「可迭代」特征 ⇒ 应先给重试机会（档 1），再靠策略表兜底（档 2）。

### 为什么不是「一次生成就重试三次」

`codeValidatorRetryCount` 与 `l0MaxRetry` 是全局预算，L0-A/L0-B 共用。为覆盖度单独加预算会挤占既有重试；档 1 只是在**同一次**重试轮里多给一条 guidance，不新增预算。

## 4. 实施拆解（三步，每步可独立验收）

### 步 1：覆盖度进 result（不改行为）

- `microcode-engineer.js` 的 `writeFiles` 已有 `this._subComponentCoverage`；在 `execute` 的 result 组装处补 `subComponentCoverage: this._subComponentCoverage || null`（与 `vue3-engineer.js:2301-2308` 同构）。
- 验收：任务 result 里出现该字段；`missing` 值与日志一致。

### 步 2：L0-B 生成 WARN issue + retryGuidance

- `code-structure-validator`（L0-B 出口）读 `result.subComponentCoverage`：
  - `missing > 0` ⇒ push issue `{ id: 'SUBCOMP-001', severity: 'WARN', file: null, message: '期望 N 个组件文件，实际 M 个，缺 X 个；内部子组件应落独立 .vue（见 planner internalSubcomponents）' }`
  - 同步把缺失清单追加进 `retryGuidance`
- `file: null` 是刻意的：`resolveTargetFilesFromIssues` 遇到无法定位会退化为全局重生成（现状兼容），不会误做局部重做。
- `gate-severity.js` 注册 `SUBCOMP-001: { action: 'WARN', rationale: '…可迭代…' }`（此步先显式写 WARN，决策留痕）。
- 验收：日志出现 `SUBCOMP-001`；`gateScore.warnCount` +1；下一轮 prompt 含缺失清单。

### 步 3：升级策略（可选，需二次授权）

- 把 `SUBCOMP-001` 的 `action` 改为 `BLOCK`，`afterStreak` 沿用默认 2。
- 验收：连续 2 轮 `missing>0` ⇒ 出现 `SUBCOMP-001-ESCALATED` 且 `result.pass=false`；第 3 轮起 fail-closed。
- 回滚：`MVGO_GATE_ESCALATE_BLOCK_IDS=none` 即可关闭，零改码。

## 6. 风险分级（A/B/C）

| 级 | 风险 | 触发条件 | 处置 |
|---|---|---|---|
| **A** | 覆盖度误报：`minFiles` 含「布局容器不占槽」规则，若 planner 计数口径漂移会误报 | `isForced=true` 且 `minFiles > 实际应有叶子+内部子组件` | 判据已按「一级 `package/components/*.vue`」计数，并有用例锁死；上线后先看 3 个任务的人工核对 |
| **B** | 重试轮次被挤占 | guidance 过长挤掉既有 L0-B issue | guidance 只追加 ≤3 行摘要，缺失清单最多列 5 条 |
| **C** | 升级 BLOCK 后大面积失败 | 模型稳定缩水 | 先用 `MVGO_GATE_ESCALATE_BLOCK_IDS=none` 灰度，观察 3 天再放开 |

## 8. 明确不做

- ❌ 不把 `body.children` 提升为 section `children`：`2:8419` 的 4 个子是 label/value 元素级，提升会把统计标签变成独立 section（比缩水更糟）。
- ❌ 不改 `collectLeafSections` / 刀 41 `_walk`：`leafSections=2` 与 `ids=2` 是 planner 设计的正确结果。
- ❌ 不为覆盖度单开重试预算。
- ❌ 不在写盘阶段补生成缺失组件（那是「生成」不是「修复」，应由重试轮完成）。
