## P-01 tab 激活态背景：bg 仍被做成独立 DOM 元素（违反既定禁令）

**现象**：`c-device-monitor-tab-item` 内部仍有 `<div class="c-device-monitor-tab-bg"></div>` 独立背景节点。用户明确要求过：bg 资源/背景样式必须是宿主元素的 CSS 背景，不允许单独建 DOM。

**证据**：
- 产物 `c-device-monitor-1c98bab9/package/components/TabsSection.vue:11`：`<div class="c-device-monitor-tab-bg"></div>` + 样式里 `.c-device-monitor-tab-bg { background: linear-gradient(...) }`
- 历史复发面广：grep `c-device-monitor-tab-bg` 命中 **20+ 个历史组件**（2677cc14/dq3a4bj3/7ba35f11/2a3fbffd/1c98bab9/ef00bb27/…几乎每代都犯）——**系统性复发，非偶发**
- prompt-builder.js:721 已有「bg/icon DOM 语义铁律（违反即门禁重试）」的文字约束，但**仅约束 `bg*` 命名的资源图**；tab 激活态背景是纯 CSS gradient（非下载资源），不在该铁律的约束范围内

**根源分析（宏观 / 非特有）**：
1. **约束的作用域错位**：现有铁律管「资源图 bg」不管「CSS 背景空壳 div」。LLM 对「有背景的元素」存在系统性建模倾向——习惯性拆成 `宿主 > bg空壳 > 内容` 三层（从 Figma 视觉上看 bg 是独立图层，LLM 逐层直译），这是**所有带背景元素**的通病，不止 tab。
2. **纯 prompt 约束无法自我监督**：prompt 说「禁止」但没有任何确定性后处理兜底；LLM 生成是概率性的，文字禁令挡不住视觉直觉，且没有门禁检查这一项。

**治本方案（无硬编码）**：
- **A. 确定性后处理（治本，第一优先）**：门禁/修复层新增「背景空壳节点剥离」规则——匹配「模板中 class 含 `-bg` / `-background` 词尾、且其样式**只有**背景类声明（background*/border-radius/box-shadow/position:absolute 铺满四边任一组合）、无文本内容无子业务节点」的空 div → 自动把背景声明**上移合并到其父元素**（或兄弟内容容器），删除空壳节点。规则按**样式声明特征**识别，不按组件名硬编码，任意组件通用。
- **B. prompt 铁律扩 wording**：把「bg/icon DOM 语义铁律」从「bg* 资源」扩展为「一切背景（含 CSS gradient / 纯色 / 资源图）：背景必须挂在**承载内容的元素**上，禁止任何 `-bg` 空壳 div」。prompt 是软约束，作为 A 的补充。

**落点**（实际落地）：`post-process.js` 新增纯函数 `collapseBackgroundShellDivs`（按样式特征识别 `-bg`/`-background` 空壳——class 词尾 + 无内容无绑定 + 纯视觉声明上移合并到父元素、父已有同名属性则丢弃，删空壳与死 CSS 规则，资源图背景优先）+ `microcode-engineer.js` 分块后管线接入（所有 `.vue` 通用，跳过非 .vue）+ `post-process.spec.ts` 5 个单测（全部 20 passed）。

**状态**：✅ 已落地（commit `18536ba`，2026-09-17）。实锤跨组件类型系统性复发（card/tab/ContentDefault…）后，从管线层根治——纯 prompt 约束升级为确定性后处理兜底。prompt-builder wording 扩展（B）作为软约束补充，可后续补。

## P-02 12 卡文字颜色错误：`(2/484)` 数值应与标签两色，产物单一继承

**现象**：`c-device-monitor-device-label`（摄像机 rgb(51,51,51)）与 `c-device-monitor-device-value`（(2/484) rgb(255,255,255)）应分别是两个颜色；产物里 value 的 `color: var(--colorBgCard, #ffffff)` 引用错槽位（colorBgCard 是卡片背景色槽，被当文字色用），且 label 写死 `#333333` 字面量。

**证据**：
- ContentCons.vue:63-77：`.device-label { color: #333333 }`（硬编码）；`.device-value { color: var(--colorBgCard, #ffffff) }`（槽位误用）
- Figma 真值：label=rgb(51,51,51)、value=rgb(255,255,255)，**两色并存**，必须两个独立色值
- vision 缓存 coverageReport.missing 列出了全部 24 个文字节点（摄像机/(2/484)×12对）→ **vision 结构层根本没采集这些文字的颜色**，LLM 只能靠猜

**根源分析（宏观 / 非特有）**：
1. **v-for 折叠导致文字真值丢失（结构性缺口）**：vision 把 12 卡折叠成一个 `role:item`（id=89:37-m2，name=12个设备名拼接），`_visualElementList` 只有列表级描述，**item 内部文字的 per-node 颜色从未进入事实链**。coverageReport.missing 明确记录了这 24 个 TEXT 节点缺失——任何「v-for 列表 + item 内多彩文字」的组件都会复现：颜色只能靠 LLM 从截图猜或随便引个变量。
2. **槽位语义混淆**：LLM 引了 `--colorBgCard`（背景槽）当文字色——槽位选择无确定性校验，fallback `#ffffff` 恰好蒙对一半（value），label 则直接写死。
3. **TEXT-TRUTH 门禁对 v-for item 文字不生效**：文字白名单(#535)/TEXT-TRUTH(#536) 检查的是「模板静态文本 vs Figma 文本」，v-for 里 `{{ item.label }}/{{ item.value }}` 是动态绑定，比对被跳过。

**治本方案（无硬编码）**：
- **A. v-for item 文字真值下钻采集（治本核心）**：vision/layout 事实源对 `role:item` 节点下钻一层——从 Figma 真值取**首个代表性 item** 内部每个 TEXT 的 color/fontSize/fontWeight，写入 item-level 事实（如 `textNodes: [{name,label:'摄像机',color:'#333333'},{label:'(2/484)',color:'#ffffff'}]`），注入分块 prompt。适用于一切 v-for 列表，非本组件特判。
- **B. 文字色专用槽位 + 校验**：主题槽位校验（THEME-SLOT 系）增加规则——**文字 color 的槽位引用必须是语义为「文字色」的槽**（colorTextBase/colorTextSecondary 家族）；引用 `colorBg*` 家族做 color → L0-B WARN 并自动纠正到最近的文字色槽。消除「拿背景槽当文字色」这类系统性误用。
- **C. per-node 文字色直引**：item 级 TEXT 颜色来自设计稿非主题槽（如 #333333 深底稿专色）时，允许走「专色登记」路径（theme-vars.less 增槽或 THEME-SPECIAL-COLOR 白名单），不写死在业务样式里。

**落点**：vision prompt/解析器（A）、code-validator THEME 检查（B）、theme-vars 槽位治理（C）。

## P-03 布局层次过深：每层业务容器外都套一个无语义比例 wrapper 空壳

**现象**：index.vue 模板 24 行里 12 行是空壳 div 开闭标签。5 个布局层级有 4 个是「flex:0.xxx wrapper 空壳 + 语义容器 div」双层叠加，可读性差、维护难。

**证据**（code-generator.js）：
- :592/:598 renderBodyNode 对每个子项无条件包 `<div style="flex:...;min-width/height:0;display:flex;flex-direction:column;">`（P2/P3/P5 注入）
- :570 容器 div 已带语义类名 + data-section-id + flex 方向
- 叶子层 :608 子组件标签又内联 flex:1;min-height:0 → wrapper（flex:0.500）+ 标签（flex:1）两层叠加

**根源（宏观 / 非特有）**：
1. **修复演化的加层惯性**：P0→P5 六连修每步只往 wrapper 叠职责，从未回头审视 wrapper 与容器能否合一。每次局部正确，整体层次失控——增量修复的典型债务。
2. **职责可合并未被合并**：容器 div 的「比例（吃父）」与「方向（对子）」样式互不冲突，一层即可承载全部职责；wrapper 是历史演化的中间产物而非必要结构。
3. **叶子 wrapper 纯多余**：子组件根元素本身就是 flex item，比例直接内联到子组件标签（flex:0.500;min-width:0）即可，flex:1 中转毫无必要。

**治本方案（无硬编码，按结构特征通用）**：
- **A. wrapper 容器化合并**：①容器与 wrapper 二合一——容器 div 把父分配比例写进自身 style（flex:0.170;min-height:0;display:flex;flex-direction:row;align-items:stretch 一层全含）；②叶子 wrapper 删除——比例直接内联到子组件标签。统一判据：wrapper 内只有 1 个元素且无其他职责 → 删 wrapper 上移 style；多叶子兄弟竞争比例 → 保留比例内联在子组件标签（每叶子自己吃比例，无需父 wrapper）。合并后业务层级 4 层 → 2 层。
- **B. wrapper 消除率门禁**：装配层输出后统计「无 class 无 data-section-id 的纯 style div」占比 >30% → WARN，防未来修复再引入同类空壳。

**落点**：code-generator.js renderBodyNode（A）、code-validator.js / mc-health-validator.js（B）。

**合并后预期形态**：
```html
<div class="c-device-monitor-slot-con" style="display:flex;flex-direction:column;">
  <div class="c-device-monitor-con-con" data-section-id="89:40" style="flex:1;min-height:0;display:flex;flex-direction:column;">
    <div class="c-device-monitor-switch-con" data-section-id="89:38" style="flex:0.170;min-height:0;display:flex;flex-direction:row;align-items:stretch;">
      <ContentActive style="flex:0.500;min-width:0;" />
      <ContentDefault style="flex:0.500;min-width:0;" />
    </div>
    <div class="c-device-monitor-antd-tab-con" data-section-id="89:37" style="flex:0.830;min-height:0;display:flex;flex-direction:row;align-items:stretch;">
      <TabsSection style="flex:0.111;min-width:0;" />
      <ContentCons style="flex:0.889;min-width:0;" />
    </div>
  </div>
</div>
```

## P-05 header-right 内容特别小/被挤出来（rem 适配 × 窄视口双重缩放）

**现象**：质量预览截图中 header-right 的统计文字极小（肉眼难辨）且被挤出标题行。

**证据链**：
- screenshot-renderer.js:1009 视口宽 = Figma 预览图宽（420px），:487 独立 BrowserContext（无父窗口）
- rem.js:14 `rem = vW × (16/1920)` → 420px 视口 html font-size = **3.5px**

## P-06 default 背景没出现 + active 双背景（5afd9ebe → 1c98bab9 实锤）

**现象**：
1. ContentDefault 卡片背景空白/只覆盖内容区——bg2 资源图挂在 `.default-bg-wrapper`（中间容器），但子组件根 `.default-root` 与 wrapper 均无 flex/尺寸约束 → 高度由内容撑开，卡片其余部分透明
2. ContentActive 双背景叠加——根 `.active-root` 已挂 bg1，内层 `.active-bg` 又挂了 bg2（default 资源图），两张资源图同时渲染

**证据**：
- Figma 源设计：active 卡片是蓝色资源背景，default 卡片是浅色资源背景，两张卡各自独立一张背景
- 产物 `c-device-monitor-1c98bab9`：
  - ContentDefault.vue:3 `<div class="c-device-monitor-default-bg-wrapper" :style="bgStyle">` 用 bg2，但 `.c-device-monitor-default-root`/`.default-bg-wrapper` 样式块无 `height/flex` 约束
  - ContentActive.vue:2 根挂 bg1，line:3 `.active-bg` 又挂 bg2，形成双背景
- 资源挂载计划：`bg1 bg-8788.png target=active role=container`、`bg2 bg-8807.png target=default role=container`——container 语义=挂卡片容器
- `.active-bg` 类规则只有 background-size/position/repeat，无 background-image，实际 image 由 inline :style 注入；它不是 P-01 能剥离的空壳，而是**资源挂载错误地把 bg2 塞进了 active 子组件**

**根源（宏观 / 非特有）**：
1. **子组件根未撑满父 flex 分配比例**（新增根因）：被父 flex 容器按比例分配的自定义子组件，其根元素若只写 `width/height:100%` 或不写尺寸，在 flex 上下文中不会自动占满父分配空间 → 任何背景资源图都只会覆盖到内容区域。这是所有「flex 子组件 + 背景图」的共性问题。
2. **多状态背景资源无状态隔离**：active/default 两张 bg 资源被 LLM 混用，bg2 被挂到 active 子组件，bg1 也可能被挂到 default 子组件；resource-mounter 只保证「被引用」，不保证「引用到正确状态容器」。
3. **bg 挂载位置校验缺失**：bgRole=container 事实存在但未被消费，LLM 把 bg 挂到叶子/中间层时无人纠正。
4. **P-01 空壳正则不容忍空白子节点**：部分版本 `.active-bg` 空壳内部有换行空白，正则漏网。
5. **CSS 渐变与资源图双轨无仲裁**：Figma 有 bg 资源图时 LLM 仍可能手捏渐变。

**治本方案（无硬编码，按 target 单一事实源）**：

**✅ 已验证 A 为伪需求（22:22）**：读 `index.vue:10-15` 确认——父容器给 `ContentActive`/`ContentDefault` 的 inline style 已是 `flex:1;min-height:0`，父为 `display:flex;flex-direction:column`，**子组件根已被撑满父分配空间**。背景塌陷的真实原因不是根没撑开，而是 bg 被挂到内层 `.default-bg-wrapper`（非根 div）→ 根内部不撑开内层 wrapper → 背景只覆盖内容。把 bg 挂到组件根即可铺满，无需额外 flex 撑满注入。

**核心一刀（消费 target 挂载事实，B/C/E 合并）**：resource-mounter 在挂载阶段对 `role=container` 的 bg 资源，按 `target` 字段定位到对应子组件文件（target=active→ContentActive、default→ContentDefault，判定基于文件名 target 语义而非硬编码组件名），把该资源图的 backgroundImage 注入到**该子组件模板根元素 inline style**（覆盖/补充），并：
1. 移除同一资源在该子组件内的其他重复引用（如内层 `.active-bg`/`.default-bg-wrapper` 上多余的同一张 bg）；
2. 删除跨状态串用（bg2 出现在 active 子组件）；
3. 移除 LLM 手捏的纯渐变背景空壳。

资源优先：若根已有同类背景图则保留挂载计划的真值资源。所有 bg 处理统一以 `target + role=container` 为单一事实源，不再放任 LLM 自由选择挂载点。

**兜底 D（P-01 正则扩容）**：空壳判定容忍 `>\s*</div>` 空白——针对仍存在的纯渐变空壳 div。与核心刀配合：核心刀已把资源挂对位置，兜底刀清掉残留空壳渐变。

**落点**（实际落地，commit `18536ba`，2026-09-17）：
- 核心一刀：在 `resource-mount-plan.js` 的 `mountPlannedResources` 挂载主循环里实现「按 `target`（`active`/`default`）+ `bgRole=container` 把 bg 挂到对应子组件模板根 + 清错挂/串用」逻辑（**注意落点是 plan 层而非 resource-mounter.js**——原文档误写为 resource-mounter.js）
