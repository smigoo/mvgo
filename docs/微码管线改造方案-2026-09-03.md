> 基于 2026-09-03 对两个真实产物的三方取证（原始 vision 缓存 + Figma 节点树 + 产物代码/截图）与 `frontend-mc-check v1.0.20` 实测，覆盖两大改造方向：

## 二、根因三层分类

| 层 | 问题 | 特性 |
|---|------|------|
| **Vision 识别层** | 资源映射错配（一图四用/icon 错指背景/装饰错当图例背景）、颜色青→绿、布局结构/方向误判 | LLM 识别能力边界，需**确定性后处理用 Figma 真值纠偏** |
| **Microcode 还原层** | Y 轴丢信息、准确率/props 漏生成、白字配色惯性、资源乱并（`bg9~13=bg14`） | LLM "自由发挥"，需**prompt 铁律 + 生成后确定性校验** |
| **标准文件模板层** | css-vars.js 缺失、declare.js 缺参、index.less 引入方式、componentId 双源、事件名漂移 | 与 LLM 无关，**纯模板补齐即可 100% 消除** |

## 三、Part A：还原度改造（产物 ↔ Figma 保真）

> 落点均为 `visual-parser.js` `_postProcessAnalysis` 后处理链与 `microcode` 生成后校验，确定性优先、不指望 LLM 自觉。
> 已有先例：`_overrideVisionDimensionsWithFigma`（尺寸覆盖，已实现）。

### A1 资源映射唯一性/语义校验（P0，第一根因）

**位置**：`src/ai-engine/roles/visual-parser.js` `_postProcessAnalysis` 新增 `_validateResourceMapping(parsed, figmaData)`。

逻辑：
1. 收集 `layoutStructure` 全部 `resourceFile` / `backgroundImage.src` 引用
2. **唯一性检查**：同一资源映射到 ≥2 个语义不同角色（backgroundBlock / imgSrc / 图例装饰）→ 判错配，只保留尺寸语义最匹配的一处（治流量监测 #1/#3）
3. **语义-尺寸匹配**：`imgSrc`/`icon` 角色的资源，其 Figma 源节点 bbox 必须与元素声明宽高同量级；源节点是面板级（如 420×807）→ 剔除映射（治流量监测 #2 汽车图标）
4. 产出 `mappingIssues` 写入 visual.json，供下游门禁消费

### A2 颜色 Figma 真值覆盖（P0）

**位置**：`visual-parser.js` 新增 `_overrideVisionColorsWithFigma(parsed, figmaData)`。

逻辑：
1. 按 **series 名称**在 Figma 定位图例行（如"上海方向"文本的兄弟色块节点 `Group 1321318245`），取其 `fill` 覆盖 `charts[].seriesColors`
2. **禁止最近邻匹配**（`#00d0ff` 与 `#00cccc` 色差极小，必串色）
3. 图例缺失时降级：取图表区域内最高频 fill 色 + warning

### A2+ 图表图例 Vision 契约强化（P0，治环境监测图例位置，16:44 增补）

> 原则（用户定调）：**图例是图表的一部分，走视觉分析，不遍历 Figma 内部节点**。
> 与管线既有原则一致（`prompt-builder.js:187`："Figma 树仅用于资源引用与样式取值，不用于决定布局结构"）——图例位置属布局结构 → Vision 通道；图例颜色属样式取值 → 仍走 A2 Figma 覆盖。两通道分离，互不越界。

**病灶**（mc-max-1788413648521-e4174d09 实锤）：Vision 的 charts 设计了 `legend`/`legendPosition`/`legendType` 字段，但本组件输出**全空**（`legend:[]`、`legendPosition:""`），series 名还臆造成"气化板数据"（真值 `zk3+785CO浓度`）；microcode 只能自由发挥 → `legend:{bottom:0,left:20}` 左下角（Figma 真值右上角）。对照流量监测组件同字段有值（`legendPosition:"top-right"`）→ **Vision 图例识别不稳定，单 series 小图例易漏**。

**三层落点**：

1. **Vision prompt 图例必填契约**（`visual-parser` prompt 强化）：
   - 每个图表必须输出图例四要素：**位置**（九宫格枚举：`top-left/top-right/bottom-left/bottom-right/none`）、**类型**（横排/竖排）、**系列名**（必须与图中文本一致，**禁止臆造**）、**marker 大小/颜色**
   - 单 series 图表同样必须判定图例存在性（本组件漏识别的直接原因）
   - 无图例时显式输出 `none`，**禁止留空字符串**（空 = 没分析，none = 确认无图例，语义区分）

2. **Vision 输出契约校验**（`_postProcessAnalysis` 新增 `_validateChartLegendContract`）：
   - `legendPosition` 为空字符串 → 非法值，记 warning 并触发**图例专项重问**（仅重发该图表区域让模型补答图例，不全量重分析）
   - notes 中出现"图例"字样但 `legend` 数组为空 → 不一致告警
   - series 名与 chartDataHints/labels 中的文本无交集 → 臆造告警（拦"气化板数据"类错误）

3. **microcode 强制消费**（prompt 铁律）：
   - `legendPosition` 为具体方位时必须映射 echarts legend 锚定（`top-right` → `top:0,right:0`；`bottom-left` → `bottom:0,left:0`），**禁止用 echarts 默认 bottom**
   - `legendPosition: none` 时 `legend.show:false`；Vision 未提图例时禁止自行发明图例

### A3 主题亮度强制约束（P0，设备监测 #3 最刺眼项）

**位置**：L0-B 门禁（`code-structure-validator` 或独立规则）。

逻辑：Vision 输出 `backgroundBrightness=light` 时，扫描产物 CSS，文字 `color` 出现 `rgba(255,255,255,*)` → **BLOCK**；dark 反之。纯确定性，掐死深色配色惯性。

### A4 布局方向 Figma 校验（P0，治设备监测 #1/#2）

**位置**：`_postProcessAnalysis` 新增方向纠偏。

逻辑：用 Figma 子节点**相对坐标**判定真实方向——同容器内 icon 与文字节点的 x 偏移 > y 偏移 → horizontal，反之 vertical；与 Vision 输出冲突时以 Figma 为准并记 warning。顶层结构（switch 整行宽 vs 两列）同理用 bbox 包含关系判定。

### A5 图表容器最小高度（P0，治刻度堆叠/柱子不可见）

**位置**：`src/ai-engine/utils/post-process.js` 增强 `injectChartMinHeight`。

逻辑：从 Figma 图表节点 bbox 取真实高度（隧道/大桥 131px、预测 160px）注入 `min-height`；echarts init 前校验 `clientHeight ≥ 80`，不足走 ResizeObserver 等待。

### A6 Y 轴刻度结构化（P1，治流量监测 #5）

- Vision prompt 增加 `yAxis: {max, interval, unit}` 结构化字段
- 后处理从 Figma `"4000 3000 2000 1000 0"` 文本节点**确定性解析**（split → max 取首值、interval 取相邻差），不依赖 LLM
- `prompt-builder.js` 加铁律：`yAxis.max/interval` 必须用结构化字段（当前 charts 经 `prompt-builder.js:196-201` 原样注入，LLM 可自由忽略）

### A7 props 传递校验（P1，治流量监测 #7）

生成后扫描子组件 `defineProps` keys → 父组件 `<Child />` 必须带同名 `:prop`；缺失则从 `resourceVarNames` 自动注入，注入失败 → L0-B BLOCK。

### A8 标注结构化（P1，治流量监测 #6）

Vision prompt 增加 `annotations: [{text, color, position}]`（替代 notes 自由文本）；microcode prompt 铁律：annotations 必须生成 DOM 元素。

## 四、Part B：规范生产化改造（mc-check v1.0.20 内建）

### B1 总原则与架构

**契约先行（Contract-First）**：LLM 写第一行代码**之前**，管线先确定性生成组件契约，**同一份契约同时喂给模板生成器与代码生成 prompt**：

```
组件契约（单一事实源，contract-builder）
├── componentId     ← c-<englishId>（见 B2 双名制）
├── 事件清单         ← businessEvents / businessStatuses（消灭 M5-4/M5-5 漂移）
├── CSS 变量规划     ← cssVariableConfig ↔ css-vars.js 同源（治 M3-7/M3-8）
└── 主题清单         ← themeConfig.list → themes/*.less 同源（治 M2-4/M4-5）
```

分工：**LLM 只生成 `package/*.vue` 业务代码**；`css-vars.js` / `declare.js` / `declare.json` / `index.less` / `themes/*.less` 全部模板生成。
mc-check 从 BLOCK 门禁**降级为出厂抽检**（交付前 + 定期），生产合规后不再烧重试 token。

### B2 T1 契约生成器 + 目录名双名制（治 M1-1）

**现状**：目录名 = 任务 sessionId（`mc-<ts>-<hash>`，任务创建时生成）；componentId = LLM 短名 → 双源必挂。
**约束**：sessionId 身兼四职（任务 ID / 目录名 / 类名前缀 `c-mc-max-<id>-xxx` / 快照路径），不能全局替换。

**方案（双名制）**：

```
生成期（内部）                      交付期（对外）
sessionId 目录                     c-<englishId> 目录
mc-max-1788...  ──publish──→       c-flow-monitor（冲突时 -2）
├── 任务追踪/快照/日志 不变          ├── declare.json componentId = 目录名 ✅
└── 中间产物路径 不变                └── 类名前缀改写 c-flow-monitor-xxx
```

落点：
1. **契约阶段**（Vision 完成后）：LLM 在子组件规划时顺带产出 `englishId`（零额外调用），管线三道确定性校验——kebab-case、≤50 字符、唯一性（扫 `custom-components/`，撞名加 `-2`）
2. **publishToWorkspace 时**：目录 rename + declare.json `componentId` 改写 + 类名前缀全文改写（前缀提取/改写逻辑已有先例：`code-fix-rules.js:28-44`）
3. sessionId 永不变，历史实锤注释（`mc-max-xxx`）不失效
4. 存量 `mc-*` 组件：只对新组件生效；存量在下次在线编辑保存时顺势迁移

### B3 T2 css-vars.js 标准模板（治 M2-3/M4-4/M4-8/M4-7/M4-9/M4-10）

新增 `resources/config/css-vars.js` 模板：
- 导出 `common` + 契约主题清单每个 key
- dark 必含 `colorTextBase` / `colorPrimary` / `colorPrimaryBg`，值走规范枚举（M4-10）；滚动条变量固定 `#424242`/`#646464`（M4-11）
- 字体变量必须 `$mcCssBuilder.getCssSize()`（M4-7）
- 与 declare.json `cssVariableConfig` 同源于契约（M3-7/M3-8 天然一致）

### B4 T3 declare 模板升级（治 M4-2/M3-1~M3-13）

- `declare.js`：`$createMcDeclare({ metaUrl, declareConfig, cssVars })`（补 cssVars 参数）
- `declare.json` 由契约渲染：`componentId`（=目录名）、`businessEvents`/`businessStatuses`（=契约事件清单）、`themeConfig`（默认 light+dark）、`layoutConfig`、`attribute.aspectRatio`
- 落点：`src/ai-engine/templates/component-template.js:96-143`（当前 componentId/事件从 LLM 短名渲染，改为从契约渲染）

### B5 T4 index.less 主题引入模板（治 M4-5）

按契约主题清单循环生成 `@import './themes/<key>.less'`，替代当前只 import theme-vars.less + 调 `.theme-light()` 的写法；同时保证 `theme-vars.less` 有 `@fontSize: var(--fontSize)` 映射（M5-6）。

### B6 T5 prompt 契约注入（prompt-builder.js）

| 注入内容 | 治 |
|---------|---|
| 事件名白名单：「`publishEvent`/`listenEvent` 只允许使用以下事件：…」 | M5-4/M5-5 |
| 字体大小一律 `calc(var(--fontSize) * N)`，禁 >5px 硬编码 | M5-7（当前 89 处违规实证缺失） |
| 颜色优先 `var(--xxx)`，变量清单来自契约 | M5-10 |
| base-panel 包裹 + 禁内联背景（已有，保留） | M5-1/M5-8/M5-9 |
| loading/空数据/交互反馈模式（Q3）、businessConfig describe（Q4-1） | Q 系列内建 |

### B7 T6 css-sanitizer 确定性修复（生成后兜底）

- `font-size: Npx`（N>5）→ 自动替换 `calc(var(--fontSize) * N/14)`（M5-7 兜底）
- base-panel / 首子元素内联背景色剥离（M5-8/M5-9）
- 代码事件名 vs 契约偏差扫描 → 自动改齐或告警（M5-4 兜底）

### B8 T7 mc-check 出厂抽检（不嵌入重试循环）

| 场景 | 动作 |
|------|------|
| 一键 Git 交付前 | 强制跑 `mc-check.cjs`，error 禁止交付（防在线编辑破坏） |
| 定期全量抽检 | 验证模板是否随规范升级失效（对比 `mc-check-config.json` 的 `specVersion`） |
| 技术集成 | `mc-check.cjs` 保持 aidocs 生态独立演进；backend-node 只 `spawn --component-path --output-dir` 消费 `check-result.json`，**不移植逻辑**，规范升级零改动跟进。脚本路径走 env（`MC_SPEC_CHECK_PATH`） |

## 五、样式规则双管线对齐与变量/主题整改（16:40 增补）

> 用户定调：**样式要求 vue3 与微码一致**；mc-check 只针对微码组件。
> 因此样式规则必须拆成「双管线共享」与「微码特有」两层——共享规则不依赖 mc-check，由管线共享模块统一落实；微码特有规则走微码模板 + mc-check 抽检。

### 5.1 样式规则分层矩阵

#### 5.3.1 关键分支：原 UI 是深色怎么办？（16:55 提问，17:31 定调修订）

**用户定调（17:31）**：原本就是深色组件，**应以自己的设计样式为准还原**；原有 dark 标准变量不变（规范枚举），**设计元素的色值额外定义**。

**规范语义**：dark 主题核心三变量（`colorTextBase`/`colorPrimary`/`colorPrimaryBg`）被 M4-10 锁枚举，保平台一致性；但这三个变量只是**语义层兜底**，并不限制组件用**自定义设计变量**还原自己的设计——M3-6~M3-8 允许并规范自定义变量（合法命名 + 双向声明一致），色值完全自由。据此形成**双轨制**：

| 轨道 | 内容 | 作用 | 规范约束 |
|------|------|------|---------|
| **标准变量轨** | dark 槽位三核心 = 规范枚举（`#ffffff`/`#44E4FF`/`#414141` 等） | 平台深色模式语义兜底（过 mc-check） | M4-9/M4-10 硬约束 |
| **设计变量轨** | dark 槽位**额外定义** Figma 深色真值（如 `colorBgDesign`/`colorAccentDesign`） | **业务样式用它们还原设计稿**（默认呈现 = 设计深色） | M3-6~M3-8：命名避开框架预设 8 变量、必须同步 `cssVariableConfig` 声明 |

**修订后分支矩阵**：

| 场景 | defaultTheme | 呈现还原 | dark 槽位构成 | light 槽位 |
|------|-------------|---------|--------------|-----------|
| 原 UI 浅色 | `light` | light 槽位 = Figma 提取，业务样式直接用 | 枚举三核心 | —（即默认主题） |
| 原 UI 深色 | `dark` | **dark 槽位设计变量还原**（业务样式 `var(--designXxx)`） | **枚举三核心（不变）+ Figma 深色真值自定义变量（额外定义）** | 派生算法（5.3.2） |

**合规要点**：
1. 设计变量命名**必须避开框架预设 8 变量**（`fontSize`/`fontWeightStrong`/`colorTextBase`/`colorPrimary`/`colorPrimaryHover`/`colorPrimaryActive`/`colorPrimaryBg`/`colorPrimaryBgHover`）——同名即被 M4-10 枚举校验劫持
2. css-vars.js 自定义变量 ↔ declare.json `cssVariableConfig` **双向一致**（M3-7/M3-8 互查，缺一即 error）
3. `colorPrimaryHover/Active/BgHover` 等预设变量若定义，值也须在枚举内；设计变量无此限

**原 UI 深色时 Figma 深色设计真值的保留通道**（即"设计变量轨"的落地）：
1. **自定义变量补充**：Figma 深色稿特有色（如大屏蓝、科技青）作为**非核心自定义变量**注入 dark 槽位——注意 M3-8 联动：自定义变量必须同步在 declare.json `cssVariableConfig` 声明，否则检查失败；框架预设 8 变量（`frameworkPresetCssVars`）之外才算自定义。
2. **业务样式分层**：语义色（文字/主色/主背景）走 `var(--xxx)` 跟随主题；装饰色/图表色允许按 Figma 真值硬编码（M5-10 仅 warning 不阻断）——还原度与主题适配各得其所。
3. **defaultTheme 跟随 `backgroundBrightness`**（Vision 已输出，无需新增识别）：产物默认呈现**设计稿深色**（设计变量轨），平台语义变量在侧（标准变量轨），切回 light 走派生算法。

**三条铁律（17:31 定稿版）**：
1. **dark 核心三变量永远来自规范枚举模板，禁止 LLM 生成、禁止 Figma 提取——无论原 UI 明暗**（M4-10 硬约束）
2. **原 UI 深色：defaultTheme=dark 且呈现以设计稿为准**——Figma 深色真值作为自定义设计变量**额外定义**进 dark 槽位（命名避开预设 8 变量），业务样式用 `var(--designXxx)` 还原；自定义变量必须同步 `cssVariableConfig` 声明
3. **light 色值分源**：原 UI 浅色 → Figma 确定性提取；原 UI 深色 → **确定性派生算法**（5.3.2：主色沿用+中性色反转+对比度兜底，非通用模板）
4. **fontSize 双管线统一 `calc(var(--fontSize) * N)`**；微码侧 css-vars.js 必须 `getCssSize()`（M4-7）

#### 5.3.2 light 色值无规范约束，管线如何自保障？（17:29 用户提问）

**先理解规范为什么不约束 light**：light 是组件的"原生主题"——每个组件设计稿不同，light 色值本就该是**设计稿真值**，无法也不该统一枚举；dark 是平台后加的统一深色皮肤，才需要锁枚举保平台一致性。**规范把 light 的质量责任留给了生产端，管线必须自己立三条内部约束**：

**① 来源确定性（禁 LLM 估计）**——light 色值分源：

| 场景 | light 槽位来源 | 说明 |
|------|---------------|------|
| 原 UI 浅色 | **Figma 高频 fill 确定性提取** | 设计真值即约束 |
| 原 UI 深色 | **确定性派生算法**（不再是通用模板一刀切） | 保持组件品牌一致性，避免所有深色组件切浅色后千篇一律 |

**② 派生算法（原 UI 深色 → light 槽位，确定性三步，不靠 LLM）**：
1. **主色沿用**：`colorPrimary` 沿用 Figma 深色稿提取的品牌主色（深浅主题共享品牌色，业界标准做法）；做明度校正——深色稿上的亮主色（如 `#44E4FF` 类）铺到白底对比度不足时，按 HSL 降明度变深至达标
2. **中性色反转**：`colorTextBase` → `#333333`（深色稿的亮文字反转为深文字）；`colorPrimaryBg` → 主色 10% 透明度铺白底（深色稿的深背景反转为浅底）
3. **对比度兜底**：派生结果过 WCAG AA 校验（正文文字/背景对比度 ≥ 4.5:1），不达标自动微调（文字加深/背景提亮）——纯计算，零 LLM

**③ 产物自查（规范不管的，门禁管）**：
- L0-B 亮度约束（A3）对 light 主题天然生效：light 槽位产物文字色出现 `rgba(255,255,255,*)` → BLOCK——这正好兜住"深色组件切浅色后白字不可读"的最高发风险
- mc-check 不查 light 色值，但 A3 + 派生算法 + 对比度校验构成管线内部的质量闭环

**一句话**：dark 听规范的（枚举），light 听设计稿的（Figma 提取）或听算法的（派生 + 对比度兜底），**任何情况下都不听 LLM 自由发挥的**。
